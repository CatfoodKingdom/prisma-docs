Spline model fitting (v1)

Spline model fitting (v1)

Properties1
tagscalibration, fitting

Jul 31, 20269 min read

In one sentence: “Color Model v1” is the server’s label for the legacy-spline model — a per-filament monotone PCHIP transmission profile built by fit_spline_profile (calibration.fitting.fitting), predicted and stacked by predict/compose (calibration.fitting.composition), and installed through the staged run_legacy_spline_fit_all path reached by both the unified workflow and /api/profiles/fit-all — while the notebook-era batch_fit.py / fitter_core.py / strip_loader.py / export.py chain sits off the live fit path.

This page maps the code of the v1 fitter: the modules, the data flow from sample to profile, how a stacked appearance is predicted, and how its two public callers converge on one internal current-fit boundary. The older code names this boundary “publication”; it does not create or change a Generator library. It deliberately does not re-derive the physics — why PCHIP, what an optical-density transmission curve is, or what pair corrections compensate for. For the model form and math — including the empirical two-filament pair corrections — read Color Model v1. For where a v1 fit sits in the operator workflow, see Model workflow, publication, and review and The Modeling page.

”Color Model v1” is the legacy-spline model

The UI and persistence layer call this the legacy-spline model. The server’s three current-fit kinds are gated by sqlite_data_access._MODEL_KINDS; a v1 fit is recorded under model_kind="legacy_spline". Wherever the interface says “Color Model v1,” the code says legacy_spline. Everything on this page produces or consumes that artifact set: per-filament profile JSONs plus a single pair_corrections.json.

The live core is calibration.fitting.fitting (fitting.py). Its module header retains the historical names batch_fit_spline.py and model_spline.py for the logic folded into this UI-driven module. Those filenames no longer exist as standalone modules. The live fit paths call fitting.py; retained notebook-origin support modules are described in the last section and sit outside the production fitting route except for the explicitly identified pair-correction helpers.

The spline profile — build, predict, serialize

A v1 profile is a plain dict: knots_mm (thicknesses, first knot 0.0) plus per-channel T_r/T_g/T_b transmission arrays, tagged model: 'spline'. The primitives that operate on it:

  • build_spline constructs three PchipInterpolators (one per channel), asserting the first knot is at d=0 and clipping T to [0,1].
  • predict evaluates a profile at thickness d, returning a linear-RGB T triple; below d=0 it returns ones, and beyond the last knot it hands off to _extrapolate, a log-linear extension. The why of that extrapolation belongs to Color Model v1.
  • to_srgb gamma-encodes linear T for display; profile_from_dict pre-builds and caches the interpolators; profile_to_save_dict strips the non-serializable _splines object and staleness flags before JSON write.
  • save_profile / load_profile write/read {profiles_dir}/{fid}.json. Loading routes through _load_fresh_profile_path, which treats any profile carrying a stale/stale_reason/stale_at flag as missing through _profile_is_stale — a stale profile is never silently used.

OKLab conversion (linear_to_oklab) and deltaE_ok live here too and back the fit-quality diagnostics.

From sample to strip dict — the adapters

The fitter’s internal unit is a strip dict (thicknesses, per-swatch linear transmission, optional fixed_layers). Adapters convert a live Sample into that shape:

  • _legacy_spline_geometry reads a sample’s canonical physical stack (via physical_stack_for_swatch, calibration.fitting.physical_stack) and returns the one variable filament plus any fixed base layers below it — or None for richer geometries the legacy spline deliberately refuses to reinterpret (is_legacy_spline_supported_stack).
  • _sample_to_strip_dict is the legacy adapter reading color from Sample.measurements. _sample_to_strip_dict_from_sidecar is its production twin, pulling measured transmission and I0 from the per-sample extraction_result sidecar while keeping geometry and filament assignments from the live sample; a measurement-bearing sample with an absent or malformed sidecar raises SidecarAdapterError rather than falling back.
  • The active source is the module switch _MEASURED_SOURCE = "sidecar"; _strip_dict_for dispatches on it, and use_measured_source is a context manager for oracle/rollback/test runs. Production reads the sidecar.

_load_strips_from_samples and _load_all_strips_from_samples walk store.list_samples(), keep only processed samples with measurements and a strip definition, and bucket the resulting strip dicts by variable filament. In the production SQLite store, Sample.measurements is projected only from an accepted extraction result. Pending-review extractions therefore fail this gate even though the fitting helpers do not repeat an explicit review_accepted test. The fit paths pass the pre-built strips_by_filament cache down so the whole corpus is loaded once per run.

The four data sources and the fit

For each filament, four loaders extract (d, T_rgb) points, each targeting a different strip geometry:

  • load_single_fil_data — solo strips (“thick”), skipping colored-base and white-base strips.
  • load_thin_strip_data — white-base + overlay strips (“thin”), peeling the base by local d=0 normalization (_d0_normalize_strip).
  • load_fixed_role_data — Role-B cross-cal, where the filament is the fixed base and a d=0 swatch is a direct profile-independent measurement of it.
  • load_crosscal_data — Role-A cross-cal (filament is the variable overlay on a colored base), T0-weighted; diagnostic-only for fitting.

fit_spline_profile is the core. It merges the caller’s exclusions with the hardwired EXCLUDED_EXPERIMENTS (still pinning exp-135 pending its per-sample migration) and the always-on registry-driven samples_excluded_by_filament set. It then combines sources by priority (thick baseline, thin fills gaps and wins below thin_wins_below; combine_datasets), drops outlier knots against a log-linear neighbor trend (_drop_outlier_knots_with_removed), prepends the d=0/T=1 anchor, enforces per-channel monotone non-increase, applies a T_FLOOR of 0.003, and truncates a trailing noise floor. It returns (profile_dict, diagnostics_dict) — (None, diagnostics) on failure with an error key. get_fit_data_points and compute_delta_e expose the same data for the review charts.

Predicting stacked appearance and pair corrections

calibration.fitting.composition (composition.py) predicts what a stack of layers looks like. compose multiplies each layer’s predict(profile, d) per channel, then — if a corrections table is supplied and there are ≥2 layers — applies an interpolated per-pair factor keyed overlay_fid|base@d through _interpolate_correction. predict_two_layer is the direct overlay-plus-base convenience path using calibration.fitting.color_math’s interp_single. calibration.fitting.color_math is a pure-math leaf (no intra-project imports) that is genuinely live — imported by both composition.py and the server. compute_sample_predictions drives compose over every processed sample of a filament to build the predicted-vs-measured review payload.

The pair corrections themselves are computed on the live path by compute_and_save_pair_corrections: it builds a registry with _build_pair_corrections_registry, then calls into calibration.fitting.fitter_core for compute_pair_corrections and save_pair_corrections, writing pair_corrections.json beside the profiles. This is the one live thread through the notebook-origin fitter_core — its correction math is reused, but its strip-file fitting is not. When a full model library is explicitly published, Generator reads the copied correction file from its selected immutable library at LUT build time; what the corrections model is covered by Color Model v1’s pair-corrections section.

The two entry points share one staged publisher

Both live entry points converge on run_legacy_spline_fit_all and the same staged publisher:

  1. Unified workflow → calibration.fitting.legacy_spline_fit_job. run_legacy_spline_fit_all creates a private .legacy-spline-fit-<uuid> workspace for SQLite publication. The implementation fits every target it can, deletes staged profiles that did not fit successfully, computes pair corrections when at least one profile fitted, and calls publish_staged_legacy_spline_fit when fitted > 0 and pair-correction generation succeeded. Despite the “legacy” name this module is live and is called by the unified model-fit workflow.

  2. Direct /fit-all routes → calibration.server. The synchronous and asynchronous endpoints call _run_profile_fit_all, whose implementation wraps _run_legacy_spline_fit_all(..., publish=True). The direct API is therefore a second entry into the same fitter and publication boundary, not a separately maintained fitting implementation. The retained per-profile and fit-all browser commands live in app/features/modeling/profiles.js, but the current Modeling mode is owned by app/features/modeling/review.js (renderModelsView); the ordinary UI enters the unified Fit Models flow through app/features/modeling/workflow.js.

The important qualification is that swap atomicity is not all-filament success. If one filament fit fails but another succeeds, the successful subset can replace the current v1 artifact set and receive a new model_fit_id. The unified workflow then notices the nonzero failed count, reports the overall operation as failed, records partial_publication.legacy_spline = true, and stops before v2. A pair-correction failure prevents publication entirely.

publish_staged_legacy_spline_fit swaps the staged profiles and pair corrections into the live paths before publishing SQLite. If an ordinary database-publication exception occurs, it restores the previous files; if that rollback is itself incomplete, it raises a distinct error and preserves surviving .rollback-* copies for manual recovery. Successful publication records the new artifact set, deletes the prior fit row and children, and removes the temporary rollback copies.

That compensation does not make the multi-step filesystem/SQLite transition process-kill atomic. A hard stop between its directory/pair swaps and SQLite replacement can leave missing or mixed live artifacts, rollback copies, or new files paired with the old database record. There is no startup journal that completes or reverses this v1 transition. Do not kill Calibration while Fit Models is publishing; after an abnormal stop, verify all three model statuses and publication readiness before trusting the working set.

Notebook-origin modules off the live path

fitting.py was ported from an earlier strip-file pipeline. Parts of that notebook-origin pipeline still ship under the current filenames below, but they are not what the live fit runs:

  • calibration.fitting.batch_fit (batch_fit.py) is the original batch_fit_spline.py: it reads pre-materialized strip files from STRIPS_DIR, prints progress, and has a __main__ main(). Its own fit_spline_profile is the direct ancestor of fitting.fit_spline_profile. It has no intra-project imports and is imported only by fitter_core; on the live pair-correction path it is loaded as a side effect but its fitting functions are never invoked. Strip files are themselves legacy — the live fitter reads samples directly.
  • calibration.fitting.fitter_core (fitter_core.py) wraps batch_fit for the notebook fitter through fit_profile and load_all_data. Only its pair-correction helpers (compute_pair_corrections, save_pair_corrections) are live-reachable, pulled in lazily by fitting.compute_and_save_pair_corrections; the rest is notebook/CLI surface. It is imported by calibration.fitting.export.
  • calibration.fitting.strip_loader (strip_loader.py) builds a filament-to-strips registry by scanning strip-file JSONs through load_strip_registry; it is self-described as extracted from 01_fitter.ipynb/02_composer.ipynb and imported only by export.
  • calibration.fitting.export (export.py, originally fitter_json_export.py) turns fitter results into REST-serializable dicts through export_transmission_curve and export_filament_summary, replacing the notebook’s matplotlib output. Its Architecture node lists no importers — it is not wired into the live server graph.

The heavy numerical photo-stack model referenced by the v2 pages lives in the shared lib.photo_stack_model.*, not here; this page’s modules are strictly the v1 legacy-spline path.
