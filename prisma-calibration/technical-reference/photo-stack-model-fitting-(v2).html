Photo-stack model fitting (v2)

Photo-stack model fitting (v2)

Properties1
tagscalibration, fitting

Aug 07, 20269 min read

In one sentence: the calibration side of Color Model v2 is a thin driver — live datastore samples become canonical fit evidence (calibration.fitting.photo_stack_model.evidence), that evidence is bridged into the vendored research numerical fitter and renamed into the public contract (calibration.fitting.photo_stack_model.live_fit), a fit-job boundary writes a staged candidate (calibration.fitting.photo_stack_model.fit_job), and the shared publication boundary coordinates its latest.json activation with SQLite replacement before deleting the old run — while the heavy model math lives entirely in lib.photo_stack_model.*.

This page is the code-level map of the v2 (photo-stack) fit driver. It maps the modules, the data flow, and what is live versus vestigial. It does not re-derive the model itself — for what an optical-density curve, a white-context term, or a pair correction is, and why the model is shaped the way it is, read the How It Works page Color Model v2 — model and correction layer both — (and, for the earlier spline model, Color Model v1). The shared numerical model — fitting, prediction, and artifact I/O — lives in lib.photo_stack_model.model, lib.photo_stack_model.predict, and lib.photo_stack_model.artifacts; calibration only feeds it and files its output. How this fit is triggered, published, and reviewed within the unified model-fit workflow is Model workflow, publication, and review; the operator’s-eye view is The Modeling page.

On this page, publish_photo_stack_fit and similar code names mean “make this Calibration fit current.” They replace Calibration’s working generation and do not create, activate, or mutate an immutable Generator model library; user-facing publication is the separate Publish Models boundary.

The driver pipeline at a glance

One public entry point strings the stages together. run_photo_stack_fit_job in calibration.fitting.photo_stack_model.fit_job reports six progress phases:

  1. Build evidence — build_photo_stack_evidence(store, …).
  2. Fit — fit_live_photo_stack_bundle(evidence), run under a heartbeat so a long fit still emits progress.
  3. Fit the correction layer — apply_or_build_photo_stack_correction(…), which lives in the shared lib.photo_stack_model.correction_layer.
  4. Write the candidate — write_photo_stack_candidate(…, update_latest=publish). Both production webapp callers pass publish=False, leaving activation to publish_photo_stack_fit after the fit returns.

Steps in between assemble a measured-vs-predicted review payload through _build_sample_predictions and a review summary through _review_summary. The reached-from edges are on the fit-job node’s Imported by list: calibration.fitting.model_fit_workflow (the unified workflow that calls it live), calibration.server, and the dev harness smoke_fit_job — see the Model workflow, publication, and review page for the workflow wiring.

Stage 1 — evidence: live samples → canonical fit rows

build_photo_stack_evidence walks store.list_samples() and emits one canonical evidence document: a summary, an input_fingerprint, per-sample records, and per-swatch records. It is strict by design — the docstring notes geometry must be annotated, with no swatch-index fallback. Failures raise EvidenceBuildError.

What the adapter does, and does not, decide:

  • It filters, it does not fit. Samples are skipped (recorded in skipped_samples, not silently dropped) for referencing an exclude_from_model filament, not being processed, or missing measurements / strip definition.
  • Accepted review is enforced by the SQLite sample projection. The adapter tests processed plus Sample.measurements; it does not repeat a review_accepted condition. In production SQLite, measurements are hydrated only from an accepted extraction, so a pending-review result never reaches the evidence rows. The focused pending-review payload test covers this boundary.
  • Measured color comes from the sidecar, not the sample. _MEASURED_SOURCE = "sidecar" makes the per-swatch linear RGB read from the extraction-result sidecar via _sidecar_swatch_map, which fails loud if the sidecar is absent or malformed. Fit-control state (fit_state, exclusion_reason) stays a live read off the sample. use_measured_source("legacy") can temporarily flip back to the Sample.measurements color path. For what the sidecar is, see Extraction and Data access and persistence.
  • It classifies the physical stack. Each swatch’s realized bottom-to-top layer stack (from physical_stack_for_swatch) is tagged by _classify_realized_stack into evidence classes (white_only, naked_single_filament, color_over_white, single_color_sandwich, cross_color_multilayer_sandwich, …) that the fitter later uses to pick a role family.
  • It fingerprints its inputs. input_fingerprint hashes the samples directory, the filament registry, the filament-role snapshot, the source-sample projection, and the evidence itself. It also records the resolved data-root path, so it is a same-workspace fit identity rather than a location-independent content identifier.

use_fit_exclusions (default False) controls whether excluded samples/swatches are marked included=False; the live workflow passes True (see Stage 3). The color math here (linear-to-OKLab, optical density) is inlined deliberately without importing the spline runtime through _linear_to_oklab — it is bookkeeping, not the model.

Stage 2 — live_fit: the bridge to the vendored fitter

live_fit.py (calibration.fitting.photo_stack_model.live_fit) describes itself as the Prisma-owned bridge from calibration datastore evidence to the accepted research numerical fitter: the research math is vendored unchanged, while the wrapper handles live evidence adaptation, candidate metadata, runtime-bundle export, and public naming. The model math is not here — the fitter is imported from the vendored research engine package, and the public model/predict/artifact surface is lib.photo_stack_model.model / lib.photo_stack_model.predict / lib.photo_stack_model.artifacts.

fit_live_photo_stack_bundle does three things:

  • Reshape. evidence_payload_to_photo_stack_rows flattens the canonical evidence into the wide pandas row schema the research fitter expects, reading each swatch’s explicit bottom-to-top model_layer_triples through _model_layers_from_swatch rather than inferring stack order from legacy fixed/variable columns. It raises if there is not at least one included swatch.
  • Fit on the full corpus — no holdout. The rows are passed straight to research_fit.full_fit_predictions(rows, …); the model is fit and predicted on the same included rows. There is a fold = sample_num % 5 column, but the live fit does not split on it — predictions are in-sample. Excluded swatches are dropped upstream (Stage 1) via the included flag, not held out for validation here.
  • Rename into the public contract. Because the vendored engine stamps its own codenames, _sanitize_public_payload and _rename_research_prediction_columns rewrite research identity tokens to the public photo_stack / v2 names. Only strings change; numbers are untouched. The assembled _build_bundle validates against the shared lib.photo_stack_model.bundle schema and stamps a reproducible fingerprint that deliberately excludes wall-clock timing fields through _fingerprint_payload. The return value is a frozen LiveFitResult.

Stage 3 — fit_job: orchestration, correction layer, review payload

Back in fit_job.py, after the live fit the job:

  • Validates the bundle is a live source-of-truth artifact through _validate_live_fit_bundle.
  • Builds/refits the correction layer by handing the live predictions to the shared apply_or_build_photo_stack_correction, producing the photo_stack_v2_corrected model named by CORRECTED_MODEL_NAME. What the correction layer does is covered by Color Model v2’s correction-layer section; the code lives in lib.photo_stack_model.correction_layer.
  • Assembles the review payload — _build_sample_predictions turns the corrected full-fit rows into per-sample, per-swatch measured-vs-predicted chips (with stack diagrams and OKLab deltas), and _review_summary rolls up mean / p90 / max ΔE. This is the JSON the review UI renders; see The Modeling page.
  • Emits progress through _emit / _run_with_heartbeat so the six phases surface in the webapp job stream.

When the unified workflow drives this job it passes use_fit_exclusions=True, so operator sample/swatch exclusions are honored; the standalone default is False.

Stage 4 — staged write and coordinated publication

write_photo_stack_candidate is a thin pass-through to the shared writer write_candidate_artifact in lib.photo_stack_model.artifacts — its only job is to write a candidate without touching legacy spline profile outputs. Everything structural happens in the shared writer:

  • Candidates land under data_root/filaments/photo_stack_models/<run_id>/ through candidate_root, written atomically: files go to .tmp-<run_id>, required files and the runtime bundle are validated, then os.replace publishes the complete directory.
  • write_candidate_artifact still supports update_latest=True for direct/compatibility callers, but that is not the production webapp publication path. The workflow and standalone server job deliberately write with publish=False.
  • publish_photo_stack_fit validates the staged directory, atomically advances latest.json with activate_candidate_artifact, and then calls SQLite publish_model_fit. If ordinary SQLite publication raises, it restores the prior pointer and deletes the staged run. Only after both pointer and database replacement succeed does it attempt to garbage-collect superseded run directories, keeping one.

There is no operator-facing commit step, but there is an internal publication sequence with compensating filesystem rollback for ordinary exceptions. A successful fit becomes the sole retained photo_stack_v2 database fit. The superseded run-directory cleanup is deliberately best-effort, so a Windows lock can leave an old, unregistered directory behind without making it current or selectable.

The pointer and SQLite update are not process-kill atomic. A hard stop after latest.json advances but before publish_model_fit commits can leave the new run selected by pointer-reading review code while SQLite still reports the old fit. There is no startup journal that reconciles this split. SQLite-aware runtime bundle lookup prefers the registered fit, but the Modeling sample-prediction reader uses latest.json directly; publication readiness detects the artifact mismatch rather than repairing it. Do not kill Calibration while Fit Models is publishing, and verify model status/readiness after an abnormal stop.

Vestigial and support modules

Three modules in this package are not on the live fit path:

  • photo_stack_engine.py (calibration.fitting.photo_stack_model.photo_stack_engine) is largely vestigial. Its docstring states outright that live fitting now happens in fitting.photo_stack_model.live_fit. What fit_job still imports from it is only ENGINE_STATUS_READY. The pending-payload machinery — build_pending_photo_stack_candidate_payload, build_context_index, require_photo_stack_runtime_ready — describes an “engine not yet wired” era and is diagnostic-only; its Imported by list is just the fit job.
  • metrics.py (calibration.fitting.photo_stack_model.metrics) is a near-stub. Its single function summarize_metric_rows returns {"row_count": …} and nothing more; the module’s docstring calls it a helper “for future photo stack fitting jobs.” Its Architecture node shows it is not imported by any other calibration module.
  • smoke_fit_job.py (calibration.fitting.photo_stack_model.smoke_fit_job) is a developer CLI. Its docstring calls it a developer smoke harness, not a user-facing webapp command. It constructs a raw DataStore and runs the fit job from a --data-root argument; it is not imported by anything.

(For contrast, the sibling legacy_spline_fit_job.py — the v1 driver — is live despite its name, reached through the same unified model-fit workflow; that is documented on the Color Model v1 fitting page, not here.)
