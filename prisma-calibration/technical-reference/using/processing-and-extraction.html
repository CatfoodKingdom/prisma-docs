Processing and extraction

Processing and extraction

Properties1
tagscalibration, webapp

Jul 31, 20268 min read

In one sentence: on Images → Processing Queue, run extraction for samples whose strip image, registered blank, and open-side orientation are ready; rescue automatic failures with the four-corner manual workflow; then Accept only the results that should become model-fitting evidence.

This is the operator’s reference for the Processing Queue screen. The image math—detection, deskew, flatfield division, and per-swatch median extraction—is covered in Extraction and The extraction pipeline. Assignment and evidence readiness are covered in Assigning images.

Related: Driving the calibration app · Assigning images · Extraction · The extraction pipeline · The Modeling page

Getting here and what counts as ready

Open Images and switch from Assign Images to Processing Queue. The screen is split into Pre-Processing Queue on the left and Post-Processing Review on the right.

A normal ready sample has all of the following:

  • an assigned strip image whose managed file is locally available;
  • an assigned registered blank whose managed file is locally available; and
  • a selected open-side orientation.

The durable workflow status must be assigned for the sample to appear under Ready to Process. Merely assigning an image and blank without an orientation is not sufficient. If a managed source or blank later becomes unavailable, the card can still reflect its stored workflow state, but the processing request fails with a specific unavailable-file error rather than fabricating a result.

Pre-Processing Queue

The left pane has three collapsible sections.

Ready to Process

Each ready card shows its strip layout and assigned evidence, with these actions:

  • Process sends one synchronous request for this sample.
  • Flag moves it to Flagged for Manual Processing without extracting it.
  • Reassign unassigns the strip image, clears any flag best-effort, and returns the sample to Assign Images.

Process All (N) takes a snapshot of the currently assigned sample IDs and processes them sequentially in the browser. It does not call the backend’s /api/process/batch route and it is not one persistent server job. For each sample, the frontend calls the same single-sample endpoint used by Process, waits for its response, refreshes application data, updates the processed/flagged/failed counters, and only then begins the next sample.

The progress panel is therefore determinate between completed samples, not within the extraction of the current sample. There is no Process All cancel control. Closing or reloading the page prevents the browser loop from starting later samples, but it does not cancel the synchronous request already running on the server. Samples committed before interruption remain committed; Process All progress itself is not persisted or resumed after relaunch.

Failed

A committing automatic extraction normally marks the sample failed, removes its extraction result, and removes its live sample visuals when detection fails or another pipeline exception occurs before a successful commit. This prevents an earlier result from masquerading as the output of the failed attempt.

There is one deliberate rollback distinction: if building or atomically saving the replacement extraction result/sample pair fails, commit_extraction_result restores the prior durable pair and re-raises. The processor reports that attempt as failed without saving a new failed state. A filesystem publication interruption after SQLite commits is handled differently again: the committed semantics remain authoritative and the journal converges source.jpg and strip.jpg at startup. See Extraction artifact sinks and blank registration.

Flagged for Manual Processing

A user can explicitly Flag a sample. The backend also retains an optional low-spine-confidence path, but its gut-check is disabled by default in the current runtime, so ordinary automatic extraction does not normally create low-confidence flags.

Cards in Failed and Flagged for Manual Processing have:

  • Manual Process to open the four-corner workflow;
  • Unflag to clear the flag; a failed sample returns to assigned only if its image, blank, and orientation are complete, while a flagged sample with an extraction result returns to processed; and
  • Reassign to detach the strip image and return to assignment.

Manual Process All (N) opens the same modal with a client-side queue. It advances only after the operator accepts each manual result; it is not a server-side batch job.

Concurrency and busy behavior

Each automatic single-sample request and each ordinary manual preview/commit request acquires the extraction writer guard. That guard conflicts with model fitting and with other operations that reserve the same extraction/SQLite/evidence resources. A conflicting request receives a busy response; it is not silently queued.

Because the UI’s Process All releases the guard after every single-sample request, it does not reserve the extraction resource for the whole batch. Another client or operation can acquire a conflicting resource between items. The local UI disables its own overlapping processing controls while its batch state is active, but the backend remains the authority for cross-window and cross-operation admission.

Ordinary manual processing

Manual Process and Manual Process All open Manual Processing. The canvas uses the rotation-baked source preview. Click the corners in this order:

  1. top-left;
  2. top-right;
  3. bottom-right;
  4. bottom-left.

Placed corners can be dragged. The normal controls are:

  • Extract & Process sends a synchronous commit:false request. It writes transient review images and shows the extracted strip, but does not change the durable sample or extraction result.
  • Reset Corners clears the selection.
  • Retry discards the displayed result and returns to corner placement.
  • Accept re-runs the same manual extraction with commit:true; it does not merely promote the preview. A successful commit creates a new pending-review extraction, clears the flag through the committed workflow state, and advances the client-side manual queue or closes the modal.

The ordinary manual request has no cancel control. While it is running, close/reset controls are disabled and the browser waits for the synchronous response. Closing or killing the client cannot cooperatively cancel the in-flight server call. The Cancel button present in the shared modal is shown only when the modal is being reused for a cancellable maintenance re-extraction candidate job; it is not part of ordinary Processing Queue manual extraction.

Manual preview artifacts live under maintenance/manual_extraction_reviews/{sample_id}. Retry only hides the current result; the next preview overwrites that workspace. Closing, committing, or failing requests its removal, and startup removes abandoned manual-review directories. A hard stop during preview does not commit sample semantics. A hard stop during commit follows the same extraction-publication recovery rules as automatic extraction.

The manual path treats the clicked corner order plus stored open-side orientation as authoritative and does not use the automatic path’s brightness-based left/right flip. It strictly registers the blank to the source lightbox and fails if that homography cannot be established; it does not fall back to an unregistered resize.

Post-Processing Review

A successful automatic or manually committed extraction is already durable when it appears in Post-Processing Review. Its ExtractionResult.review_state is pending_review, and the sample’s review_accepted flag is false. The card shows the source and blank, the extracted strip, a thickness row, and a mock strip derived from the measured display colors.

  • Accept does not run extraction again. It atomically sets the SQLite sample’s review_accepted=true and synchronizes the current extraction result to review_state="accepted". Accepted results are the extraction evidence eligible for model fitting.
  • Reject invalidates the current extraction result, clears its measurements and flag, removes derived visuals, marks affected model fits stale as required, and returns the sample to assigned when its evidence is still complete (otherwise unassigned).

Accept All and Reject All apply those actions sequentially to the cards currently in review, refresh from the backend, and report partial failures.

There is a current single-card Accept error-path defect: if the backend update fails, the frontend logs the error but still hides the card locally until Refresh Data restores the authoritative state. Bulk Accept does not have that particular behavior; it collects and reports failed updates. This is a tracked implementation finding, not intended persistence semantics.

Acceptance is separate from later fit controls. On the Modeling tab, an accepted sample, swatch, or filament can still be excluded from fitting without rejecting or deleting the underlying extraction.

Short version

  1. Finish image, blank, and open-side assignment.
  2. Use Process All or Process and let the current request finish.
  3. Manually process failures by clicking TL, TR, BR, BL, previewing, then committing with Accept.
  4. In Post-Processing Review, accept trustworthy results and reject bad ones.
  5. Continue to The Modeling page; only accepted current extraction results are fitting evidence.
