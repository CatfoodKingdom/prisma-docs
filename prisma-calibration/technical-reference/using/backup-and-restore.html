Backup and restore

Backup and restore

Properties1
tagscalibration, webapp

Jul 25, 202610 min read

In one sentence: the topbar Backup / Restore dialog creates a portable ZIP of either the SQLite library alone or the library plus its durable files, validates and previews a package before restoring it, and separately archives bulky camera-RAW files so they can be removed from and later returned to active storage.

This page covers making backups and restoring them, plus the raw-image archive workflow that lives in the same dialog. It is a manual, operator-initiated screen; the app also keeps its own automatic database snapshots behind the scenes (see Automatic restore points below), which are a different thing and are not managed here.

Related: Driving the calibration app · Running maintenance · Managing filaments

Opening the dialog

The topbar Backup / Restore button opens a single dialog titled Backup / Restore with four stacked panels: Create Backup, Restore From Backup, Archive RAW Images, and Restore Archived Images. Everything below maps to one of those panels.

Backup creation, library restore, RAW-archive creation, archived-image removal, and archived-image restore all use the same custody lock, so only one can run at a time. Inbox import, model publication, and internal SQLite restore-point application also coordinate through that lock. A running Maintenance job blocks the operations on this screen, and library restore or archived-image removal also refuses to start while a model fit that could conflict with it is active. A rejected start normally reports Backup or restore is already running or names the active blocker.

These jobs have progress displays but no user-cancel action. Closing the dialog does not stop the server-side work. Let a job finish, especially a restore or archived-image removal; the Interruption and restart behavior section explains what happens if the server process itself stops.

Create Backup

Under Create Backup, pick a backup type, then click Create Backup. Two choices:

Essential Data Only

A small package containing a consistent SQLite snapshot — filaments, geometries, samples, image assignments, extracted measurements, model-fit records, and the rest of the database state. The private snapshot keeps only the lifecycle-owned fit for each model family; it does not modify the live database while doing so. The package does not contain source images, model artifact files, or generated STEP/STL exports.

Restoring it replaces only SQLite and leaves the current files and exports in place. That makes it a quick, portable snapshot of the workbook’s knowledge, not a self-contained library: files left beside an independently restored database are not guaranteed to match its records.

All Data and Artifacts

The operational working state: the normalized SQLite snapshot plus durable files from Calibration’s managed asset tree and supported .step/.stl geometry exports. This includes accepted sample visuals such as source.jpg and strip.jpg and the durable model artifacts needed by the retained fits. It deliberately omits regenerable preview-cache JPEGs, interrupted thumbnail transaction files, manual-review images, staged re-extraction candidate sets, generator cache files, logs, lock files, and other temporary work. Those are not restore invariants and their absence does not make backup creation fail.

When All Data and Artifacts is selected, an Include raw image files checkbox appears. Leave it on to include recognized camera-RAW originals (.cr2, .cr3, .dng, .nef, .arw, .raf, .rw2, and .orf). Turn it off to keep the database, non-RAW managed files, extracted data, durable artifacts, and geometry exports while omitting those multi-gigabyte originals. This switch does not remove ordinary JPEG/PNG assets from the package. The checkbox only applies to All Data and Artifacts; Essential Data Only contains no asset files at all.

The backup is written as a timestamped .zip in Calibration’s visible Backups folder, and the result supplies both its path and a download action. If Windows temporarily prevents a completed, validated ZIP from being promoted out of the backup .tmp workspace, Prisma preserves it there and retries during startup or later housekeeping. Invalid or unrecoverable abandoned temporary entries are retained for a 24-hour grace period before cleanup. Move important packages somewhere safe; the Backups folder is local working storage, not an off-machine backup by itself.

Restore From Backup

Under Restore From Backup, point the Backup File control at a Prisma backup .zip (type or select its path), then click Restore Backup.

A full All Data and Artifacts backup is also the supported way to move an existing Calibration library into a fresh Suite release: create the backup in the old copy, keep the ZIP outside both Prisma folders, start the new blank copy once, and restore the ZIP through this dialog. Do not copy Calibration/Workspace by hand or point two Prisma copies at one working directory. After restore, verify the sample/image counts and Modeling status before retiring the old copy.

Restore never applies a package blind. It first validates the manifest, member paths and hashes, SQLite integrity/schema, package semantics, and required file references, then shows a preview of the package and what it can replace. Validation is synchronous, so its progress display is animated but intentionally indeterminate rather than a file-by-file percentage. The preview token expires after 15 minutes if unused; a local path is also checked again for identity and validity when the restore starts.

Only after validation does the app ask you to type the package’s exact confirmation phrase. The wording differs by package: an all-data package with RAW warns that it will replace all existing data; one without RAW says it will replace all existing data except source images; and an essential-data package says it will replace the current database. The action stays disabled until the normalized phrase matches.

Before replacing live state, the restore job creates a fresh database-only safety backup. If the strict backup cannot be made it attempts a more permissive emergency core backup; if neither succeeds, the restore aborts before applying the package. The subsequent restore progress is six coarse phases, with package validation/staging shown as indeterminate rather than byte-counted.

What a restore replaces depends on which package you are restoring:

  • Essential Data Only → replaces the database only; your current images and exports stay as they are.
  • All Data and Artifacts, with raw images → replaces the database, assets, and exports, and brings in the package’s raw images too.
  • All Data and Artifacts, without raw images → replaces the database, assets, and exports, but keeps your current raw source images in place (the package has none to supply).

When restore finishes, the app reconstructs the active SQLite store and refreshes the UI automatically. Restore refuses unsafe symlinks, junctions, and reparse points at its managed boundaries; a linked managed asset tree is rejected before replacement, while a later unsafe-path failure is handled by the rollback transaction. This prevents a disposable worktree link from silently redirecting destructive work into another library.

During replacement, Prisma writes a durable restore journal and moves displaced state into a restore_previous_* rollback directory. The new workspace becomes authoritative only after validation, a store smoke check, and a durable committed journal phase. An ordinary failure before commit rolls the old state back. After commit, cleanup removes the rollback workspace; if that cleanup fails, the restore remains successful and reports restore_previous_cleanup_failed with the residual path so it can be removed manually after the restored library is verified.

Archive RAW Images

Raw camera files are the largest thing in the library and, once extracted, are rarely needed day to day. The Archive RAW Images panel lets you move them out of the active library without losing them. It has two steps, deliberately separated so you never delete originals you have not safely stored first.

Create RAW Image Archive

Create RAW Image Archive packages the current recognized camera-RAW image assets into a standalone archive ZIP. It records file identity and library-use context and validates the completed package. It only copies — nothing is deleted or moved out of the active library. Missing RAW files are recorded as missing and reported as a warning rather than silently represented as archived. Do this first, verify the archive, and move it somewhere safe.

Remove Archived Images From Active Library

This is the destructive step. Point its Archive or Backup File control at the archive you just made (a RAW-image archive, or an All Data and Artifacts backup that includes RAW files), and the app validates it and reconciles the package against the current SQLite image catalog. Because it deletes local files, it is confirmation-gated: type Remove archived images from active library before the action enables.

For every candidate, Prisma rechecks the archive entry, managed relative path, SQLite hash/size identity, and actual local file hash/size before a root-confined delete. Images absent from the package, changed since archiving, or otherwise conflicting are skipped and reported; they are not silently deleted. Store the archive somewhere safe before running this step.

Restore Archived Images

Restore Archived Images is the inverse: select a RAW-image archive ZIP (or an all-data backup that includes RAW files) and click Restore Archived Images. The app validates and reconciles it, then restores only files that are missing, represented in the current SQLite catalog, and still match the catalog’s expected identity. It uses exclusive creation and final hash/size verification, so an existing matching file is left alone and an existing conflict is not overwritten. Afterward it attempts to regenerate affected source thumbnails and reports samples whose extraction visuals still need a Maintenance rebuild.

Interruption and restart behavior

The operations on this screen are noncancelable. Closing a workflow window merely hides it; killing the server terminates its in-memory job and progress record.

  • Backup or archive creation: an incomplete, unvalidated temporary ZIP is disposable and housekeeping removes it. A complete validated ZIP that failed only during final promotion is retained for automatic recovery.
  • Library restore: this is the process-kill-safe workflow. On the next startup, the durable journal rolls back every noncommitted restore or finishes cleanup for one that had already committed. If Prisma cannot prove which files are safe to keep or remove, startup stops in recovery mode instead of guessing.
  • Archived-image restore or removal: work is committed one image at a time and has no full-operation rollback journal. If the process stops, files already restored or removed remain that way. Reopen the workflow, validate the archive again, and retry; reconciliation skips completed matches and reports conflicts. Avoid intentionally killing the server during removal because the final file’s custody-state update can lag its deletion until a retry reconciles it.

Automatic restore points (not this dialog)

Separately from this dialog, Calibration maintains internal SQLite restore points. Startup considers creating a database-only snapshot, with a six-hour minimum interval, and prunes the collection to at most 12 points no older than 30 days. They contain no RAW images, managed artifacts, or ZIP package. Applying one first preserves the displaced SQLite files under output/restore-points/recovery/; those preservation runs are not selectable restore points and are pruned with the same default count/age bounds.

Restore points are an automatic corruption-recovery safety net, not portable user backups and not something managed in this dialog. See Data access and persistence for the persistence and recovery boundaries.
