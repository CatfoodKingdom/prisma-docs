Assigning images

Assigning images

Properties1
tagscalibration, webapp

Jul 27, 202610 min read

In one sentence: on Images → Assign Images, a three-pane workspace connects the raw lightbox photos you shot outside the app to your samples — you import the photos, register the empty-lightbox blanks that flatfield correction needs, then give each sample a strip image, matching blank, and open-side orientation so it is ready to extract.

Extraction can’t run until a sample knows three things: which photo is its printed strip, which photo is the empty-lightbox reference, and which way the strip’s open side faces in the photo. This screen is where you supply all three. A blank is a photograph of the lit lightbox with no strip on it; during extraction the strip photo is divided by the blank to cancel the lightbox’s spatial unevenness — that division is the flatfield correction. See Extraction for how the blank is actually used.

Reach this screen from the Images tab, Assign Images subtab. The three panes read left to right: Registered Blanks, Image Inbox, and Assign Images and Blanks.

The three panes

Image Inbox (center)

This is where raw photos enter the app and where you pick the one to assign.

  • Import from Inbox verifies and copies supported files placed directly in the user-facing Inbox into managed custody. After the SQLite commit, custody finalization removes a successfully imported source from the Inbox; exact duplicates are moved under Removed Images. Nothing else on this screen can use a new photo until it has been imported.
  • Open Inbox Folder opens the exact user-facing Inbox folder used by this running app, so a user does not have to guess which installation receives a file.
  • Clean Up Unused moves eligible managed images into the user-facing Inbox/Removed Images tree and deletes their custody rows. It leaves assigned strip images and blanks referenced by samples alone.
  • CSV Bulk Assignment opens the bulk-assignment dialog (below).

The grid groups thumbnails into collapsible Unassigned, Assigned, and Ignored sections. An available unassigned image has both a rotate button (Rotate thumbnail 90 degrees clockwise) and an ignore button (the ×). An assigned image retains the rotate button but cannot be ignored until it is unassigned. An ignored image instead has a restore button and cannot be rotated. Ignore is persistent UI state; it does not move or delete the managed file.

Rotation is stored as a per-image 90-degree override. The server clears stale preview-cache variants, and extraction reads the override for both detection and measurement. A strip image cannot be rotated while it belongs to a processed, failed, or flagged sample. For a still-editable assignment, rotating the strip image clears its open-side orientation and returns an assigned sample to unassigned, so the user must confirm the orientation again.

There is an important current asymmetry for registered blanks: the same rotation override is used when the blank is read, but changing a blank’s rotation does not automatically find or invalidate samples that already use that blank. Set a blank’s rotation before processing samples with it. If it must change later, reprocess the affected samples before fitting models.

Below the grid, Selected Image names the thumbnail you’ve clicked, with two footer actions:

  • ← Register as Blank turns the selected photo into a flatfield reference (it moves to the Registered Blanks pane).
  • Assign Image to Sample → attaches the selected photo to the sample selected in the right pane as its strip image.

Registered Blanks (left)

The catalog of empty-lightbox references. To add one, either select a photo in the inbox and click ← Register as Blank, or drag a thumbnail onto this pane’s drop zone (Drop image to register blank, shown compactly as Drop to Register). Registration assigns an id and records capture time from EXIF when available. SQLite reuses the managed image asset and inserts the registered_blanks relation; only the legacy JSON path copies a second file into blank storage.

Selected Blank names the blank you’ve clicked; Assign Blank to Sample → attaches it to the sample selected in the right pane.

Register one blank per capture session and reuse it across samples shot without changing the lightbox, camera/lens position, exposure, or other capture conditions. It does not have to correspond to a particular printed strip, but it must represent the same imaging setup.

Assign Images and Blanks (right)

The sample list shows what each sample has so far. Selecting a row here sets the target for the two → assign buttons in the other panes; Selected Sample echoes your choice. Each sample’s assigned image and blank appear as slots with an Unassign (×) control to detach either one. The four-arrow control records whether the strip’s open side points up, right, down, or left.

The sample enters Ready For Processing only when all three inputs are present and locally available: strip image, registered blank, and orientation. Changing or clearing the image or blank, or changing the stored orientation, invalidates earlier processing for that sample — the app clears stale results so the sample re-extracts against the current evidence rather than showing measurements from the old inputs.

The current UI lets a user click the active orientation arrow as though to clear it, but that null value is omitted from the request: the card appears pending only until the next data refresh, while the server retains the old orientation and still considers the sample ready. Until that frontend/backend defect is fixed, select the correct replacement direction directly; unassigning the strip image is the reliable way to clear its orientation.

The assignment loop

For one sample by hand:

  1. Import from Inbox to bring your session’s photos in.
  2. Register the session’s empty-lightbox shot: select it, ← Register as Blank (do this once per session).
  3. Select a sample in the right pane.
  4. Select its strip photo in the inbox, Assign Image to Sample →.
  5. Select the session blank in the left pane, Assign Blank to Sample →.
  6. Use the arrows on the sample card to say which way the strip’s open side faces.

Repeat 3–6 for each sample. When every intended sample appears under Ready For Processing, move to Processing and extraction.

Import progress, cancellation, and interruption

Import from Inbox starts a background job and opens a progress dialog. The dialog polls the in-memory job record every 500 ms, retries transient status failures, and cannot be closed while the import is active. A second start request joins the already-active import rather than starting a competing one. Image import is also excluded while backup, restore, RAW archive work, another import, or conflicting maintenance holds the relevant resources.

Before it changes persistent state, the importer scans and hashes every supported file in the Inbox. If any file fails that scan, the batch reports the errors and imports none of them. During the write phase it creates a durable custody journal, copies each new image into managed storage, verifies the copy’s hash, and inserts the new custody rows in one SQLite transaction. An exact filename-and-content duplicate is skipped and moved under Removed Images when the transaction is finalized.

Cancel is cooperative. If it reaches a cancellation check before the SQLite commit, the transaction rolls back, newly created managed copies are removed, and the Inbox sources remain available. Once the database commit has completed, the import must finish custody finalization; a late cancel is reported as a successful import that completed before cancellation took effect.

The progress job itself exists only in memory and cannot be resumed after a server restart. The custody transaction is durable, however: startup/next-import reconciliation removes uncommitted managed copies or completes the Inbox cleanup for a committed import. This converges persistent image custody even though the old progress dialog and job id do not survive.

Clean Up Unused is different. It is a confirmed, synchronous request with a busy state, but no progress job or cancel control. It handles eligible images one at a time, moving each managed file before deleting its SQLite custody row. Normal failures are reported per image and later images continue. Do not kill the server during cleanup: a hard stop between a file move and its row deletion can leave a custody row whose managed file is missing, and retry currently skips rather than repairs that row.

CSV Bulk Assignment (the bulk path)

For many samples at once, CSV Bulk Assignment assigns images and blanks from a spreadsheet instead of clicking each one. Place every referenced sample and blank image in the Calibration Inbox first, click Import from Inbox, and then open the bulk dialog. The flow is template → validate → commit.

Download CSV Template gives you a header-only file with four columns:

ColumnWhat goes in it
Sample IDThe sample’s id (exp-123), or just the number 123 when that number is unambiguous.
Sample ImageThe imported strip photo’s filename (extension optional) or managed image id. Use a name/id, not a filesystem path.
Blank ImageA registered blank’s id, or an imported photo filename/id — an unregistered photo here is registered as a blank during commit. Use a name/id, not a filesystem path.
OrientationWhich way the strip’s open side faces: U, D, L, or R (T is accepted as up, B as down).

Choose CSV loads your filled-in UTF-8 file; Validate CSV checks it without changing anything and returns a preview: a per-row table plus counts of rows ready, blocked, blanks to register, and warnings. Extra columns are ignored with a warning. A row is blocked (and skipped) when its sample or image can’t be found, an image is ambiguous, a photo is missing or ignored, an image is already assigned to another sample, the same sample/image is reused elsewhere in the CSV, the sample photo is also the blank, or the sample isn’t eligible.

CSV assignment only touches fresh samples: a row is rejected if the sample already has an image, a blank, an orientation, a non-unassigned status, or existing extraction results. This makes bulk import a safe first-fill, not a way to overwrite work you’ve already done.

The validation preview and its commit token live only in server memory, expire after 15 minutes, and disappear on restart. Commit rechecks the live samples, images, assignments, and blanks; if anything relevant changed after validation, it rejects the stale preview instead of applying an outdated plan.

The commit button reads Import Assignments when every row is clean, or Import Valid Rows when some are blocked (only the ready rows commit). If any ready row names a photo that isn’t a registered blank yet, you’re asked to confirm registering those blanks before the import proceeds. Blank registration and all ready sample assignments then commit as one SQLite transaction: a failure leaves neither partial assignments nor a newly registered-but-unused blank. On success the app reports how many assignments landed and how many blanks it registered. CSV validation and commit are synchronous requests; they do not expose progress or cancellation.
