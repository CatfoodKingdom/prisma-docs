Driving the calibration app

Driving the calibration app

Properties1
tagscalibration, webapp

Jul 26, 20269 min read

In one sentence: the calibration app is a single-user FastAPI logbook that walks a filament from a printed strip to a published Generator library — register filaments and geometries, create samples, assign lightbox photos, extract and accept per-swatch measurements, curate the evidence, fit Calibration’s working models, and explicitly publish a static copy — while scoped resource guards keep conflicting writers from overlapping.

This page serves two readers: the operator driving the app end to end, and the developer who needs the backend’s shape — how the app is wired, which backend stores the data, and why a second job returns a “busy” error. For the phenomena behind each step (what a measurement is, how the models work) see the How It Works section; for the code-level map see the Technical Reference.

Related: Managing filaments · Samples and geometries · Assigning images · Processing and extraction · The Modeling page · Maintenance operations

Starting the packaged app

The Windows Suite starts this server through Prisma Calibration.exe; the Linux Suite uses the executable Prisma Calibration (Prisma/calibration_launcher.py). Both enter the same launcher. It fixes the app root to the folder containing the executable, creates and probes Calibration’s portable folders, takes an exclusive lock on Calibration/Workspace, creates a blank SQLite database only when that workspace is genuinely blank, applies the SQLite/database/asset environment contract, reserves a loopback port (preferring 8016 and trying the next 19 ports), and asks the host platform to open the browser. Starting a second instance for the same healthy workspace opens the lock owner’s local URL instead of creating a second writer.

server.py builds one FastAPI instance titled Unified Calibration Workbook and, after defining the API routes, mounts the single-page frontend from calibration/app/ with html=True, so / resolves to index.html. All operational routes live under /api/...; everything else is the static frontend. index.html loads the native-module entrypoint bootstrap.js, which composes the endpoint modules in api/, shared services in core/, and workflow owners in features/; style.css preserves the ordered stylesheet cascade. See Frontend architecture.

The POSIX lock and macOS browser-opening paths have been statically audited, but Prisma has not been run on a Mac and macOS support is not currently claimed. Direct server.py execution remains a lower-level developer interface: it requires explicit backend configuration plus the matching SQLite or JSON paths and does not establish the complete portable runtime contract for you.

Which store the data lives in

The backend is chosen explicitly at launch and never falls back silently. server.py reads PRISMA_CALIBRATION_BACKEND and accepts only json or sqlite. The packaged/source launcher always supplies SQLite, Calibration/Workspace/calibration.sqlite3, Calibration/Workspace/Assets, and the portable app root through the runtime-layout environment contract. The older JSON file store and local pointer-file compatibility remain explicitly selectable for migration tools, tests, and source maintenance; they are not packaged-runtime fallbacks.

The workflow, end to end

The five top-level tabs are workspaces, not a left-to-right wizard: the visible order is Logbook, Images, Filaments, Geometries, and Modeling, while the usual dependency order starts by setting up the reusable Filaments and Geometries libraries. You then create samples in Logbook, assign/process their images, and curate/fit in Modeling.

1 — Register the building blocks

Before a sample can exist, its parts must be in the library:

  • Filaments tab → + New Filament opens the create drawer: color name, manufacturer, material, hex color, and the policy checkboxes (White-cap eligible, Special role: Transparent, Special role: Black, and Exclude from model fits). The exclusion also withholds that filament from newly published libraries. See Managing filaments.
  • Geometries tab → + New Sample Geometry opens the step builder, where you lay out the strip’s variable and fixed layers. Related geometries can be grouped with Manage Bundles. See Samples and geometries.

2 — Create samples

A sample is a strip geometry filled with specific filaments. On the Logbook tab, + New Samples opens the bulk create drawer: pick a single geometry or a bundle, assign a filament to each layer role (in Multi mode you batch across several filaments to spawn many samples at once), and create. The sample now exists in the logbook awaiting photographs. See Samples and geometries.

3 — Assign photographs

The physical strips are 3D-printed and photographed on a lightbox outside the app. On Images → Assign Images, a three-pane workspace connects those raw photos to samples:

  • Image Inbox — Open Inbox Folder opens the user-facing drop folder; Import from Inbox moves supported files into managed custody. Import is the action that scans the folder; the topbar Refresh Data button does not import it. Select an imported image and use Assign Image to Sample →.
  • Registered Blanks — a blank is an empty-lightbox photo used for flatfield correction. Register one, then Assign Blank to Sample →.
  • Assign Images and Blanks — the sample list showing what each sample has so far.

For many samples at once, CSV Bulk Assignment bulk-assigns images and blanks from a spreadsheet. See Assigning images.

4 — Extract the colors

On Images → Processing Queue, samples with images assigned appear under Ready to Process. Process All (N) runs strip detection, deskew, flatfield correction, and per-swatch color extraction across the batch. Samples that fail auto-detection land in Failed or Flagged for Manual Processing, where Manual Process opens a modal to click the strip’s four corners by hand. See Processing and extraction.

5 — Accept the results

Extraction results appear in Post-Processing Review (the right side of the Processing Queue). You Accept or Reject each result. Accepting promotes it to the sample’s trusted extraction; rejecting does not make it model evidence. Only accepted extractions feed the models and appear in Modeling’s evidence tables.

6 — Curate the evidence

The Modeling tab is where you decide what the models learn. Overview summarizes accepted evidence and flags stale/missing models, samples blocked by excluded filaments, and samples without an accepted extraction. Samples lists accepted-extraction samples and exposes persistent sample/swatch inclusion controls through the comparison drawer; Filaments shows accepted-evidence coverage and health. Excluding a sample or swatch keeps a suspect measurement out of later fits without deleting it. See The Modeling page.

7 — Fit the working models

Fit Models opens the dedicated, noncancelable Maintenance workflow. It always attempts Color Model v1 (the legacy spline) and Color Model v2 (the photo-stack model) from the currently included evidence. Camera Transform preflight rebuilds that family only when forced or when its registered inputs/artifacts are missing, invalid, or changed; it is skipped when already current and can also be skipped when fewer than five eligible samples exist. Each successful stage coordinates its own filesystem/pointer and SQLite replacement and compensates for ordinary exceptions, but neither that cross-layer transition nor the multi-family workflow is one process-kill-safe transaction. A completed family—or v1’s successful filament subset—can already be current before a later failure stops the run. Generator cannot see this mutable working state. The mechanics live in Color Model v1, Color Model v2, and The Camera Transform.

8 — Publish a Generator library

The topbar Publish Models action first reads /api/models/publication/readiness, which requires one current registered fit for every required family, intact registered artifacts/pointers, and a valid public filament catalog. Publish to Generator calls /api/models/publication/install and installs a new inactive, application-immutable library in the sibling Generator store. Export Library Package calls /api/models/publication/export and writes the equivalent transfer ZIP to Calibration/Output/Published Models. Calibration will not mutate either published copy afterward. Neither path activates a Generator library, changes Calibration’s working-model lifecycle, or modifies an older published library.

How the app is wired (developer view)

One process, one user

The app holds its live state in a single Python process. There is no per-user or per-browser isolation: two tabs pointed at the same server share one backend and one set of jobs. This is a workbench tool, not a multi-tenant service.

Conflicts are scoped, not global

Calibration does not have one global heavy-job lock. It combines operation-family job registries with explicit resource ownership:

  • the backup/restore/RAW-custody lock serializes package and image-custody work;
  • the model-fit owner prevents conflicting fit/evidence writers;
  • the extraction-writer owner protects accepted extraction evidence and sample visuals;
  • Maintenance reserves the concrete resources declared by an operation before its worker starts.

Independent reads and nonconflicting work can overlap. Conflicting work is rejected with HTTP 409 and a blocker message. Depending on the endpoint, a repeated same-operation start may instead return the already-active job. Nothing waits in a general-purpose queue for an unrelated heavy operation to finish.

The practical UI pattern is start, poll, report. A click starts or joins the relevant background job, the frontend polls its operation-specific status route, and only workflows classified for safe cancellation expose a Cancel action. Other workflows are intentionally noncancelable; see Web API and job orchestration, Running maintenance, and Backup and restore for the individual contracts.

Restarting

Restarting the server drops the in-memory job registries, so a browser cannot resume polling an old job id. Durable state lives in SQLite and the managed asset/output roots: accepted extractions, filaments, geometries, samples, normally completed working models, staged re-extraction review sets, backups, and published Generator libraries survive independently of the worker that created them.

That does not mean every interrupted operation is rolled back wholesale. Startup reconciles the workflows that have durable journals or housekeeping rules — notably full restore, image import custody, complete/transmission extraction publication, backup temporary-package promotion, and immutable-library staging cleanup. It does not reconcile a hard stop between a working model’s filesystem/pointer activation and SQLite replacement. Other workflows retain only their completed units or staging data. If the process stops during work, restart through the launcher and inspect the affected workflow rather than assuming the old progress panel remains authoritative; after an interrupted fit, use Publish Models readiness as the stricter artifact-integrity check.
