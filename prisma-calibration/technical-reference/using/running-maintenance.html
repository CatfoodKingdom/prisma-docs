Running maintenance

Running maintenance

Properties1
tagscalibration, webapp

Aug 07, 20267 min read

In one sentence: the topbar Maintenance button opens a dialog of named housekeeping operations — audits, image and geometry rebuilds, database health checks, and the model fit — each of which you run through the same preflight → run → report cadence, one at a time, with a running Maintenance Activity Log; the one exception is Re-extract Sample Images, a staged review workflow that never overwrites your accepted data until you explicitly save.

This page is the operator’s how-to for the Maintenance dialog: what each control does and in what order you click it. For what each operation does mechanically — what an audit inspects, what a rebuild regenerates, why the fit is safe to re-run — see Maintenance Operations and don’t re-derive it here.

Related: Maintenance Operations · Processing and extraction · The Modeling page · Backup and restore · Driving the calibration app

Opening the dialog

The topbar Maintenance button opens the Maintenance dialog. Operations are laid out as selectable cards, grouped under category caps and spread across up to three columns. Each card shows the operation’s name, a one-line description, and a small meta tag telling you whether it is Read-only or writes something. Clicking a card selects it; the Selected Operation panel on the right then shows a Start Workflow button.

The dialog header carries one extra button, Activity Log, covered below.

The operations, by group

The groupings and exact names come straight from the operation registry:

  • Audit — Audit Library Integrity, Audit Missing Artifacts, Audit Orphaned Artifacts, Audit Source Image Custody. All read-only; they report problems without changing anything.
  • Images — Rebuild Image Previews, Rebuild Extraction Images Only, Re-extract Sample Images.
  • Calibration Models — Fit Models.
  • Geometry Artifacts — Regenerate STEPs/STLs, Export Geometry Files.
  • System Maintenance — SQLite Integrity Check, Quarantine Orphaned Artifacts.

An operation that is currently unavailable appears grayed out with a reason line in its detail panel, and its Start Workflow button is disabled.

Two of these overlap actions you can reach elsewhere:

  • Fit Models here runs the exact same unified fit you can launch from The Modeling page — Color Model v1, Color Model v2, and the Camera Transform, from the currently-included evidence.
  • Export Geometry Files writes the same user-facing STEP/STL exports that the Geometries tab’s export action produces.

Running a standard operation

Every operation except Re-extract Sample Images runs through one workflow dialog with the same three beats.

  1. Start Workflow opens the operation’s dialog, headed with the operation name. It restates the description and, where relevant, exposes options:
    • Operations with more than one mode show a Mode picker — for the rebuilds and exports this is Missing Only (act only on what’s absent or repairable) versus Force Rebuild / Force Export (rewrite everything in scope). A help line explains the difference.
    • Export Geometry Files adds an Export Options block: Only Geometries Used By Samples or All Geometries, plus STEP / STL file-type checkboxes.
    • Fit Models adds a Fit Options block with a Force Camera Transform checkbox.
  2. Run Preflight inspects the current state and reports what the operation would do — a summary, any warnings, and any blockers — without touching data. If preflight blocks the operation, the run button stays disabled.
  3. The run button (labeled by what it does: Run Audit, Run Maintenance, Export Files, or Fit Models) executes the job. Progress streams into the dialog. Safe-point operations offer Cancel and remain visibly Cancelling… until the worker actually stops; operations labeled Runs to completion never offer Cancel. A Result section then shows the outcome, summary, any warnings, and the path to the saved report. Export Geometry Files in its overwrite mode also asks you to type a confirmation phrase before the run button unlocks.

That preflight-first-then-run rhythm is deliberate: nothing that writes data does so until you have seen the preflight and clicked the run button.

Only one at a time

Maintenance operations are not queued. Only one standard maintenance worker or dedicated re-extraction worker may execute at any moment. A second standard start is normally rejected with 409 and a message naming the active job; family/resource admission rejects conflicting re-extraction starts as well. There is one race-safe qualification: a request can create a queued record just before its daemon worker acquires the shared run lock. If another owner wins, that record is marked failed/blocked rather than waiting or running concurrently. Backup, restore, or RAW-archive work blocks maintenance in the same way, and vice versa — see Backup and restore. In practice you start a job, watch it finish in its dialog, and only then start the next.

The Activity Log

The Activity Log button (dialog header) opens Maintenance Activity Log, a history of standard-operation reports. It is a four-column table: Name, Type, Status, File Name. Each standard executor that returns its structured report gets one report row here; the newest sits on top. A job blocked before execution—or a worker that raises before returning a report—has no row. The dedicated Re-extract Sample Images workflow keeps its generation/apply reports inside its candidate set rather than adding them to this list. A clean completed re-extraction apply deletes that candidate set, so its candidate-local reports are not a durable Activity Log history.

The footer’s Clear Log button deletes those saved report files. It asks first (a Clear Activity Log confirmation), and it is narrow in scope: clearing the log removes only the maintenance report JSON files — it does not touch backups, RAW archives, source images, generated artifacts, quarantine files, SQLite data, or any sample records.

Re-extract Sample Images

Re-extract Sample Images is not a one-shot job — it is a staged review workflow, and the important thing to understand is that it is non-destructive: it re-runs extraction into a temporary candidate set and leaves your accepted measurements untouched until you explicitly save. You review every candidate and decide, sample by sample, whether to keep it.

Start Workflow on this card opens its own dialog with three scope controls:

  • Data — Complete, Transmission Only, or Appearance Only. This chooses which color data gets recomputed. (See Transmission vs Appearance for what those two halves are.)
  • Coordinates — Use Accepted Coordinates (reuse the strip corners already accepted for each sample) or Re-detect Strip (find the strip from scratch). Choosing Re-detect Strip forces Data back to Complete and disables the partial options — a full re-detect has to redo everything.
  • Samples — All Accepted (every accepted, processed sample) or Selected Samples, which reveals an id textarea. Type or paste sample ids separated by commas or spaces, e.g. exp-055, exp-056.

From there:

  1. Run Preflight counts the targets and splits them into automated, manual, and blocked, and warns you which samples will need manual corners.
  2. Extract Images runs the re-extraction into a fresh candidate set. Nothing accepted has changed yet.
  3. Samples that couldn’t auto-detect surface in a manual step first: open each one, place Manual Corners by hand, then Review Results.
  4. The Review Extracted Images dialog lists every candidate with a before/after strip comparison (Extracted Transmission and Extracted Appearance). For each reviewable sample, toggle Save or Skip; a failed candidate offers Retry, and a re-detect candidate offers Manual Corners. You must decide Save or Skip on every pending sample before you can commit.
  5. Commit with Save Results (which shows the final Save / Skip / Failed / Blocked counts) or throw the whole candidate set away with Discard Results. Only Save Results writes the kept candidates over the accepted measurements.

Like the standard operations, each active re-extraction phase takes the shared maintenance run lock. A second re-extraction or standard maintenance job cannot run concurrently; admission normally rejects the conflicting start, while a queue-to-worker race is recorded as blocked rather than waiting.
