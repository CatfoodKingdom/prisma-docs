The camera transform fitter

The camera transform fitter

Properties1
tagscalibration, camera-transform

Jul 15, 202611 min read

In one sentence: run_camera_transform_build_job (calibration.fitting.camera_transform.job) builds a corpus of (transmission → embedded-JPEG appearance) pairs, validates with deterministic five-fold sample-grouped cross-validation, refits on all clean evidence, bakes the numeric inverse into a 3D LUT, and writes a staged generation that the shared publication boundary coordinates with SQLite before retiring the old generation.

This page is the code-level map of the module cluster under calibration/fitting/camera_transform/: how a Camera Transform artifact is built. The model form it fits — the root-polynomial feature map, the per-channel monotone PCHIP curves, F (fitted transmission → appearance) and its numeric inverse G baked as a LUT — is derived in The Camera Transform; this page links it rather than re-deriving it. The distinction between the transmission the corpus reads and the appearance it targets is Transmission vs Appearance. The shared model runtime that both the fitter and the generator import is lib.camera_transform. How this build job is dispatched alongside the other model fits, and how its output is published, is Model workflow, publication, and review.

Here, the older internal “publication” names mean coordinated replacement of Calibration’s current working Camera Transform. They do not create or update a Generator library; that requires the separate user-facing Publish Models action after all three working fits are current.

The build job — five phases, two gates

run_camera_transform_build_job is the single entry point. It is called by both the unified workflow and the server’s standalone Camera Transform job: its Imported by list is calibration.fitting.model_fit_workflow and calibration.server. It takes a store, an optional output_dir (default store.root / "camera_transform"), and a use_fit_exclusions flag (default False; the production webapp callers pass True); it emits five progress phases through an optional _emit callback.

The phases run in fixed order:

  1. Corpus. build_camera_transform_corpus_from_extraction_results builds the (T, appearance) corpus from stored sidecars (see below). Alongside it, build_camera_transform_fit_fingerprint computes the robust fit-input fingerprint. An empty corpus raises RuntimeError; fewer than five eligible samples cannot support the validation policy; a corpus below MIN_USABLE_SWATCHES = 200 does not fail — it appends a “coverage is thin” warning and continues.
  2. Fit. fit_camera_transform(corpus.rows) returns a CameraTransformFitResult.
  3. Validate. The pooled out-of-fold mean dE76 is read from fit.metrics["validation"]["dE76_CIELAB"]["mean"]; if it exceeds MAX_VALIDATION_MEAN_DE76 = 6.0, the job raises RuntimeError and — crucially — the existing artifact is not modified. Nothing is written until this gate passes.
  4. Bake. bake_inverse_lut(fit.params) produces the inverse LUT.
  5. Export. write_camera_transform_artifact writes the payload, LUT, and manifest into a complete generation directory. Its activate=publish argument controls whether the writer also advances CURRENT; both production webapp callers pass publish=False and publish through publish_camera_transform_fit afterward.

Between bake and export the job assembles the payload and manifest. The manifest carries the corpus summary, pooled and per-fold out-of-fold CIELAB/OKLab metrics, final-fit training diagnostics, hygiene drop counts, the source_data_fingerprint, the params_sha256 identity hash, and the quality-gate thresholds and warnings. The return value reports status "warning" or "ok" and echoes the summary and manifest.

Stable identity hash across identical re-fits

_previous_params_sha256_if_same is a small but deliberate detail: before hashing the new payload it loads the existing artifact, and if the freshly fit params array is bit-for-bit equal to the stored one it reuses the prior params_sha256. So a rebuild that lands on identical parameters keeps its identity hash stable rather than minting a new one from an unrelated payload field.

The corpus — transmission paired with embedded-JPEG appearance

calibration.fitting.camera_transform.corpus builds the training table. Each row pairs a swatch’s transmission (T_R/T_G/T_B, the linear measured values) with its appearance (jpeg_r/g/b, median byte RGB from Canon’s embedded CR2 JPEG). The appearance target is the embedded JPEG render specifically — the module docstring is emphatic that it never falls back to the libraw visual render, thumbnails, or measurement medians, because those use per-image auto-brightening and different tone/hue rendering. This transmission-vs-appearance split is the whole point of the Camera Transform; see Transmission vs Appearance.

There are two builders, and only one is on the live path:

  • build_camera_transform_corpus_from_extraction_results is the live builder. It does not reopen source images at fit time. The live Sample controls which samples and swatches participate, their row order, fit_state, excluded_swatches, and variable_fid. For each participating swatch, the accepted extraction_result sidecar supplies the stored nominal thickness, measured transmission, embedded-JPEG appearance, appearance source, and extraction diagnostics. It fails loud via StoredCorpusError when a measurement-bearing sample is missing or has a malformed sidecar, when successful appearance diagnostics are incomplete, or when an included swatch lacks stored appearance — never a silent skip.
  • build_camera_transform_corpus is the older fit-time re-extraction path — it opens each CR2, locates the strip in the JPEG frame, and samples swatch boxes directly. It is aliased build_camera_transform_corpus_legacy_extract and is kept callable only for the parity oracle and tests; the job comment records it was retired from the fit path once a full-library parity oracle passed exact. Its geometry helpers still live here — _locate_strip, _compute_swatch_boxes, _box_median — and the fit-time and stored paths share _build_corpus_summary so their summaries stay identical.

Both builders return a frozen CameraTransformCorpus: the rows DataFrame, a summary dict, the skipped_samples list, and a source_fingerprint. _orient_colors correlates each swatch’s stored G_linear transmission against JPEG luminance (signed Spearman) and flips the swatch order if the reversed correlation is stronger; the resulting order_correlation is a per-sample extraction-quality guard, not a transmission-vs-thickness check. The legacy builder performs that work at fit time. On the production path it was already performed when the accepted extraction sidecar was created; the live corpus reads appearance_orientation_flipped and appearance_order_correlation back from that sidecar rather than recomputing them.

The live builder’s accepted-only boundary is enforced indirectly by the production SQLite sample projection. It checks for a processed sample with Sample.measurements; SQLite hydrates those measurements only from an accepted extraction result. Pending-review results therefore do not enter the corpus even though the corpus helper does not repeat a review_accepted predicate. The focused pending-review payload test covers this behavior.

The corpus module is imported beyond the fitter by calibration.maintenance_reextract, calibration.processing.extraction_result, and calibration.processing.extraction_visuals, which reuse its extraction helpers for re-extraction, sidecar production, and review visuals. calibration.maintenance reaches that behavior through the re-extraction workflow rather than importing the corpus module directly.

The fit — filter, cross-validate, refit

calibration.fitting.camera_transform.fit holds fit_camera_transform and the numerical machinery around it. It runs three stages on the corpus rows:

  1. Filter. load_and_filter applies five hygiene rules — drop fit_state == "excluded", drop whole samples whose order_correlation is below 0.8, drop physically suspicious bright/opaque rows, drop NaNs, and mark (but keep) JPEG-clipped rows so they are censored from the loss (JPEG_CLIP_THRESHOLD = 250). It returns the cleaned frame plus a drop_counts dict that becomes the manifest’s hygiene_drop_counts.
  2. Assign validation folds. assign_validation_folds scores each sample from its measured transmission, sorts samples by score and id, and assigns each consecutive block across five folds using a seeded SHA-256 ordering. Every swatch from one sample stays in the same fold. No name-derived filament category participates.
  3. Cross-validate and refit. Five temporary fits each train on four folds and predict the fifth, producing exactly one out-of-fold prediction per clean row. The pooled dE76/OKLab metrics drive the publication gate. After validation, a sixth fit trains on all clean rows and supplies the published parameter vector. als_fit provides an alternating-least-squares warm start, then joint_polish refines with scipy.optimize.least_squares.

fit_camera_transform returns a frozen CameraTransformFitResult carrying the final params, the cleaned frame, out-of-fold predictions, the sample-to-fold assignment, validation/final-fit metrics, and hygiene counts. The parameter layout, feature map, and monotone-curve construction are the model form — see The Camera Transform and lib.camera_transform.

The LUT bake — numeric inverse on a grid

calibration.fitting.camera_transform.lut is one function. bake_inverse_lut samples a grid_size = 33 cube over [0,1]³ appearance space, calls invert_forward from lib.camera_transform to solve back to transmission at each grid point, clips to [0,1], and returns a (33, 33, 33, 3) float32 array. This is the baked G — the numeric inverse of the fitted forward model — that the generator interpolates at solve time. Why the inverse must be baked numerically rather than solved in closed form belongs to The Camera Transform.

Staged export and coordinated publication

calibration.fitting.camera_transform.export writes complete generation directories so a reader never sees half-written files. write_camera_transform_artifact validates the payload and LUT before creating a generation, then:

  1. Writes camera_transform.json, inverse_lut_33.npz, and manifest.json into a unique temporary generation, computes the two data-file hashes into the manifest, and fsyncs all three files.
  2. Renames that temporary directory to gen-<timestamp>-<uuid> through _rename_generation_with_retry, making the staged generation complete but not necessarily current. On Windows only, access-denied and sharing/lock violations (winerror 5, 32, or 33) are retried after bounded delays of 0.10, 0.25, 0.50, 1.00, and 2.00 seconds. Other errors fail immediately; exhausting the retries fails without advancing CURRENT.
  3. If activate=True, activate_camera_transform_generation writes and atomically replaces CURRENT, then finalize_camera_transform_generation removes legacy flat files and attempts to garbage-collect old generations with keep=1. This direct activation mode remains available, but production fitting uses activate=False. Cleanup is best-effort: an old generation that Windows still has locked can remain as an unregistered filesystem orphan, but it is not retained as a selectable or current Calibration fit.

Any failure before the generation rename removes the unfinished temporary directory and re-raises, so a failed staged build leaves CURRENT untouched. The production publication wrapper also discards a complete staged generation if activation or SQLite registration raises. build_payload is the sibling that stamps the schema, model version, architecture string, and parameter layout into the JSON.

Production activation is owned by publish_camera_transform_fit. It advances CURRENT, then registers a replaceable SQLite camera_transform fit whose artifact root is the Camera Transform family directory and whose artifacts are the newly hashed CURRENT pointer plus the three files in the selected generation. Registering the pointer is essential: publication readiness verifies both the pointer hash and the generation it names. Only after SQLite replacement succeeds does the wrapper finalize keep-1 garbage collection. If activation fails, it discards the staged generation. If an ordinary SQLite publication exception occurs, it restores the previous pointer and discards the staged generation. This is a coordinated pointer/database replacement with compensation, not one cross-filesystem/SQLite transaction.

A process kill is outside that compensation. If Calibration stops after CURRENT advances but before SQLite replacement commits, pointer-reading consumers can load the new generation while model status still names the old fit. No startup publication journal completes or reverses this transition. Publication readiness detects the registered-pointer/hash mismatch rather than repairing it. Do not kill Calibration while Fit Models is publishing; after an abnormal stop, verify model status and readiness before trusting or publishing the working set.

The fingerprint — what actually reached the optimizer

calibration.fitting.camera_transform.fingerprint answers “does this need rebuilding?” more robustly than a sample count. build_camera_transform_fit_fingerprint re-runs load_and_filter and assign_validation_folds, then hashes the rows that reach validation/final fitting plus the deterministic fold assignment. It produces fit_input_hash, raw_corpus_hash, validation_hash, and diagnostic_hash under CT_FINGERPRINT_SCHEMA_VERSION = 3, with floats canonicalized to 17 significant digits. The fit policy records five-fold validation followed by a final all-data fit; it contains no filament-name classification metadata. The job stores the whole fingerprint as the manifest’s source_data_fingerprint; robust_fit_input_hash reads it back for rebuild decisions.

Parity — a migration oracle, not steady state

calibration.fitting.camera_transform.parity is read-only and transitional. It captures a legacy (or stored) corpus plus hygiene and validation-fold assignment into a deterministic snapshot, so the parity oracle can prove the extraction-path switch preserves membership, row order, skips, folds, and per-row values. It is a verification harness invoked from tests/tooling, not part of the live build path.
