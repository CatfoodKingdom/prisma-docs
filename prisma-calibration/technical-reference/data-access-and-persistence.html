Data access and persistence

Data access and persistence

Properties1
tagscalibration, persistence

Jul 14, 202612 min read

In one sentence: packaged Calibration owns Calibration/Workspace/calibration.sqlite3 plus a materialized Workspace/Assets root fronted by SQLiteDataStore (calibration.sqlite_data_access, sqlite_data_access.py:265); visible Inbox/Output directories are siblings of that app-managed Workspace; the older JSON-tree DataStore (calibration.data_access) is retained for migration tools and tests only; and two different safety nets sit on top — operator-driven ZIP backups (calibration.backup_restore) and internal automatic SQLite restore points (calibration.sqlite_restore_points).

This page is the code-level map of where calibration data is stored and which backend reads it. For the operator’s view of packaging and restoring data, see Backup and restore. For how the web layer opens a store at startup and dispatches jobs against it, see Web API and job orchestration; for the batch operations that mutate the store in place, The maintenance backend.

Related: calibration.sqlite_data_access · calibration.data_access · calibration.models · calibration.backup_restore · calibration.sqlite_restore_points

The backend split — SQLite is production, JSON is migration-only

There are two store implementations and they are not peers. Backend selection is explicit and refuses to guess: _configured_backend (calibration.server, server.py:305) reads the PRISMA_CALIBRATION_BACKEND env var (or a local .backend file) and raises if neither is set, so “a launch cannot silently fall back to legacy JSON” (server.py:310-314). _create_store (server.py:336) then builds one of:

  • json → DataStore (server.py:355-356) — the legacy filesystem tree. Its own header comment states it exists so “JSON can still be constructed intentionally for migration tests/tools, but it is never selected as an implicit fallback” (server.py:344-347).
  • sqlite → SQLiteDataStore(sqlite_path, asset_root=...) (server.py:368) — the production store. Both the database path and the asset root must be configured (env var or local pointer file) or construction errors out (_configured_required_path, server.py:324).

The module module-level _store is typed DataStore | SQLiteDataStore (server.py:203) and every request handler treats them polymorphically, but on a live install the object is always the SQLite one. Read the rest of this page with that in mind: sqlite_data_access.py is the live path; data_access.py is dormant except during migration.

The production store — SQLiteDataStore

SQLiteDataStore (sqlite_data_access.py:112) is the production SQLite-backed store. Its module/class header still contains transitional “Stage 1” wording (sqlite_data_access.py:1-6, :113-118), but that wording is stale relative to the implemented runtime: the class now provides the live geometry, filament, sample, image, extraction, bundle, and model-fit read/write paths described below. Its class attribute backend = "sqlite" (:120) is what the server checks to gate SQLite-only behavior.

The two-root design — database + materialized assets

The constructor takes two paths and keeps them apart (__init__, sqlite_data_access.py:265):

  • self.sqlite_path — the single SQLite database file (:148).
  • self.root — the materialized asset root, a directory tree of the binary/large artifacts that do not belong inside the database (:149).

Structured rows live in SQLite; bytes live under the asset root. The store exposes the asset layout as path properties so callers never hardcode subpaths:

The packaged shape is recognized only when the asset root is exactly Calibration/Workspace/Assets (portable_calibration_root, sqlite_data_access.py:589-:598). This keeps user-facing files outside the internal asset tree without making them external to the portable Suite. Source-maintenance/migration roots retain their compatibility path derivation.

Fitted spline profiles are still JSON files on the asset root, not database rows — the profile artifact format survived the SQLite changeover unchanged.

Startup validation and schema migrations

Construction is fail-closed. _validate_paths (:155) requires the database file and asset root to already exist; then two idempotent in-place schema migrations run — _migrate_bundle_mapping_schema (:221) and _migrate_raw_archive_custody_schema (:361) — followed by _validate_schema (:441), which reads sqlite_master and hard-fails if any of the 22 tables in _REQUIRED_TABLES (:122-:145) is missing. There is no _migrate_filament_classification_schema in the current implementation. A store either opens against a database with the required schema or refuses to open.

Connections are split by intent: _connect_readonly opens the file mode=ro for projections (:165-:169), while writes go through _connect_write with foreign keys enabled (:171-:175) inside _write_transaction, which wraps every mutation in BEGIN IMMEDIATE and commit/rollback (:177-:188).

Domain accessors — the shape, not the catalog

The class is large (~9k lines) because it holds every read projection and write path for the whole domain, but the surface is regular. Representative accessors, most returning the pydantic models from calibration.models (a few return raw dicts or a Path, noted inline):

  • Filaments — list_filaments (:1481), get_filament (:1532).
  • Samples — list_samples (:2783), get_sample (:2809).
  • Geometries — surfaced as StepRecords via list_step_records (:4326) / get_step_record (:4329), with the reconstructed GeometryDefinition from get_geometry_definition (:2090). See Geometry and strip definition for what a geometry is.
  • Blanks — list_blanks (:5725).
  • Extraction — get_extraction_result (:3244, returns a dict) / save_extraction_result (:3676, returns a Path).
  • Bundles — list_bundles (:4526, returns list[dict]).

The remaining compatibility gaps are explicit rather than silently redirected: list_strip_filaments returns an empty list and get_strips returns None (:4314-:4318); _step_record_from_components, save_steps_registry, and set_image_ignored call _not_implemented (:497-:502, :4367-:4371, :5881-:5883). The implemented SQLite paths do not use those legacy operations.

Current working models — the three model kinds

Fitting outputs are recorded as model fits in the model_fits / model_artifacts tables, gated to exactly three kinds by _MODEL_KINDS = {"camera_transform", "legacy_spline", "photo_stack_v2"}. The internal helper name publish_model_fit means “make this Calibration fit current”; it is not the user-facing act of publishing a Generator library. In one transaction it inserts the replacement current fit, contributors, and artifacts, then deletes the previous fit row for that family; foreign-key cascades remove old child rows. The tables therefore retain one replaceable working fit per family, not operator-selectable historical fits.

The separate calibration.model_library_publication boundary validates exactly one current fit per family plus the public filament catalog, copies only the allowlisted runtime payload, and either installs a new inactive immutable Generator library or writes a transfer ZIP. It does not change the current-fit transaction above and never grants Generator access to this database or asset root.

Currentness still has a real invalidation role. Contributor/evidence or fit-control mutations can update the retained row from current to stale with a reason (_mark_model_fits_stale_for_sample_in_tx, :1111-:1165; fit-control variant :1205-:1240). This means the fit no longer reflects the current state of model inputs that were in its fitting corpus; it does not mean that merely adding unconsumed evidence invalidates yesterday’s fit. Appearance refresh separates model inputs from provenance metadata: changed RGB values, inclusion-relevant correlation/error state, or orientation can stale Camera Transform, while a decoder-version (decode_environment) metadata refresh with identical model inputs is persisted without invalidating the fit. The stale row and files remain until replacement publication succeeds. prune_superseded_model_fits (:4368) is startup compatibility cleanup for databases that still contain multiple rows from the earlier history-retaining implementation.

The legacy JSON store — DataStore (off the production path)

DataStore (data_access.py:56) is the original filesystem backend: “Read/write operations for all domain objects … all file I/O scoped to a configurable DATA_ROOT” (data_access.py:1-6). Instead of a database it materializes a directory tree — _ensure_dirs (:65) creates filaments/, filaments/profiles/, samples/, strips/, images/, segmentation/, extraction_results/, blanks/, and _system/ — with one JSON file per object.

It is dormant on a live install. It is constructed only when the backend is explicitly json (server.py:355), which the production launch never selects. Its Imported by list on calibration.data_access is dominated by processing/migration code (processing.backfill, processing.processor, maintenance, sample_mutations) and it is the only importer of the legacy notebook-era strip generator strips.generator (data_access.py:30); it also imports the strips.step_parser filename reader (:31), which the server imports too — see the “legacy strip generator” section of Geometry and strip definition. Treat DataStore as the read/write shape the SQLite store had to reproduce, and as the backend that migration tools (e.g. the one-shot processing/backfill.py, calibration.processing.backfill) still drive — not as a runtime option.

The shared domain models — models.py

Both stores read and write the same pydantic v2 models in models.py (calibration.models), “data shapes for API requests, responses, and internal domain objects” (models.py:1-5). The module has no intra-project imports — it is the foundational leaf that everything else depends on. Two families live here:

  • Domain objects — Sample (models.py:64, “central domain object — a calibration sample”), Filament (:104), Blank (:94, a registered flatfield reference), StripGeometry (:22) / StripDefinition (:30), Measurements (:56), and the sidecar ExtractionResult (:505) with its per-swatch measurement payload.
  • Request/response models — the *Request classes (AssignImageRequest, CreateSampleRequest, BackupCreateRequest, BundleMappingSaveRequest, …) that the FastAPI handlers validate against. These are contract types for Web API and job orchestration, not persisted state.

Because the models are backend-agnostic, a Sample loaded from SQLite and a Sample loaded from the JSON tree are the same object — which is exactly what made the migration verifiable.

User backups — backup_restore.py

backup_restore.py (calibration.backup_restore) is the operator-facing packaging layer: it snapshots the SQLite database and, for working-state packages, managed assets and step exports into a validated ZIP, then restores one through a staged apply. It imports calibration.path_safety for destructive filesystem boundaries. The package taxonomy is a set of module constants (backup_restore.py:22-:25), and the server exposes the core-library and working-state families:

  • “Essential Data Only” → core_library (CORE_LIBRARY_PACKAGE_TYPE, :22). create_core_library_backup (:1598) packs only sqlite/calibration.sqlite3 — no images, model artifact files, STEP/STL exports, or raw archives.
  • Working state with or without RAW images → working_state_with_raw or working_state_no_raw (:23-:24). create_working_state_backup (:1228) packs the SQLite snapshot plus collected asset files and step-export files. include_raw_images selects the package type; a no-RAW manifest explicitly lists omitted source files.

Other formats: create_raw_image_archive packages just RAW source images; create_emergency_core_library_backup and create_emergency_pre_restore_backup create safety packages. Restore is staged: stage_restore_package validates and unpacks into a private staging area, then apply_restore moves current state aside, replaces the parts described by PackageSemantics, audits references, and rolls back on failure. Backup collection, RAW local-release, and restore refuse an asset or STEP tree containing symlinks, junctions, or other reparse points; restore checks configured path components before moving current files aside. resolve_package_type describes whether a package replaces SQLite, managed assets, or step exports. ZIP handling is bounded by total-size, per-file, and compression-ratio ceilings. The operator walkthrough is Backup and restore.

Every SQLite snapshot passes through _normalize_model_fit_lifecycle (backup_restore.py:972) before packaging. It retains the current row for each family—or the newest row when an older database has no current row—and deletes other fit, contributor, and artifact rows from the private snapshot only (:978-:1004). Backup creation does not mutate the live database. Working-state validation then requires and hash-checks only artifacts owned by those retained rows (_retained_model_artifact_rows, :950; _validate_referenced_assets, :2990). This prevents obsolete database history from requiring already-garbage-collected model files.

For a working-state restore, apply_restore keeps the displaced SQLite/assets/exports under a temporary restore_previous_* directory until reference auditing and the optional smoke check pass (:3350-:3389). An exception before that boundary triggers _restore_previous_state. After a successful smoke check, safe_rmtree clears Windows read-only flags as needed while removing the rollback tree. Any cleanup exception is converted into a restore_previous_cleanup_failed warning containing the residual path and error; it does not turn an otherwise successful restore into a rollback attempt after cleanup may have partially removed the old tree.

Automatic restore points — sqlite_restore_points.py (a different mechanism)

Do not conflate restore points with backups. sqlite_restore_points.py (calibration.sqlite_restore_points) makes “internal SQLite-only snapshots … intentionally separate from user-facing Backup/Restore packages: no RAW images, no derived artifacts, and no ZIP packaging” (sqlite_restore_points.py:1-7). Their job is to keep a recent known-good database around for corruption recovery, not to be handed to a user.

They are created at startup, debounced, and pruned, not on demand:

  • startup_restore_point_check (:372) runs during post-store startup checks (invoked by _run_sqlite_restore_point_startup, server.py:390, from _run_post_store_startup_checks, :449-:473). It validates database integrity first and skips creation with reason "debounced" when the latest point is younger than DEFAULT_MIN_INTERVAL_SECONDS (6 hours, sqlite_restore_points.py:36, decision :406-:421).
  • Otherwise create_sqlite_restore_point (:267) writes a new snapshot, then prune_restore_points (:317) trims to DEFAULT_MAX_COUNT (12) and DEFAULT_MAX_AGE_DAYS (30), defined at :37-:38.
  • Recovery is apply_sqlite_restore_point (:520), which first calls preserve_current_sqlite_for_recovery (:472) to set the about-to-be-replaced database aside. Those output/restore-points/recovery/ copies are emergency filesystem preserves, not additional selectable restore points: prune_recovery_copies_for_paths applies the same default 12-copy/30-day bounds as normal restore points. Linked roots and runs are refused rather than traversed. Restore points reuse backup_restore.validate_sqlite_readonly for integrity checking.

So: backups are explicit, packaged, and can carry every managed artifact; restore points are silent, database-only, startup-cadenced, and self-pruning. SQLiteDataStore also refuses to open a symlinked or multiply-hardlinked mutable database, because ordinary SQLite writes through a hardlink would mutate every linked pathname. These are complementary safety layers, not the same feature.
