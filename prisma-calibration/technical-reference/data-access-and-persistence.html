Data access and persistence

Data access and persistence

Properties1
tagscalibration, persistence

Jul 23, 202612 min read

In one sentence: packaged Calibration owns Calibration/Workspace/calibration.sqlite3 plus a materialized Workspace/Assets root fronted by SQLiteDataStore (calibration.sqlite_data_access); visible Inbox/Output directories are siblings of that app-managed Workspace; the older JSON-tree DataStore (calibration.data_access) remains explicitly selectable for migration, compatibility, and test workflows but is never an implicit fallback; and two different safety nets sit on top — operator-driven ZIP backups (calibration.backup_restore) and internal automatic SQLite restore points (calibration.sqlite_restore_points).

This page is the code-level map of where calibration data is stored and which backend reads it. For the operator’s view of packaging and restoring data, see Backup and restore. For how the web layer opens a store at startup and dispatches jobs against it, see Web API and job orchestration; for the batch operations that mutate the store in place, The maintenance backend.

Related: calibration.sqlite_data_access · calibration.data_access · calibration.models · calibration.backup_restore · calibration.sqlite_restore_points

The backend split — SQLite is production, JSON is explicit compatibility

There are two store implementations and they are not peers. Backend selection is explicit and refuses to guess: _configured_backend in calibration.server reads the PRISMA_CALIBRATION_BACKEND environment variable (or a local .backend file) and raises if neither is set, so a launch cannot silently fall back to legacy JSON. _create_store then builds one of:

  • json → DataStore — the legacy filesystem tree. It can still be selected deliberately for migration, compatibility, and tests, but the packaged launcher does not select it and the server never chooses it implicitly.
  • sqlite → SQLiteDataStore(sqlite_path, asset_root=...) — the production store. Both the database path and the asset root must be configured (environment variable or local pointer file) or _configured_required_path errors out.

The module-level _store is typed DataStore | SQLiteDataStore | None and request handlers generally treat the implementations polymorphically, but the packaged application configures SQLite. Read the rest of this page with that in mind: sqlite_data_access.py is the production path; data_access.py remains an intentionally selectable compatibility backend, not a production fallback.

The production store — SQLiteDataStore

SQLiteDataStore is the production SQLite-backed store. Its class docstring still contains transitional “Stage 1” wording, but that wording is stale relative to the implemented runtime: the class now provides the live geometry, filament, sample, image, extraction, bundle, and model-fit read/write paths described below. Its class attribute backend = "sqlite" identifies the backend to callers.

The two-root design — database + materialized assets

The constructor takes two paths and keeps them apart:

  • self.sqlite_path — the single SQLite database file.
  • self.root — the materialized asset root, a directory tree of binary and other file artifacts that do not belong inside the database.

Structured rows live in SQLite; bytes live under the asset root. The store exposes the asset layout as path properties so callers never hardcode subpaths:

The packaged shape is recognized only when portable_calibration_root sees the asset root at exactly Calibration/Workspace/Assets. This keeps user-facing files outside the internal asset tree without making them external to the portable Suite. Other configured roots retain the compatibility path derivation used by source and migration workflows.

Fitted spline profiles are still JSON files on the asset root, not database rows — the profile artifact format survived the SQLite changeover unchanged.

Startup validation and schema migrations

Construction is fail-closed. _validate_paths requires an ordinary, non-linked, single-hardlink database file and an existing non-linked asset directory; then two idempotent in-place schema migrations run — _migrate_bundle_mapping_schema and _migrate_raw_archive_custody_schema — followed by _validate_schema, which reads sqlite_master and hard-fails if any of the 22 tables in _REQUIRED_TABLES is missing. There is no _migrate_filament_classification_schema in the current implementation. A store either opens against a database with the required schema or refuses to open.

Connections are split by intent: _connect_readonly opens the file mode=ro for projections, while writes go through _connect_write with foreign keys enabled inside _write_transaction, which wraps each store mutation using it in BEGIN IMMEDIATE and commit/rollback.

Domain accessors — the shape, not the catalog

The class is large (~6.5k lines) because it holds most read projections and write paths for the whole domain, but the surface is regular. Representative accessors, most returning the pydantic models from calibration.models (a few return raw dicts or a Path, noted inline):

  • Filaments — list_filaments, get_filament.
  • Samples — list_samples, get_sample.
  • Geometries — surfaced as StepRecords via list_step_records / get_step_record, with the reconstructed GeometryDefinition from get_geometry_definition. See Geometry and strip definition for what a geometry is.
  • Blanks — list_blanks.
  • Extraction — get_extraction_result (returns a dict) / save_extraction_result (returns a Path).
  • Bundles — list_bundles (returns list[dict]).

The remaining compatibility gaps are explicit rather than silently redirected: list_strip_filaments returns an empty list and get_strips returns None; _step_record_from_components and save_steps_registry call _not_implemented. set_image_ignored is not an unconditional stub: it persists hidden state when the optional image_asset_ui_state table is present and raises not-implemented only for older or minimal schemas without that table; the standard blank_calibration_schema.sql creates it.

Current working models — the three model kinds

Fitting outputs are recorded as model fits in the model_fits / model_artifacts tables, gated to exactly three kinds by _MODEL_KINDS = {"camera_transform", "legacy_spline", "photo_stack_v2"}. The internal helper name publish_model_fit means “make this Calibration fit current”; it is not the user-facing act of publishing a Generator library. In one SQLite transaction it inserts the replacement current fit, contributors, and artifacts, then deletes the previous fit row for that family; foreign-key cascades remove old child rows. That database transaction does not include a fitter’s preceding live-file or pointer activation, whose process-kill boundary is documented in Model workflow, publication, and review. The tables retain one replaceable registered working fit per family, not operator-selectable historical fits.

The separate calibration.model_library_publication boundary validates exactly one current fit per family plus the public filament catalog, copies only the allowlisted runtime payload, and either installs a new inactive immutable Generator library or writes a transfer ZIP. It does not change the current-fit transaction above and never grants Generator access to this database or asset root.

Currentness still has a real invalidation role. Contributor/evidence mutations can update fits that used a sample from current to stale with a reason through _mark_model_fits_stale_for_sample_in_tx; a changed fit-control signature on a sample with accepted extraction stales every current model family through _mark_current_model_fits_stale_for_fit_controls_in_tx because it changes the prospective fitting corpus. This means a fit no longer reflects the current state of its relevant model inputs; it does not mean that merely adding unconsumed evidence invalidates yesterday’s fit. Appearance refresh separates model inputs from provenance metadata: changed RGB values, inclusion-relevant correlation/error state, or orientation can stale Camera Transform, while a decoder-version (decode_environment) metadata refresh with identical model inputs is persisted without invalidating the fit. current_model_fit trusts the persisted currentness_state; it does not rehash registered files on an ordinary read. The stricter Generator-library publication readiness path performs artifact, pointer, and catalog validation. The stale row and files remain until replacement publication succeeds. prune_superseded_model_fits is compatibility cleanup for databases that still contain multiple rows from the earlier history-retaining implementation.

The legacy JSON store — DataStore (off the production path)

DataStore is the original filesystem backend: its module contract scopes all file I/O to a configurable DATA_ROOT. Instead of a database it materializes a directory tree — _ensure_dirs creates filaments/, filaments/profiles/, samples/, strips/, images/, segmentation/, extraction_results/, blanks/, and internal system directories — with JSON files carrying most structured state.

It is off the packaged production path. It is constructed only when the backend is explicitly json, so it remains technically runnable by source, migration, compatibility, and test workflows even though the packaged launcher selects SQLite. Its Imported by list on calibration.data_access is dominated by processing and migration code (processing.backfill, processing.processor, maintenance, sample_mutations) and it is the only importer of the legacy notebook-era strip generator strips.generator; it also imports the strips.step_parser filename reader, which the server imports too — see the “legacy strip generator” section of Geometry and strip definition. Treat DataStore as the compatibility shape the SQLite store had to reproduce and as the backend driven by tools such as the one-shot processing/backfill.py (calibration.processing.backfill), not as the packaged application’s data store.

The shared domain models — models.py

Both stores read and write the same pydantic v2 models in models.py (calibration.models), the data shapes for API requests, responses, and internal domain objects. The module has no intra-project imports — it is the foundational leaf that everything else depends on. Two families live here:

  • Domain objects — Sample (the central calibration-sample object), Filament, Blank (a registered flatfield reference), StripGeometry / StripDefinition, Measurements, and the sidecar ExtractionResult with its per-swatch measurement payload.
  • Request/response models — the *Request classes (AssignImageRequest, CreateSampleRequest, BackupCreateRequest, BundleMappingSaveRequest, …) that the FastAPI handlers validate against. These are contract types for Web API and job orchestration, not persisted state.

Because the models are backend-agnostic, a Sample loaded from SQLite and a Sample loaded from the JSON tree are the same object — which is exactly what made the migration verifiable.

User backups — backup_restore.py

backup_restore.py (calibration.backup_restore) is the operator-facing packaging layer: it snapshots the SQLite database and, for working-state packages, durable managed assets and supported STEP/STL exports into a validated ZIP, then restores one through a staged apply. It imports calibration.path_safety for destructive filesystem boundaries. Module constants define the package taxonomy, and the server exposes the core-library and working-state families:

  • “Essential Data Only” → core_library (CORE_LIBRARY_PACKAGE_TYPE). create_core_library_backup packs only sqlite/calibration.sqlite3 — no images, model artifact files, STEP/STL exports, or raw archives.
  • Working state with or without RAW images → working_state_with_raw or working_state_no_raw. create_working_state_backup packs the normalized SQLite snapshot plus collected asset files and supported STEP/STL export files. include_raw_images selects the package type; a no-RAW manifest explicitly lists omitted RAW source files while ordinary non-RAW managed image assets remain included.

Other formats: create_raw_image_archive packages RAW source images; create_emergency_core_library_backup and create_emergency_pre_restore_backup create safety packages. Restore is staged: stage_restore_package validates and unpacks into a private staging area, then apply_restore uses the flags resolved into PackageSemantics to replace SQLite and, where appropriate, managed assets and STEP exports. Backup collection and restore refuse unsafe linked trees; release_local_raw_storage verifies archive, database, path, size, and hash identity before using a root-confined safe unlink. Restore also checks configured path components before moving current files aside. ZIP handling is bounded by 100 GiB total uncompressed, 25 GiB per file, and a 1000:1 suspicious compression-ratio ceiling. The operator walkthrough is Backup and restore.

Every SQLite snapshot passes through _normalize_model_fit_lifecycle before packaging. It retains the current row for each family—or the newest row when an older database has no current row—and deletes other fit, contributor, and artifact rows from the private snapshot only. Backup creation does not mutate the live database. Working-state validation then requires and hash-checks only artifacts owned by those retained rows (_retained_model_artifact_rows; _validate_referenced_assets). This prevents obsolete database history from requiring already-garbage-collected model files.

For a destructive restore, apply_restore first reconciles any earlier interrupted transaction, writes a recovery journal, and keeps displaced SQLite/assets/exports under restore_previous_<transaction-id> until reference auditing and the optional smoke check pass. The replacement becomes authoritative only after the journal reaches durable committed; failures before that boundary call restore_recovery.reconcile, and startup reconciliation also rolls an unfinished transaction back. After commit, finalize_committed removes the rollback workspace and journal. A cleanup exception is converted into a restore_previous_cleanup_failed warning containing the residual path and error; it does not attempt to roll back a restore that has already committed.

Automatic restore points — sqlite_restore_points.py (a different mechanism)

Do not conflate restore points with backups. sqlite_restore_points.py (calibration.sqlite_restore_points) makes internal SQLite-only snapshots intentionally separate from user-facing Backup/Restore packages: no RAW images, no derived artifacts, and no ZIP packaging. Their job is to keep a recent known-good database around for corruption recovery, not to be handed to a user.

The application considers creating one automatically at startup, with integrity checks, debouncing, and pruning. The module also exposes create_sqlite_restore_point as an internal callable, but the current web API exposes status and restore—not a user-facing create-on-demand operation:

  • startup_restore_point_check runs during _run_post_store_startup_checks through _run_sqlite_restore_point_startup. It validates database integrity first and skips creation with reason "debounced" when the latest point is younger than DEFAULT_MIN_INTERVAL_SECONDS (6 hours).
  • Otherwise create_sqlite_restore_point writes a new snapshot, then prune_restore_points trims to DEFAULT_MAX_COUNT (12) and DEFAULT_MAX_AGE_DAYS (30).
  • apply_sqlite_restore_point first calls preserve_current_sqlite_for_recovery to set the about-to-be-replaced database aside. Those output/restore-points/recovery/ copies are emergency filesystem preserves, not additional selectable restore points: prune_recovery_copies_for_paths applies the same default 12-copy/30-day bounds as normal restore points. Linked roots and runs are refused rather than traversed. Restore points reuse backup_restore.validate_sqlite_readonly for integrity checking.

So: backups are explicit packages that can carry the durable managed working state; restore points are internal, database-only, startup-cadenced, and self-pruning. SQLiteDataStore also refuses to open a symlinked or multiply-hardlinked mutable database, because ordinary SQLite writes through a hardlink would mutate every linked pathname. These are complementary safety layers, not the same feature.
