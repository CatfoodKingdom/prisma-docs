Extraction artifact sinks and blank registration

Extraction artifact sinks and blank registration

Properties1
tagscalibration, extraction, artifacts, blanks

Jul 25, 20266 min read

Extraction produces derived JPEGs through a small sink protocol, while blank registration establishes the flatfield evidence used by extraction. These are related filesystem concerns but different ownership layers: live thumbnails are replaceable derived output; a registered blank is durable metadata that points at an onboarded image asset.

Related: The extraction pipeline · Processing and extraction · Assigning images · Data access and persistence · calibration.processing.artifact_sinks · calibration.processing.blank_registry

Artifact sink contract

ExtractionArtifactSink in processing/artifact_sinks.py exposes two operations:

  • wants_image(kind) -> bool lets a destination decline artifacts it does not own.
  • write_image(sample_id, kind, image_bgr, max_dim=800) -> Path writes one requested image.

The allowed kinds are source, blank, strip, appearance, and transmission_roi. Sample IDs are restricted to alphanumeric characters plus _, ., and -, and kinds come from an allow-list, so neither value can inject arbitrary path components. sink_wants_image preserves compatibility with older test or extension sinks that implement only write_image, treating them as interested in every kind.

stage_jpeg_image rejects empty arrays, optionally downsizes the longest dimension with OpenCV INTER_AREA, and encodes a quality-80 JPEG to a unique same-directory temporary file. It verifies that cv2.imwrite returned success and that the staged file exists and is non-empty. write_thumbnail_image then promotes that checked file with publish_staged_files; it does not write directly over a live target.

publish_staged_files requires every staged file to be a non-empty sibling of a distinct target. It copies any existing target to a rollback sibling, replaces the targets with os.replace, and restores already-replaced targets if a later replacement fails. A rollback copy is deliberately preserved if restoring it also fails. This makes an ordinary multi-file publication rollback-capable, but it is not by itself a database transaction or a process-kill journal.

Candidate and review directories

SampleArtifactDirectorySink writes all five artifact kinds into a caller-owned fixed directory. The filenames are:

Maintenance re-extraction uses it for a candidate directory. Ordinary manual preview uses it under maintenance/manual_extraction_reviews/{sample_id}. Manual review directories are transient: closing the ordinary manual workflow requests their deletion, a committed or failed manual attempt removes them, and startup removes abandoned manual-review directories.

Committing SQLite semantics and live visuals together

The SQLite production path coordinates the extraction result, sample workflow state, and the two live JPEGs through processing/extraction_publication.py rather than asking a sink to approximate a database transaction.

  1. create_visual_stage gives the processor a hidden StagedLiveThumbnailSink.
  2. The processor writes and verifies source.jpg and strip.jpg there.
  3. prepare_publication creates a durable pub_<uuid> directory under {data_root}/_system/extraction_publications/, copies and fsyncs both visual payloads, and atomically writes journal.json before the semantic commit.
  4. The semantic callback atomically saves the replacement extraction result and sample state in SQLite.
  5. Only if the replacement extraction-result ID is current does the coordinator publish both live visuals. Existing live files are backed up and restored on an ordinary replacement failure.
  6. Completed automatic/manual records are marked complete and removed. Re-extraction records may require separate candidate finalization before their journal is removed.

This is recover-forward publication, not a claim that SQLite and the filesystem share one atomic primitive. If the process stops before the SQLite replacement is current, startup discards the uncommitted/superseded publication. If SQLite committed but visual promotion did not finish, startup republishes the journaled pair. Ambiguous or invalid journals are preserved and reported rather than guessed through. Thumbnail resolution can serve the current committed journal payload while recovery is pending, preventing a stale live path from being treated as authoritative.

Startup also deletes rigorously named abandoned visual-stage directories and interrupted live .publication/.rollback siblings when it can identify them safely. Unknown, unsafe, invalid, or ambiguous paths are preserved for diagnosis.

Invalidation and cleanup

source.jpg and strip.jpg are derived views of the current extraction result. Sample invalidation deletes the durable extraction result transactionally, then the surrounding workflow requests best-effort live-visual cleanup; a filesystem cleanup error does not roll the database invalidation back. Rejecting a pending-review result uses that invalidation path. Review-only images belong to their candidate/review workspace and are discarded rather than promoted into the live thumbnail tree.

The artifact sink itself never creates, accepts, rejects, or deletes an extraction result. Its responsibility ends at validated image output. SQLite transactions, publication journals, invalidation helpers, and the caller’s review lifecycle own the durable state changes.

Blank registration: SQLite production path

POST /api/blanks/register dispatches to SQLiteDataStore.register_blank_from_image on the production SQLite backend. The method resolves an onboarded image_assets row, rejects an already registered asset, allocates the next blank ID, and inserts a registered_blanks row in a write transaction. The returned Blank.storage_path is the image asset’s managed relative path. Registration does not copy a second file into blanks/.

list_blank_assets exposes the joined blank/image information current consumers need, and get_blank_storage_path resolves a blank ID back to the managed image. A blank cannot be unregistered while a sample assignment references it.

Image rotation is less comprehensive than blank registration. set_image_rotation blocks and invalidates sample assignments only where the rotated asset is the sample’s strip image. It does not currently inspect samples that use the same asset through blank_id. Rotating a registered blank after extraction can therefore leave those samples’ existing results bound to the earlier blank orientation. Until that runtime gap is fixed, set blank rotation before processing and explicitly reprocess every affected sample after a change.

CSV pending-blank registration

The CSV assignment importer can register an unregistered blank as part of an explicitly confirmed commit. For that path, save_samples_with_blank_registrations clones the proposed samples, registers every needed managed image as a blank, substitutes the allocated blank IDs, and saves all sample assignments inside one SQLite write transaction. If any sample save fails, both the new blank registration and all assignments roll back. Existing registered-blank CSV commits likewise save their sample set in one transaction. See CSV assignment import and commit lifecycle for preview custody and stale-state validation.

JSON compatibility path

The JSON DataStore route calls processing.blank_registry.register_blank_image. It resolves the source through get_image_path, rejects duplicate original filenames, best-effort reads EXIF DateTimeOriginal, copies the source into root/blanks/{blank_id}{suffix}, and registers a legacy Blank pointing at that copy. If registration fails, it deletes the copied file. This remains a compatibility and migration path, not the distributable SQLite custody model.
