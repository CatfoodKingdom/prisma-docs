CSV assignment import and commit lifecycle

CSV assignment import and commit lifecycle

Properties1
tagscalibration, samples, csv, sqlite

Jul 16, 20265 min read

The CSV importer is a SQLite-only, two-request workflow for assigning a source image, a registered blank, and an open-side orientation to otherwise unassigned samples. The implementation is split between csv_assignment_import.py (calibration.csv_assignment_import) and two FastAPI routes in server.py.

HTTP contract

GET /api/samples/assignment-template.csv returns a header-only UTF-8 CSV named prisma_sample_assignment_template.csv. Its columns are exactly Sample ID, Sample Image, Blank Image, and Orientation.

POST /api/samples/assignment-import/validate reads the uploaded file and calls validate_assignment_csv. The route requires the SQLite backend. A successful response contains row counts, valid_rows, error_rows, warnings, and pending_blank_registrations, plus a random preview_token. The server keeps the commit specifications, upload digest, validation errors, and pending blank references in the process-local _csv_assignment_previews dictionary, guarded by _csv_assignment_previews_lock.

The preview expires after _CSV_ASSIGNMENT_PREVIEW_TTL_SECONDS (15 minutes) and is pruned when either assignment route is called. It is process-local and therefore also disappears on server restart. The upload digest is recorded but is not used by the commit route to reread the file: commit uses the stored internal row specifications from the preview.

POST /api/samples/assignment-import/commit accepts the preview token and register_unregistered_blanks. It rejects an expired token with 409, rejects a preview with no valid rows with 400, and converts domain-level stale-preview failures to 409. On success it removes the token and reports committed_count, skipped invalid rows, and any blanks registered during the commit.

Parsing and resolution

The parser decodes UTF-8 with an optional BOM (utf-8-sig). Header matching is case-insensitive and ignores spaces, underscores, and hyphens. Missing required columns, duplicate normalized headers, invalid encoding, an empty file, and a file with no nonblank assignment rows are errors. Extra columns are ignored and returned as warnings; blank CSV rows are skipped.

Sample IDs resolve first by exact ID, then by an unambiguous numeric suffix for IDs shaped like exp-N. Image and blank values must be identifiers or filenames, not paths. Images resolve by asset ID, exact filename, or an unambiguous filename stem. Blanks resolve by blank ID, exact filename, or stem. If the selected value resolves to a managed image that is not registered as a blank, the row becomes valid-but-pending and the preview reports a blank-registration confirmation requirement.

Orientation accepts U/T as zero rotations, R as one clockwise quarter-turn, D/B as two, and L as three. The public error text names the supported UI values as U, D, L, or R.

Every row is checked against current state. A sample must be unassigned, have no source image, blank, or orientation, and have no measurements or extraction result. The sample image must exist in managed storage, not be ignored, and not already be assigned to another sample. The blank must exist and have a present managed path. Cross-row validation rejects duplicate samples, duplicate sample images, and a sample image used as the selected blank. Invalid rows remain in the preview and do not prevent valid rows from being offered for commit.

Commit and stale-preview protection

commit_assignment_rows reconstructs current samples, images, blanks, existing sample-image assignments, and extraction-result membership before writing. It validates every stored row specification again. This is the concurrency boundary: changes made after preview—such as another assignment, image removal/ignore, extraction output, or a sample becoming ineligible—cause CsvAssignmentError("CSV assignment preview is stale.") and no sample assignment is saved.

If pending blank registration was requested but register_unregistered_blanks is false, commit stops before writing. With confirmation, the importer requires the SQLite store’s combined save_samples_with_blank_registrations operation. Within that one write transaction, each distinct managed blank image is either matched to its now-existing blank relation or registered through _register_blank_from_image_in_tx; registration reuses the existing image asset and does not copy a second image file. The corresponding blank IDs are then applied to in-transaction copies of the samples before those assignments are saved.

For a row whose blank was already registered at validation time, each valid row mutates a Sample in memory: assigned_image receives the image asset ID, assigned_blank_id receives the blank ID, and orientation_rots receives the normalized integer rotation. recompute_sample_status sets the sample to assigned when all three evidence fields are present. SQLite saves all collected samples through save_samples in one write transaction.

In both paths, all ready rows are one SQLite transaction. When pending blanks are involved, blank registration and sample assignment share that transaction: a sample-save failure rolls back the new blank relation as well as every assignment. The preview token is removed only after the complete commit succeeds. Validation and commit are synchronous HTTP requests with no progress or cancel endpoint; an interrupted validation changes nothing, while SQLite provides the rollback boundary for an interrupted commit.

Ownership and compatibility

The live SQLite path uses image_assets, registered_blanks, sample_evidence_assignments, and the samples workflow state. The JSON DataStore has resolver fallbacks for older filename-shaped assignments, but the HTTP importer is explicitly rejected for that backend. The Architecture page calibration.csv_assignment_import is generated from the module; this page documents the cross-module server lifecycle.
