The extraction pipeline

The extraction pipeline

Properties1
tagscalibration, extraction

Jul 28, 202610 min read

In one sentence: process_sample turns an oriented strip photo and registered blank into per-swatch display colors and linear transmission, builds a pending-review ExtractionResult, and—on committed SQLite runs—publishes that result, sample state, and the source/strip visuals as one recoverable unit; extract_strip_manual supplies the four-corner fallback when automatic location is unsuitable.

This page maps the production code path from evidence to a stored extraction. For the physical meaning of flatfield division and transmission, see Extraction. For the operator workflow, see Processing and extraction and Assigning images.

Related: calibration.processing.processor · calibration.processing.extraction · calibration.processing.manual · calibration.processing.extraction_result · calibration.processing.artifact_sinks · calibration.processing.extraction_visuals · calibration.processing.blank_registry · Extraction artifact sinks and blank registration

Live entry points and execution modes

The stateless image math lives in processing/extraction.py. Production orchestration belongs to three callers:

  • process_sample in processing/processor.py is the automatic path used by single-sample processing, the retained backend batch/reprocess helpers, thumbnail regeneration, and automatic maintenance re-extraction.
  • extract_strip_manual in processing/manual.py replaces automatic strip location with four operator-selected corners while reusing the shared flatfield, boundary, measurement, result, and publication contracts.
  • maintenance_reextract.py runs noncommitting automatic/manual extraction into a candidate workspace and applies an accepted candidate through the extraction-publication coordinator.

commit=True may change the durable sample and extraction result. commit=False never changes either one, but its visual destination depends on the caller: thumbnail regeneration intentionally recreates live derived source/strip JPEGs, ordinary manual preview writes a transient review directory, and maintenance writes a candidate directory.

The browser’s Process All does not invoke processing.processor.process_batch; it loops over the single-sample route. The retained Python batch function and /api/process/batch route are still callable backend paths, but are not the current Processing Queue UI path.

Stage 0 — geometry and sampling configuration

SwatchConfig carries num_swatches, border_mm, step_w_mm, step_h_mm, physical lightbox dimensions, open_side, and sample_fraction (default 0.50). __post_init__ derives total strip dimensions and border fractions. _build_swatch_config projects the sample’s stored strip definition through SwatchConfig.from_experiment, falling back to dataclass defaults for missing legacy geometry fields. The measurements are only meaningful when these values match the printed strip; see Geometry and strip definition.

Stage 1 — preview detection and full-resolution measurement

Automatic extraction is deliberately two-resolution:

  1. load_preview_jpeg extracts a RAW embedded thumbnail (or reads a raster), applies the image’s stored rotation, and caps the longest dimension at 2000 px. If no preview can be decoded, the processor falls back to the full visual render.
  2. After location succeeds, load_raw_both returns an 8-bit visual BGR render and a linear float32 RGB render. RAW input uses camera white balance for both; the linear decode uses gamma=(1,1), disables auto-brightening, and normalizes 16-bit output to [0,1]. Raster input is normalized/linearized and converted to the same visual-BGR/linear-RGB contract.

The processor applies the stored strip-image rotation and the sample’s open-side rotation to the source preview and full arrays. It independently applies the blank’s stored rotation, then uses match_flatfield_orientation to align the blank’s lightbox orientation with the source frame.

Stage 2 — automatic strip location

find_strip_contour first finds and slightly insets the lightbox region; if no lightbox is found, it searches the full frame. It tries these strategies in order and returns the first acceptable hull:

  1. flatfield per-channel ratio deviation;
  2. flatfield absolute difference;
  3. Otsu BINARY_INV;
  4. Otsu BINARY;
  5. Canny edges;
  6. LAB chroma and then HSV saturation; and
  7. a geometry-sized synthetic rectangle when the lightbox itself was found.

Each image strategy tries individual convex hulls and then a merged-fragment hull. Candidate scoring rejects implausible area fractions and aspect ratios relative to the configured strip/lightbox geometry. Because strategy 7 can synthesize a contour, failure means all image strategies failed and no lightbox rectangle was available.

On a committing contour failure, the processor saves processing_status="failed", deletes any prior extraction result, and removes live sample visuals. A noncommitting run only returns the failure. Other pre-commit pipeline exceptions follow the same commit-versus-preview distinction.

Stage 3 — deskew and direction

deskew_strip uses cv2.minAreaRect, rotates the frame, crops the strip with DESKEW_PAD_PX = 6, and forces a landscape result. deskew_strip_linear applies the same transform to a second array so the visual and linear domains remain pixel-aligned.

The preview contour is used for cheap early rendering. After the full image is loaded, the processor runs contour detection again at full resolution. If that fails, it scales the preview contour into the full frame and records provenance that does not pretend it was a full-frame detection.

Automatic extraction compares the left and right fifths of the deskewed strip and rotates it 180 degrees when the brighter, nominally thinner end is on the right. Manual extraction deliberately does not use this brightness heuristic; its corner order and recorded open-side orientation are authoritative.

The processor records a spine score in its diagnostics. An optional gut-check can convert a nonpositive score into low_confidence/flagged, but _SPINE_GUT_CHECK_ENABLED is false by default, so the current normal runtime records the score without automatically flagging on it.

Stage 4 — register and divide the blank

The full linear blank is rotated into the source frame. register_flatfield detects the lightbox border in blank and source and warps the blank with a homography. If either lightbox or the homography cannot be found, the automatic path logs a warning and resizes the unregistered flatfield to the source dimensions.

register_flatfield_strict, used by the manual path, performs the same homography but raises FlatfieldRegistrationError instead of using that resize fallback. This is a physically-correct-or-fail boundary for operator-selected extraction.

Automatic extraction then deskews the registered blank with the same source contour and applies the same left/right flip. Manual extraction first registers the blank in the full source frame, perspective-warps source/linear/blank through the same clicked quad, and rotates all three together.

Stage 5 — swatch extent, boxes, and measurements

detect_swatch_extent derives the active swatch rectangle from physical strip geometry and the measured pixel scale. Automatic deskew passes the 6 px padding; edge-to-edge manual perspective output passes zero. The bottom is inset to 95% of step_h to avoid the open-edge over-extrusion region.

find_swatch_boundaries currently returns pure equal spacing across the known active width. It still calculates a column gradient, but the signal-snapping branch is unreachable below the early return and is not part of current behavior.

swatch_sampling_boxes_from_boundaries shrinks each cell to its configured central sampling fraction. Those half-open boxes are shared by the median sampler and the transmission-ROI overlay, so a review overlay represents the pixels the current code sampled.

For each swatch:

  • median_color_bgr takes the per-channel median of the visual BGR patch and returns display RGB/hex; and
  • the processor takes the per-channel median of the flatfield-corrected linear RGB patch and rounds R_linear, G_linear, and B_linear to six decimals.

The registered blank’s median over the active region is retained as I0_linear. The per-swatch values, I0_linear, and source/blank filenames form the compatibility Measurements object that feeds the canonical result builder.

Manual four-corner extraction

The manual endpoint receives corners in the rotation-baked preview frame in tl,tr,br,bl order. The server derives the preview-to-raw scale with the stored source rotation accounted for. extract_strip_manual:

  1. scales the corners into the rotated full-image coordinate space;
  2. loads and applies stored rotations to source and blank;
  3. strictly registers the blank lightbox to the source frame;
  4. perspective-warps the visual source, linear source, and registered blank through the same quad;
  5. applies the open-side rotation to all three;
  6. performs the shared flatfield division, geometric boundaries, boxes, and medians; and
  7. either returns a preview or commits through the shared result/publication path.

Ordinary commit:false manual extraction writes all review artifacts to a transient maintenance/manual_extraction_reviews/{sample_id} directory. Its UI Accept action re-runs the extraction with commit:true; it does not promote the preview files or preview measurements directly.

Building and committing the canonical extraction result

build_extraction_result projects the new Measurements into an ExtractionResult with a fresh ext_<uuid> ID, sample/geometry identity, automatic or manual method, provenance, evidence binding, diagnostics, every swatch (including fit-excluded swatches), and review_state="pending_review".

Appearance is the builder’s intentional impure step. It calls the Camera Transform corpus’s embedded-JPEG extraction helper using the caller-resolved source and sampling geometry. Success fills each swatch’s appearance bucket and decode diagnostics. Failure records diagnostics.appearance_error, leaves appearance absent, and does not fail the transmission extraction.

commit_extraction_result sets the replacement sample state (processed or optional flagged), measurements, flag reason, and review_accepted=False. On SQLite it calls save_extraction_result_with_sample, which saves the replacement result and sample workflow state in one database transaction. The JSON compatibility backend uses a sidecar snapshot/save/sample-save/restore fallback.

If build or save fails, the function clears the attempted in-memory outputs and re-raises without saving a new failed sample. SQLite rolls its transaction back; JSON restores the prior sidecar snapshot. The processor catches this specific aborted commit and reports a rolled-back failure, leaving the prior durable sample/result pair authoritative. This differs from a normal detection/pipeline failure, which deliberately persists failed and removes an old result.

Commit is not review acceptance. A successful new result remains pending review until the operator’s later Accept action atomically synchronizes the sample flag and the sidecar’s review state. Only current accepted extraction results are eligible fitting evidence.

Recoverable SQLite visual publication

Committed SQLite automatic/manual extraction does not write directly to the observable thumbnail paths. It creates a hidden StagedLiveThumbnailSink and writes only the durable live pair, source.jpg and strip.jpg. Before the semantic callback runs, publish_extraction_update copies and fsyncs both JPEGs into a durable publication directory and writes a journal containing prior/replacement extraction IDs and origin metadata.

After SQLite makes the replacement ID current, the coordinator promotes both visuals with rollback-capable sibling replacements. If ordinary visual promotion fails, the operation reports pending recovery rather than undoing already-committed semantics. Startup compares each journal with the current extraction-result ID: it discards uncommitted/superseded work, republishes the current pair, completes origin-specific bookkeeping where safe, and preserves ambiguous/invalid records for diagnosis. resolve_visual_path prefers a unique current journal payload while recovery is pending.

This gives process-kill convergence across the database/filesystem boundary without pretending they share one atomic transaction. See Extraction artifact sinks and blank registration for directory names and recovery details.

Blank registration

On SQLite, /api/blanks/register relates an existing managed image_assets row to a new registered_blanks row. It does not copy the image. The CSV importer can create pending blank relations and all associated sample assignments in one combined SQLite transaction.

The JSON compatibility path instead copies the source into blanks/{blank_id}{suffix}, records best-effort EXIF time, and deletes the copy if registration fails. For the current rotation/invalidation limitation affecting images used as blanks, see Extraction artifact sinks and blank registration.

Backfill is migration, not extraction

processing/backfill.py is a one-shot compatibility migration for legacy samples that already contain Sample.measurements but lack a canonical extraction result. It classifies records and builds sidecars only for the eligible class. It does not re-run transmission extraction and does not mutate legacy measurements. It is not imported into the steady-state processing path.
