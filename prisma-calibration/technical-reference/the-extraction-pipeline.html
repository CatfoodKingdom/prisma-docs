The extraction pipeline

The extraction pipeline

Properties1
tagscalibration, extraction

Jul 14, 202612 min read

In one sentence: a lightbox photograph becomes a committed per-swatch ExtractionResult by the headless process_sample (calibration.processing.processor, processor.py:284), which detects the strip, deskews it, divides out a registered flatfield blank, samples a median color per swatch, and hands the measurements to the commit_extraction_result transaction (calibration.processing.extraction_result, extraction_result.py:248) that writes the sidecar into the store — while extract_strip_manual (calibration.processing.manual, manual.py:369) is the 4-corner fallback for strips that fail auto-detection.

This page is the code-level map of the path from a raw photo to a stored extraction. For the phenomena — what flatfield division and median extraction physically mean — see Extraction. For the operator’s view — which buttons run this and what the review states mean — see Processing and extraction and Assigning images.

Related: calibration.processing.processor · calibration.processing.extraction · calibration.processing.manual · calibration.processing.extraction_result · calibration.processing.blank_registry · calibration.processing.artifact_sinks · calibration.processing.extraction_visuals · calibration.processing.backfill · Extraction · Processing and extraction

Production orchestration and shared image math

The image math (loading, detection, deskew, flatfield, boundaries, median color) lives as free functions in extraction.py (calibration.processing.extraction) — a module of stateless helpers with no intra-project imports (see its Architecture node). Orchestration belongs to the production callers:

  • process_sample (processor.py:284) — the headless production pipeline. It has no UI, takes a Sample plus resolved image/blank paths, and is the one the web server and maintenance re-extract paths call (see Imported by on calibration.processing.processor: server, maintenance, maintenance_reextract). commit=True is the durable path; commit=False is used for previews/thumbnail regeneration and must not mutate the sample or delete a valid sidecar. This is the path this page describes.
  • extract_strip_manual (manual.py) owns the operator-selected four-corner fallback and commits through the same extraction-result transaction.
  • maintenance_reextract stages re-extraction candidates for review before applying accepted replacements.

The old notebook-era process_one/Tkinter path has been removed. It had no repository caller or supported CLI entry point and wrote unconsumed per-swatch crops, segmentation JSON, and debug PNGs outside the webapp artifact contract.

Stage 0 — configuration: SwatchConfig

Every stage reads geometry from a SwatchConfig dataclass (extraction.py:33). It carries the physical strip geometry that must match the printed design — num_swatches (default 8), border_mm, step_w_mm, step_h_mm — plus lightbox dimensions, the open_side edge, and the sample_fraction (default 0.50, the central fraction of each swatch cell that is sampled). __post_init__ (extraction.py:62) derives the total strip width/height and border fractions. process_sample builds it per-sample via _build_swatch_config (processor.py:125), which reads the sample’s strip_definition through SwatchConfig.from_experiment (extraction.py:71) and falls back to class defaults for any field a legacy sample lacks. For the geometry contract behind these numbers, see Geometry and strip definition.

Stage 1 — load the image (preview first, then full RAW)

process_sample is deliberately two-pass on resolution to keep detection cheap:

  1. Preview load for detection. load_preview_jpeg (extraction.py:154) pulls the camera’s embedded JPEG at up to 2000 px for the fast detection/deskew pass (processor.py:322). If there is no embedded preview it falls back to a full RAW decode (processor.py:325-327).
  2. Full RAW load for measurement. Once the strip is located, load_raw_both (extraction.py:116) decodes the CR2 twice via rawpy: a visual 8-bit sRGB-ish render (RAWPY_PARAMS_VISUAL, camera white balance, auto-bright) and a linear 16-bit render with gamma=(1,1) and no_auto_bright (RAWPY_PARAMS_LINEAR, extraction.py:92-97). The linear array — normalized to [0,1] — is what the transmission math consumes; the visual array drives detection and the display hex. Stored per-image rotations are applied via _apply_rotations (processor.py:80) plus the sample’s open-side orientation count from _open_side_to_rotation_count (processor.py:88).

Stage 2 — find the strip: find_strip_contour

find_strip_contour (extraction.py:299) first crops to the lightbox with find_lightbox_region (extraction.py:252), then runs a multi-strategy cascade, stopping at the first success (extraction.py:307-314):

  1. Flatfield ratio (per-channel division reveals a strip of any color),
  2. Flatfield absolute difference,
  3. Otsu BINARY_INV (strip darker than lightbox),
  4. Otsu BINARY (strip brighter),
  5. Canny edges (brightness-agnostic),
  6. Saturation/chroma (translucent tinted filaments),
  7. Physical-dimensions fallback (synthesize the expected rectangle from geometry).

Candidate hulls are scored against the expected strip area fraction and aspect ratio (_best_hull, extraction.py:370; area bounds extraction.py:366-368). When a blank is available it is threaded in as flatfield_bgr so strategies 1–2 can background-subtract (processor.py:342). If every strategy fails, process_sample returns a failed_detection result and — only on a committing run — stamps the sample failed and deletes any stale sidecar (processor.py:344-361). A non-committing preview reports the failure without changing durable sample or sidecar state.

Stage 3 — deskew

deskew_strip (extraction.py:511) fits a cv2.minAreaRect, rotates the whole frame to level the strip, and crops to the rotated bounding box plus a fixed DESKEW_PAD_PX (6 px) margin, forcing a landscape crop. deskew_strip_linear (extraction.py:543) applies the same rotation/crop geometry to the float32 linear array so visual and linear stay pixel-aligned. process_sample re-detects the contour on the full-resolution visual before the measurement deskew (processor.py:412), falling back to a scaled preview contour if that re-detection fails (processor.py:417-422). It then flips the strip 180° if the brighter (thinner-swatch, higher-transmission) end is on the right, enforcing thin-on-left (processor.py:439-443).

Stage 4 — flatfield correction: register, then divide

The blank is the per-pixel reference illumination I0. Two steps:

  • Register the blank onto the strip frame. register_flatfield (extraction.py:802) detects the lightbox border in both images and warps the blank through a border homography; if detection fails it warns and falls back to a bare cv2.resize (extraction.py:819-822). The registered blank is deskewed with the same contour as the strip (processor.py:452).
  • Divide. apply_flatfield (extraction.py:883) computes per-pixel transmission strip_linear / max(blank, 1e-6) clipped to [0,1] (extraction.py:886). This is the multiplicative inverse of the illumination — the physical meaning is in Extraction.

There is a strict variant, register_flatfield_strict (extraction.py:842), which raises FlatfieldRegistrationError (extraction.py:838) instead of resizing when the lightbox cannot be located — a physically-correct-or-fail contract used by the manual path (the bare resize stretches the blank without aligning the lightbox and is wrong; annotation [@theo 2026-06-17], extraction.py:851). Automatic register_flatfield is intentionally left with the lenient fallback.

Stage 5 — swatch boundaries and median color

  • Extent. detect_swatch_extent (extraction.py:903) computes the inner swatch rectangle geometrically from border_mm/step_w_mm/step_h_mm and the measured pixel scale — it does not hunt for edges. The bottom is inset 5% of step_h to dodge the open-edge over-extrusion artifact (extraction.py:934). The deskew_pad_px argument must match the padding actually present (auto strips carry DESKEW_PAD_PX; manual perspective strips carry 0).
  • Dividers. find_swatch_boundaries (extraction.py:945) returns num_swatches + 1 x-offsets. As of the current code it uses pure equal spacing from the known swatch width; the gradient-snapping branch is disabled below the early return (extraction.py:965-966) because geometry-first margins proved more reliable than signal snapping.
  • Sampling boxes. swatch_sampling_boxes_from_boundaries (calibration.processing.extraction_visuals, extraction_visuals.py:13) turns those boundaries into the exact half-open crop box per swatch, shrinking each cell by sample_fraction on every side.
  • Median. For each swatch, median_color_bgr (extraction.py:998) takes the per-channel median of the visual patch (→ the display hex/RGB via rgb_to_hex, extraction.py:1004), and the linear transmission is the per-channel median of the flatfield-corrected patch, rounded to 6 places into a SwatchMeasurement (processor.py:522-536). The blank’s own median over the inner crop is stored as I0_linear for traceability (processor.py:539-544).

The per-swatch measurements plus I0_linear, blank_image, and source_image are packed into a legacy Measurements object (processor.py:546).

The manual fallback — extract_strip_manual

When auto-detection fails (typically near-transparent filaments that blend into the lightbox), the operator clicks the strip’s four corners and calibration.processing.manual takes over. extract_strip_manual (manual.py:369) scales the preview-space corners into raw coordinates (_scale_corners, manual.py:161; rotation-aware scale via _preview_scale_for_rotation, manual.py:189), rectifies the quad with a perspective warp (_perspective_extract, manual.py:103, expecting tl,tr,br,bl order), then runs the same flatfield-and-extract math as the automatic path — but through register_flatfield_strict, so a manual strip either gets a properly registered blank or fails explicitly rather than silently diverging (manual.py:23-24, module docstring). Manual extraction does not use the brightness heuristic to reorder the strip; the operator’s corner order and open-side are authoritative (manual.py:22-24). Commit runs through the shared _commit_manual producer (manual.py:206), which requires image promotion before building the sidecar (manual.py:229-235).

The commit — what “commit” actually writes

Accepting or committing a successful extraction runs the canonical transaction commit_extraction_result (extraction_result.py:248), the IO half of the producer. process_sample calls it inside its commit=True branch (processor.py:597), after promoting the source image into managed storage so the sample is Camera-Transform-eligible and cr2_source resolves against the post-promotion location (processor.py:589, _resolve_cr2 processor.py:229). Manual extraction uses the same producer (manual.py:329-340). The transaction is (extraction_result.py:283-308):

  1. Set sample fields — processing_status (processed or flagged), flag_reason, measurements, and review_accepted = False.
  2. Snapshot any prior sidecar bytes (store.snapshot_extraction_result, extraction_result.py:290).
  3. Build the canonical sidecar via build_extraction_result (extraction_result.py:162).
  4. Save the sidecar — store.save_extraction_result(sample_id, result.model_dump()) (extraction_result.py:306).
  5. Save the sample (extraction_result.py:308).

On any exception in build/save this is an aborted commit, not a committed failure: the in-memory measurements/review_accepted are cleared, the prior sidecar bytes are restored exactly (or the new one deleted if there was none), and the exception re-raises without saving a failed sample (extraction_result.py:309-315) — so the durable sample and durable sidecar stay paired. process_sample catches that re-raise and returns a rolled-back failure (processor.py:627-638). A failure outside that protected commit block reaches the outer handler, which saves processing_status="failed" and deletes the sidecar (processor.py:680-690).

Be precise about the store. process_sample takes a store: DataStore, but the live backend is the SQLite store — save_extraction_result persists the sidecar as a row keyed by sample_id, not a loose JSON file, on a production install. (The JSON DataStore is the non-production path; see Data access and persistence.) And commit is not acceptance: the freshly built ExtractionResult carries review_state="pending_review" and the sample’s review_accepted is False (extraction_result.py:237, :287). Commit writes a pending-review sidecar; operator acceptance is a separate downstream state change.

What the built sidecar contains

build_extraction_result (extraction_result.py:162) is a pure projection of the legacy Measurements into the canonical ExtractionResult shape (extraction_result.py:231): an extraction_result_id, the sample_id/geometry_id, the method ("automatic"/"manual"), method_provenance and evidence_binding (caller-built), and ExtractionMeasurements where each swatch is projected by _project_swatch (extraction_result.py:124) into transmission + display + appearance buckets. All swatches are stored, including excluded ones — exclusion is a downstream fit-control concern (extraction_result.py:11-12).

Appearance is the one impure step (extraction_result.py:187-219): the builder calls _extract_appearance (extraction_result.py:83), which delegates to the Camera Transform corpus’s embedded-JPEG extractor _embedded_jpeg_extraction (calibration.fitting.camera_transform.corpus, imported function-locally at extraction_result.py:99). A failure here is recorded in diagnostics.appearance_error and leaves appearance=None — an appearance failure never fails the transmission extraction (extraction_result.py:213-219). For the camera-transform side of this, see The Camera Transform.

Registering a blank — blank_registry

Before any of the above can use a flatfield, a photo of the empty lightbox is registered as a blank. The public /api/blanks/register route branches on the backend (server.py:6904-6930): SQLite calls SQLiteDataStore.register_blank_from_image (sqlite_data_access.py:5823), which requires the image to already be an onboarded managed asset, inserts the registered_blanks relation in a write transaction, and reuses the managed asset path; it does not copy a second file into blanks/. The legacy JSON branch calls register_blank_image (blank_registry.py:49), which verifies the image, best-effort reads DateTimeOriginal (:24), copies it into blanks/{blank_id}{suffix}, and rolls that copy back if registration fails (:88-:111). Both paths reject duplicate registration. How a sample points at its blank is in Assigning images.

Visual artifacts — durable accepted views and transient review views

The pipeline’s visual artifact destination is normally an ExtractionArtifactSink (calibration.processing.artifact_sinks). LiveThumbnailSink writes bounded JPEGs under {store.root}/thumbnails/{sample_id}/; SampleArtifactDirectorySink writes staged candidate artifacts into a caller-selected directory for maintenance re-extraction. Both validate the sample id, artifact kind, and filesystem boundary before writing. write_thumbnail_image encodes to a same-directory temporary JPEG, requires cv2.imwrite to report success and produce a non-empty file, and promotes it with rollback-capable os.replace publication instead of writing directly over the live path. Accepted samples retain only source.jpg and strip.jpg. Blank, appearance, and transmission-ROI views are review-time artifacts: re-extraction writes them inside the current candidate set, and applying or superseding that set removes them instead of promoting them into the accepted thumbnail tree. The processor retains a direct write_thumbnail_image fallback when no sink is supplied; production automatic/manual calls create a LiveThumbnailSink by default, while re-extraction passes the staged sink explicitly. Overlay geometry is shared in calibration.processing.extraction_visuals, so the sampled boxes drawn on a review ROI are the boxes the median sampler used.

The backfill migration (transitional, not steady-state)

backfill.py (calibration.processing.backfill) is a one-shot migration, not part of the live extraction path — it is not imported by any other calibration module (see its Architecture node). It exists to populate extraction_result sidecars for legacy samples that already carry Sample.measurements but predate the sidecar format, so the historical corpus has appearance buckets before the Camera Transform starts reading stored appearance. It writes sidecars only — it never re-extracts transmission and never mutates Sample.measurements (backfill.py:5-8). run_backfill (backfill.py:144) drives a read-only classify pass (classify_backfill_sample, backfill.py:45) and acts only on the HAS_MEASUREMENTS_NO_SIDECAR class (BACKFILL_ELIGIBLE, backfill.py:42); malformed or incomplete sidecars are reported, never silently repaired. Once the corpus is migrated it has no steady-state role.
