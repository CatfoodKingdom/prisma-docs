Web API and job orchestration

Web API and job orchestration

Properties1
tagscalibration, server

Jul 15, 202612 min read

In one sentence: server.py (calibration.server) is Calibration’s single FastAPI application: it requires an explicit storage backend, serves the browser UI and /api routes, runs several long operations in daemon threads, and combines family locks with resource leases so conflicting work is rejected or joined rather than queued behind an external worker system.

This page is the code-level contract of the calibration server: how it boots, what its route surface looks like, and — the load-bearing part — how it admits or rejects overlapping work. It is the backend counterpart to the operator-facing Driving the calibration app; where that page describes buttons and screens, this one describes the server the buttons talk to. For where data actually lives, see Data access and persistence; for the long-running operations the server dispatches, see The maintenance backend.

Related: calibration.server · calibration.csv_assignment_import · calibration.sample_mutations · Driving the calibration app

One process, local clients, start-then-report

The whole app is a single FastAPI instance, server.app. The source CLI’s main launches that instance with uvicorn.run; the desktop launcher creates an equivalent uvicorn.Server around the same app. There is no external task queue, worker process, or broker. That shapes everything else on this page:

  • Most long UI operations use start-then-poll jobs. Backup creation, restore, RAW archive work, Inbox import, Fit All, Photo Stack, Camera Transform, general maintenance, and the dedicated re-extraction stages create an in-memory record, start threading.Thread(..., daemon=True), and return without waiting. The browser polls the job-specific status route. Synchronous compatibility routes still exist for backup/restore and legacy profile fitting; therefore “heavy work always runs in a background job” would be false.
  • Job state is in-memory. Running and recently completed jobs live in module-level dictionaries guarded by their own locks: profile, Photo Stack, Camera Transform, backup/restore/RAW archive, Inbox import, maintenance, and re-extraction. TTL pruning removes old records. A process restart forgets the job identities and cannot resume their polling contract.
  • Restart recovery is filesystem/database recovery, not job resumption. _run_post_store_startup_checks reconciles image-import custody and staged extraction publication, removes abandoned immutable-library export/install staging, prunes re-extraction candidate sets only after publication recovery is safe, promotes/cleans backup temporaries, reports (but does not repair) interrupted maintenance scratch entries, and runs the automatic SQLite restore-point startup check. It does not reconcile a hard stop inside the working-model filesystem/pointer-to-SQLite replacement described in Model workflow, publication, and review.
  • Polling access logs are suppressed. _PollingAccessLogFilter mutes the high-frequency status routes for profile fitting, maintenance, Photo Stack, Camera Transform, backup, and Inbox import.

Some start endpoints return the already-active job for their own family (Fit All, Photo Stack, Camera Transform, and Inbox import); maintenance and cross-family conflicts generally return HTTP 409. Nothing waits in a durable queue.

Backend selection — explicit, never silent

The store is chosen explicitly. _configured_backend reads PRISMA_CALIBRATION_BACKEND, falling back only to Prisma/calibration/.backend; if neither contains a value it raises RuntimeError instead of selecting JSON. Only "json" and "sqlite" are accepted by _VALID_BACKENDS.

_create_store turns that choice into a concrete store:

  • "sqlite" builds an SQLiteDataStore (calibration.sqlite_data_access) from a required database path and materialized asset root, both supplied explicitly or resolved through _configured_required_path. This is the production backend.
  • "json" builds a DataStore (calibration.data_access) over an explicitly selected data root. It remains available for migration/tests and some direct development use, but it is not the packaged production path and is never a silent fallback.

At import time _store is None. The packaged calibration_launcher.py resolves the portable layout, prepares the SQLite Workspace, sets the required environment, and only then imports the server. Direct python server.py can instead supply CLI paths; bare Uvicorn relies on the environment or local configuration files when get_store invokes _auto_init. SQLite initialization records recovery context before constructing the store. If construction or full-restore reconciliation fails, the process can still serve the recovery endpoints and /api/system/health, but ordinary get_store calls raise that SQLite recovery is required. GET /api/config (get_config) reports the selected backend, data root, user-facing STEP export directory, and internal managed STEP cache.

The packaged desktop path is Prisma Calibration.exe on Windows or Prisma Calibration on Linux. calibration_launcher.py prefers local port 8016, chooses another available local port when necessary, and asks the host to open the browser. The server.py CLI’s default port 8000 is a lower-level source interface, not packaged-user guidance; see Driving the calibration app.

The /api route surface

Routes are declared as decorated functions across server.py (the module exports well over a hundred endpoint handlers — see the Defines list on calibration.server). They group into a stable set of families, keyed by the first path segment:

Read endpoints generally return JSON or a FileResponse. The background-job families expose separate start and status routes, while cancellation exists only where the underlying operation supports it. This page groups the surface by responsibility; the generated Defines block on calibration.server lists Python symbols, not an authoritative route catalog.

The SPA is mounted last, at /

_mount_static mounts Prisma/calibration/app at / with StaticFiles(..., html=True). The module calls it only after all API route declarations, so /api/... handlers remain reachable and other paths fall through to the static UI. main() calls the helper again after source-CLI store setup; the import-time mount is already the active route.

Backup and restore orchestration

Backup and restore are SQLite-only through _require_sqlite_backup_store. The server separates package validation from destructive application. POST /api/backup/validate-restore first copies an upload into managed temporary storage; local-path validation is accepted only from a local client. Both call _register_restore_preview, which validates package structure and semantics and, for a supported restore type, records an expiring preview token bound to the source identity. Validation is a synchronous HTTP request rather than its own job; the browser shows an indeterminate busy indicator while it waits.

A restore request must claim that token through _claim_restore_preview; a claimed preview cannot be reused or deleted underneath a running restore. POST /api/backup/restore-job creates the UI’s background job and _run_restore_job reports progress through six coarse phases. The synchronous compatibility route /api/backup/restore uses the same claim and executor under _backup_restore_lock. _execute_claimed_restore optionally creates the required emergency core backup, stages the package, delegates the transactional filesystem/database replacement and smoke check to backup_restore.apply_restore, reinitializes the active SQLite store, and then consumes the preview. Restore jobs have no cancel endpoint: once application begins they run to success or rollback/failure.

Backup creation has the same sync/background split: /api/backup/create holds _backup_restore_lock for the request, while /api/backup/create-job starts _run_backup_job and exposes progress at /api/backup/jobs/{job_id}. RAW-archive creation/import/release and Inbox import share _backup_restore_lock, so those custody operations cannot overlap backup or restore. Backup and RAW archive jobs also have no cancel route. Preview deletion is allowed only while the preview is unclaimed.

The lock / 409 blocker mechanism

There is no single global “heavy work” lock. Several mechanisms cover different collision domains; treating them as interchangeable would overstate the guarantee. Beyond the per-dictionary locks that only protect job records, the main run locks are:

  • _backup_restore_lock — backup, restore, RAW-archive work, and Inbox import.
  • _model_fit_run_lock — spline fits, photo-stack fits, and Camera Transform builds (all “model fitting”).
  • _extraction_writer_lock — anything that writes extraction evidence (notably re-extraction).
  • _maintenance_run_lock — general maintenance execution; admission also allows only one active maintenance job record.
  • _evidence_activity_gate_lock — a short-held mutex that makes model-fit/extraction-writer blocker checks and ownership changes atomic.
  • _maintenance_resource_gate_lock — admission lock for queued/running maintenance reservations and ordinary writer leases. It protects the transition between “checked” and “owned,” not the filesystem or SQLite directly.

The behavior is intentionally not uniform:

  • A second start for Fit All, Photo Stack, Camera Transform, or Inbox import returns that family’s already-active job so the browser can rejoin polling.
  • A conflicting maintenance, backup/restore, model-fit, extraction-writer, or protected state-mutation request normally receives HTTP 409 immediately.
  • A job record can be created just before its daemon worker acquires the family lock. If another owner wins that race, the worker marks its record failed/blocked; it does not wait in a queue.
  • Backup/restore and RAW archive validation use expiring claim tokens so the validated input cannot be silently replaced or reused during execution.

The model-fit and extraction-writer locks use a context-manager guard so acquire/release is exception-safe:

  • _model_fit_run_guard calls _try_begin_model_fit_run, raises HTTP 409 when admission fails, and releases ownership in finally through _end_model_fit_run.
  • _extraction_writer_guard mirrors that. _try_begin_extraction_writer cross-checks active model fitting, while model-fit admission cross-checks extraction writers. A model fit and extraction-evidence writer therefore cannot overlap.

The _try_begin_* helpers take _maintenance_resource_gate_lock before _evidence_activity_gate_lock, inspect the other evidence-writer family, and attempt non-blocking run-lock acquisition. Maintenance admission takes the gates in the same order, avoiding an ABBA deadlock. A model or extraction worker also advertises an ordinary resource lease for its entire worker lifetime.

Each MaintenanceOperation.conflict_resources tuple drives maintenance-versus-ordinary admission. start_maintenance_job_endpoint checks active ordinary leases and creates the queued maintenance job while still holding the resource gate; that queued record is the reservation and closes the queue-to-worker race. _request_resource_claims classifies ordinary requests into SQLite, image custody, preview cache, extraction evidence, sample visuals, geometry state, model evidence, and model artifacts. _maintenance_resource_middleware acquires a lease before dispatch and releases it in finally. On-demand source/blank preview GETs claim preview_cache because they may create cached files.

An ordinary lease is not a mutex between two ordinary HTTP requests: _try_acquire_ordinary_resource_lease checks queued/running maintenance reservations, while maintenance admission checks existing ordinary leases. Ordinary requests continue to rely on their domain transactions and any family-specific locks. Unrelated reads and writes also continue. Worker-start failure changes the queued maintenance record to a terminal failed state, removing it from the active reservation set.

Cancellation is likewise operation-specific. Inbox import has a cooperative cancel callback and a dedicated cancel route. Maintenance exposes /api/maintenance/jobs/{job_id}/cancel, but cancel_maintenance_job accepts it only for an operation whose registry metadata says it is cancellable; the job remains cancelling until a safe point acknowledges it. The dedicated re-extraction stages have their own cancel routes and safe-point semantics. Backup, restore, RAW archive, direct profile-fit, Photo Stack, and Camera Transform jobs expose no cancel endpoint and run to a terminal result once started.

CSV bulk image↔sample assignment

csv_assignment_import.py (calibration.csv_assignment_import) is the one bulk-entry path: an operator uploads a CSV mapping sample IDs to sample/blank images and an orientation, instead of assigning each by hand. TEMPLATE_COLUMNS fixes the columns — Sample ID, Sample Image, Blank Image, Orientation — and ORIENTATION_MAP accepts U/D/L/R plus T/B aliases.

It is a two-phase, validate-then-commit flow, and it is SQLite-only — both endpoints call _require_sqlite_assignment_store, which returns HTTP 501 for the JSON backend:

  1. Validate. POST /api/samples/assignment-import/validate runs validate_assignment_csv, resolves every row against live samples/images/blanks, accumulates row errors, and stores only commit specifications plus preview diagnostics behind a 15-minute in-memory token. It does not assign anything.
  2. Commit. POST /api/samples/assignment-import/commit looks the cached specs up and calls commit_assignment_rows. The committer re-reads all referenced state and rejects a stale preview as HTTP 409. Existing-blank assignments use save_samples; if the operator explicitly confirms unregistered blank images, save_samples_with_blank_registrations registers or resolves those blanks and saves every assignment in one SQLite transaction. A database validation, registration, or sample-save failure therefore does not retain a partial set of assignments.

Eligibility is deliberately strict: _sample_eligibility_errors rejects a row whose sample already has an image, a blank, an orientation, a non-unassigned status, or any extraction results — the importer only fills in genuinely empty samples, never overwrites work. Optionally, when the register_unregistered_blanks flag is set, commit includes not-yet-registered blank images in the same transaction as their assignments.

Sample mutations — domain logic lifted out of the server

sample_mutations.py (calibration.sample_mutations) holds sample create/update domain logic pulled out of the HTTP handlers to keep them thin; its functions raise ValueError for domain errors and the server converts those to HTTPException. The live functions — the ones server.py and csv_assignment_import.py actually import and call — are:

  • recompute_sample_status — sets a sample’s status to assigned vs unassigned from assignment completeness (used by both the server and the CSV committer).
  • invalidate_sample_processing — clears processing-derived fields on a sample after a meaning-changing mutation (filament/geometry/source changes or rejection) and returns the recomputed assignment state. On legacy JSON it also removes visuals/sidecars and marks dependent profiles stale directly. On SQLite, the subsequent SQLiteDataStore save owns transactional extraction invalidation, model-fit staleness, and derived-visual cleanup. Current call sites include the live sample update, assignment/swap, and rejection handlers.
  • mark_profiles_stale_for_sample — the profile-ownership helper invalidate_sample_processing uses, exposed for direct use on delete.

The manual stale/sidecar path is gated to non-SQLite stores inside invalidate_sample_processing. SQLite callers must persist the mutated sample through SQLiteDataStore; calling this helper alone does not perform the database-side invalidation.

Live vs dormant: repository-wide call search currently finds no caller for apply_sample_update, create_samples_from_step_files, or compute_fit_result. tests/calibration/test_step_2_invalidation_review.py explicitly characterizes apply_sample_update as dead. The live update_sample route implements its own mutation flow. Treat those three helpers as vestigial unless a caller is introduced.
