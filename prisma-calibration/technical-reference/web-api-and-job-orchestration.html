Web API and job orchestration

Web API and job orchestration

Properties1
tagscalibration, server

Jul 14, 202611 min read

In one sentence: server.py (calibration.server) is the calibration app’s one FastAPI process — it selects a storage backend explicitly (no silent fallback), serves the single-page frontend, exposes every /api route family, and guards each heavy operation behind a module-level lock so that only one backup, model fit, extraction write, or maintenance job can run at a time — the second caller gets an HTTP 409, not a queue.

This page is the code-level contract of the calibration server: how it boots, what its route surface looks like, and — the load-bearing part — how it enforces “one job at a time.” It is the backend counterpart to the operator-facing Driving the calibration app; where that page describes buttons and screens, this one describes the server the buttons talk to. For where data actually lives, see Data access and persistence; for the long-running operations the server dispatches, see The maintenance backend.

Related: calibration.server · calibration.csv_assignment_import · calibration.sample_mutations · Driving the calibration app

One process, one user, start-then-report

The whole app is a single FastAPI instance (server.py:200) launched by one uvicorn.run (server.py:9004). There is no task queue, no worker pool, no external broker. That shapes everything else on this page:

  • Heavy work runs on a daemon thread, not a subprocess or a queue. A “start” endpoint validates, acquires a lock, spawns a threading.Thread(..., daemon=True), and returns a job record immediately (e.g. start_photo_stack_fit server.py:8217; start_camera_transform_build server.py:8244). The client then polls a matching status endpoint (get_photo_stack_status server.py:8235, get_camera_transform_status server.py:8262) until the job record reports terminal state. This is the start-then-report model: the HTTP call that starts the job does not wait for it.
  • Job state is in-memory. Running/finished jobs live in module-level dicts — _photo_stack_jobs, _camera_transform_jobs, _profile_fit_jobs, _backup_jobs, _image_import_jobs, _maintenance_jobs, _reextract_jobs (declared server.py:204–233) — each with its own dict-guarding threading.Lock and a TTL for pruning stale records. A server restart forgets them.
  • The polling is chatty by design, so a log filter mutes the high-frequency status GETs from uvicorn’s access log (_PollingAccessLogFilter server.py:251, installed server.py:274).

Because there is exactly one process and (in practice) one operator, the concurrency model can be this simple. The lock/409 mechanism below is what actually keeps two conflicting operations from colliding.

Backend selection — explicit, never silent

The store is chosen at startup and validated up front. _configured_backend (server.py:305) reads PRISMA_CALIBRATION_BACKEND, falling back only to a local .backend file — and if neither is set it raises RuntimeError rather than defaulting (server.py:311). Only "json" and "sqlite" are accepted (_VALID_BACKENDS server.py:48); anything else is a hard error.

_create_store (server.py:336) turns that choice into a concrete store:

  • "sqlite" builds an SQLiteDataStore (calibration.sqlite_data_access) from a required database path and a required materialized asset root (server.py:368), each resolved through _configured_required_path, which likewise raises if the path is not configured. This is the production backend.
  • "json" builds a DataStore (calibration.data_access) over a data-root directory (server.py:356). Per the docstring (server.py:343–348), JSON “can still be constructed intentionally for migration tests/tools, but it is never selected as an implicit fallback.” Treat the JSON store as migration/test-only, off the production path.

At import time _store is None (server.py:203); the packaged calibration_launcher.py first resolves the portable layout, prepares/initializes the SQLite Workspace, applies the required environment, and then imports the server. A source-only main() or bare Uvicorn launch can still populate the store through the development paths. SQLite initialization records recovery context before constructing the store; if construction fails, _store remains unset and get_store (server.py:465) raises an error saying SQLite recovery is required. A successful store runs interrupted-maintenance scanning and the SQLite restore-point startup check (server.py:430-:436). GET /api/config (get_config server.py:947) echoes the resolved backend and paths back for the UI’s copy-path controls.

The supported Windows release path is Prisma Calibration.exe, whose desktop launcher defaults to local port 8016 and searches upward if that port is occupied. Commands and defaults in server.py are source-development interfaces, not end-user installation guidance (see Driving the calibration app).

The /api route surface

Routes are declared as decorated functions across server.py (the module exports well over a hundred endpoint handlers — see the Defines list on calibration.server). They group into a stable set of families, keyed by the first path segment:

FamilyPurpose
/api/samples, /api/bundles, /api/geometries, /api/stepsSample CRUD, batch creation, geometry/bundle/STEP management
/api/filaments, /api/profilesFilament registry and fitted-profile read/activate
/api/images, /api/blanks, /api/thumbnails, /api/previewsManaged image assets, blank registration, preview/thumbnail serving
/api/processExtraction — process one/all samples, manual extract, status summary
/api/fitting, /api/models, /api/photo-stack, /api/camera-transformModel fitting, review, and the Camera Transform build
/api/maintenance, /api/systemLong-running maintenance jobs, re-extraction, SQLite restore points
/api/backup, /api/raw-archivesBackup/restore and RAW image archive lifecycle

Read endpoints return JSON directly; the heavy families (backup, maintenance, photo-stack, camera-transform, profiles/fit-all, images/import-inbox) follow the start-then-poll pattern above. This page describes the families, not every route; the exhaustive list is the module’s Defines block on its Architecture node.

The SPA is mounted last, at /

_mount_static (server.py:8892) mounts the frontend directory at the root with StaticFiles(directory=..., html=True) (:8897). It is called by main after store initialization and after the API routes have been registered (:8998-:9002). Mounting it last means /api/... paths resolve to their handlers and everything else falls through to the SPA’s index.html.

Backup and restore orchestration

Backup and restore are SQLite-only (_require_sqlite_backup_store, server.py:1068). The server separates package validation from destructive application. Upload or local-path validation registers a preview token (/api/backup/validate-restore and /api/backup/validate-restore-path, server.py:3950-:4014); the preview records the source identity and validated package semantics. A restore request must claim that token before starting (_claim_restore_preview, server.py:3188); the claim prevents a preview from being reused or changed between validation and execution.

POST /api/backup/restore-job (server.py:4156) claims a validated preview and starts _run_restore_job (:3781) on a daemon thread after checking maintenance and backup blockers. The synchronous /api/backup/restore endpoint (:4182) performs the same claim and calls _execute_claimed_restore while holding _backup_restore_lock. The executor creates an emergency pre-restore package, stages and validates the ZIP, applies only the package semantics, runs a store smoke check, and reinitializes the SQLite store (_execute_claimed_restore, :3398). apply_restore restores displaced state when application or smoke checking fails. Once the smoke check succeeds, rollback cleanup handles read-only files; any residual cleanup failure is returned as a warning rather than re-entering rollback after the old tree may be partially deleted.

Backup creation has the same split: /api/backup/create runs synchronously under _backup_restore_lock, while /api/backup/create-job starts _run_backup_job and exposes in-memory progress through /api/backup/jobs/{job_id} (server.py:3732-:3793). RAW-archive creation, import, release, and restore-preview deletion use the same lock family and are not independent concurrent workers.

The lock / 409 blocker mechanism

This is the heart of “one job at a time.” Beyond the per-dict locks that just guard the job registries, a family of run locks serializes the operations themselves (declared server.py:234–242):

  • _backup_restore_lock — backups, restores, and RAW-archive work.
  • _model_fit_run_lock — spline fits, photo-stack fits, and Camera Transform builds (all “model fitting”).
  • _extraction_writer_lock — anything that writes extraction evidence (notably re-extraction).
  • _maintenance_run_lock — general maintenance operations.
  • _evidence_activity_gate_lock — a short-held mutex that makes the check-then-acquire of the model-fit and extraction-writer locks atomic (server.py:235).
  • _maintenance_resource_gate_lock — admission lock for queued/running maintenance reservations and ordinary writer leases. It protects the transition between “checked” and “owned,” not the filesystem or SQLite directly.

The pattern is uniform: a start endpoint asks whether a conflicting operation holds the relevant lock, and if so raises HTTPException(409, ...) immediately — it does not block or enqueue. Backup/restore endpoints additionally use preview tokens and a claimed-preview state before destructive work begins; the lock prevents overlapping backup, restore, and RAW-archive operations.

The model-fit and extraction-writer locks use a context-manager guard so acquire/release is exception-safe:

  • _model_fit_run_guard (server.py:2050) calls _try_begin_model_fit_run (server.py:2026); on failure it raises HTTPException(409, ...) with a blocker message (server.py:2054) and otherwise releases the lock in its finally (_end_model_fit_run server.py:2042).
  • _extraction_writer_guard (server.py:2088) mirrors that, and additionally cross-checks the model-fit lock so a model fit and an extraction write can never overlap (server.py:2098–2100).

The _try_begin_* helpers take _maintenance_resource_gate_lock and then _evidence_activity_gate_lock, inspect the other evidence-writer family, and attempt a non-blocking run-lock acquisition. Maintenance admission takes those locks in the same order, avoiding a model/extraction-start versus maintenance-start deadlock. A model or extraction worker also owns an ordinary resource lease for its full worker lifetime.

Each MaintenanceOperation.conflict_resources tuple drives the shared admission policy. start_maintenance_job_endpoint checks active ordinary leases and creates the queued job while still holding the resource gate; the queued job itself is therefore the reservation and closes the queue-to-worker race. Ordinary API mutations are classified into SQLite, image custody/preview, extraction evidence/sample visuals, geometry, and model categories. Middleware acquires the request’s lease before dispatch and releases it in finally. On-demand source/blank preview GET routes are classified as preview writers because they can create cache files. A conflicting request receives HTTP 409; unrelated reads and writes continue. Worker-start failure marks the queued job failed, which immediately removes it from the active-reservation set.

Net effect: the “one job at a time” behavior the operator sees in the UI is not a frontend nicety — it is enforced server-side by these locks, and a conflicting second request is rejected with a 409 the moment it arrives.

CSV bulk image↔sample assignment

csv_assignment_import.py (calibration.csv_assignment_import) is the one bulk-entry path: an operator uploads a CSV mapping sample IDs to sample/blank images and an orientation, instead of assigning each by hand. The template columns are fixed — Sample ID, Sample Image, Blank Image, Orientation (TEMPLATE_COLUMNS csv_assignment_import.py:14) — and orientation accepts U/D/L/R (plus T/B aliases) via ORIENTATION_MAP (csv_assignment_import.py:16).

It is a two-phase, validate-then-commit flow, and it is SQLite-only — both endpoints call _require_sqlite_assignment_store, which 501s on the JSON backend (server.py:1103):

  1. Validate. POST /api/samples/assignment-import/validate (server.py:4317) runs validate_assignment_csv (csv_assignment_import.py:34), which resolves each row against live samples/images/blanks, accumulates per-row errors, and returns a preview plus a token that caches the valid rows’ commit specs server-side.
  2. Commit. POST /api/samples/assignment-import/commit (server.py:4351) looks the token’s cached specs back up and calls commit_assignment_rows (csv_assignment_import.py:120), which re-validates against current state and raises CsvAssignmentError if the preview went stale (the server maps that to HTTP 409 with a stale flag). Existing-blank assignments use save_samples; when the operator confirmed one or more unregistered blanks, save_samples_with_blank_registrations (sqlite_data_access.py:3524) registers or resolves those blanks and writes every sample assignment inside one SQLite transaction. A registration, validation, or sample-save failure therefore rolls back the entire database mutation rather than retaining a partially registered blank.

Eligibility is deliberately strict: _sample_eligibility_errors (csv_assignment_import.py:569) rejects a row whose sample already has an image, a blank, an orientation, a non-unassigned status, or any extraction results — the importer only fills in genuinely empty samples, never overwrites work. Optionally, when the register_unregistered_blanks flag is set (csv_assignment_import.py:124), commit includes not-yet-registered blank images in the same transaction as their assignments.

Sample mutations — domain logic lifted out of the server

sample_mutations.py (calibration.sample_mutations) holds sample create/update domain logic pulled out of the HTTP handlers to keep them thin; its functions raise ValueError for domain errors and the server converts those to HTTPException (module docstring sample_mutations.py:1–7). The live functions — the ones server.py and csv_assignment_import.py actually import and call — are:

  • recompute_sample_status (sample_mutations.py:47) — sets a sample’s status to assigned vs unassigned from assignment completeness (used by both the server and the CSV committer).
  • invalidate_sample_processing (sample_mutations.py:83) — the profile-staleness / invalidation core. When a sample’s provenance changes (new filament, new STEP geometry, swapped source image, rejection), it clears the derived state (measurements, thumbnails, the extraction-result sidecar) and marks every dependent profile stale so downstream fits know their inputs moved. The server calls it on delete, swap, reject, and provenance edits (server.py:4649, 8454, 8531, 8609).
  • mark_profiles_stale_for_sample (sample_mutations.py:38) — the profile-ownership helper invalidate_sample_processing uses, exposed for direct use on delete.

Note the staleness marking is gated to the JSON backend inside invalidate_sample_processing (sample_mutations.py:99–103): on SQLite the store tracks profile dependencies itself, so the function skips the manual stale-flagging path.

Live vs dormant: three functions in this module — apply_sample_update (sample_mutations.py:132), create_samples_from_step_files (sample_mutations.py:239), and compute_fit_result (sample_mutations.py:292) — are not called anywhere in Prisma/ or tests/; a characterization test even refers to “the dead apply_sample_update” (tests/calibration/test_step_2_invalidation_review.py:7). The server’s update_sample handler (server.py:4439) reimplements sample-update logic inline rather than delegating to apply_sample_update. Treat those three as vestigial — superseded by inline server logic; only the three functions above are live.
