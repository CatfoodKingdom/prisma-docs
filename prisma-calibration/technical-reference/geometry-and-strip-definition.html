Geometry and strip definition

Geometry and strip definition

Properties1
tagscalibration, geometry

Jul 15, 202610 min read

In one sentence: a calibration strip’s shape is a frozen GeometryDefinition (calibration.geometry_builder), validated to a strict canonical form, hashed into a structural_fingerprint, and turned into a build-independent body plan that the STEP/STL exporters render — the notebook-era strips/generator.py is off the production SQLite path.

This page is the code-level map of how a strip geometry is represented and exported. For the concept — what a swatch, a role, and the spine are, and why the strip is shaped the way it is — see Sample Geometry. How a sample points at its geometry, and where geometries are persisted, is in Data access and persistence.

Related: calibration.geometry_builder · calibration.lightweight_step · calibration.strips.generator · calibration.strips.step_parser · Sample Geometry

The source-of-truth definition

Everything hangs off three frozen dataclasses in geometry_builder.py, deliberately independent of a CAD kernel:

  • GeometryDefinition — the whole strip: layout_rows × layout_columns, per-swatch and spine dimensions in millimeters, a tuple of roles, and a tuple of swatch_slots. swatch_count is just rows * columns.
  • GeometryRoleDefinition — one bottom-to-top material slot, tagged role_kind "fixed" or "variable", with a role_index and (for fixed roles) a fixed_thickness_mm.
  • GeometrySwatchSlotDefinition — one swatch cell’s position (row_index, column_index) and its variable_thickness_mm (the thickness the single variable role takes at that swatch).

Note what is absent: there is no layer height and no layer count. Thicknesses are absolute millimeters; the definition never knows about a slicer’s layer grid. (The legacy generator below does snap to a layer height — a key difference.)

The canonical invariants

validate_geometry_definition is the gatekeeper; it accumulates every violation and raises one ValueError. The invariants worth knowing, because they are what “a valid geometry” means everywhere downstream:

  • Roles are contiguous from 1. role_index values must be exactly 1..len(roles).
  • Exactly one variable role. Not zero, not two — one. This is the layer whose thickness varies swatch to swatch; every other role is fixed.
  • Role labels are unique and, if set, must equal LR_%02d of the index.
  • Fixed roles carry a positive thickness; variable roles carry none.
  • Slots tile the layout exactly. len(swatch_slots) must equal rows * columns, swatch_index must be contiguous from 0, and no two slots may share a (row, column).
  • The spine is tall enough. spine_total_thickness_mm must be at least the tallest swatch stack, as summed by _slot_stack_height.

Structural fingerprint — the identity

compute_structural_fingerprint is how the system decides whether two geometries are “the same shape.” It builds a canonical_geometry_payload — layout, roles (variable roles force fixed_thickness_mm to null), and slots, every float rounded to 6 places by _canonical_float — serializes it with sorted keys and no whitespace, and SHA-256s it. Because the payload is canonicalized (roles and slots sorted, floats rounded), two definitions that differ only in field order or sub-micro precision noise fingerprint identically; any structural change that survives six-decimal canonicalization produces a new hash.

build_geometry_body_plan re-derives the fingerprint and refuses to build if a definition arrived carrying a structural_fingerprint that no longer matches its content — a cheap guard against a stored geometry being edited out from under its hash.

The live API and persistence path

The production web path is the structured-geometry API, not the older STEP-record generator. The server exposes GET /api/geometries, GET /api/geometries/{geometry_id}, POST /api/geometries, PATCH /api/geometries/{geometry_id}, and DELETE /api/geometries/{geometry_id}. These routes call the corresponding SQLiteDataStore methods — list_geometry_definitions, get_geometry_definition, create_geometry_definition, update_geometry_metadata, and delete_geometry_definition — and serialize the dataclass through _geometry_payload.

SQLiteDataStore.create_geometry_definition accepts the structured roles and swatch slots, computes the fingerprint through _definition_from_create_command, and inserts one geometry row plus its geometry_roles and geometry_swatch_slots rows in one write transaction. Both alias and structural_fingerprint are unique in the database. Updating metadata changes only alias and notes; changing dimensions, roles, or slots means creating a different definition. Deletion is rejected when the geometry is referenced by a sample or bundle.

The server still exposes GET /api/steps and returns StepRecord objects. In SQLite, that is a compatibility projection reconstructed by _step_records_by_id / _step_record_from_geometry, not a second geometry store. The projection supplies compatibility values such as file_name = {geometry_id}.step and _COMPAT_LAYER_HEIGHT_MM; layer height is not part of the source-truth GeometryDefinition.

The old POST /api/steps/generate route is not the SQLite production creation path. _guard_sqlite_unimplemented_write rejects it with HTTP 501 for the SQLite backend because the route still targets the legacy DataStore/STEP-record workflow. The structured replacement is POST /api/geometries, followed by the structured artifact endpoint described below. This is a current compatibility boundary, not evidence that SQLite geometry artifact generation is absent.

The body plan

build_geometry_body_plan turns a definition into a GeometryBodyPlan of GeometryBodyPlanItems — axis-aligned RectPrisms grouped by role, in canonical builder coordinates. It has no CAD dependency; it is pure geometry the exporters consume. Two body families:

  • Swatch bodies (_swatch_bodies). Each role is laid down as a z-interval stacked from 0 upward in role order by _role_intervals_for_slot. A fixed role that spans every swatch at the same z-interval collapses to one swatch_area prism over the whole grid; otherwise the role emits one swatch prism per nonzero slot. This keeps the common fixed-backing case a single solid instead of N identical boxes.
  • Spine bodies (_spine_bodies). The surrounding frame (left, right, and top borders from _spine_interval_bodies) is split into z-intervals, each owned by the highest-index role present in any swatch at that height (_spine_owner_for_interval), with adjacent same-owner intervals merged. If no swatch role is present above the tallest stack, the top role owns the remaining spine height.

Footprint is columns * swatch_width + 2 * spine_width wide and rows * swatch_height + spine_width tall (_footprint_width, _footprint_height).

Export — lightweight STEP and per-role STL

geometry_builder.py delegates production serialization to lightweight_step.py; neither path imports a CAD kernel:

  • export_geometry_step calls export_geometry_step_lightweight and writes one role-grouped STEP.
  • export_geometry_stls calls export_geometry_stls_lightweight and writes one binary STL per geometry role, named {prefix}_{role}.stl. A geometry role is still an unfilled material slot at this point; the filament is assigned only when a sample is created.
  • export_geometry_artifacts is the convenience wrapper that emits a STEP plus a stl/ subdirectory in one call and returns a GeometryExportResult.

build_lightweight_geometry groups the body plan’s axis-aligned prisms by role and computes exact boundary components for each union. Every component is validated as a closed, positively oriented rectilinear solid with the expected volume before serialization by _validate_component. write_lightweight_step emits millimeter, planar AP214-style BREP records and labels each role’s product and solid. write_lightweight_stl triangulates those same validated quad boundaries into atomic binary STL files. STEP and STL therefore share one geometry model instead of asking two independent exporters to reinterpret the strip.

The packaged Calibration runtime excludes build123d, OCP, and VTK. Build123d remains a development/test dependency only for independent parity comparisons; it is not on the production structured-geometry path.

SQLite artifact lifecycle

POST /api/geometries/{geometry_id}/artifacts calls SQLiteDataStore.generate_geometry_artifacts. The store rebuilds the definition with an empty stored fingerprint, recomputes the builder fingerprint, and stages managed artifacts beside their final _system/geometry_artifacts/{geometry_id}/{fingerprint} directory. The managed STEP also has a staged compatibility copy destined for _system/step_artifacts/{geometry_id}.step.

Each generation writes manifest.json into the staged fingerprint directory. The manifest records the database and builder fingerprints, builder_version, the complete managed STEP/STL inventory, the subset requested by the current API call, body names, and remembered public export paths. get_geometry_artifact_summary resolves the manifest-owned filenames back inside the current fingerprint root rather than trusting historical absolute roots; it reports a missing/unreadable manifest, missing STEP, absent or incomplete STL set, and absent or incomplete body labels separately. The Maintenance missing-artifact audit and regeneration preflight consume that same health classification.

When export_to_output is true, the public destinations are under store.step_export_dir (Calibration/Output/Steps in the packaged Suite): {export_name}.step and an {export_name}/ directory containing the per-role STL files. A request without overwrite=true returns HTTP 409 when those destinations conflict. With overwrite enabled, Prisma stages every requested public file before publication and removes only obsolete STL paths recorded as owned by the previous manifest; unrelated files in an existing export directory are preserved.

Publication is one rollback-capable filesystem transaction across the staged fingerprint directory, compatibility STEP, requested public STEP/STLs, and manifest-owned stale removals. Existing targets are displaced to short sibling rollback paths, staged targets are promoted with os.replace, and any later failure removes promoted replacements and restores every displaced path. Generation or manifest-staging failure occurs before this boundary and cannot alter live files. The transaction rejects filesystem links and hardlinked mutable file targets; managed trees are inspected for nested links before replacement. A rollback failure preserves and reports its recovery path instead of deleting it. POST /api/steps/{step_id}/ensure-artifact remains the compatibility repair endpoint and calls this same structured generator.

The public endpoint can generate STEP, STL, or both, but it rejects a request that selects neither. Unrequested managed file types already present in the current fingerprint directory are retained and inventoried, while the response’s legacy step_path/stl_paths fields continue to describe the types requested by that call. The lightweight serializer collects every disconnected component of one role into the same role product/file, so STL export still produces one file per role.

Geometry bundles and sample creation

Bundles are SQLite records that group geometry definitions and map each geometry role to a shared material slot. They are not CAD artifacts. geometry_bundles and geometry_bundle_members store the bundle and ordered geometry membership; geometry_bundle_material_slots and geometry_bundle_role_slot_mappings store the material-slot vocabulary and role assignments.

_bundle_detail_in_tx derives mapping_status as unmapped, incomplete, invalid, or mapped and exposes creation_eligible only for the fully mapped state. save_bundle_mapping validates the draft against the member roles and rewrites the slot and mapping rows transactionally. create_samples_from_bundle_slots refuses any bundle that is not mapped, then creates samples for every bundle member, with optional multiple filament values for one batch material slot. The bundle API is therefore a role-assignment and sample-generation layer above geometry definitions; it does not alter the geometry fingerprint.

Role labels in STEP

Role labeling is now part of serialization rather than post-export string surgery. write_lightweight_step creates one named PRODUCT and ADVANCED_BREP_SHAPE_REPRESENTATION per role, while _add_component_geometry gives every component’s MANIFOLD_SOLID_BREP the same role-derived name. Fusion and OrcaSlicer therefore receive role identity directly from the generated STEP entities.

The legacy strip generator (off the production path)

strips/generator.py (calibration.strips.generator) is the older geometry code, self-described as “Used by experiment_builder.ipynb.” It hardcodes a fixed 8-swatch strip with baked physical constants (SWATCH_W = 12.0, N_SWATCHES = 8) and snaps thicknesses to a layer height through snap_offset — the opposite of the flexible, layer-height-free GeometryDefinition. It has its own generate_step / generate_stls, and is imported only by the JSON DataStore (data_access.py), not by the production SQLite path — so it is dormant in the packaged app. The live geometry consumers are sqlite_data_access.py and maintenance.py, both of which use geometry_builder.py.

strips/step_parser.py (calibration.strips.step_parser) is a small compatibility helper that parses metadata (variable_thicknesses_mm, fixed_layers, layer_height_mm, layer_count) back out of legacy STEP filenames, tolerating both the double-underscore and older single-underscore naming. It is a filename reader, not part of structured geometry construction. The SQLite projection does not need it to reconstruct a geometry; it reads the normalized role and slot tables instead.
