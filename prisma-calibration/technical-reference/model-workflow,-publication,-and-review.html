Model workflow, publication, and review

Model workflow, publication, and review

Properties1
tagscalibration, workflow

Jul 28, 202615 min read

In one sentence: the Fit Models maintenance operation drives execute_model_fit_workflow (calibration.fitting.model_fit_workflow), which runs Color Model v1 and v2 and conditionally runs the Camera Transform in a fixed order, replaces each successfully fitted family’s current Calibration fit through calibration.fitting.model_publication, and leaves one registered artifact set per family for modeling_review.py (calibration.modeling_review) — while the separate Publish Models workflow copies an exact, validated snapshot into an immutable Generator model library.

This page is the hub that ties the three model fitters together. It maps the unified fan-out and preflight, Calibration’s replaceable one-current-fit-per-kind contract, the separate immutable-library publication boundary, the read side that powers the operator’s modeling surface, and the three shared modules every fit calls before it touches color data. In older implementation names, publish_model_fit means “make this Calibration fit current”; it does not mean “publish a library to Generator.” It does not re-derive any model’s math — the physics of each fit lives in its own page and in How It Works. For the three fitters themselves see Spline model fitting (v1), Photo-stack model fitting (v2), and The camera transform fitter; for the model forms, Color Model v1 / Color Model v2 / The Camera Transform.

Related: calibration.fitting.model_fit_workflow · calibration.fitting.model_publication · calibration.model_library_publication · lib.standard_model_library · lib.model_library_store · calibration.modeling_review · calibration.fitting.physical_stack · calibration.fitting.filament_roles · calibration.fitting.filament_exclusions

The unified fan-out — one button, three fitters

“Fit Models” is the operator label for the maintenance operation refit_calibration_models. It is registered as a maintenance operation, so it runs through the same preflight/execute boundary as every other operation: _preflight_refit_calibration_models and _execute_refit_calibration_models, both of which delegate to model_fit_workflow.py through options_from_scope, build_model_fit_preflight, and execute_model_fit_workflow. The workflow preflight is SQLite-only; non-SQLite stores are returned as blocked rather than being sent through the fitters.

The workflow recognizes three model kinds, named by module constants: MODEL_LEGACY_SPLINE = "legacy_spline", MODEL_PHOTO_STACK = "photo_stack_v2", MODEL_CAMERA_TRANSFORM = "camera_transform". execute_model_fit_workflow runs them in a fixed sequence and short-circuits on the first failure:

  1. Legacy spline (v1) — run_legacy_spline_fit_all(..., publish=True), from calibration.fitting.legacy_spline_fit_job. Detail: Spline model fitting (v1).
  2. Photo Stack (v2) — run_photo_stack_fit_job(..., publish=False), then the exception-compensated publish_photo_stack_fit. Detail: Photo-stack model fitting (v2).
  3. Camera Transform — run_camera_transform_build_job(..., publish=False), then the exception-compensated publish_camera_transform_fit. Detail: The camera transform fitter.

The three fitters are parallel siblings on a shared spine, not layered: each loads its own evidence, fits, and independently replaces its current Calibration fit; the workflow just orders them and aggregates status. The legacy-spline and photo-stack stages always run; the Camera Transform runs only when its plan says so (below). _stage_progress rescales each fitter’s inner progress into an overall bar sized by total_stages. The workflow contains cooperative cancellation checks before and between stages, and the legacy-spline fitter also accepts the callback while it runs. However, the registered Fit Models maintenance operation uses the default not_supported cancellation policy, so the application does not offer a user cancel action. Photo Stack and Camera Transform also have no intra-stage cancellation callback.

Workflow options and the preflight

ModelFitWorkflowOptions is a frozen two-field dataclass: force_camera_transform and use_fit_exclusions (the latter pinned to True). options_from_scope builds it from the request scope, reading only force_camera_transform — the per-run fit-state exclusions are always on for this workflow.

build_model_fit_preflight is the gate. It first refuses any non-SQLite backend outright (“Fit Models requires the SQLite backend”), then builds a model_plan for the three kinds. Legacy and Photo Stack are hardwired to action: "run" with reason always_refit_color_models — the two color models are always refit. The Camera Transform is the only conditional stage: _build_camera_transform_plan compares the live fit-input fingerprint against both the stored artifact manifest and the current model-fit record. It returns run for a forced, missing, invalid, unregistered, fingerprint-mismatched, old-fingerprint, or input-changed transform; skip/up_to_date for an unchanged transform; and skip/insufficient_evidence when fewer than five eligible samples exist. An insufficient-evidence skip does not manufacture a current Camera Transform, so immutable-library publication remains blocked if one is missing or stale.

The preflight also computes a plan_digest through _build_plan_digest — a SHA-256 over the scope, per-kind action/reason, the Camera Transform input hash, legacy target filaments, and Photo Stack evidence hash. execute_model_fit_workflow recomputes the preflight and refuses to run if the stored plan_digest no longer matches (“Model fitting plan changed. Run preflight again”), so a reviewed plan cannot silently change before execution.

The result envelope carries status, per-kind model_results, a historically named partial_publication map recording which kinds actually got a new current model_fit_id, and a ui_refresh directive that invalidates the model-artifact caches for all three kinds. Current-fit replacement is not a transaction spanning all three fitters: the spline stage can complete before Photo Stack or Camera Transform fails, and the internal cancellation paths after a completed stage return the earlier replacement with a targeted refresh. No immutable Generator library is created by Fit Models.

V1 has an additional partial-success boundary inside its own stage. If at least one profile fits and pair-correction generation succeeds, its successful subset can be published even when another filament failed. The unified workflow then sees the nonzero v1 failed count, returns an overall failure with partial_publication.legacy_spline = true, and does not start v2. “Rollback-capable publication” therefore describes recovery from ordinary publication exceptions; it does not mean every target filament must fit before any v1 replacement can occur.

Direct fitter entry points

The unified operation is the main fan-out, but the server also exposes separate asynchronous Photo Stack and Camera Transform jobs and synchronous/asynchronous spline /api/profiles/fit-all routes. These paths run one fitter and replace its current result through the same coordinated publication boundary; they are not alternate model kinds and do not publish a Generator library. The server uses _try_begin_model_fit_run / _end_model_fit_run around these jobs and the direct spline routes, so overlapping model-fit jobs are rejected with a conflict rather than allowed to replace the same working state concurrently. The unified maintenance job also claims the maintenance_model_fit owner and is checked by the same blocker logic. The current Modeling UI calls the unified workflow; the old direct-profile frontend renderer remains dormant.

The direct asynchronous v1 worker has a status-reporting defect: after _run_profile_fit_all returns it records the job as completed even when the result contains per-filament failures or a failed status. The unified workflow does not share this defect because it explicitly checks those fields and stops. Treat the direct async route as a compatibility/developer surface, not the user-facing success authority.

Internal current-fit replacement — one fit per kind, staleness aware

calibration.fitting.model_publication holds the shared publish helpers that every fitter routes through. It keeps common path/artifact registration logic at the store boundary and imports each model family’s pointer-management helpers inside the coordinated publisher that needs them. The entry shapes are:

  • Directory publish primitive — publish_artifact_directory_model_fit walks an artifact directory through model_artifacts_from_directory, converts every file to a store-relative POSIX path through store_relative_posix_path (which raises if a path escapes the data root), and calls the store’s publish_model_fit.
  • Coordinated directory-model publishers — publish_photo_stack_fit and publish_camera_transform_fit activate the staged filesystem pointer, invoke the directory primitive with an explicit artifact set, roll the pointer and staged directory back if ordinary SQLite publication raises, and garbage-collect the prior run/generation only after both layers succeed. Camera Transform uses the family directory as its registered root and registers the active CURRENT pointer alongside the three generation files; Photo Stack registers the selected run directory.
  • Legacy-spline publish — production fitting uses publish_staged_legacy_spline_fit, which swaps the staged successful-profile subset and pair_corrections.json into place, calls publish_legacy_spline_fit, and restores the old files if ordinary database publication raises. The lower-level publisher records one spline_profile:{fid} artifact per fitted filament plus the shared pair-correction file. publish_legacy_spline_artifact_set is the sibling that republishes current files outside the staged fit path, guarded by profile_file_is_publishable: excluded filaments and profile JSON carrying stale / stale_reason / stale_at are omitted.

All of them converge on the store’s historically named publish_model_fit, which treats a model family as one replaceable current Calibration fit, not a fit-history archive. Before writing, it collects every existing row for the same model_kind. In one SQLite write transaction it inserts the replacement fit, contributors, and artifacts as current, then deletes all prior parent rows; foreign-key cascades remove their contributor and artifact rows. The return payload reports those deleted ids as superseded_model_fit_ids, but there is no durable superseded activation state. model_kind is validated against _MODEL_KINDS = {"camera_transform", "legacy_spline", "photo_stack_v2"}, and current-fit replacement requires at least one contributor.

The SQLite transaction does not include the preceding filesystem or pointer changes. All three publishers compensate for ordinary exceptions, but none has a process-kill journal. A hard stop inside v1’s directory/pair swaps can leave missing or mixed artifacts; a hard stop after v2 latest.json or Camera Transform CURRENT advances can leave pointer-reading consumers on the new files while SQLite still names the old fit. Startup does not complete or reverse these model-publication transitions. Publication readiness detects resulting hash/pointer mismatches; it does not repair them.

stale means something different from superseded. A currently retained fit is marked stale when tracked evidence or fit controls that contributed to it are changed, so its artifacts no longer describe the corpus state from which it was fitted. Adding newly accepted evidence does not retroactively stale an existing fit merely because that sample was not among its recorded contributors. One current exception is review revocation: changing a contributor’s accepted result back to pending removes it from future-fit eligibility but does not stale the existing fit. The ordinary UI has no standalone unaccept action; Reject uses full extraction invalidation. A stale row remains available to status/review code until a successful current-fit replacement deletes it. Startup also calls prune_superseded_model_fits to collapse databases created under the older history-retaining lifecycle to one row per family.

User publication — one-way immutable copy to Generator

The topbar Publish Models workflow is a separate ownership boundary implemented by calibration.model_library_publication, lib.standard_model_library, and lib.model_library_store. It never changes Calibration’s current-fit lifecycle. GET /api/models/publication/readiness verifies that all three required fits are current, their registered artifacts still match their hashes and schemas, the combined contract is consistent, and the public filament catalog is available. A missing, stale, changed, or incomplete component blocks both publication actions. Camera Transform readiness specifically requires the registered and hash-matching camera_transform/CURRENT pointer plus the three registered files in the generation it names.

After the operator supplies the library name, version, and publisher (plus optional description and release notes), the dialog offers two copies of that exact current generation:

  • Export Library Package calls POST /api/models/publication/export and writes a validated ZIP under Calibration/Output/Published Models.
  • Publish to Generator calls POST /api/models/publication/install and installs a new immutable library under Generator’s Model Libraries folder. It is deliberately inactive; the operator uses Model Library → Manage in Generator’s configuration rail and chooses Activate and Restart Prisma.
  • Open Published Models Folder calls the local-only POST /api/models/publication/open-folder.

The allowlisted payload contains the public filament manifest/catalog plus the runtime artifacts for legacy spline v1, Photo Stack v2, and Camera Transform. It does not contain Calibration’s SQLite database, source or extracted images, samples, raw evidence, per-sample calibration predictions, or private notes. Publication stages and validates a copy, then either packages it or lets the Generator library store install it; Calibration does not retain a mutable published-model tree and cannot later modify or activate the installed copy. Generator likewise cannot see or alter Calibration’s working artifacts.

The read side — what the Modeling page renders

calibration.modeling_review is the read half: it never fits anything, it loads Calibration’s current working artifacts and compares them against observed color. It is imported only by calibration.server, which exposes it at /api/models/status and /api/models/review/.... Its six public builders back The Modeling page:

  • build_model_status_payload — per-kind currentness (state, generated_at, stale_reason) via _model_currentness_payload, labeled by MODEL_LABELS: legacy_spline → "Color Model v1", photo_stack_v2 → "Color Model v2", camera_transform → "Camera Transform".
  • build_modeling_overview — inclusion counts (samples/swatches included vs excluded) plus an attention block.
  • list_modeling_samples / get_modeling_sample — the per-sample review, whose _sample_model_detail is the heart of the comparison.
  • list_modeling_filaments / get_modeling_filament — the per-filament view.

_sample_model_detail is where observed and predicted meet. It loads the current Camera Transform as the display transform, then builds two predictions: _photo_stack_model_domains (reads the v2 sample_predictions.json selected by latest.json) and _legacy_spline_model_domains (recomposes v1 on the fly through composition.compose using the sample’s canonical geometry). Both, plus the measured values, are emitted in two domains — transmission (raw linear-to-hex) and appearance (the Camera Transform applied to model predictions) — each with corrected and uncorrected prediction variants. The Camera Transform is not a fourth per-swatch prediction: measured appearance comes directly from the accepted extraction sidecar, while v1 and v2 transmission predictions are transformed for display. If the Camera Transform is missing, predicted appearance is returned unavailable while measured embedded-JPEG appearance can still be present. Because v2 review reads latest.json directly, an interrupted publication can temporarily disagree with SQLite currentness until the working set is repaired. The transform math is The Camera Transform; the modeling surface is The Modeling page.

The sample and filament evidence tables are accepted-only because modeling_review._model_eligible_sample_rows filters rows by has_accepted_extraction. This is explicit on the read side, in addition to the SQLite measurement projection that protects all three production fit adapters.

Shared foundation 1 — the sample→stack bridge

calibration.fitting.physical_stack is the single bridge from a sample record to a canonical bottom-to-top layer stack; its module docstring is explicit that callers “must not reconstruct stack order from legacy fixed/variable convenience fields.” Both v1 and v2 go through it (its Imported by list is fitting and the v2 evidence module).

physical_stack_for_swatch reads sample.roles in canonical role_index order, pulls the one variable role’s thickness from the swatch’s variable series, validates exactly one variable role, and returns a frozen PhysicalStack of RoleLayers. Along the way _model_role_hints assigns each layer a semantic role from physical position: a white below all color is base_white, white above is cap_white, color is color, and a white sandwiched between non-white layers is rejected as ambiguous. physical_stacks_for_sample maps it over every swatch. Two predicates round it out: has_fixed_above_variable and is_legacy_spline_supported_stack (true only when the variable role is physically topmost) — the latter is how v1 decides whether it can interpret a geometry at all. Failures raise PhysicalStackError rather than guessing. The optics of stacking these layers is Color Model v1 / Color Model v2.

Shared foundation 2 — filament role and white classifiers

calibration.fitting.filament_roles supplies the explicit model-white classification used by the color-model fitters:

  • White — model_white_filament_ids returns the set of filaments flagged white_cap_eligible; is_model_white tests membership. This is the set physical_stack’s role-hint logic uses to tell base white from cap white. Crucially, the module also bakes classifier provenance into a color-model fit. filament_role_snapshot captures each filament’s white_cap_eligible and exclude_from_model flags; filament_role_snapshot_hash hashes that snapshot; photo_stack_bundle_classifier_metadata packages the white-classifier schema, version, id list, and snapshot hash into the v2 runtime bundle. require_known_filaments fails loudly if evidence references a filament absent from the library. Camera Transform validation instead groups only by sample and measured transmission.

Shared foundation 3 — per-filament model exclusion

calibration.fitting.filament_exclusions is a small, always-on, stateless dropper: a filament flagged exclude_from_model in the registry is removed from every production fit. It is imported by all three fit paths (v1 fitting, v2 evidence, CT corpus).

The precise semantic is the load-bearing part. excluded_filament_ids reads the flagged ids from the registry. sample_references_excluded_filament drops a sample if the excluded filament appears in ANY role — variable or fixed backing — via _sample_filament_ids, which walks the canonical sample.roles table and returns every referenced filament id, not just the characterized (variable) one. So excluding a white backing filament removes not only its own solo strips but every overlay sample that stacks on top of it. samples_excluded_by_filament precomputes that whole-corpus set of dropped samples; only the v1 spline fit unions it in directly. The v2 Photo Stack evidence builder and live Camera Transform corpus instead read excluded_filament_ids and apply the same rule per sample — row by row rather than from the precomputed set.

This is distinct from the per-run fit_exclude / fit_state toggles (which are UI-gated on use_fit_exclusions): exclude_from_model is a permanent property of the filament, ungated, replacing the old hardwired SKIP constant. Where the flag is set and what it means operationally is Managing filaments.
