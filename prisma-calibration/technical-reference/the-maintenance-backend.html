The maintenance backend

The maintenance backend

Properties1
tagscalibration, maintenance

Jul 14, 202612 min read

In one sentence: every standard maintenance chore is one frozen MaintenanceOperation (calibration.maintenance, maintenance.py:310) in a single OPERATIONS registry, run through a uniform preflight → execute → JSON report lifecycle where each operation declares a structured frontend-refresh impact; the heaviest operation, Re-extract Sample Images, is registered as preflight-only and uses a separate staged, non-destructive backend (calibration.maintenance_reextract) that builds a candidate set the operator reviews sample-by-sample before anything overwrites accepted data.

This page maps the framework: how an operation is defined and registered, the lifecycle that runs it, the refresh impact it reports, and the staged re-extraction candidate store. It deliberately does not explain what each operation means or when to run it — for that, see Maintenance Operations (the mechanism, per operation) and Running maintenance (the operator surface). The one-operation-at-a-time run lock lives in the server, not here (see Web API and job orchestration); the Fit Models operation delegates to the model workflow (Model workflow, publication, and review); and re-extraction commits write through the stores in Data access and persistence.

Related: calibration.maintenance · calibration.maintenance_reextract · Maintenance Operations · Running maintenance · Web API and job orchestration

An operation is a frozen dataclass in one registry

MaintenanceOperation (maintenance.py:310) is a frozen dataclass — the whole definition of one chore. Its fields:

  • Identity and display — operation_id, name, category (e.g. "Audit", "Images", "System Maintenance", "Geometry Artifacts", "Calibration Models"), description.
  • Risk and modes — risk_class (e.g. "read_only", "cleanup", "writes_derived_files", "writes_user_output", "changes_semantic_data"), a tuple of allowed modes and a default_mode, and a writes flag.
  • Concurrency metadata — resource_claims describes everything the operation reads or writes (for example "sqlite_semantic_state", "preview_cache", and "geometry_artifacts"). conflict_resources is the smaller, enforced set of ordinary-writer categories that must remain stable while the operation is queued or running. Both are exposed by public_dict; the server uses the latter at its shared maintenance resource gate.
  • Cancellation metadata — cancellation_policy is either "safe_points" or "not_supported"; the derived cancellable boolean is exposed to the frontend. Public job state also includes dynamic cancel_available, which becomes false after the request is accepted or the job reaches a terminal state.
  • Availability — enabled plus an unavailable_reason string for operations that are registered but not runnable.
  • Behavior — two callables, preflight and execute (maintenance.py:323-324), each Callable[..., dict] | None.

public_dict serializes everything except the two callables — that dict is what the API hands the frontend. All operations live in one module-level OPERATIONS: dict[str, MaintenanceOperation]; list_operations returns their public dicts and get_operation looks one up by id (raising KeyError on an unknown id). The registry spans audits, image/artifact rebuilds, a read-only SQLite integrity check, geometry export, model fitting, and re-extraction.

The two resource lists intentionally differ. A filesystem audit may read SQLite to discover ownership without needing to freeze every unrelated database-backed edit, while an integrity operation can require a stable database snapshot by declaring the enforced sqlite_write conflict. Image custody/preview, extraction evidence/sample visuals, geometry state, and model evidence/artifacts have their own conflict categories. Ordinary browsing remains available, except that source and blank preview GET routes acquire a preview_cache writer lease when they may generate a missing JPEG on demand.

The preflight → execute → report lifecycle

Two module functions drive every operation uniformly:

  • preflight_operation (maintenance.py:353) resolves the mode (defaulting to default_mode), rejects a mode not in operation.modes with ValueError, and short-circuits a disabled operation into a synthetic blocked result carrying its unavailable_reason (:364-380). Otherwise it calls operation.preflight(store, mode, scope). Preflight is read-only: it computes the target set and any blockers so the operator can confirm before writes happen.
  • execute_operation (maintenance.py:386) re-validates mode and enablement, then introspects the execute function’s signature with inspect.signature and passes through only the optional kwargs it accepts — preflight, confirmation, job_id — alongside the always-present progress_cb and should_cancel (:406-421). This is how one caller drives execute functions with different signatures. After the operation returns its report dict, it writes it to disk via report_path_for + _atomic_write_json and stamps report_path onto the returned payload (:423-425).

Reports are canonical JSON. _report (maintenance.py:232) builds the "prisma-maintenance-report-v1" schema: operation_id, mode, scope, status, timestamps, a summary dict, findings, changed_paths, blocked, warnings, errors, and the ui_refresh impact (:249-264). Findings are built by _finding (:201) with a severity/category/target/message shape and tallied by _count_findings (:218). Reports land in reports_dir(store) = <project>/output/maintenance/reports/, named {timestamp}_{operation_id}_{job_id[:12]}.json (report_path_for, :98); the same maintenance root holds a .tmp scratch dir (temp_dir, :90) and a quarantine dir (:94). startup_scan_interrupted_temp (:3008) reports leftover temp entries from an interrupted run so the server can surface them at boot.

Quarantine Orphaned Artifacts has a deliberately narrow destructive boundary. It can move only direct preview JPEGs whose exact filenames are not expected by a current image/blank record, strictly named interrupted publication files directly inside a sample-thumbnail directory, direct sample-thumbnail directories with no matching sample, direct managed geometry-artifact directories with no matching geometry, and 64-hex fingerprint directories that are direct children of a live geometry but are not its recomputed current fingerprint. Preview ownership is computed once after the operation has reserved preview_cache; this avoids re-listing every image and blank for every orphan while keeping ownership stable through the run. Geometry fingerprints and live-row ownership are still revalidated per target, so a fingerprint that becomes current is skipped. Source photographs, blank source files, SQLite, models, backups, RAW archives, public geometry exports, and reports are not eligible. Quarantine is only a seven-day filesystem safety buffer: prune_quarantine_runs deletes expired Prisma-named runs during startup/activity housekeeping, while malformed entries and anything containing a filesystem link are skipped and reported.

Source preview cache stems come from a SHA-256 digest of stable image_asset_id (source_preview_cache_stem in processing/extraction.py), with the rotation suffix added afterward. The filename fallback exists for the legacy backend. Consequently, same-stem files with different extensions and filenames containing cache-like __rN text cannot share a SQLite source-preview key. Older filename-derived JPEGs have no current owner: the missing-preview audit requests regeneration under the current key and the orphan audit can quarantine the old cache files.

Preview publication is pair-safe within a running process. generate_preview_jpeg encodes and verifies both same-directory staged JPEGs before publish_staged_files replaces either live file. The publisher copies existing targets to rollback siblings, promotes with os.replace, and restores already-promoted targets if a later promotion fails; a rollback failure preserves and reports its recovery copy. Rebuild Extraction Images Only similarly stages all requested source.jpg/strip.jpg replacements for one sample and promotes that sample’s set together. Cancellation or one renderer failure removes the staged set and leaves that sample’s previous live images unchanged. A process crash can leave a strictly named stage/rollback JPEG; preview-root leftovers are ordinary orphan previews, while thumbnail-root leftovers have their own narrow quarantine category.

Progress and cancellation are cooperative only for operations registered with the "safe_points" policy: execute functions call _progress (:184) to emit phase/current/total updates and _cancelled (:197) to poll the should_cancel check, returning a status of "cancelled" when interrupted. The job API changes accepted requests to "cancelling", preserves its resource reservation, and reports terminal cancellation only after the executor returns. Repeated requests while cancelling are idempotent; unsupported and terminal requests receive HTTP 409. Library Integrity, SQLite Integrity, and Fit Models are registered as "not_supported" and run to completion once started.

The frontend-refresh impact

Every operation reports what the UI must invalidate after it runs, so the frontend re-fetches exactly what changed instead of a blanket reload. The vocabulary is fixed by ui_refresh_none (maintenance.py:128), the canonical empty impact:

  • a kind of "none", "targeted", or "full";
  • four coarse booleans — reload_app_data, reload_import_data, rerender_workspace, rerender_open_drawers;
  • four fine-grained invalidation sets — invalidate_preview_cache (by filename / blank id), invalidate_sample_thumbnails (by sample id / kind), invalidate_geometry_artifacts (by geometry id), and invalidate_model_artifacts (by filament id / model type), each with an all flag; plus a display message.

An audit reports ui_refresh_none — it changed nothing. A write operation reports a targeted impact naming exactly what it touched: for example _execute_rebuild_image_previews reports kind: "targeted" with reload_import_data, rerender_workspace, rerender_open_drawers, and the rebuilt filenames/blank ids in invalidate_preview_cache (maintenance.py:1093-1104). merge_ui_refresh (:155) combines impacts when an operation aggregates sub-steps — booleans OR together, the list-valued invalidation sets union (deduped by _merge_unique, :143), and kind escalates toward full.

Two operations that delegate outward

Most operations implement their own preflight/execute in maintenance.py. Two hand off:

  • Fit Models (refit_calibration_models, maintenance.py:2974) is the maintenance entry to the whole calibration-model pipeline. Its executor _execute_refit_calibration_models (:2793) converts scope to options with options_from_scope and calls execute_model_fit_workflow (from calibration.fitting.model_fit_workflow), then wraps that workflow’s status/findings/ui_refresh back into a maintenance report (:2806-2832). The physics and publication of that fit belong to Model workflow, publication, and review.
  • Re-extract Sample Images (maintenance.py:2993) is registered with only a preflight (_preflight_reextract_sample_images_operation, no execute). Its multi-phase generate/review/apply lifecycle is too large for the single-shot execute contract and lives entirely in maintenance_reextract.py, orchestrated by the server (see Web API and job orchestration).

Staged re-extraction — a non-destructive candidate store

calibration.maintenance_reextract (maintenance_reextract.py, “Staged candidate storage and sample-image re-extraction workflows”) re-runs image extraction for already-accepted samples without touching live data until the operator explicitly commits. The whole design is a stage-then-review-then-apply cycle keyed on a candidate set.

Scope options

_normalize_scope (maintenance_reextract.py:355) defines three independent scope axes, and _mode_supported (:387) is the gate on their combinations:

  • domain_mode — "complete", "transmission_only", or "appearance_only": which parts of the extraction result get regenerated.
  • segmentation_mode — "existing_coordinates" (replay extraction at the sample’s stored swatch coordinates) or "redetect_from_scratch" (re-run detection; only valid with complete).
  • sample_scope — {"kind": "all_accepted"} or {"kind": "sample_ids", ...} for an explicit list.

The candidate store

Staged artifacts live under reextract_root(store) = <store.root>/maintenance/reextract_sample_images/, one directory per id-validated rext_<32 hex> candidate set. create_candidate_set writes a ReextractManifest containing schema version, scope (workflow_options), plan_digest, per-status counts, sample ids, and generation/apply report ids. Each ReextractCandidatePayload records its status, source/blank fingerprints, the current extraction_result_id it was staged against, the replacement result when applicable, and staged source/blank/strip/transmission/appearance JPEGs. Statuses include ready_changed, ready_unchanged, manual_required, failed, blocked, stale, applied, and rejected_in_candidate_set. Creating a new set supersedes older sets; prune_candidate_sets retains at most the newest recoverable set for seven days and removes older validly named sets. Candidate paths and cleanup refuse linked ancestors and linked contents.

Generation is a family of functions: preflight_reextract_sample_images (:1009) plans the target rows and blockers; generate_reextract_candidates (:2286) is the main producer; generate_appearance_existing_coordinate_candidates (:1631) is the appearance-only path; generate_manual_candidate (:2143) handles operator-guided re-detection; retry_candidate (:2785) re-runs a single failed one.

Per-sample save/skip review

A candidate carries a separate ReextractReviewPayload (:496) holding the operator’s decision — one of pending, save, skip (STAGED_REVIEW_DECISIONS, :102). update_candidate_review (:2665) sets one sample’s decision and update_candidate_reviews_bulk (:2701) sets many; both refuse to mark a candidate save/skip unless its status is a ready one (READY_CANDIDATE_STATUSES, :101). A candidate with nothing to change defaults to pending; a non-ready one defaults to skip (_default_review_decision, :536).

Non-destructive commit — save vs discard

apply_reextract_candidates (:3348) is the only step that writes to live data, and it is deliberately paranoid:

  • Appearance-only sets delegate to apply_appearance_candidates (:3097); the transmission/complete path requires the SQLite backend (:3373).
  • It applies only the sample ids the operator marked save (_saved_sample_ids_from_reviews, :3376); everything else is skipped.
  • For each saved sample it re-verifies staleness before writing — the current accepted extraction still exists and its extraction_result_id still matches what the candidate was staged against, the source/blank files still match (_candidate_sources_still_match), and the stored semantic digest is unchanged. Any mismatch flips the candidate to stale and skips it rather than overwriting drifted data (:3449-3492).
  • Only a surviving ready_changed candidate calls store.replace_accepted_extraction_result (:3537), which swaps the accepted extraction and returns the dependent model fits it just marked stale (stale_model_fit_ids); a ready_unchanged candidate rewrites live visual artifacts only. The candidate is then stamped applied (:3576).
  • Appearance-only apply can persist changed decoder provenance while remaining applied_unchanged: SQLiteDataStore.update_extraction_result_appearance distinguishes any persisted metadata change from model_inputs_changed. Decoder-version metadata alone does not alter Camera Transform’s corpus and therefore does not stale the current fit.

Because staging, review, and apply are separate steps, an operator can generate a whole set, inspect each sample, and discard it entirely with delete_candidate_set (:2918) — the accepted corpus is never modified unless apply runs and a candidate clears every freshness check. The commit itself flows through the SQLite store (see Data access and persistence); the run lock that keeps only one maintenance job (this or any other) in flight at a time is held in the server (Web API and job orchestration).
