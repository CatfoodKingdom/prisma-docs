The maintenance backend

The maintenance backend

Properties1
tagscalibration, maintenance

Jul 26, 202614 min read

In one sentence: every standard maintenance chore is one frozen MaintenanceOperation in calibration.maintenance’s single OPERATIONS registry, run through a uniform preflight → execute → JSON report lifecycle whose report carries a structured frontend-refresh impact; the heaviest operation, Re-extract Sample Images, is registered as preflight-only and uses a separate staged backend (calibration.maintenance_reextract) that builds a candidate set the operator reviews sample-by-sample before anything overwrites accepted data.

This page maps the framework: how an operation is defined and registered, the lifecycle that runs it, the refresh impact it reports, and the staged re-extraction candidate store. It deliberately does not explain what each operation means or when to run it — for that, see Maintenance Operations (the mechanism, per operation) and Running maintenance (the operator surface). The one-operation-at-a-time run lock lives in the server, not here (see Web API and job orchestration); the Fit Models operation delegates to the model workflow (Model workflow, publication, and review); and re-extraction commits write through the stores in Data access and persistence.

Related: calibration.maintenance · calibration.maintenance_reextract · Maintenance Operations · Running maintenance · Web API and job orchestration

An operation is a frozen dataclass in one registry

MaintenanceOperation is a frozen dataclass — the whole definition of one chore. Its fields:

  • Identity and display — operation_id, name, category (e.g. "Audit", "Images", "System Maintenance", "Geometry Artifacts", "Calibration Models"), description.
  • Risk and modes — risk_class (e.g. "read_only", "cleanup", "writes_derived_files", "writes_user_output", "changes_semantic_data"), a tuple of allowed modes and a default_mode, and a writes flag.
  • Concurrency metadata — resource_claims describes everything the operation reads or writes (for example "sqlite_semantic_state", "preview_cache", and "geometry_artifacts"). conflict_resources is the smaller, enforced set of ordinary-writer categories that must remain stable while the operation is queued or running. Both are exposed by public_dict; the server uses the latter at its shared maintenance resource gate.
  • Cancellation metadata — cancellation_policy is either "safe_points" or "not_supported"; the derived cancellable boolean is exposed to the frontend. Public job state also includes dynamic cancel_available, which becomes false after a cancellation request is accepted or the job reaches a terminal state.
  • Availability — enabled plus an unavailable_reason string for operations that are registered but not runnable.
  • Behavior — two Callable[..., dict] | None callables, preflight and execute.

public_dict serializes everything except the two callables — that dict is what the API hands the frontend. All operations live in one module-level OPERATIONS: dict[str, MaintenanceOperation]; list_operations returns their public dicts and get_operation looks one up by id (raising KeyError on an unknown id). The registry spans audits, image/artifact rebuilds, a read-only SQLite integrity check, geometry export, model fitting, and re-extraction.

The two resource lists intentionally differ. A filesystem audit may read SQLite to discover ownership without needing to freeze every unrelated database-backed edit, while an integrity operation can require a stable database snapshot by declaring the enforced sqlite_write conflict. Image custody/preview, extraction evidence/sample visuals, geometry state, and model evidence/artifacts have their own conflict categories. Ordinary browsing remains available, except that source and blank preview GET routes acquire a preview_cache writer lease when they may generate a missing JPEG on demand.

The preflight → execute → report lifecycle

Two module functions drive every operation uniformly:

  • preflight_operation resolves the mode (defaulting to default_mode), rejects a mode not in operation.modes with ValueError, and short-circuits a disabled operation into a synthetic blocked result carrying its unavailable_reason. Otherwise it calls operation.preflight(store, mode, scope). Preflight is read-only: it computes the target set and blockers so the operator can confirm before writes happen.
  • execute_operation re-validates mode and enablement, then introspects the execute function’s signature with inspect.signature and passes through only the optional kwargs it accepts — preflight, confirmation, job_id — alongside the always-present progress_cb and should_cancel. This is how one caller drives execute functions with different signatures. After the operation returns its report dict, it writes it to disk via report_path_for + _atomic_write_json and stamps report_path onto the returned payload.

Reports are canonical JSON. _report builds the "prisma-maintenance-report-v1" schema: operation_id, mode, scope, status, timestamps, a summary dict, findings, changed_paths, blocked, warnings, errors, and the ui_refresh impact. Findings are built by _finding with a severity/category/target/message shape and tallied by _count_findings. Reports land in reports_dir(store) = <app-managed-root>/output/maintenance/reports/, named {timestamp}_{operation_id}_{job_id[:12]}.json; the same maintenance root holds a .tmp scratch dir (temp_dir) and a quarantine dir (quarantine_dir). startup_scan_interrupted_temp lists leftover temp entries from an interrupted run so _run_post_store_startup_checks can report them to the console at boot.

Quarantine Orphaned Artifacts has a deliberately narrow destructive boundary. It can move only direct preview JPEGs whose exact filenames are not expected by a current image/blank record, strictly named interrupted publication files directly inside a sample-thumbnail directory, direct sample-thumbnail directories with no matching sample, direct managed geometry-artifact directories with no matching geometry, and 64-hex fingerprint directories that are direct children of a live geometry but are not its recomputed current fingerprint. Preview ownership is computed once after the operation has reserved preview_cache; this avoids re-listing every image and blank for every orphan while keeping ownership stable through the run. Geometry fingerprints and live-row ownership are still revalidated per target, so a fingerprint that becomes current is skipped. Source photographs, blank source files, SQLite, models, backups, RAW archives, public geometry exports, and reports are not eligible. Quarantine is only a seven-day filesystem safety buffer: prune_quarantine_runs deletes expired Prisma-named runs during startup/activity housekeeping, while malformed entries and anything containing a filesystem link are skipped and reported.

Source preview cache stems come from a SHA-256 digest of stable image_asset_id (source_preview_cache_stem in processing/extraction.py), with the rotation suffix added afterward. The filename fallback exists for the legacy backend. Consequently, same-stem files with different extensions and filenames containing cache-like __rN text cannot share a SQLite source-preview key. Older filename-derived JPEGs have no current owner: the missing-preview audit requests regeneration under the current key and the orphan audit can quarantine the old cache files.

Preview publication is pair-safe against ordinary in-process exceptions. generate_preview_jpeg encodes and verifies both same-directory staged JPEGs before publish_staged_files replaces either live file. The publisher copies existing targets to rollback siblings, promotes with os.replace, and restores already-promoted targets if a later promotion raises; a rollback failure preserves and reports its recovery copy. Rebuild Extraction Images Only similarly stages all requested source.jpg/strip.jpg replacements for one sample and promotes that sample’s set together. Cancellation or one renderer failure before/during the guarded call removes or rolls back the staged set.

That multi-file helper has no process-kill journal. A hard stop between two os.replace calls can leave one live JPEG new and its sibling old, with stage/rollback files beside them. Startup does not choose a recovery copy or restore the pair; the orphan/quarantine tools can identify or move the strictly named leftovers but do not repair the mixed live set. Re-run the appropriate rebuild after an abnormal stop and verify the previews/visuals before discarding recovery files.

Progress and cancellation are cooperative only for operations registered with the "safe_points" policy: execute functions call _progress to emit phase/current/total updates and _cancelled to poll the should_cancel check, returning a status of "cancelled" when interrupted. The job API changes accepted requests to "cancelling", preserves its resource reservation, and reports terminal cancellation only after the executor returns. Repeated requests while cancelling are idempotent; unsupported and terminal requests receive HTTP 409 from cancel_maintenance_job. Audit Library Integrity, SQLite Integrity Check, and Fit Models are registered as "not_supported" and run to completion once started.

"safe_points" means stop between operation-defined units, not generic rollback. Work completed before the safe point remains completed: already-moved quarantine targets stay quarantined, already-published preview or sample-visual units stay published, and already-written geometry outputs remain. The preview and sample-visual publishers protect each current unit with staging/rollback, but the framework does not reverse earlier units when a later cancellation is observed.

The frontend-refresh impact

Every operation report describes what the UI must invalidate after it runs. The vocabulary is fixed by ui_refresh_none, the canonical empty impact:

  • a kind of "none", "targeted", or "full";
  • four coarse booleans — reload_app_data, reload_import_data, rerender_workspace, rerender_open_drawers;
  • four fine-grained invalidation sets — invalidate_preview_cache (by filename / blank id), invalidate_sample_thumbnails (by sample id / kind), invalidate_geometry_artifacts (by geometry id), and invalidate_model_artifacts (by filament id / model type), each with an all flag; plus a display message.

An audit reports ui_refresh_none — it changed nothing. A write operation reports a targeted impact naming what it touched: for example _execute_rebuild_image_previews includes reload_import_data, rerender_workspace, rerender_open_drawers, and the rebuilt filenames/blank ids in invalidate_preview_cache. merge_ui_refresh combines impacts when an operation aggregates sub-steps — booleans OR together, the list-valued invalidation sets union (deduped by _merge_unique), and kind escalates toward full.

The current frontend consumes this impact automatically only in the standard job’s succeeded branch in showMaintenanceWorkflow/applyMaintenanceRefreshImpact. A safely cancelled write report may therefore describe completed partial changes without automatically refreshing the rest of the open application; a manual Refresh Data reconciles that display. This is a frontend follow-up, not a stronger rollback guarantee from the backend.

Two operations that delegate outward

Most operations implement their own preflight/execute in maintenance.py. Two hand off:

  • Fit Models (refit_calibration_models) is the maintenance entry to the whole calibration-model pipeline. Its executor _execute_refit_calibration_models converts scope to options with options_from_scope and calls execute_model_fit_workflow (from calibration.fitting.model_fit_workflow), then wraps that workflow’s status, findings, partial-publication metadata, and ui_refresh into a maintenance report. The physics and publication of that fit belong to Model workflow, publication, and review.
  • Re-extract Sample Images is registered with only _preflight_reextract_sample_images_operation and no execute. Its multi-phase preflight/generate/review/apply lifecycle is handled by dedicated job registries and routes in the server rather than the single-shot execute contract (see Web API and job orchestration).

Staged re-extraction — a non-destructive candidate store

calibration.maintenance_reextract (maintenance_reextract.py, “Staged candidate storage and sample-image re-extraction workflows”) re-runs image extraction for already-accepted samples without touching live data until the operator explicitly commits. The whole design is a stage-then-review-then-apply cycle keyed on a candidate set.

Scope options

_normalize_scope defines three independent scope axes, and _mode_supported is the gate on their combinations:

  • domain_mode — "complete", "transmission_only", or "appearance_only": which parts of the extraction result get regenerated.
  • segmentation_mode — "existing_coordinates" (replay extraction at the sample’s stored swatch coordinates) or "redetect_from_scratch" (re-run detection; only valid with complete).
  • sample_scope — {"kind": "all_accepted"} or {"kind": "sample_ids", ...} for an explicit list.

The candidate store

Staged artifacts live under reextract_root(store) = <store.root>/maintenance/reextract_sample_images/, one directory per id-validated rext_<32 hex> candidate set. create_candidate_set writes a ReextractManifest containing schema version, scope (workflow_options), plan_digest, per-status counts, sample ids, and generation/apply report ids. Each ReextractCandidatePayload records its status, source/blank fingerprints, the current extraction_result_id it was staged against, the replacement result when applicable, and staged source/blank/strip/transmission/appearance JPEGs. Statuses include ready_changed, ready_unchanged, manual_required, failed, blocked, stale, applied, and rejected_in_candidate_set. Creating a new set prunes older sets; prune_candidate_sets retains at most the explicitly preserved set or, during ordinary housekeeping, the newest recoverable set no older than seven days, and removes other validly named sets. Candidate paths and cleanup use root-confined path validation and safe recursive deletion; link-like candidate entries are skipped or refused.

Generation is a family of functions: preflight_reextract_sample_images plans the target rows and blockers; generate_reextract_candidates is the main producer; generate_appearance_existing_coordinate_candidates is the appearance-only path; generate_manual_candidate handles operator-guided re-detection; retry_candidate re-runs one member of a non-appearance set. The current UI exposes Retry for failed or stale candidates, although the backend helper itself does not enforce that status restriction; appearance-only retry is not implemented and requires a fresh set.

Generation cancellation never commits accepted extraction data. It leaves the candidate-set manifest as cancelled/incomplete and retains whatever staged candidates were completed so the set can be inspected, retried, or discarded. Candidate images are written before the final candidate JSON; a cancellation or hard stop in that narrow interval can therefore leave an incomplete staged row, or on Retry/Manual Corners leave older candidate metadata beside newly written staged images. That inconsistency is confined to the candidate store, not the accepted corpus.

Per-sample save/skip review

A candidate carries a separate ReextractReviewPayload holding the operator’s decision — one of pending, save, skip (STAGED_REVIEW_DECISIONS). update_candidate_review sets one sample’s decision and rejects changes to a non-ready candidate; update_candidate_reviews_bulk changes ready candidates and counts non-ready rows as skipped. A candidate with nothing to change still has ready status and defaults to pending; a non-ready one defaults to skip (_default_review_decision). Apply is blocked until manual or incomplete rows are resolved, every ready candidate is explicitly Save or Skip, and at least one is marked Save (_saved_sample_ids_from_reviews).

Non-destructive commit — save vs discard

apply_reextract_candidates is the only step that writes to live accepted data, and it is deliberately paranoid:

  • Appearance-only sets delegate to apply_appearance_candidates; both paths require the SQLite backend.
  • It applies only the sample ids the operator marked save (_saved_sample_ids_from_reviews); ready candidates marked Skip are counted and left untouched.
  • The complete/transmission path re-verifies staleness before writing — the current accepted extraction still exists and its extraction_result_id still matches what the candidate was staged against, the source/blank files still match (_candidate_sources_still_match), and the stored semantic digest is unchanged. Any mismatch flips the candidate to stale and skips it rather than overwriting drifted data.
  • Only a surviving ready_changed candidate’s semantic callback calls store.replace_accepted_extraction_result, which swaps the accepted extraction and returns the dependent model fits it just marked stale (stale_model_fit_ids); a ready_unchanged candidate keeps the same extraction id and republishes the live source/strip visuals.
  • Appearance-only apply checks that the accepted extraction id and source-image identity still match, then calls SQLiteDataStore.update_extraction_result_appearance. It does not currently compare the staged old_appearance_digest before writing. The store distinguishes any persisted metadata change from model_inputs_changed, so decoder-version metadata alone does not alter Camera Transform’s corpus or stale the current fit; such a result is counted as applied_unchanged.

Complete/transmission publication is process-kill recoverable per sample. publish_extraction_update in processing.extraction_publication journals the semantic and visual publication unit, and complete_reextract_publication makes candidate/review state converge after the live extraction is committed. Startup calls reconcile_publications before candidate pruning and defers pruning when recovery is ambiguous. Appearance-only apply does not use this publication journal: its SQLite update and later candidate-status write are separate operations, so a hard stop between them can leave live appearance data newer than the staged candidate metadata. A clean completed apply deletes its candidate set; partial, cancelled, or failed sets remain for review or another apply (_finalize_apply_report).

Cancellation is checked between samples and immediately before the short non-interruptible per-sample publication unit. Samples already published stay applied; unprocessed saved candidates remain staged, and the manifest/report records cancellation so apply can be run again. The dedicated frontend reloads the candidate-set review after a cancelled apply but currently performs the full application refresh only after succeeded, so other open Calibration surfaces can require Refresh Data to reflect already-applied samples.

Because staging, review, and apply are separate steps, an operator can generate a whole set, inspect each sample, and discard it entirely with delete_candidate_set — the accepted corpus is never modified unless apply runs and a candidate clears every freshness check. The commit itself flows through the SQLite store (see Data access and persistence); the run lock that keeps only one standard maintenance or dedicated re-extraction job in flight at a time is held in the server (Web API and job orchestration).
