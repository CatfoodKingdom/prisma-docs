The white cap

In one sentence: the white cap is the clear/white skin laid on top of the solved colour stack, and its per-pixel thickness is whatever height is left under the t_max total-height contract — optionally biased toward the source image’s dark regions by a default-off luminance prior.

The colour stack the solver picks decides each pixel’s colour ceiling (white base + committed colour layers). The white cap is everything above that ceiling, up to the total object height. This page covers how that cap thickness is determined: the colour ceiling, the budget contract, the optional luminance prior, the boundary-vs-detail split, the post-solve detail smoothing, and the (currently inert) luminance tie-break.

Related: The live staged printability diagnostic owns material_exposure and the live printability fields — it does not use the cap-ceiling helpers below. The dormant Blueprint triage the unwired engine is the only consumer of colour_ceiling_from_plan / top_surface_from_fields. generator.height_budget, generator.luminance_handler, generator.detail_cap_smoothing, generator.cap_quality are the modules described here.

The colour ceiling

Every pixel sits under a colour ceiling = white base thickness plus the total committed colour thickness of its solved stack. colour_ceiling_from_plan builds this from the solved plan: it maps each pixel to its committed stack via committed_stack_label_map(plan) and adds d_wb to that stack’s total_colour_thickness_mm (pipeline/cap_quality.py:58, summed at pipeline/cap_quality.py:61-67). Pixels with no colour stack get a ceiling of just d_wb (pipeline/cap_quality.py:66).

This function is computed-but-unwired: its only product caller is the dormant blueprint-triage engine at pipeline/blueprint_triage/fields.py:146, which also composes the top surface with top_surface_from_fields (pipeline/blueprint_triage/fields.py:147; the composer itself is colour ceiling + visible cap at pipeline/cap_quality.py:70-78). No live solve or export path constructs an AnalysisContext or calls analyze_triage, so neither helper actually runs in production today — see Blueprint triage the unwired engine. Do not confuse this with the genuinely-live printability diagnostic in pipeline/staged_printability.py, which builds its own layered view and never touches these two helpers.

The total-height budget contract

t_max is the total object height, white base included. The only headroom the white cap may occupy is whatever is left above the colour ceiling. generator.height_budget is the whole policy:

HelperContractAnchor
max_cap_height_for_colour_thicknessscalar headroom = t_max - d_wb - colour_thickness, optionally clamped by a max-cap ceiling, floored at 0pipeline/height_budget.py:12, computed :20-23
max_cap_height_map_for_colour_ceilingper-pixel headroom = t_max - colour_ceiling, optional d_wc_max clamp, floored at 0pipeline/height_budget.py:26, :34-37
clamp_cap_height_map_to_budgetclamp any cap map so total height never exceeds t_maxpipeline/height_budget.py:40, :48-54

The scalar form is live in the solve: Stage 2 cap precompute calls max_cap_height_for_colour_thickness per unique stack to find the printable cap range, then marks over-budget cap steps as inf so the optimizer can’t pick them (pipeline/staged_solver_helpers.py:116, masked at pipeline/staged_solver_helpers.py:125). Note that call passes d_wc_max_mm=cfg.effective_boundary_d_wc_max() (pipeline/staged_solver_helpers.py:120) — the boundary ceiling, not the full one.

What sets the cap maximum

Three config accessors define the ceilings (defaults in pipeline/state.py):

  • effective_d_wc_max() — explicit d_wc_max if set, else t_max - d_wb - d_wc_min (pipeline/state.py:190-193).
  • effective_boundary_d_wc_max() — the full max, then clamped down by (a) the runtime luminance boundary authority if one was computed and (b) an explicit boundary_cap_authority_mm, always floored at d_wc_min (pipeline/state.py:195-202).
  • effective_white_cap() — the cap filament; falls back to the white base when white_cap is unset (pipeline/state.py:180-181).

Relevant defaults: d_wb=0.20, d_wc_min=0.08, t_max=3.0, layer_height=0.08 (pipeline/state.py:66,67,70,64).

The default-off source-luminance prior

generator.luminance_handler gives the cap an optional bias toward darker source regions (a thicker cap dims the backlight, so dark image areas request more white). It is default-off: gated by luminance_handler_enabled reading cfg.luminance_handler_enabled (pipeline/luminance_handler.py:47-49), whose default is False (pipeline/state.py:82).

It is wired into the live solve when enabled. Two entry points:

  1. Before LUT building, configure_luminance_handler_runtime computes a reference and stashes the boundary authority on the config so effective_boundary_d_wc_max can clamp to it (pipeline/luminance_handler.py:527, authority set at pipeline/luminance_handler.py:552). Returns None early if disabled or if state lacks profiles/target (pipeline/luminance_handler.py:535-541).
  2. In Stage 4, the staged runner calls LuminanceHandler(cfg, state.profiles).build(...) to get boundary and detail cap references (pipeline/staged_runner.py:8834, gated by luminance_handler_enabled(cfg) at :8833). When disabled, Stage 4 falls back to quantizing the raw solver-implied cap directly (pipeline/staged_runner.py:8864-8876).

How the prior is built (LuminanceHandler.build_reference, pipeline/luminance_handler.py:160):

  • Source luminance is the OKLab L of the solve target (pipeline/luminance_handler.py:175).
  • It samples the white-base × white-cap appearance curve over the printable cap-step range (pipeline/luminance_handler.py:385; photo-stack provider path at :399, historical-spline fallback at :405-412).
  • Mode boundary_prior (the default, pipeline/state.py:83) maps source darkness into a cap-mm request: floor + darkness × (available range) (full-image at pipeline/luminance_handler.py:213-216, boundary at :217-220). Mode absolute_optical instead interpolates the appearance curve directly (pipeline/luminance_handler.py:187-208).
  • “Darkness” is a percentile-normalised, optionally toe/shoulder-shaped inverse of luminance (_darkness_map pipeline/luminance_handler.py:470; response curves linear/smoothstep/smootherstep/gamma/sqrt at pipeline/luminance_handler.py:506-522).
  • Every cap map is layer-quantized and clamped to [floor, d_wc_max] via _quantize_cap_map (pipeline/luminance_handler.py:107); the floor is the smallest layer-grid multiple ≥ d_wc_min (_quantized_cap_floor, pipeline/luminance_handler.py:99).

Boundary authority

The handler also derives a single boundary authority (mm) — a ceiling on how thick the boundary cap may go. It is the smaller of an optical authority (the cap thickness reaching a configured fraction, default 0.75, of the achievable OKLab swing — _optical_authority pipeline/luminance_handler.py:444; fraction default pipeline/state.py:85) and, in absolute_optical mode, a percentile of the boundary prior (_boundary_authority pipeline/luminance_handler.py:432). An explicit boundary_cap_authority_mm clamps it further (pipeline/luminance_handler.py:240-248). This authority is what feeds back into effective_boundary_d_wc_max (above).

Boundary cap vs detail cap

LuminanceHandler.build emits two references that Stage 4 consumes (pipeline/luminance_handler.py:289):

TierMeaningBuilt at
boundary_cap_request_mmthe smooth cap thickness at segment boundaries, ceilinged by the boundary authoritypipeline/luminance_handler.py:310-332
detail_cap_reference_mmthe per-pixel detail cap, ≥ boundary request, ceilinged by the full d_wc_max and never exceeding remaining t_max headroompipeline/luminance_handler.py:334-354

Three blend modes set the boundary request: blend_solver (alpha-blend raw vs prior), boundary_ceiling (min of raw and a blended ceiling), and the default else-branch (floor + strength × (prior − floor)) at pipeline/luminance_handler.py:311-326. The detail reference defends the t_max contract directly: it subtracts the colour ceiling from t_max and clips against that remaining budget before quantizing (remaining at pipeline/luminance_handler.py:341-345, then np.minimum at :345). Stage 4 reads both back out at pipeline/staged_runner.py:8840-8841.

Detail-cap smoothing (post-solve)

generator.detail_cap_smoothing is a live post-solve cleanup that removes single-pixel topographic noise from the detail cap only — it never touches colour maps, boundary cap, or stack topology. It runs from server.py:

  • Entry: _apply_detail_cap_smoothing_to_result (server.py:1327), invoked on every solve result at server.py:4743.
  • Gated to luminance-detail mode and the two enable flags: luminance_mode == "luminance_detail" plus detail_cap_enabled and detail_cap_smoothing_enabled (server.py:1336-1341). The two enable flags default on (server.py:365,367), but luminance_mode defaults to "standard" (server.py:425) — so on a default run the gate short-circuits and the smoothing is a no-op; it only acts once the run is switched into luminance-detail mode.
  • It converts the detail map to integer layer counts, smooths, converts back, and rewrites only the detail contribution inside the aggregate __white_cap__ map (server.py:1363-1377).

The smoothing itself (smooth_detail_cap_layers, pipeline/detail_cap_smoothing.py:100) does two passes on the integer layer map: replace exact-height speckles (≤1 px by default) with the local ring mode (pipeline/detail_cap_smoothing.py:117, remove_exact_height_speckles at :139), then on cumulative material masks drop tiny components and fill tiny holes (pipeline/detail_cap_smoothing.py:122, cleanup_cumulative_detail_masks at :167). Defaults: max 8 layers, 1-px speckle, 2-px component, 2-px hole (DetailCapSmoothingSettings, pipeline/detail_cap_smoothing.py:12-20), overridable from config (server.py:1306-1324).

The luminance tie-break (computed but currently unconsumed)

resolve_luminance_tiebreak (pipeline/luminance_handler.py:71) resolves a (weight, window) pair intended to break near-ties in colour cost toward the luminance-preferred cap. It reads luminance_tiebreak_weight/luminance_tiebreak_de_window (defaults 0.0/0.0, pipeline/state.py:80-81) and, when the handler is enabled, falls back to handler-specific overrides or a fraction of de_threshold (pipeline/luminance_handler.py:80-94).

It is called on the live staged path — staged_runner.py:6259 computes luminance_tiebreak_weight, luminance_tiebreak_de_window = resolve_luminance_tiebreak(cfg). However, those two local variables are never read again anywhere later in staged_runner.py (verified: no occurrence after line 6259). So as the code stands the tie-break resolution runs but its result does not currently influence Stage 2 zone scoring — treat the tie-break as resolved-but-inert pending a consumer. The config fields and resolver are not dead (the resolver is invoked), but the downstream wiring is absent.

Legacy: the cap quality scorecard

generator.cap_quality also contains analyze_cap_quality (pipeline/cap_quality.py:576), which computes a full cap scorecard — exposed-colour cliffs, island/pinhole risks, boundary/neighbour deltas, dE stats. This is test-only. Grepping the product tree, analyze_cap_quality, compare_assignment_stability (pipeline/cap_quality.py:724), and metric_subset (pipeline/cap_quality.py:761) are referenced only by tests/generator/test_cap_quality.py outside their own module. The sub-analyses they drive — find_cap_island_risks (:306), find_cap_pinhole_risks (:318), exposed_colour_cliff_analysis (:330), default_line_profile (:536) — are reachable in product code only through analyze_cap_quality, so they are dormant too.

The two helpers colour_ceiling_from_plan and top_surface_from_fields are no exception — they are not live either. The module’s only non-test product import is pipeline/blueprint_triage/fields.py:11, which pulls in exactly those two functions; but that consumer (the blueprint-triage engine) is itself computed-but-unwired (see Blueprint triage the unwired engine), so the whole of cap_quality.py is dormant in production. The genuinely-live printability path is the separate pipeline/staged_printability.py diagnostic, which does not import this module at all.

Driving it (for users)

  • Leave luminance_handler_enabled off for the standard colour-faithful solve; the cap then just fills remaining t_max headroom.
  • Turn it on to bias the cap toward darker image regions; tune luminance_handler_strength (pipeline/state.py:84) and the response curve (pipeline/state.py:88-89).
  • Detail-cap smoothing only acts when the run is in luminance-detail mode (server.py:1336); in standard mode it is a no-op regardless of the enable flags.
  • To cap total height, set t_max; to cap just the white cap, set d_wc_max or boundary_cap_authority_mm.
