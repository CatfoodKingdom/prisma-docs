Printability three layers

In one sentence: the generator has three separate “printability” subsystems at three abstraction levels — a per-pixel-column triage (blueprint_triage, test-only/dormant), a per-layer staged diagnostic + Stage 4 gate (staged_printability, the one that actually runs on every web solve), and a mesh-level measurement roll-up (mesh/printability.py, suspected inert) — and only the middle one is on the live path.

This is the orientation page for everything named “printability” in the generator. The name is overloaded: three unrelated modules share it, two of them define their own PrintabilityReport class, and most module docstrings are stale. Before trusting any liveness claim, read the master liveness map in What Actually Runs — this page links there rather than re-deriving each verdict, and adds the per-module physical detail the map omits.

The three subsystems differ in what they look at and whether they run:

Level 1 — per-pixel column triage (blueprint_triage) — dormant

pipeline/blueprint_triage/ walks the solved plan one pixel column at a time. Each column is a stack of MaterialIntervals, and the detectors flag structural hazards by inspecting those intervals: an empty column raises a MissingColumnHazard (“Pixel column has no material schedule.”, pipeline/blueprint_triage/detect/general.py:24), a positive-z gap inside a column is a VoidHazard (detect/general.py:37), and adjacent intervals that overlap become an OverlapHazard (detect/general.py:114). analyze_triage (pipeline/blueprint_triage/api.py:18) runs all detectors — voids, floating, overlaps, sub-features, narrow strands, cliffs, skyscrapers — and assembles them into a Verdict of CLEAN / WARNINGS / DISQUALIFYING (api.py:67-71) inside the triage PrintabilityReport (pipeline/blueprint_triage/report.py:180). A separate plan_fixes (pipeline/blueprint_triage/planning.py:25) proposes FixCandidates and apply_fixes (pipeline/blueprint_triage/application.py:19) mutates the plan.

It looks like a full repair pipeline, but nothing on the live solve invokes it. analyze_triage, plan_fixes, and apply_fixes have only test callers (tests/generator/blueprint_triage*); the sole non-test references to those three functions inside Prisma/generator are their own package re-exports (pipeline/blueprint_triage/__init__.py:1, :2, :17) — no production code calls them. (Other symbols from the module are imported on the live path — server.py:94, facade.py:36, and state.py:14 pull in PrintabilityError/PrintabilityReport — but only as a type or exception class, never the analyzer/fixer functions.) The runner clears the carrier field: _finalize_staged_backend_state sets state.blueprint_triage = None (runner.py:555 per What Actually Runs) and the staged path never writes a real report there. So the field threads through the facade and is read by the server, but always reads None. See What Actually Runs > blueprint_triage (printability triage) — dormant, and not the mesh report.

Its PrintabilityError is a different gate. blueprint_triage/report.py:29 defines PrintabilityError and the server imports it (server.py:94). The one place that raises it on a solve-shaped path is _assert_material_exposure_safe_for_product (server.py:2445), and even that is flagged suspected inert in a code comment at server.py:2438-2444 — during a real solve only the non-raising _run_material_exposure_audit runs. Do not assume PrintabilityError ⇒ blueprint triage ran.

Level 2 — per-layer staged diagnostic + Stage 4 gate (staged_printability) — LIVE

This is the printability layer that actually executes. It works on the staged blueprint’s per-layer occupancy, not pixel columns. build_layered_blueprint_view (pipeline/staged_printability.py:170) derives a read-only LayeredBlueprintView (staged_printability.py:31) — one boolean/label map per color layer, cap layer, and detail layer — from the staged artifacts (VisibleRecipeRawGeometryPlan, CapSynthesisPlan). resolve_blueprint_printability_settings (staged_printability.py:72) resolves the physical thresholds (minimum extrusion width, minimum/preferred line length, pitch, layer height) from the solve config.

It has two distinct jobs:

(a) The diagnostic report. run_blueprint_printability_diagnostic (staged_printability.py:410) labels the connected components inside each layer, grades each via grade_blueprint_component (staged_printability.py:271, which flags tiny_component / narrow_width / short_length against the physical minima), additionally runs a morphological-opening neck test (_opening_width_loss / _opening_width_loss_is_structural, staged_printability.py:312, :326) and a vertical-support check, and returns a frozen BlueprintPrintabilityDiagnostic (pipeline/staged_artifacts.py:501) carrying per-surface hard-fail pixel maps and a list of BlueprintPrintabilityComponentFacts (staged_artifacts.py:477). On the live path this is gated by emit_blueprint_printability and runs at staged_runner.py:10715-10733, attaching the result to cap_plan.blueprint_printability_diagnostic.

(b) The Stage 4 enforcement gate. The same grading helpers are re-exported publicly (opening_width_structure / opening_width_loss / opening_width_loss_is_structural, staged_printability.py:358, :362, :370) precisely so Stage 4 can apply the identical neck criterion as an in-place repair. _apply_stage4_boundary_cap_printability_gate (staged_runner.py:5230) grows or suppresses boundary-cap coverage and _apply_stage4_detail_printability_gate (staged_runner.py:5941) suppresses hard-failing detail material. These run inside Stage 4 guarded by a local enforce_printability = _printability_enforcement_enabled(cfg) flag (staged_runner.py:9630, applied at :9925 and :9993). _printability_enforcement_enabled (staged_runner.py:3346) returns config.enforce_printability when that attribute is present, falling back to config.stage4_printability_gate_detail otherwise.

Why it is LIVE, with defaults pinned. On the web app the relevant config flags are all forced on, not user-toggleable:

FlagLive defaultAnchor

So the gate repairs the blueprint and the diagnostic reports on it on every normal solve. The diagnostic results surface to the UI as performance counters (server.py:2401-2409) and overlay maps (server.py:5034-5040). See How a Solve Works for where Stage 4 sits and The Joint LUT and Staged Solve for the staged backend internals.

VisibleRecipe vs StackDefinition. The view builder consumes VisibleRecipe (staged_artifacts.py:73) thickness-by-filament records. This is a near-duplicate of StackDefinition — same shape, different role. When citing one, name it explicitly; do not assume they are interchangeable in a given call.

Level 3 — mesh-level measurement (mesh/printability.py) — suspected inert

mesh/printability.py is a measurement-only toolkit over already-built trimesh.Trimesh objects — it never mutates meshes or alters export behaviour. It answers geometry questions the other two levels cannot: do the per-filament STLs share an XY origin (compare_xy_footprints, mesh/printability.py:78); does the top of one layer meet the bottom of the next or is there a measurable gap/overlap (inter_mesh_gap_overlap, :359, bucketed by classify_seal_severity, :458); are there connected XY components below a printable footprint area (thin_island_risks, :601).

The export-facing roll-up is what is flagged inert. build_printability_report (mesh/printability.py:1071) aggregates the measurements and classify_printability_report (:1041) maps them onto a pass / warn / fallback / block ladder with a next_action such as do_not_export (_classify_printability_summary, :916), wrapping it in this module’s own PrintabilityReport dataclass (:680). A code comment at mesh/printability.py:1061-1070 records that no live solve/export path appears to consume this classification — the only known callers are tests/generator/test_mesh_printability.py and scripts/characterize_mesh_printability.py.

Treat “inert” as a hint, not a fact. That same comment (:1066-1069) warns that an earlier audit declared this “dead” after missing real references, so the reference graph is subtle. Re-verify exhaustively across tests, scripts, the config chain, and the separate blueprint_triage module before removing or disabling anything. See What Actually Runs > mesh printability + canonical mesh — suspected inert.

The two PrintabilityReport traps

These two classes share a name and nothing else — keep them straight:

ClassDefined atWhat it isLives where
Triage PrintabilityReportpipeline/blueprint_triage/report.py:180Per-column hazard report with Verdict + PrintabilityError (report.py:29)Level 1, dormant
Mesh PrintabilityReportmesh/printability.py:680Export-facing mesh summary with status/severity/next_actionLevel 3, suspected inert

The middle (live) level uses neither — its report type is BlueprintPrintabilityDiagnostic (staged_artifacts.py:501), a third, separately-named dataclass.
