The live staged printability diagnostic

The live staged printability diagnostic

Properties1
tagsgenerator, printability

Jun 21, 202611 min read

In one sentence: after the staged solve builds the white cap, the generator re-derives the layered plan, grades every connected component on every layer against the printer’s physical min-feature thresholds, and records a read-only diagnostic (per-pixel fail maps + worst-component facts) that the UI overlays — while a separate, always-on audit counts any colour filament left exposed to air.

The live staged printability diagnostic

This is the plan-level printability check that runs as part of a production solve. It does not repair geometry — it measures it. Two distinct things live here, both wired into the live solve path:

  1. The blueprint printability diagnostic — a layer-by-layer grade of every connected component against resolved physical thresholds (min extrusion width, min/preferred line length, plus a neck, clearance, and vertical-support audit). Built in generator.pipeline.staged_printability.
  2. The material exposure audit — a 3D face-count of colour filament left touching air, plus the mandatory white boundary-shield floor implied by colour-height cliffs. Built in generator.pipeline.material_exposure.

The diagnostic is read-only. The enforcement passes inside generator.pipeline.staged_runner (Stage 4 boundary-cap and detail repair) reuse the same grading helpers so a component the diagnostic flags is the same component the gates repair — see Reuse by the enforcement passes. For the stage that owns those gates see The staged backend (Stage 0-5).

How to drive it

You do not call any of this directly. It runs automatically inside run_staged_backend_path (the live webapp solve engine, pipeline/staged_runner.py:10310; the only caller is the runner at pipeline/runner.py:843-846 — not the legacy solve.py CLI engine). The diagnostic stage is gated on one flag and bounded by a handful of physical settings you set per run:

KnobDefaultWhere setEffect
emit_blueprint_printabilityTruefacade.py:174, server.py:375, state.py:112, app.js:312Master on/off for the diagnostic stage (staged_runner.py:10715).

When emit_blueprint_printability is off the diagnostic stage is skipped entirely; the exposure audit (below) still runs on every solve.

Step 1 — Resolving physical thresholds

resolve_blueprint_printability_settings (staged_printability.py:72) collapses the user/printer config into a frozen BlueprintPrintabilitySettings (staged_printability.py:20) carrying five numbers in millimetres: minimum_extrusion_width_mm, minimum_line_length_mm, preferred_line_length_mm, pitch_mm, layer_height_mm.

The resolver is forgiving — each field falls through a chain of candidates via _first_positive (staged_printability.py:59), which returns the first strictly-positive value:

  • Width: printability_minimum_extrusion_width_mm → printer_min_line_width_mm → hard floor 0.40 (staged_printability.py:79-84).
  • Min line: explicit value, else max(0.40, width + 0.10) (staged_printability.py:85-89).
  • Preferred line: explicit value, else max(0.60, minimum_line) (staged_printability.py:90-94).
  • Pitch: the pitch_mm argument → solver_fine_pitch_mm → image_sample_pitch_mm → 0.20 (staged_printability.py:95-100). The live call passes pitch_mm=solver_fine_pitch_mm (staged_runner.py:10720) so grading happens at the true fine solve resolution.
  • Layer height: layer_height → 0.08 (staged_printability.py:101).

Pitch is the linchpin: every pixel-count is converted to physical area/width/length by multiplying by pitch_mm, so the thresholds are compared in millimetres regardless of solve resolution.

Step 2 — The layered blueprint view

build_layered_blueprint_view (staged_printability.py:170) derives a read-only per-layer occupancy view (LayeredBlueprintView, staged_printability.py:31) from two staged artifacts: the VisibleRecipeRawGeometryPlan (colour recipes per zone) and the CapSynthesisPlan (white cap + detail heights). It splits the plan into three surface families:

  • Colour layers — each visible recipe’s per-filament thickness is quantized into integer layer counts (_positive_layer_counts, staged_printability.py:132; note ≥ 1 layer for any positive thickness, staged_printability.py:138), expanded into an ordered label stack per recipe (_recipe_color_layer_table, staged_printability.py:142), then scattered across the image via the recipe label map (staged_printability.py:191-193). Material ordering follows the declared palette, with any stragglers appended (_ordered_material_ids, staged_printability.py:113).
  • Cap layers — the boundary cap, computed as cap_height_mm − detail_height_mm clamped at 0 (staged_printability.py:199-203), sitting on top of the colour ceiling (color_ceiling = cap_boundary_top_mm − boundary_cap_height, staged_printability.py:204-208).
  • Detail layers — the detail cap, stacked on color_ceiling + boundary_cap_height (staged_printability.py:248-255).

Each surface is materialized into a stack of boolean layer masks anchored to an absolute Z grid (absolute_layer_masks, staged_printability.py:211), so the support audit (Step 4) can look downward through the stack.

Step 3 — Grading a component

grade_blueprint_component (staged_printability.py:271) is the atomic check. Given a connected component’s pixel count and bounding-box height/width in pixels, it computes three physical measures and returns a grade:

MeasureFormula (staged_printability.py)Compared against
area_mm2pixel_count · pitch² :279min_extrusion_width · min_line_length :282-285
width_mmmin(h, w) · pitch :280minimum_extrusion_width_mm :290
length_mmmax(h, w) · pitch :281minimum_line_length_mm :292, then preferred_line_length_mm :296

Grades and their reason flags:

  • hard_fail if area below min_area (tiny_component), or width below min (narrow_width), or length below min (short_length) — any one trips it (:288-295).
  • soft_warn with short_length_preferred if it clears the hard length floor but falls short of the preferred length (:296-297).
  • pass otherwise (:298).

Bounding-box width/length alone cannot catch a fat blob joined by a one-pixel neck, so the diagnostic adds two more per-component checks on top of the bbox grade.

The opening-width neck criterion

grade_blueprint_component only sees the bounding box; a dumbbell shape (two wide lobes joined by a sub-width neck) passes its width test. The neck is caught by a morphological opening with a square structuring element sized to the minimum printable width:

  • _minimum_width_px (staged_printability.py:301) → ceil(min_extrusion_width / pitch) pixels; _opening_width_structure (:307) builds an N×N all-ones kernel.
  • _opening_width_loss (:312) opens the component and returns the pixels the opening removed — the kernel cannot fit there, i.e. sub-width features. A 1×1 kernel is a no-op (:320-321).
  • _opening_width_loss_is_structural (:326) decides whether the loss matters: opening also rounds harmless exterior corners. The loss is structural only if removing the lost pixels destroys the component or splits it into more than one piece (:342-349). Only structural loss escalates to hard_fail with narrow_width (:545-553); harmless corner rounding is ignored.

These three helpers are public re-exports (opening_width_structure :358, opening_width_loss :362, opening_width_loss_is_structural :370) precisely so the enforcement passes apply the identical criterion — the comment at :352-357 spells out why.

Step 4 — The full diagnostic run

run_blueprint_printability_diagnostic (staged_printability.py:410) walks every layer of every surface and accumulates per-pixel fail maps plus component-level facts. The inner consume_mask closure (:463) does the work for one (surface, layer, material) mask:

  1. Connected-component labelling with 4-connectivity (ndi.label, structure from :460), iterating bounding boxes via find_objects (:504-509).
  2. Bbox grade via grade_blueprint_component (:515).
  3. Centre clearance — a distance transform in mm gives each pixel’s clearance to the nearest edge (_component_center_clearance_mm, :377; applied :529-536). Recorded as max_center_clearance_mm, not itself a fail.
  4. Opening-width neck — structural loss escalates to hard_fail and marks width_loss_map (:538-553).
  5. Vertical support — see below. Any unsupported pixel escalates to hard_fail with low_vertical_support (:566-575).

Every non-pass component becomes a BlueprintPrintabilityComponentFacts (:579, dataclass at staged_artifacts.py:476) carrying its bbox, physical measures, grade, reason flags, clearance, width-loss pixels, and support fraction. The full set is sorted hard-fail-first then by pixel count (:708-720) and the worst max_worst_components (default 128) are kept (:808).

Support-fraction checks

A colour pixel printed with nothing under it overhangs. _support_fraction_for_layer (staged_printability.py:392) measures, for layer k, the mean occupancy of the window of layers below it (window_layers=3, :397; layer 0 is treated as fully supported on the base, :400-401). Inside consume_mask, the per-pixel support map is sampled over the component; the mean is its support_fraction (:555-561), and any pixel with support < 1.0 is unsupported (:566).

Support sources differ per surface (:654-697):

SurfaceSupport mapSource (staged_printability.py)

cap (boundary)full support (sits on the colour ceiling)full_support :682

Projected clustering

Beyond per-component facts, the run projects all hard-fail pixels down to a 2D map and clusters them (projected_cluster_summary, :721) at two radii: tight (:739-744) and dilated by a cluster_radius_px derived from min_line_length / pitch (:745-756). This surfaces “many small fails packed into one region” as a single large-cluster fraction — the color_hard_fail_largest_cluster_fraction family on the result.

The result object

The run returns a BlueprintPrintabilityDiagnostic (staged_artifacts.py:500): the resolved thresholds, per-surface layer/mask/fail counts, the tiny/narrow/short/soft tallies, the projected-cluster summaries, the worst-component tuple, and a stack of float32 per-pixel maps (hard_fail_map, soft_warn_map, narrow_width_map, short_component_map, color_hard_fail_map, cap_hard_fail_map, detail_hard_fail_map, center_clearance_map, width_loss_map, low_support_map).

Where it goes

In the live solve the diagnostic is attached to the cap plan (cap_plan.blueprint_printability_diagnostic = blueprint_printability, staged_runner.py:10733) and its scalar counts are timed/recorded into the run’s performance profile (staged_runner.py:10734+). The bridge (Step 5 of the staged backend) copies the float maps into the solve’s debug-map dict under blueprint_printability_* keys (pipeline/staged_bridge.py:325-372), which is how they reach the generator’s overlay viewer. A subset of the scalar counts is also promoted into run_metadata["stats"] for display (server.py:2400-2412). This is purely diagnostic — it gates nothing and raises nothing.

Reuse by the enforcement passes

The diagnostic is the measurement; the Stage 4 boundary-cap and detail repair passes are the enforcement, and they reuse the diagnostic’s grading helpers so the two stay in lockstep:

  • grade_blueprint_component is imported by staged_runner.py:68 and called from the enforcement graders — e.g. _stage2_component_physical_grade (staged_runner.py:3386), _component_physical_grade_with_opening (:3416), a local growth grader (:3808), and the vectorized layer-failure scan _stage4_layer_failures_vectorized (:5879).
  • opening_width_structure / opening_width_loss / opening_width_loss_is_structural are imported (staged_runner.py:69-71) and applied in those same passes (:3427-3431, :5901-5905) so the neck criterion is identical. The header comment at staged_printability.py:352-357 is explicit that bbox/area/length-only gates would let a 1-pixel neck slip past.

The material exposure audit

This page owns material_exposure.py. It is a separate, always-on audit (independent of emit_blueprint_printability) that asks one question: does any colour filament touch air in the final print? It is geometry-agnostic — it audits the raster material occupancy the export path will use, and it never smooths or repairs (material_exposure.py:1-7 header; trust the line behaviour, not the prose).

The boundary-shield floor

lateral_boundary_shield_floor_layers (material_exposure.py:78) computes, per pixel, how many white cap layers are mandatory to shield internal colour-height cliffs. For each 4-neighbour pair it compares colour-layer counts: the lower side must carry enough white cap to cover its neighbour’s colour-height excess; the higher side needs none for that pair (:99-108). This floor is enforced in the live solve — staged_runner.py:7117 feeds the result into the implied cap heights as minimum_cap_height_mm (:7120-7132), but only when a non-fixed cap mode is active (_non_fixed_lateral_shield_required, staged_runner.py:1300, gating at :7111). In fixed cap mode the cap already covers everything, so no floor is computed.

The colour-air exposure count

audit_colored_filament_exposure_from_layer_counts (material_exposure.py:112) counts exposed colour faces in 3D without building a voxel stack, given colour and white-cap layer-count maps:

Face typeWhat it countsCode
lateral_internal_face_countcolour stack on one side taller than the total (colour + cap) stack of a 4-neighbour:131-136
top_face_countpixels with colour but zero white cap on top:138
exterior_face_countcolour layers on the four image borders (no neighbour to shield them):139-144

A MaterialExposureAudit (material_exposure.py:29) bundles these counts plus the exposed-colour pixel count and stack maxima. Its passes property (:54) is True only if the print is fixed_thickness_exempt or the total exposed face count is zero (:55-57). The height-based entry point audit_colored_filament_exposure_from_heights (:188) just quantizes mm → layer counts first; audit_colored_filament_exposure_from_thickness_maps (:204) sums every exposure-relevant material map (exposure_relevant_material_keys, :241 — everything not prefixed __, minus explicit exclusions, :267-270) and resolves the white cap from WHITE_CAP or WHITE_BOUNDARY_CAP + WHITE_DETAIL_CAP (:273-289).

How the audit is wired

In the live solve, server.py calls the non-raising _run_material_exposure_audit (server.py:2419, invoked :5123) once per solve. It excludes the white base/cap ids (_white_ids, server.py:798) and marks the solve exempt when the cap is in fixed thickness mode (server.py:2415-2435). The summary lands in run_metadata["material_exposure_audit"] and the boolean white_cap_exposure_safe (server.py:5127-5130) for display — it records, it does not block.

A second, assert-form gate _assert_material_exposure_safe_for_product (server.py:2445) does raise PrintabilityError on exposure, but per the in-code note at server.py:2438-2444 it is suspected inert on the live solve path (no confirmed live caller found; appears exercised only by tests/generator/test_material_exposure_product_gate.py). Treat that as unconfirmed — the note itself asks for a full reference re-check before relying on it.

Disambiguation (do not confuse)

  • The blueprint BlueprintPrintabilityDiagnostic here is unrelated to the mesh-side PrintabilityReport classes. There are two unrelated report types in the codebase (blueprint-triage vs mesh) — this page is strictly the blueprint/plan-level one.
  • VisibleRecipe (staged_artifacts.py:73) is the per-zone recipe the layered view consumes; it is a near-duplicate of StackDefinition but not the same type — the view reads recipe.to_mapping() (staged_artifacts.py:105) and recipe.thickness_by_filament (:76).
