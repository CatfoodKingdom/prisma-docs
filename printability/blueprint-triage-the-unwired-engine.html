Blueprint triage the unwired engine

Properties1
tagsgenerator, printability

Jun 21, 20269 min read

In one sentence: pipeline/blueprint_triage/ is a complete, tested printability-analysis engine — seven defect detectors, a CLEAN/WARNINGS/DISQUALIFYING verdict, and a fix planner with counterfactual-dE costing — that the live solve never calls (the state slot it would fill is hard-wired to None), so today it runs only under its own test corpus.

Blueprint triage: the unwired engine

This page documents the blueprint_triage package at design-intent altitude. It is not an exhaustive API reference for every helper, because the whole subsystem is computed-but-unwired: no live solve or export path constructs an AnalysisContext or calls analyze_triage. Read it to understand what was built and how it was meant to work, and as a map for anyone considering wiring it in.

Liveness up front — this is dormant, test-only

The state slot that would hold a triage report is PipelineState.blueprint_triage, declared Optional["PrintabilityReport"] = None at pipeline/state.py:275. Its full lifecycle in the live path:

SiteWhat happensAnchor
Declaredblueprint_triage: Optional["PrintabilityReport"] = Nonepipeline/state.py:275
Written (live)Stage-5 bridge of the staged backend sets state.blueprint_triage = None — never a real reportpipeline/runner.py:555
Read (live)Facade passes it straight through: blueprint_triage=getattr(state, "blueprint_triage", None)facade.py:890
Asserted dormantA real run_pipeline test asserts state.blueprint_triage is None after solvingtests/generator/blueprint_triage/test_runner_invocation.py:31

The engine’s three public entry points — analyze_triage, plan_fixes, apply_fixes — have zero callers outside the package and its tests. A repo-wide grep for those symbols excluding blueprint_triage/** returns only one legacy-audit markdown doc (Prisma/generator/docs/legacy_audit/07_COMPATIBILITY_MAPS_AND_EXPERIMENTAL_BRIDGE.md), never production code. The only generator-code reference to the package at all (outside state.py/runner.py/facade.py above) is server.py:94, which imports only PrintabilityError — see the disambiguation trap below; that import is unrelated to the triage engine’s verdict path.

The detectors, planner, and costing are nonetheless substantially tested: ~30 test modules under tests/generator/blueprint_triage/ plus four sibling suites (blueprint_triage_cliff, blueprint_triage_gate, blueprint_triage_line_width, blueprint_triage_sub_feature). So the code is exercised and presumed correct in isolation — it is simply not invoked by the product.

Calling it “Lane A/D” etc.: the source carries internal lane labels (e.g. application.py:42 references “Lane D”; planning.py:459 references “D.3”). These are development-phase tags, not user-facing concepts.

AnalysisContext — the precomputed input bundle

AnalysisContext (fields.py:109) is the immutable bundle every detector reads. The classmethod AnalysisContext.from_state(state, *, exposure) (fields.py:130) builds it from a solved pipeline state; it requires state.solved_plan and raises ValueError otherwise (fields.py:137). What it precomputes:

FieldBuilt byMeaning
colour_ceiling_mapcolour_ceiling_from_plan (cap_quality.py:58), called at fields.py:146per-pixel top of coloured material (white base + colour stack)
top_surface_maptop_surface_from_fields (cap_quality.py:70), called at fields.py:147colour ceiling + white-cap height
interval_schedule_build_interval_schedule (fields.py:222)per-pixel ordered MaterialInterval column: white base → colours (palette order) → white cap
per_filament_masks_build_per_filament_masks (fields.py:283)boolean occupancy per filament id; white base omitted (everywhere by construction), __white_cap__ added where cap > 0
salience_build_salience_fields (fields.py:314)Sobel luminance/chroma gradients on the solve-grid OKLab target
fidelity_prior_build_fidelity_prior (fields.py:361)residual proxy = __de__ raster scaled by normalized salience
configTriageConfig (config.py:21)triage-owned thresholds + ranking weights
colour_profiles / wb_profile / wc_profile_resolve_profiles (fields.py:204)forward-model spline profiles, needed only for counterfactual prediction

The interval schedule is the spine of the structural detectors. Each pixel column is a list of MaterialInterval(z_start_mm, z_end_mm, material_id) (fields.py:20), starting with MaterialInterval(0.0, d_wb, "__white_base__") (fields.py:254) and ending with a "__white_cap__" interval from the colour ceiling to ceiling+cap (fields.py:264).

ExposureContext (fields.py:46) carries edge-exemption data: an exempt_outer_perimeter flag and an optional exempt_edge_mask of shape (H, W, 4) in direction order (up, down, left, right) (fields.py:54). ExposureContext.from_export_bundle (fields.py:93) derives the inset border-exemption mask from a print’s border width — this is the one piece a test exercises directly (tests/generator/blueprint_triage_gate/test_orchestration_gate.py:20).

The seven detectors

analyze_triage (api.py:18) runs seven detectors and assembles a PrintabilityReport. Detectors split across detect/general.py (structural column invariants), detect/features.py (xy footprint geometry), and detect/cliffs.py (colour-step exposure). All return lists of Hazard dataclasses (report.py:33).

#DetectorSourceWhat it flagsDefault severity
1Voiddetect_voids (detect/general.py:15)a pixel column with no schedule (MissingColumnHazard, general.py:22) or a positive-z gap between stacked intervals (general.py:33)always DISQUALIFYING
2Floatingdetect_floating (detect/general.py:48)column starts above z=0 unsupported (general.py:56), or an interval doesn’t abut material below it (general.py:69)always DISQUALIFYING
3Overlapdetect_overlaps (detect/general.py:86)non-finite / negative-thickness interval (general.py:92), or adjacent intervals overlapping in z (general.py:109)always DISQUALIFYING
4Sub-featuredetect_sub_features (detect/features.py:29)xy connected component below min printable area/width, per material per z-layer, deduped by (material_id, bbox)graded — see below
5Narrow stranddetect_narrow_strands (detect/features.py:107)skeletonized footprint segments thinner than the soft line-width thresholdgraded — see below
6Cliffdetect_cliffs (detect/cliffs.py:20)a colour step where one pixel’s colour ceiling is exposed to air above a shorter 4-neighbour (cliffs.py:188)graded by exposure depth in analyze_triage
7Skyscraperidentify_skyscrapers (detect/cliffs.py:38)isolated tall thin plateau among cliff high-sides (prominence + isolation gated)structural metadata only

The structural trio (void/floating/overlap) walk context.interval_schedule.intervals directly and treat any breach as a hard invariant violation — they always emit Verdict.DISQUALIFYING. The column epsilon is max(1e-6, layer_height_mm * 0.01) (general.py:127).

Graded severities (sub-feature, narrow strand, cliff)

The footprint detectors classify against hard/soft thresholds in TriageConfig:

  • Sub-feature (_sub_feature_severity, detect/features.py:196): DISQUALIFYING below hard_min_feature_area_mm2 or hard_min_feature_width_mm; WARNINGS below the soft_* equivalents; otherwise None (no hazard).
  • Narrow strand (_strand_severity, detect/features.py:214): DISQUALIFYING below hard_min_line_width_mm; WARNINGS below soft_min_line_width_mm. Uses skimage.morphology.skeletonize (features.py:124) and an EDT-derived local width.
  • Cliff: detectors emit raw CliffRegions; severity is decided in analyze_triage itself by comparing region.max_exposure_depth_mm against cliff_block_depth_mm / cliff_warn_depth_mm (api.py:42, api.py:50), wrapping each into a CliffHazard (report.py:130).

Skyscrapers and salience

identify_skyscrapers (detect/cliffs.py:38) clusters cliff high-side pixels into cap-floor-coherent components (_cluster_high_side_pixels, cliffs.py:372), then gates each on footprint area, width, prominence (skyscraper_prominence_mm) and isolation score (skyscraper_isolation_threshold) — cliffs.py:90–cliffs.py:98. Survivors get a blended feature_salience_score mixing the cliff salience, local feature support (score_noise_vs_feature, cliffs.py:136), prominence, and target-vs-ring contrast, with an isolation penalty (cliffs.py:108–cliffs.py:115). Crucially, skyscrapers are not a verdict input — analyze_triage never adds them to blocking_hazards or warnings; they only inform fix planning.

Salience itself is image-driven: _build_salience_fields (fields.py:314) takes Sobel derivatives of the solve-grid OKLab target (fields.py:334), with chroma being the gradient norm over the (a,b) channels (fields.py:344) and combined = hypot(luminance, chroma) (fields.py:351).

The verdict

analyze_triage aggregates into a PrintabilityReport (report.py:179). The verdict logic (api.py:67–api.py:71):

blocking_hazards = voids + floating + overlaps
                 + DISQUALIFYING sub-features + DISQUALIFYING narrow-strands + blocking cliffs
warnings         = WARNINGS sub-features + WARNINGS narrow-strands + warning cliffs

verdict = DISQUALIFYING if blocking_hazards
          else WARNINGS if warnings
          else CLEAN

Verdict is the three-value enum CLEAN / WARNINGS / DISQUALIFYING (report.py:12). The report also carries a ReportSummary of per-category counts (report.py:166), plus a plan_fingerprint and context_fingerprint (api.py:94, api.py:95) so a verdict can be checked for staleness against a (plan, exposure) pair. That check is the job of ValidatedBlueprintToken (report.py:199): from_report snapshots the fingerprints + verdict + summary, and is_valid_for(plan, context_fingerprint) re-hashes the plan and compares (report.py:214). No live code constructs or consumes such a token today.

Fix planning, costing, and application

If the verdict is not clean, the engine can propose and cost repairs. None of this runs in production; it is the most elaborate dormant part.

Fix types

FixType (report.py:18) enumerates ACCEPT, SHORTEN, WALL, SMOOTH, HYBRID, TRANSLUCENT_SMOOTH, TRANSLUCENT_HYBRID, BULLDOZE. Of these, only a subset is actually implemented end-to-end:

FixTypeGenerated in plan_fixes?Applied in apply_fixes?Simulated in costing?
ACCEPTyes (every hazard)no-op (application.py:27)n/a
SHORTENyes_apply_shorten (application.py:84)yes (costing.py:86)
WALLcliff only_apply_wall (application.py:103)yes (costing.py:95)
SMOOTHcliff only_apply_smooth (application.py:111)yes (costing.py:99)
HYBRIDcliff only_apply_hybrid (application.py:146)yes (costing.py:107)
BULLDOZEskyscraper onlyrouted through _apply_shorten (application.py:29)yes (costing.py:86)
TRANSLUCENT_*never generatedNotImplementedError (“see Lane D”, application.py:41)NotImplementedError (costing.py:137)

plan_fixes — candidate generation and ranking

plan_fixes(report, policy=None) (planning.py:25) iterates cliff / skyscraper / sub-feature / narrow-strand hazards (planning.py:33–planning.py:36), generates candidates per hazard via _generate_candidates (planning.py:77), and scores them in two passes:

  1. Heuristic pass — _heuristic_scores (planning.py:343) fills a FixScoreBreakdown (report.py:146) from cheap proxies: material cost (pixel area), a per-FixType workflow_cost table (planning.py:376), a shape_cost table keyed on feature salience (planning.py:383), and a printability_gain (planning.py:425).
  2. Counterfactual pass — for the top-N viable candidates per hazard (counterfactual_top_n_per_hazard, default 3, planning.py:40), it replaces the heuristic image_cost with the true counterfactual_cost (planning.py:57) and re-finalizes the composite (planning.py:64).

The composite score (_composite, planning.py:414) is a weighted sum: image·w_image + material·w_material + shape·w_shape + workflow·w_workflow − printability_gain·w_gain, with weights from TriageConfig. Candidates are then ranked (planning.py:66), and a phase-2 refinement (_apply_phase2_refinement, planning.py:600) folds the cheapest realized fix cost back into each region’s feature_salience_score.

counterfactual_cost — the dE penalty of a fix

counterfactual_cost (costing.py:15) answers “how much does this fix hurt the image match on the pixels it touches?” It:

  1. simulates the fix on a copy of the plan (_simulate_fix, costing.py:67),
  2. runs the forward model on just the affected pixels (_predict_oklab_for_pixels, costing.py:196, via predict_transmission + to_oklab from generator.model),
  3. compares the modified per-pixel dE against the baseline dE (__de__ raster or recomputed baseline, costing.py:47),
  4. returns the mean positive increase in dE — an improvement scores 0 (costing.py:40).

This is the only part of the engine that needs the forward-model profiles on the context; if they are missing it raises ValueError (costing.py:205).

apply_fixes — mutation and cache invalidation

apply_fixes(plan, candidates, *, state=None) (application.py:19) first asserts the batch’s target masks don’t overlap (_assert_non_overlapping, application.py:69), then dispatches each candidate to its _apply_* mutator. When a state is passed it invalidates derived caches (invalidate_triage_cache, application.py:12 — sets state.blueprint_triage = None and state.plan_derived_cache = None) and rebuilds state.thickness_maps via compatibility_thickness_maps (application.py:48), preserving any __de__ / __gamut_mask__ diagnostics (application.py:60). The shared SMOOTH/HYBRID geometry builder is build_smooth_target_cap_height_map (application.py:182), a linear distance-falloff cap raise reused by both planning.py and costing.py.

TriageConfig — the knobs

TriageConfig (config.py:21) holds only triage-owned thresholds and ranking weights; physical printer constraints stay on PipelineConfig. TriageConfig.from_pipeline_config (config.py:53) derives them: the hard floors come from the printer’s minimum extrusion width (config.py:55), while the soft (warning) band uses the nozzle-derived feature scale _FEATURE_WIDTHS_PER_NOZZLE * nozzle_diameter from generator.preprocessing.feature_scale (config.py:68). Cliff depths key off layer height: cliff_warn_depth_mm = layer_height, cliff_block_depth_mm = max(2·layer_height, layer_height) (config.py:73).

Two PrintabilityError, two PrintabilityReport (trap)

There are two unrelated PrintabilityError and PrintabilityReport symbols in the generator — do not conflate them:

SymbolThis page’s moduleThe other, unrelated one
PrintabilityReportblueprint_triage/report.py:180 (verdict + hazards)mesh/printability.py mesh-export classification (build_printability_report, mesh/printability.py:1071)
PrintabilityErrorblueprint_triage/report.py:29reused by the mesh-exposure gate

The single live raise of blueprint_triage’s PrintabilityError is not in the triage engine at all: server.py:94 imports it, and _assert_material_exposure_safe_for_product (server.py:2445) raises it when a non-fixed white-cap solve exposes coloured filament. Even that gate is flagged suspected-inert / test-only by an in-code note (server.py:2438) — during a live solve only the non-raising audit runs. Likewise, mesh/printability.py:1061 carries an explicit warning that its export classification is suspected inert and that its PrintabilityError/PrintabilityReport must not be confused with this module’s. See Printability three layers for how these distinct printability mechanisms relate.
