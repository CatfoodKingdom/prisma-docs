Model-domain ingress

In one sentence: the generator solves in the model domain (flatfield-normalized transmission RGB the calibration models were fit in), so it pulls source photos into that domain on the way in with an inverse Camera Transform (G), and pushes its predictions back out to display-encoded “lit appearance” with the forward Camera Transform (F) only when it bakes preview images.

This page covers the whole F/G round trip: how source colours get mapped in, what space the solve actually optimises in, the exact maths of the forward transform, and which PNGs get baked through F for the viewer.

Why two domains exist

The calibration app fits its appearance models against camera-captured swatch colours — what a strip of filament looks like when photographed on the lightbox and rendered to sRGB by the camera. Those colours are not plain display sRGB; they live in a “model domain” of flatfield-normalized transmission. The forward Camera Transform F is the bridge: it maps model-domain transmission RGB to that camera-rendered display sRGB (“what the lit lithophane will look like”). The inverse G = F^-1 goes the other way (lib/camera_transform.py:3).

DomainWhat lives thereUsed for
Source sRGBThe photo bytes on diskInput only

The solve never leaves the model domain. F is applied only at the very end, when baking preview images.

Ingress: pulling the source into the model domain (G)

image_to_target (generator/model.py:128) is the seam. With model_domain_ingress=True it runs the source image through the inverse 33³ LUT (G); with it off it falls back to a plain srgb_to_linear gamma-2.2 decode (generator/model.py:148-152).

  • On → _apply_model_domain_ingress_lut → apply_inverse_lut (generator/model.py:122-125, lib/camera_transform.py:356), a trilinear lookup into the baked 33×33×33×3 inverse LUT. The LUT already encodes the full-stack transmission oklab(T_wb × T_wc × ∏T_colour), so T_wb is not divided back out — it is baked into every LUT entry (generator/model.py:136-147).
  • Off → srgb_to_linear (generator/model.py:108-115), the legacy bit-identical path. Tests pin that the off path never even loads the LUT (tests/generator/test_model_domain_ingress.py:27).

The targets the solve aims at are built from the output of this step, via the OKLab conversion in pipeline/target_cloud.py:72 (the cloud builder calls image_to_target in the configured ingress mode, then to_oklab).

The facade threads the toggle and LUT path straight through to image_to_target (generator/facade.py:644-646). It is also a solve-owned identity key — it appears in _SOLVE_OWNED_KEYS (generator/server.py:1978) and is persisted with Settings Profiles via _SETTINGS_PROFILE_KEYS (generator/server.py:2959), and it is echoed in the runner’s solve-identity diagnostics (generator/pipeline/runner.py:631), so toggling it changes a run’s fingerprint and old solves cannot masquerade as new ones.

Artifact required

The Prisma/data/camera_transform/ artifact is required on the ingress-on path. It is git-ignored, so a fresh checkout without it fails solve work until it is present. Missing/invalid artifacts are a hard, loud error (CameraTransformError), never a silent fallback to raw transmission (lib/camera_transform.py:43, model_domain_display.py:11-13). The actionable message points to Rebuild via Calibration → Camera Transform (lib/camera_transform.py:34).

The webapp solves the staged backend

For developers: the live web solve does not run solve.py’s legacy “6-step” CLI engine. After the fixed Load stage builds the target cloud through compute_solve_target_cloud → image_to_target (pipeline/runner.py:779), the solve path dispatches to run_staged_backend_path (pipeline/runner.py:843-846, defined pipeline/staged_runner.py:10310). solve.py’s image_to_target callers (solve.py:337, :464, :607) are the legacy CLI/pipeline_cli.py engine.

The appearance provider that the staged backend predicts with is model-domain by construction after the 2026-06-12 projection-slot retirement: appearance_model’s appearance-named methods are pass-throughs that return model-domain RGB unchanged, not a separate display projection (generator/appearance_model.py:418-424 — project_model_linear_rgb_to_appearance literally return np.asarray(rgb); predict_stack_appearance_linear_rgb_batch just calls the model-domain batch). The contract version "domain-pass-through-v1" (generator/appearance_model.py:79) is folded into the provider fingerprint so a domain-contract change invalidates stale solves.

Egress: the forward Camera Transform F

The forward transform is implemented in two layers. generator/model_domain_display.py is the thin generator-side wrapper; lib/camera_transform.py holds the maths. apply_appearance_transform (model_domain_display.py:37) is a direct call to apply_forward (lib/camera_transform.py:259).

F is a v2 fit: a Finlayson degree-2 root-polynomial matrix followed by per-channel monotone PCHIP tone curves.

Step 1 — root-polynomial expansion + 3×6 matrix

Model-domain linear RGB (r,g,b) is expanded to a 6-feature root-polynomial vector and multiplied by a learned 3×6 matrix W (lib/camera_transform.py:244-251):

phi(r,g,b) = [r, g, b, sqrt(r·g), sqrt(g·b), sqrt(r·b)]
z = clip(phi @ W.T, 0, 1)

Negative inputs are clamped to 0 before the square roots (rp_features, lib/camera_transform.py:245).

Step 2 — per-channel monotone PCHIP tone curves

Each of the 3 output channels passes through its own PchipInterpolator over 10 knots on x ∈ [0,1] (lib/camera_transform.py:266-269, N_KNOTS = 10 at :26). The knot y-values are not stored raw — they are decoded from unconstrained params through a softplus-cumulative scheme that guarantees monotonicity (_decode_knots, lib/camera_transform.py:230-241): a sigmoid-scaled base, strictly-positive log1p(exp(·)) deltas, and a rescale so the top knot never exceeds OUT_MAX = 1.05. Output is clipped to [0,1] (lib/camera_transform.py:270).

The 18 matrix weights + 30 curve params give N_PARAMS = 48 (lib/camera_transform.py:31). unpack_params splits them into the 3×6 W and the 3×10 curve block (lib/camera_transform.py:254-256).

The inverse (G) is consistent with F

G exists in two forms. The baked 33³ LUT (apply_inverse_lut) is what ingress actually uses at runtime — fast trilinear lookup. There is also an analytic invert_forward (lib/camera_transform.py:279): it inverts the PCHIP curves (invert_curve_channel, :273), seeds t via the matrix inverse, then runs n_newton=4 Newton iterations against the root-polynomial Jacobian. This analytic inverse is what the calibration side bakes the LUT from; tests assert F(G(·)) is near-identity (tests/generator/test_model_domain_display.py:125).

The artifact: generation pinning + sha256

The Camera Transform is a versioned, hash-pinned artifact loaded by load_camera_transform (lib/camera_transform.py:201).

  • Generation pointer. A CURRENT text file names one local generation directory (gen-*); _read_current_generation reads it and rejects absolute paths or anything other than a single local name (lib/camera_transform.py:69-85).
  • Hash verification. When loading from a generation dir, _verify_generation_hashes reads manifest.json’s artifact_hashes and recomputes the sha256 of both camera_transform.json and inverse_lut_33.npz, erroring on any mismatch (lib/camera_transform.py:160-175). This is how a committed generation is guaranteed unmodified.
  • Provenance sha. Beyond the artifact-integrity hashes, load_camera_transform also computes the sha256 of the transform JSON bytes (lib/camera_transform.py:223) and returns it on the CameraTransform dataclass (:48-53). load_display_transform_params surfaces (params, sha256) (model_domain_display.py:31-34) so every baked image records exactly which transform produced it.
  • Schema gate. validate_camera_transform_payload requires schema == "camera_transform_v1", model_version == "v2", used_lattice falsy, and exactly 48 finite params / 10 knots (lib/camera_transform.py:178-198). Lattice transforms are explicitly unsupported.
  • Caching. Both the transform and the LUT are cached keyed on (resolved path, mtime_ns) and the cache is cleared on every fresh load (lib/camera_transform.py:209-227, :340-353).

The PNG encoding contract

This is the part most likely to bite a developer. The pixels move between domains and encodings in a fixed, test-pinned sequence (bake_view_domain_images, model_domain_display.py:73-125):

ImageDomainEncoding written
predicted.pngmodel-domain transmissiongamma-2.2 sRGB (_srgb8_from_linear, appearance_model.py:70 → clip(rgb)**(1/2.2)*255)
predicted_appearance.pngdisplay appearance (F applied)round(F · 255) — no extra gamma
target_transmission.pngmodel-domain target_srgb8_from_linear (comparable to predicted.png)

The recipe is:

  1. Recover model-domain transmission from predicted.png as (png/255) ** 2.2 (model_domain_display.py:105). This undoes the gamma-2.2 encoding predicted.png was written with.
  2. Apply F via apply_appearance_transform — its output is already display-encoded sRGB, so it must be written as round(F·255 + 0.5) with no further gamma (model_domain_display.py:106-109, contract pinned at :86-92).
  3. Target image depends on the ingress toggle: ingress-on writes G(source) (the actual solve target this run aimed at) through _srgb8_from_linear; ingress-off byte-copies source.png (the decoded source was the target) so the frontend’s Appearance/Transmission rule stays unconditional (model_domain_display.py:111-120).

bake_view_domain_images returns a provenance dict (display_transform_path, display_transform_sha256) that the server folds into run.json as run_metadata["model_domain_display"] (generator/server.py:5141).

Which preview images get baked

The server bakes these inside _run_solve (loud failure = solve failure; a run without these assets must not render):

  • bake_view_domain_images (generator/server.py:4836) writes predicted_appearance.png + target_transmission.png. These back the Appearance / Transmission display toggle; the predicted-appearance URL is surfaced at generator/server.py (predicted_appearance_url).
  • bake_appearance_png (model_domain_display.py:47, called at generator/server.py:4859) writes the colour-only predicted render for the Recipe viewer’s Color Regions tab. The source is result.predict_image_color_only() (generator/facade.py:494) — the same forward composition as predict_image, but with the white-cap term (boundary + detail) zeroed via _cap_zeroed_thickness_maps() so the cap’s luminance shaping does not drown out the colour story. It is baked through the same F as the full appearance so the two viewer cards are comparable; it shares bake_view_domain_images’s exact encoding contract (recover (png/255)**2.2, apply F, write round(F·255)). Output: predicted_color_only_appearance.png, surfaced as predicted_color_only_appearance_url (generator/server.py:5162).

Liveness

Both bakers are wired and live on master. bake_appearance_png and predict_image_color_only exist only in the merged-recipe-viewer state (the main checkout / master); some development worktrees predate that merge and lack them. Verified via git grep against the main checkout (generator/server.py:4855, :4859; generator/facade.py:494).

How to drive it

  • Leave ingress on. It is the default and matches how the models were calibrated. Turning it off reverts to a plain sRGB decode that ignores the camera’s colour rendering — useful only for A/B diagnostics. The toggle lives in the solve-owned settings (it changes the run fingerprint).
  • Keep the artifact fresh. If solves fail with a CameraTransform artifact … Rebuild via Calibration → Camera Transform error, the Prisma/data/camera_transform/ generation is missing or its hashes don’t match — rebuild it from the calibration app.
  • Reading the previews. In the viewer, Transmission mode shows the model-domain pair (predicted.png vs target_transmission.png); Appearance mode shows predicted_appearance.png — the print as it should look backlit. The recipe viewer’s colour-only card drops the white cap on purpose.
