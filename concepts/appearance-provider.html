Appearance provider

In one sentence: the appearance provider is the one swappable object a solve creates to answer “what colour will this stack of filament layers be when backlit?”, so the solver and LUT builder never care which colour model is underneath.

The appearance provider is the forward-model boundary of the generator. Everything downstream of profile-loading — LUT construction, the solver, ΔE diagnostics, the luminance handler, palette suggestion — talks only to this interface. Swap the implementation and the colour model changes without touching any caller. There are two backends today, both in Prisma/generator/appearance_model.py.

How to drive it (for users)

You pick the backend with one config field, appearance_model_provider (server.py:408 default, server.py:594 typed field). The web UI exposes it as the #cfgAppearanceModelProvider selector (app/index.html:694, set in app/app.js:4629, read in app/app.js:6329). Two legal values:

ValueBackend classWhat it is
historical_spline (default)HistoricalSplineAppearanceProvider (appearance_model.py:82)The multiplicative spline model: a stack’s colour is the product of independent per-filament transmission curves. No extra artifact needed — it reads the spline profile JSONs you already have.
photo_stack_bundlePhotoStackBundleAppearanceProvider (appearance_model.py:210)A context-aware model fit from photographed swatch stacks, loaded from a calibration bundle artifact.

The photo-stack backend needs two more settings:

  • photo_stack_bundle_path — a live calibration candidate directory or its runtime_bundle.json (appearance_model.py:229). It is mandatory for this backend; passing None raises immediately (appearance_model.py:232). Whenever the selected provider is anything other than photo_stack_bundle, the UI nulls this path so it can’t leak into a spline solve (app/app.js:6330).
  • use_corrections (server.py:407 default, server.py:593 typed field) — the direct-vs-corrected toggle described below.

These are per-run solve settings, not export presentation. Changing any of them produces a different solve fingerprint and invalidates a cached solve (see Solve fingerprint / stale-solve invalidation below).

The factory

create_appearance_provider (appearance_model.py:606) is the only construction path. It is called live on every solve at runner.py:670 and again for the palette-suggest white-rescale pass at server.py:3803 — both confirmed by grep, not dead code. It normalises the kind string and dispatches:

  • historical / historical_spline / spline → spline provider (appearance_model.py:618)
  • photo_stack_bundle → photo-stack provider (appearance_model.py:624)
  • anything else → ValueError("unknown appearance_model_provider: …") (appearance_model.py:629). The v2 rename dropped the old non_ml_photo_stack / v63 aliases, so those are now rejected here.

The constructed instance is stashed on the pipeline state as state.appearance_provider (runner.py:670, pipeline/state.py:236) and read back wherever appearance is needed.

StackRequest / Layer — the request shape

A Layer is just tuple[str, float] = (filament_id, thickness_mm) (appearance_model.py:33). A StackRequest (appearance_model.py:36, frozen dataclass) is one physical stack: white_base, a tuple of color_layers, and white_cap — all Layers. The batch methods take a Sequence[StackRequest]. The LUT builder builds a grid of them (lut.py:826) and scores the whole grid in one provider call (lut.py:847); the paper-white rescale helper builds a single white-only request at solve.py:267.

Disambiguation: StackRequest is the input to a prediction. It is a near-duplicate in spirit of VisibleRecipe / StackDefinition used elsewhere for recipe display, but those describe a result (what colours a region used), not a query. Do not conflate them.

The two backends, mechanically

Spline (HistoricalSplineAppearanceProvider). predict_stack_linear_rgb (appearance_model.py:106) assembles [(wb_profile, d_wb), (colour_profile, d)…, (wc_profile, d_wc)] and calls compose_stack (model.py:71 → lib.transmission.compose), which multiplies the per-layer transmission vectors. Layer order is irrelevant because multiplication commutes. Thickness-map prediction (appearance_model.py:171) precomputes per-step transmission LUTs and multiplies them pixel-wise. This is the model described on The Transmission Model.

Photo stack (PhotoStackBundleAppearanceProvider). Loads a runtime bundle (appearance_model.py:268) and builds a row-shaped predictor (appearance_model.py:271). Each StackRequest is collapsed (collapse_adjacent_layers, appearance_model.py:294) and turned into a model runtime row (appearance_model.py:296) the predictor can score. Off-grid thicknesses fall back to the row predictor; grid-aligned thicknesses go through a vectorized LUT evaluator (photo_stack_lut.predict_combo_model_linear_rgb, appearance_model.py:534). Because it is context-aware, it cannot be reduced to independent per-filament profile JSONs — that is the whole reason this boundary exists (appearance_model.py module docstring, line 1; verified against the code, not just the header).

Direct vs corrected toggle

The photo-stack backend has two flavours selected by use_corrections:

  • direct (use_corrections=False) — the raw bundle model output.
  • corrected (use_corrections=True) — the direct output with a separate correction_layer.json sibling artifact applied (apply_photo_stack_correction, appearance_model.py:404).

Corrections live in a separate sibling artifact on purpose, so you can compare direct against corrected without rebuilding the baseline bundle (appearance_model.py:215). Requesting corrections when no valid correction_layer.json is present raises rather than silently falling back to direct (appearance_model.py:261). The chosen flavour is baked into the fingerprint as direct or corrected:<hash> (appearance_model.py:273).

Fingerprints and stale-solve invalidation

Each provider exposes fingerprint() — a string that changes whenever the model’s meaning changes:

  • Spline: "historical_spline:" + hash(colour/wb/wc profiles) (appearance_model.py:97). Edit a profile JSON and the fingerprint moves.
  • Photo stack: "photo_stack_bundle:<bundle.fingerprint>:photo_stack_logic:<N>:<direct|corrected:hash>:<APPEARANCE_DOMAIN_VERSION>" (appearance_model.py:277). It folds in the bundle identity, the predictor logic version, the correction choice, and the domain-contract version.

APPEARANCE_DOMAIN_VERSION (appearance_model.py:79, currently "domain-pass-through-v1") is the lever for the pass-through change described below: bump it and every photo-stack fingerprint changes.

The fingerprint does two jobs:

  1. LUT cache key — _build_luts_with_provider keys the cached .npz on provider.fingerprint() (lut.py:658, fed into _provider_cache_key at lut.py:680). A different model → a different cache file → no stale LUT reuse.
  2. Solve freshness — the server’s _solve_owned_fingerprint (server.py:2035) mirrors the photo-stack predictor logic version (server.py:2080) and APPEARANCE_DOMAIN_VERSION (server.py:2089) into the solve-identity hash. So a code-only predictor change, or a domain-contract bump, marks existing solves/exports stale on swap/export — even though the provider instance doesn’t exist at config-hash time. This is checked at export (server.py:5444) and swap-instructions (server.py:5782).

The pass-through naming trap (read this)

This is the easiest thing to get wrong. After the 2026-06-12 projection-slot retirement, the photo-stack provider’s appearance-named methods return model-domain RGB, not display-domain. They are pure pass-throughs kept only for API-name stability:

  • predict_stack_appearance_linear_rgb_batch just calls predict_stack_model_linear_rgb_batch (appearance_model.py:423).
  • predict_stack_linear_rgb_batch is a “compatibility alias” for the same model-domain method (appearance_model.py:413).
  • project_model_linear_rgb_to_appearance returns its input unchanged — a “compatibility pass-through for the retired solve-domain conversion” (appearance_model.py:418).
  • predict_thickness_maps_appearance_linear_rgb forwards to predict_thickness_maps_model_linear_rgb (appearance_model.py:565).

So the word “appearance” in a method name does not mean display-converted output. Model-domain values are the flatfield-normalized model/correction output; conversion to display happens at the generator’s ingress/display boundaries, not here (appearance_model.py:218 domain-contract comment). The class docstring at appearance_model.py:210 documents this; the APPEARANCE_DOMAIN_VERSION = "domain-pass-through-v1" constant is the live proof the projection was retired. If you are looking for where model→display happens, it is not in this file — see Colour domains / docs/color_domain_doctrine.md.

Where it sits in a solve

The webapp solve runs the staged backend (run_staged_backend_path / staged_runner.py), not solve.py’s legacy “6-step” CLI engine. The staged runner still branches on state.appearance_provider.model_kind (staged_runner.py:6209, staged_runner.py:8257) and the runner picks the matching LUT builder: spline → _build_luts_raw (runner.py:799), photo-stack → _build_luts_with_provider (runner.py:815). So the provider choice also selects the Joint LUT builder, exactly as the solver path does.
