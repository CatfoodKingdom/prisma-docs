Gamut mapping

In one sentence: before the solver picks filament thicknesses, out-of-reach target colours are pulled onto the set of colours the palette can actually print — either by squeezing chroma (keeping lightness and hue) or by projecting onto the convex hull of achievable colours (allowing a small lightness shift).

The set of colours a chosen palette can reproduce when backlit is its gamut. A source image almost always asks for colours outside it (vivid saturated reds, deep blues). Rather than let the Joint LUT nearest-neighbour query chase an impossible target and return whatever LUT sample happens to be closest, the pipeline first remaps every out-of-gamut target onto (or very near) the achievable set, in OKLab space, on the solve grid. The solver then queries against targets it can actually hit.

Where it runs

Gamut mapping is stage 3 of 5 in the fixed pipeline spine (load → lut → gamut → solve → stats, with an optional group stage). The tracker advances the "gamut" stage at generator/pipeline/runner.py:832 and the work is done by _apply_target_gamut_mapping (generator/pipeline/runner.py:67), called at generator/pipeline/runner.py:833.

It runs after the LUTs are built (the hull and chroma checks both need the achievable colour cloud) and before the staged solve. The runner mutates state.solve_target_oklab in place (generator/pipeline/runner.py:146); the staged backend then reads that already-remapped cloud (generator/pipeline/staged_runner.py:759) and never re-runs gamut mapping itself.

This is the webapp path

The live webapp runs the staged backend (run_staged_backend_path, invoked at generator/pipeline/runner.py:846). The remap happens once, in the runner, on the targets. solve.py’s solve_image (which embeds its own gamut step at generator/solve.py:472) is the legacy CLI engine — reached only through generator/pipeline_cli.py:634, not the web app. Both engines share the same two batch functions in solve.py, so the behaviour described below is identical regardless of entry point.

The three modes

The mode is the gamut_mode setting (PipelineConfig.gamut_mode, default "hull", generator/pipeline/state.py:75). The runner lower-cases and normalises it (generator/pipeline/runner.py:95); "none", "off", "disabled" all mean no remap; anything other than hull/chroma/none raises (generator/pipeline/runner.py:108-109).

chroma — chroma compression (preserves L* and hue)

gamut_map_batch (generator/solve.py:115) first queries the LUT for every target and flags those whose nearest-achievable dE exceeds de_threshold as out of gamut (generator/solve.py:132-133). For each flagged pixel it runs a 12-step binary search (n_steps=12, generator/solve.py:119) on a single scalar s ∈ [0,1] applied to the chroma channels:

candidate = [L, a*s, b*s]

L is never touched (generator/solve.py:142 keeps L constant), and because a and b are scaled by the same factor the hue angle atan2(b,a) is preserved — only chroma (saturation) shrinks. The search narrows [lo, hi] toward the largest s whose candidate is within de_threshold of an achievable colour, and keeps the best-seen candidate even if no s fully lands in gamut (generator/solve.py:155-176). The whole batch is searched in parallel — all out-of-gamut pixels step together (generator/solve.py:151-163), which is the vectorisation that replaced the old per-pixel gamut_map_oklab (still present at generator/solve.py:89 but with no live caller — only used in the now-removed scalar path).

This mode is conservative: it never changes how light or dark a colour looks, only how vivid. The cost is that very saturated targets can compress to noticeably duller colours.

hull — convex-hull facet projection (allows a small L* shift)

gamut_map_hull_batch (generator/solve.py:180) works geometrically instead of by LUT query. The achievable colours form a point cloud; build_hull_from_luts (generator/lut.py:1295) wraps them in a scipy.spatial.ConvexHull (deduplicated to 4-decimal OKLab points, generator/lut.py:1306-1308). Each hull facet has a plane equation normal·x + offset; a point’s signed distance to a facet is positive when it lies outside.

Two subtleties, both verified in code:

  1. What counts as out of gamut here is geometric, not LUT-distance. A point is flagged only if its maximum signed distance over all facets exceeds de_threshold (generator/solve.py:210-212). This deliberately differs from chroma mode: a target can sit inside the hull yet be farther than de_threshold from the nearest discrete LUT sample. Projecting such interior points to a facet would invent artificial saturated boundary colours, so hull mode leaves them alone (generator/solve.py:205-209).
  2. Projection is iterated up to 4 times. Each pass subtracts the violation along the single most-violated facet’s normal (generator/solve.py:224-233). One pass handles points outside a single facet; the loop handles points outside several facets near a hull corner, where one projection can still leave the point outside a neighbouring facet.

Because the projection moves the point in full 3D OKLab, L* can shift (along with a and b). The docstring trade-off is real: hull mode produces lower total dE at the gamut boundary than chroma compression, at the price of letting lightness move a little (generator/solve.py:191-193).

Hull-corner slight-outside is acceptable by design

Single-facet projection is an intentional approximation (generator/solve.py:195-197). After up to 4 passes a point near a hull corner may still land slightly outside the hull. This is fine because the downstream Joint LUT query (the solve stage) always snaps to the nearest achievable colour regardless — it can only ever return a real, printable LUT sample. The remap’s job is to get the target close, not to land it exactly on the surface.

none

No remap. The runner still records a diagnostic header with effective_mode = "none" and remapped_count = 0 (generator/pipeline/runner.py:98-107) and returns early, so the raw targets flow straight into the solve. Useful for diagnosis (seeing how far the solver drifts unaided) but generally leaves saturated regions chasing colours the print cannot make.

The optional white-point rescale (pre-step)

Independent of the mode, an optional white-point rescale runs first, gated by the gamut_white_rescale toggle (default False, generator/pipeline/state.py:76). When the toggle is off the block is skipped entirely and compute_paper_white_rgb is never even called (generator/pipeline/runner.py:79-83).

When on, apply_gamut_white_rescale_to_targets (generator/pipeline/target_cloud.py:106) computes the print’s paper white — the appearance of the thinnest printable white-only stack (white base + minimum-thickness cap, no colour layers) through the active Appearance provider (compute_paper_white_rgb, generator/solve.py:245). It then applies a per-channel von Kries adaptation of every OKLab target from source-white to that paper white (rescale_oklab_targets, generator/solve.py:282): round-trip OKLab → linear RGB, multiply channel-wise by the paper-white RGB, convert back to OKLab. Because OKLab↔linear is bijective, the only net change is the per-channel scale.

The rescale no-ops (returns None, no change) when there is no white base configured, or when the model’s paper white is effectively [1,1,1] (generator/solve.py:256, generator/solve.py:277). It runs before the mode is even inspected, so it applies whether the mode is hull, chroma, or none (generator/pipeline/runner.py:76-93). In hull mode the runner additionally does a diagnostic-only hull count pass on the pre-rescale targets to report how the rescale changed the out-of-gamut population (pre_rescale_out_of_gamut, generator/pipeline/runner.py:124-130).

The first two describe the remap; the last describes residual unreachability — colours so far outside the gamut that even after remapping the best achievable stack still misses by more than de_threshold. Because __gamut_mask__ is computed on the already-remapped state.solve_target_oklab, a non-zero count there is genuine: the palette physically cannot reach those colours. The remapped-pixel count shown in __target_gamut_mapping__ is usually much larger (everything that needed moving), while n_out_of_gamut counts only what remained unreachable.

The de_threshold knob

Both modes key off de_threshold (PipelineConfig.de_threshold, default 0.05, generator/pipeline/state.py:72). It is an OKLab Euclidean distance, where roughly 0.02 ≈ 1 JND (just-noticeable difference) per the in-code note at generator/solve.py:99. It sets two things at once: how far from achievable a target must be to count as out of gamut (and so get remapped), and — separately, at the solve stage — how far the final stack may miss before a pixel is counted in n_out_of_gamut. Raising it remaps fewer pixels but tolerates larger colour error; lowering it remaps aggressively.

How to drive it (users)

  • Leave it on hull unless you have a reason not to — it gives the lowest colour error at saturated boundaries.
  • Switch to chroma if you specifically need lightness preserved exactly (e.g. a portrait where you care more about correct brightness than correct saturation). It will never change how light/dark a region reads, only how vivid.
  • none is a diagnostic setting, not a production one.
  • gamut_white_rescale adapts targets to the print’s actual paper white; turn it on if the print reads with a colour cast relative to the source’s white. It is a no-op when there is no white base or the paper white is already neutral.
