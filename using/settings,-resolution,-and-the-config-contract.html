Settings, resolution, and the config contract

In one sentence: the generator stores a flat dict of solve settings per session, validates resolution fields against a canonical schema that rejects legacy aliases and enforces a solve-coupled pitch pair, force-enables the mandatory printability settings the UI cannot turn off, and then translates that dict into the typed SolveConfig / PipelineConfig dataclasses whose __post_init__ re-runs the resolution backstop as a last line of defence.

This page is for two readers: the user driving the Settings panel who wants to know what each knob does and which ones they are not allowed to disable, and the developer who has forgotten how a flat session dict becomes the typed config the solver consumes. See also The solve pipeline, generator.facade, and generator.config.resolution_schema.

The two-layer config model

There are two distinct config representations and you should never confuse them:

LayerTypeWhereRole
Session configplain dictsession["config"] in server.pyMutable per-session settings the frontend PATCHes. Canonical-only.
Typed solve configSolveConfig dataclassfacade.py:160Built fresh from the session dict at each solve via _build_solve_config (server.py:984). Immutable snapshot the solve consumes.

A third type, PipelineConfig (pipeline/state.py:58), is what the runner actually receives. The facade translates SolveConfig → PipelineConfig field-by-field in _to_pipeline_config (facade.py:612). Both dataclasses re-validate resolution in their __post_init__ (covered below).

The flow at solve time:

session dict
  → _apply_luminance_mode_preset       (server.py:907)   expand luminance_mode → backend flags
  → _force_mandatory_product_settings  (server.py:847)   force printability ON, etc.
  → _build_solve_config                (server.py:984)   dict → SolveConfig (validates in __post_init__)
  → _to_pipeline_config                (facade.py:612)   SolveConfig → PipelineConfig (validates again)
  → run_pipeline                       (runner.py:587)   → run_staged_backend_path (staged backend)

Note for developers: the webapp solve runs the staged backend. run_pipeline delegates to run_staged_backend_path (pipeline/runner.py:843, imported from pipeline/staged_runner.py:10310). The “6-step” engine in solve.py is the legacy CLI engine and is NOT on the webapp path. Diagnostics (__de__, __gamut_mask__) for staged results live in PipelineState.diagnostics, not in thickness_maps (pipeline/state.py:266-273).

Resolution: three canonical fields, one coupled pair

All resolution is expressed through exactly three canonical fields (config/resolution_schema.py:17):

FieldDefaultMeaning
image_sample_pitch_mm0.20mm per sampled source pixel — the observation grid the image is read onto.
solver_fine_pitch_mm0.20mm per solver cell — the solve grid the thickness maps are computed on.
color_region_target_mm0.60target width for colour regions — independent of the pitch pair.

The defaults are _PITCH_FAMILY_DEFAULT = 0.20 and _COLOUR_FAMILY_DEFAULT = 0.60 (config/resolution_schema.py:149-150).

The solve-coupled pitch invariant

image_sample_pitch_mm and solver_fine_pitch_mm are a coupled pair: when both are present they must agree (within rel_tol=1e-9, abs_tol=1e-6 per _agree, config/resolution_schema.py:95), and supplying one without the other is an error. The normalizer (normalize_resolution_schema, config/resolution_schema.py:99) enforces this three ways:

  • image set but solver missing → conflict error (:119)
  • solver set but image missing → conflict error (:123)
  • both set but disagree → conflict error (:127)

When valid, the normalizer collapses the pair: it writes the single accepted pitch into both fields (config/resolution_schema.py:132-134), so downstream code can read either. The colour-region target is validated independently and never coupled (:139).

Practical consequence for users: there is no way to set the image sampling pitch different from the solver pitch. They are one number wearing two names. The colour-region size is the only resolution knob you can move independently.

Rejected legacy aliases

Three retired field names are hard-rejected at ingress (LEGACY_RESOLUTION_REPLACEMENTS, config/resolution_schema.py:23):

Legacy aliasReplaced by
pixel_size_mmimage_sample_pitch_mm and solver_fine_pitch_mm
mesh_xy_pitch_mmimage_sample_pitch_mm and solver_fine_pitch_mm
color_pixel_mmcolor_region_target_mm

If any of these appears with a non-None value, the normalizer raises ResolutionSchemaLegacyFieldError (config/resolution_schema.py:111-112), whose message names the canonical replacement(s). A legacy key present but set to None is silently dropped, not rejected (:113).

ConfigPayload is declared with model_config = ConfigDict(extra="allow") (server.py:539) specifically so stale aliases land in model_extra and can be inspected and rejected loudly — _payload_model_fields (server.py:2745) scans the extras for legacy aliases (:2760) and for a frozen set of _RETIRED_CONFIG_FIELDS (server.py:2682, e.g. smooth_stl, solver_backend, the retired guided_surface_* / hybrid_* cap-shaping fields, tv_weight, the v2_translucent_underfill_* family) and raises HTTP 422 rather than silently swallowing them. Unknown non-retired extras keep the old behaviour and are ignored (:2770).

On egress, _with_canonical_pitch_egress (server.py:1921) defensively pops pixel_size_mm, color_pixel_mm, and mesh_xy_pitch_mm from any dict before it is returned to the client, so the live session never serialises a legacy alias.

Where the schema runs (ingress vs. backstop)

There are two enforcement points and they have different jobs:

  1. Ingress normalizer — normalize_resolution_schema(...) operates on external dict payloads. It rejects legacy aliases and validates the pitch pair before anything is stored. It runs at every external write surface:

    • POST /api/session/config (server.py:2791) — merges incoming over current session, then normalizes the merge
    • POST /api/settings-profiles create (server.py:3371)
    • PUT /api/settings-profiles/{id} update (server.py:3418)
    • loading a saved settings-profile record (server.py:3162)

  2. Runtime dataclass backstop — _apply_resolution_backstop(cfg) (config/resolution_schema.py:153) runs inside __post_init__ of both typed configs: SolveConfig (facade.py:283-286) and PipelineConfig (pipeline/state.py:175-178). Because the runtime dataclasses use canonical fields only and never see external dicts, the backstop does not check for legacy aliases. It only:

    • applies the family defaults when both pitch fields are absent (config/resolution_schema.py:167-169)
    • re-enforces the coupled pitch invariant — missing-one or disagreeing values still raise ResolutionSchemaConflictError (:170-181)
    • defaults color_region_target_mm to 0.60 when absent, else coerces to float (:187-190)

So even a SolveConfig constructed directly in a test or a future code path cannot smuggle in a mismatched pitch pair: construction itself raises.

Typed errors → HTTP

Both schema errors subclass ValueError:

  • ResolutionSchemaConflictError (config/resolution_schema.py:39) carries field_a, value_a, field_b, value_b.
  • ResolutionSchemaLegacyFieldError (config/resolution_schema.py:63) carries field and replacements.

_translate_resolution_schema_error (server.py:2649) maps them to HTTP 422 with structured detail:

Errordetail.errorExtra fields
Legacy aliaslegacy_resolution_fieldfield, replacements
Pitch conflictresolution_schema_conflictfield_a, value_a, field_b, value_b

Retired non-resolution fields map to retired_config_field (also 422) via _retired_config_field_error (server.py:2731). The session-config and settings-profile endpoints all wrap their normalize_resolution_schema calls in try/except (ResolutionSchemaConflictError, ResolutionSchemaLegacyFieldError) and re-raise the translated HTTPException (e.g. server.py:2792, :3372, :3419).

Mandatory product settings the UI cannot disable

_force_mandatory_product_settings (server.py:847) is the safety gate. It is called on every config merge (server.py:2807), on egress (server.py:1923), and again inside _build_solve_config (server.py:991) — so even a hand-edited saved profile cannot ship with printability off. It forces:

SettingForced toEffect
enforce_printabilityTruePrintability enforcement is always on.
cap_continuity_cleanupTrueSingle-pixel cap pinholes are always filled.
color_region_target_from_printabilityTrueColour-region width is derived from the printability floor.
stage2_final_printability_gate_fine_overrideTrueFinal Stage-2 printability gate always runs.
stage2_printability_gate_fine_overrideTrueStage-2 printability gate always runs.
stage2_printability_repair_fine_overrideTrueStage-2 printability repair always runs.
stage4_printability_gate_detailTrueStage-4 detail printability gate always runs.

It also quantises d_wc_min up to a whole number of layers (server.py:850-853) — the minimum white cap is rounded to ceil(d_wc_min / layer_height) layers — and, in fixed cap mode, disables the detail-cap surfaces (server.py:864-867). stage2_boundary_mutation_edge_run_mode is forced to mirror whether boundary mutation is enabled (server.py:861).

Inside _build_solve_config these same flags are hard-wired again — enforce_printability, emit_blueprint_printability, the three stage-2 gates, stage4_printability_gate_detail, and color_region_target_from_printability are all passed as literal True / _enforce (server.py:1040-1079), regardless of what the session dict said. The defaults in ConfigPayload (server.py:573-579) and _DEFAULT_CONFIG (server.py:379-385) agree: these ship True.

User-facing summary: printability is not a toggle. You can change how aggressive the printer feature-size floor is (via the active printer’s nozzle config, threaded in at server.py:998-1003), and you can set allow_print_despite_hazards to acknowledge a hazardous result, but you cannot turn the gates off.

Research-only knobs

A few flags are deliberately not exposed for normal webapp solves and stay off unless a CLI/API caller sets them:

  • emit_pressure_diagnostics and emit_geometry_attribution — heavier attribution artifacts, defaulted False and only honoured from the raw session value (server.py:1034-1039). The comment at server.py:1006-1007 marks them CLI/API-only.
  • emit_blueprint_printability stays on for normal solves (forced True at server.py:1040).

Solve-cache invalidation

_SOLVE_OWNED_KEYS (server.py:1945) lists every setting that, when changed, invalidates a cached solve — the canonical pitch trio, the detail-cap family, the stage-2/4 gates, core physics (palette, d_wb, d_wc_min, d_wc_max, t_max, k_max), and source-ingress settings (de_threshold, gamut_mode, model_domain_ingress, chroma_weight, luminance_mode, …). The legacy aliases are intentionally absent from this list because they are rejected at ingress and never stored (server.py:1939-1944). Grouping selection is hashed separately via module state.
