Command-line entry points and filament availability

In one sentence: the generator ships two command-line scripts — a legacy batch solver (pipeline_cli.py, not the web-app path) and a preprocessing A/B harness (preprocessing_eval_cli.py) — and one of pipeline_cli.py’s files quietly hosts the image-loader and palette-validator that the live server still imports, gated by an exclude_from_model generation-availability policy.

This page serves two readers: the user who wants to drive a CLI, and the developer who has forgotten which parts of pipeline_cli.py are dead and which are load-bearing. The short version: the CLI’s run() solve engine is legacy and unused by the product, but several helper functions defined in the same file are imported by the live server.

pipeline_cli.py — legacy batch solver

Driving it

main() (pipeline_cli.py:916) parses args, resolves the palette (positional IDs or --palette-file JSON, pipeline_cli.py:934), auto-loads pair corrections from data/filaments/pair_corrections.json unless --no-corrections (pipeline_cli.py:944), calls run(...), then prints a per-filament usage table via print_summary() (pipeline_cli.py:991). --list-filaments (pipeline_cli.py:920) just lists every spline profile on disk with its registry display name and exits.

Header warning. The module docstring (pipeline_cli.py:1) calls the file lith_pipeline.py and shows from lith_pipeline import run — that filename no longer exists. Trust the line anchors below, not the header.

run() is legacy and unwired

run() (pipeline_cli.py:402) is a self-contained “6-step” solve engine: validate palette → load image → load spline profiles → build joint LUTs → solve (per-pixel or SLIC-superpixel) → save diagnostic PNGs (de_map.png, predicted.png, source.png, cap_height.png, etc.). It explicitly does not export a mesh — the final step prints “Mesh export is handled by the post-solve exporter” (pipeline_cli.py:787).

This engine is not the web app. The product solve runs the staged backend — run_staged_backend_path (pipeline/staged_runner.py:10310), invoked from pipeline/runner.py:846. Grep confirms no product module imports run: it is reachable only from pipeline_cli.main(). The in-repo legacy audit reaches the same verdict — “pipeline_cli.run(...) is not part of the live webapp solve path” (generator/docs/legacy_audit/03_LEGACY_PIPELINE_CLI_SOLVE_PATH.md:106), classing both run(...) and its segment_image(...) helper as dead_or_legacy_cli_only (lines 164-165). See generator.pipeline.staged_runner for the path that is live.

What in this file the live server actually uses

The same pipeline_cli.py file hosts a handful of helpers that the product imports — this is the trap. They live in a CLI file but are not legacy. server.py:65 imports exactly two of them:

HelperDefinedLive caller(s)Role
load_imagepipeline_cli.py:61server.py:825 (in _load_run_source_image), palette/suggest.py:403sRGB load + EXIF transpose + frame crop/rotate/flip + resize to print resolution
apply_adjustmentspipeline_cli.py:199server.py:832 (only call site)non-destructive exposure/contrast/saturation/tint/highlight/shadow/temperature on the loaded raster
validate_palettepipeline_cli.py:338pipeline/runner.py:654, and run() itself (pipeline_cli.py:508)profile-present + not-excluded gate for a new solve

So in the product: server.py’s shared loader _load_run_source_image (server.py:822) calls load_image then apply_adjustments, and the live solve calls validate_palette from pipeline/runner.py:654 (the staged path’s “Fixed spine: Load” step). The legacy audit confirms all four as live (generator/docs/legacy_audit/03_LEGACY_PIPELINE_CLI_SOLVE_PATH.md:159-163); their eventual rehoming out of a CLI file is a noted cleanup, not done yet.

For developers: do not assume “it’s in pipeline_cli.py, so it’s dead.” run()/segment_image()/main() are legacy; load_image/apply_adjustments/validate_palette/load_filament_registry are live product surface. See Pipeline Map for where they sit.

preprocessing_eval_cli.py — the A/B harness

Driving it

This is a thin wrapper (main(), preprocessing_eval_cli.py:97). It loads two images, builds one shared SolveConfig from --palette / --white-base / --profiles (preprocessing_eval_cli.py:89), calls evaluate_pair (preprocessing_eval_cli.py:114), and prints the metric bundle as JSON. Artifact writes (predicted PNGs, delta-dE heatmap, report.json) are opt-in via --out-dir (preprocessing_eval_cli.py:72). --solver-preset accepts only "full" (preprocessing_eval_cli.py:49).

How it works (and why it’s not the legacy engine)

The CLI delegates to evaluate_pair (evaluation/preprocessing_harness.py:105), part of generator.evaluation.preprocessing_harness. Because it builds a real SolveConfig, each arm solves through the live facade/staged path, not pipeline_cli.run() — so the two scripts share a name space (“CLI”) but exercise different engines. evaluate_pair is live and tested (tests/generator/test_preprocessing_evaluation_harness.py) and is also driven by scripts/evaluate_preprocessing_first_bakeoff.py:315. The CLI module itself is a leaf — nothing imports preprocessing_eval_cli (only the harness it wraps is imported elsewhere).

Note the metrics reported are A4 primitives — dE, out-of-gamut, small-component, cap total-variation — per the CLI’s own description (preprocessing_eval_cli.py:58). Its own header cites a planning doc (F4_PHASE.md) — verify behaviour against the line anchors, not the prose.

Filament generation-availability policy (exclude_from_model)

Both the CLIs and the web app share one gate on which filaments may enter new work, defined in generator.filament_policy (filament_policy.py).

The rule

A filament flagged exclude_from_model: true in data/filaments/registry.json is treated as unavailable for new generation (filament_policy.py:1). The flag is originally a calibration model-fit policy field, but the generator reuses it as a stop-gap until a dedicated generation_availability field exists. The contract: an excluded filament must not silently enter a new solve, palette validation, or palette suggestion just because a stale profile file still sits on disk — but existing saved palettes/runs are preserved; only NEW work is gated (filament_policy.py:9).

The three functions and who calls them

FunctionDefinedReturnsLive callers
is_generation_available(fid, registry)filament_policy.py:35False iff flaggedbase predicate for the other two
unavailable_for_generation(ids, registry)filament_policy.py:48excluded subset, ordered + de-dupedpipeline_cli.validate_palette (pipeline_cli.py:360), server.py:3501 (palette pre-check endpoint), server.py:3767 (suggestion white-base/cap refusal)
excluded_filament_ids(registry)filament_policy.py:40set of all excluded idsserver.py:3886 + palette/suggest.py:1939 (passed as exclude_filament_ids to the suggester so candidates are filtered up front)

Where the gate fires

  • Palette pre-check (UI): POST /api/palette/validate (server.py:3488) returns missing (no profile on disk) and unavailable (excluded) separately. This is advisory; the solve re-validates.
  • Solve / suggestion validation: validate_palette (pipeline_cli.py:338) raises plain ValueError for a missing profile, and raises FilamentUnavailableError (filament_policy.py:18) for an excluded one. That error subclasses ValueError so existing except ValueError handlers still catch it, while callers that care can distinguish a policy refusal from a missing-profile error (pipeline_cli.py:343, filament_policy.py:22).
  • Suggestion: an excluded white base/cap is a hard 400 up front (server.py:3768), because the suggester cannot drop a fixed white the way it drops colour candidates; excluded colour candidates are filtered via excluded_filament_ids before search.

See Model-domain ingress and generator.model for why a profile’s existence on disk is not sufficient to trust it.

Disambiguation — two different excluded_filament_ids

There are two unrelated functions with this name; do not confuse them:

GeneratorCalibration / fitting
Modulegenerator/filament_policy.py:40calibration/fitting/filament_exclusions.py:19
Inputa registry dicta store object (calls store.list_filaments())
Purposegate new generation workdrop a filament from every production fit

Both read the same underlying exclude_from_model field, but they operate on different inputs and serve different halves of the product (generation vs. model fitting). When working in the generator, the registry-dict version is the relevant one.
