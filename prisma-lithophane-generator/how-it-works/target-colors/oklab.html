OKLab

OKLab

Jul 23, 20263 min read

The solver has to answer one question millions of times: how far is this candidate stack’s color from the color this pixel asked for? Distance between raw red, green, and blue values is a poor judge of that, because equal steps in RGB do not look equally different to the eye. A small numeric gap in one part of the range is glaring; a larger gap elsewhere is invisible. A solver that trusted RGB distance would spend its effort on differences no one can see and ignore ones that stand out.

OKLab is a perceptual color space built so that equal numeric distance corresponds to roughly equal perceived difference. Every color becomes a point on three axes — one lightness axis and two color-opponent axes — arranged so that the straight-line distance between two points tracks how different they look. The transform from linear RGB is fixed: a 3×3 matrix into an intermediate cone-response space, a cube-root compression, and a second 3×3 matrix out. Lightness here runs on a 0–1 scale, not the 0–100 of textbook Lab.

Why the solver lives here

Putting both sides into OKLab turns “find the closest printable color” into ordinary nearest-point search. Prisma converts the image’s per-pixel targets into OKLab once, up front, and stores every candidate filament stack’s predicted color in OKLab too — that is what fills The Color LUT. Choosing a recipe for a region then reduces to finding the stored point nearest the target. The distance used is plain, unweighted Euclidean:

ΔE=(ΔL)2+(Δa)2+(Δb)2​

That same distance, taken between each pixel’s target and the color the solved stack is predicted to produce, is the solve’s quality measure. The headline figure is the root-mean-square of those per-pixel distances over the image; the interface reports it as RMSE % — the RMS distance times 100 — so a raw OKLab error of 0.03 shows on screen as about 3. Lower is better, everywhere.

The one control that bends the metric

By default the three axes count equally. The Chroma weight control changes that, but only inside the recipe search: it divides the lightness axis by its value, so a setting above 1 makes the search favor hue and saturation over brightness when deciding which stored stack is nearest. It reshapes which recipe gets chosen, nothing more — the quality number that comes back is always measured in true, unweighted OKLab, so it stays comparable whatever the weight. Aside from this, the metric is fixed; nothing else lets you change it.

A caution on comparing numbers

This is the generator’s yardstick. The calibration half of Prisma scores its own color accuracy with a different one — CIE76 difference in CIE Lab, whose lightness runs 0–100. These are different metrics in different spaces on different scales, so a generator figure and a calibration figure are not comparable even when they happen to print similar digits. Within a single solve, though, the OKLab distance is the consistent measure of how close the print lands.

The space underlies everything the solver touches: how targets first arrive (Model-domain ingress), what happens when one cannot be reached (Gamut mapping), and how recipes are scored (The Solve).
