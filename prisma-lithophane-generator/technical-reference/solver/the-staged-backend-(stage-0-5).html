The staged backend (Stage 0-5)

The staged backend (Stage 0-5)

Properties1
tagsgenerator, solver

Jul 12, 202610 min read

In one sentence: the staged backend is the generator’s sole production solve engine — it turns a prepared image into per-filament thickness maps through six ordered passes (directives → zones → recipes → filler → cap → bridge), each handing a frozen artifact to the next.

The staged backend (Stage 0-5)

When you click Solve in the generator web app, the color decomposition is performed by run_staged_backend_path in generator.pipeline.staged_runner, not by the older solve_image engine in solve.py (that is the legacy CLI region engine — solve.py:480 solve_image, solve.py:647 solve_regions — and is not on the webapp solve path). The webapp path is run_pipeline → the staged backend; the only caller of the staged entry point is the runner: pipeline/runner.py:1222-1225 imports and calls run_staged_backend_path(state, progress=solve_progress).

The function lives at pipeline/staged_runner.py:11163. That one file is ~11,000 lines; this page stays at stage-contract altitude — what each stage consumes, what it produces, and which knobs you control — and deliberately does not narrate gate/beam/mutation internals.

How to drive it

You never call the stages directly. You configure a PipelineConfig (palette, layer height, budgets, region target, feature flags) and run a solve from the web app or pipeline_cli.py. The staged backend reads state.config and state.solve_target_oklab (the prepared OKLab targets on the solve grid) and returns a StagedBackendResult bundle. The runner then copies that bundle onto legacy-facing state (pipeline/runner.py:677 _finalize_staged_backend_state), after which filament grouping, statistics, and mesh export run as usual.

Two hard preconditions, enforced by the stages themselves:

  • state.solve_target_oklab must be set — Stage 1 and Stage 2 raise RuntimeError otherwise (pipeline/staged_runner.py:698, :783, :6232).
  • The solve grid shape is taken from state.image.shape[:2]; everything downstream operates on that lattice.

The pipeline at a glance

run_staged_backend_path runs the six stages in strict order, timing each into a StagedPerformanceProfile and emitting progress callbacks (all reported under stage_index: 1, stage_count: 1, pipeline/staged_runner.py:11188-11189). Each stage is a single builder function whose output is a frozen artifact consumed by the next.

The artifact names are stable; some docstrings still call this an “experimental proof slice” (e.g. staged_artifacts.py headers, staged_runner.py:11164). That language is stale — this is the production path. Trust the caller at runner.py:1225, not the docstring.

Stage 0 — Directives

_compile_directives(state) (pipeline/staged_runner.py:589) builds a tiny, explicit directive set rather than letting later stages re-derive geometry. It computes the planning lattice pitch as solver_fine_pitch_mm × stage1_coarsening_factor (:594) and quantizes the minimum visible cap (d_wc_min) to a whole number of layers (:608-612). The solver_shape it pins is the raw image shape (h, w) (:635).

Each directive is a CompiledDirective with a gate (here "require") and a scope ("image"); each gets a DirectiveReceiptEntry marked status="held", stage="stage0" (:615-630). The output QuantizedDirectiveSet (staged_artifacts.py:22) is consumed by Stage 2 as its evaluation lattice (:6258 reads compiled_directives.solver_shape).

Stage 1 — Lateral zone segmentation

_build_stage1_zone_plan(state, diagnostics) (pipeline/staged_runner.py:693) partitions the image into lateral color zones — contiguous regions that will each receive one recipe in Stage 2.

What it does:

  1. Optionally coarsens the planning grid by stage1_coarsening_factor (_effective_stage1_coarsening_factor, :297), block-averaging both the RGB image (_downsample_rgb_image, :366) and the flat OKLab targets (_downsample_flat_oklab_targets, :421) onto the coarse lattice, with an optional lattice offset (_stage1_lattice_offset_px).
  2. Calls generate_stage1_zone_labels (imported from generator.pipeline.staged_solver_helpers, :731) to produce the integer zone-label raster, honoring cell_mode, the effective color_region_target_mm, smooth_boundaries, and boundary_smooth_radius.
  3. Derives per-zone bookkeeping: flat membership indices (_zone_flat_indices, :666), per-zone OKLab mean/variance (_summarize_zone_targets, :676), and 4-neighbor adjacency with shared-edge lengths (_build_zone_adjacency, :641).

The effective region target can be widened from the printability minimum width when color_region_target_from_printability is on (_effective_color_region_target_mm, used at :719 and :11224); the requested-vs-effective values are both recorded as counters (:11225-11234). Output LateralZonePlan (staged_artifacts.py:114) carries zone_label_map, zone_flat_indices, adjacency_edges, edge lengths, per-zone means/variances, and the coarse_to_fine_scale Stage 2 will reverse.

Stage 2 — Recipe assignment

_build_stage2_visible_plan(...) (pipeline/staged_runner.py:6221) is the heart of the solver: it chooses one visible filament recipe per zone while balancing local color fidelity against seam continuity. This is the single largest stage in the file.

Projection back to fine grid. If Stage 1 coarsened, the zone labels are projected back onto the fine evaluation lattice (_project_zone_labels_to_fine, :6259), optionally refined into source-edge subzones (_split_stage2_source_edge_subzones, :6273, gated by stage2_source_edge_subzones). Adjacency and per-zone variance are recomputed on this evaluation lattice (:6282-6292).

Candidate query. _query_stage2_pixel_stacks (:779) runs query_luts_batch (from generator.lut) over the OKLab targets to get a per-pixel best stack plus a per-pixel ΔE; pixels above de_threshold form the gamut_mask (:785). _vectorized_stack_ids (:6308) quantizes those thickness vectors into a discrete set of unique stack ids under effective_max_layers(). Palette ordering: the palette handed to the encoder is cfg.palette order for both appearance lanes — config materialization already canonicalizes color-filament order and stack ids inherit it exactly (:6304-6313); the physical photo-stack model in particular must keep that order because its layers are physically stacked.

Enumeration + pruning. _enumerate_zone_candidates (:789) collects, per zone, the unique stack ids that appear among that zone’s pixels and scores each candidate against the zone’s targets with _score_candidates_batch (:816); a single-candidate zone gets score 0 (:812-813). Each candidate also carries its total visible thickness (:820-826). The candidate frontier is then enriched — neighboring zones’ strong local-best stacks are injected as extra candidates (_augment_zone_candidates_with_neighbor_local_bests, :837) so a zone can match a neighbor it would not have considered alone. This frontier is what keeps the assignment search tractable instead of enumerating the full LUT.

Coordinate-descent + beam under continuity/seam. Selection is a two-step optimization over candidate indices:

  1. _seed_zone_recipe_labels_with_beam (:1452, called :6515) runs a small beam search (_STAGE2_BEAM_WIDTH = 12, :100) to build a good initial assignment that already respects neighbor continuity.
  2. _optimize_zone_recipe_labels (:1913, called :6603) takes that seed and refines it: _run_coord_descent (:1693, up to _STAGE2_MAX_COORD_DESCENT_PASSES = 4, :90) followed by _repair_worst_boundary_pairs pair repair (:1765).

The objective per zone/candidate is computed in _zone_objective_breakdown (:1606): local_cost + continuity_weight × boundary_cost + retaining_wall_weight × retaining_cost (:1636-1640), where boundary_cost is the edge-length-weighted squared visible-thickness step to each neighbor’s current choice (:1629-1631) and retaining_cost penalizes excess thickness above the zone’s thinnest candidate (:1634-1635). Defaults: _STAGE2_CONTINUITY_WEIGHT = 0.12, _STAGE2_RETAINING_WALL_WEIGHT = 0.02 (:88-89); the continuity weight is overridable via _stage2_continuity_weight. “Seam” quality is the mean shared-boundary thickness step, tracked before/after by _mean_boundary_step_mm (:1649).

Output VisibleRecipeRawGeometryPlan (staged_artifacts.py:264) carries the zone_recipe_labels, the recipe_table of VisibleRecipe entries, the raw color ceiling, the gamut mask, an optional fine_recipe_label_map (when a within-zone detail override fires), and a Stage2ObjectiveSummary. Its recipe_label_map property (:295-299) returns the fine override if present, else the zone-level labels.

VisibleRecipe vs the photo-stack StackDefinition. VisibleRecipe (staged_artifacts.py:73) is the staged backend’s committed recipe — an ordered tuple of (filament_id, thickness_mm) pairs with from_mapping/to_mapping helpers. It is structurally near-identical to but distinct from the model-layer StackDefinition; do not conflate them.

Stage 3 — Filler

_build_stage3_filler_plan(...) (pipeline/staged_runner.py:9582) is the geometry-only filler pass. In current code it is effectively a pass-through: it sets filler_height = zeros_like(raw_color_ceiling) and therefore color_ceiling_mm == raw_color_ceiling_mm (:9589-9590). It still runs every solve (called unconditionally at :11277) and emits a FillerGeometryPlan (staged_artifacts.py:311) so Stage 4 has a uniform color_ceiling_mm field to build on. The stage exists as a wired seam for support/filler logic; today it adds no height. Confirmed live but no-op: the only writer of filler_height is the np.zeros_like at :9589.

Stage 4 — Cap and detail / printability

_build_stage4_cap_plan(...) (pipeline/staged_runner.py:10287) synthesizes everything above the color layers: the white boundary cap, edge guards, an optional detail surface, and the printability gates.

Key contract points:

  • Budget. The remaining cap budget is t_max − color_ceiling, clamped to effective_d_wc_max() (:10303-10307); the boundary cap is further clamped to effective_boundary_d_wc_max() (:10308-10311). The minimum cap floor is quantized to layers via _quantized_cap_floor (:10298).
  • Requested cap & guards. _requested_stage4_cap_maps (:9319) returns the requested boundary cap, a detail reference cap, and a boundary_edge_guard_weight map. Stage 4 supports cap_mode ∈ {"smooth_variable", "appearance_bounded_smooth"} (_STAGE4_SUPPORTED_CAP_MODES, :208); the retired "fixed" mode — and any other value — raises ValueError rather than falling back (:9350-9351). "appearance_bounded_smooth" (UI “Detail Aware”, the default) keeps the boundary cap structural and pushes tonal relief into the detail cap within an appearance-ΔE budget (boundary_cap_de_budget, default 0.008); Luminance mode forces smooth_variable.
  • Lateral boundary shield. When printability is enforced and a non-fixed lateral shield is required, Stage 4 honors the mandatory shield floor handed off by Stage 2 (visible_plan.mandatory_lateral_boundary_shield_floor_mm, :10327), raising a ValueError if its shape disagrees with the cap (:10330-10333).
  • Detail surface. The detail cap is now mandatory — detail_cap_enabled is force-True (SolveConfig rejects False, server.py:688-692) and drives the detail branch at :10470; its depth is bounded by detail_cap_max_layers (UI “Detail depth”, default 5). The old stage4_optical_detail_surface / stage4_independent_detail_surface mode selectors were retired (2026-07-01); which source fills the detail cap now follows the cap mode. Under the appearance-bounded structural split it is the residual above the boundary cap (:10473-10496); otherwise it is a synthesized optical detail surface (_build_stage4_optical_detail_surface, :8840, called :10498). Detail candidates are scored per connected zone and accepted/rejected with explicit reasons (Stage4DetailZoneSummary, staged_artifacts.py:344); rejection categories include too-small, weak-optical-gain, and weak-signal (_STAGE4_DETAIL_REJECT_*, :220-223).
  • Printability gates. Two optional gate families run here and surface as Stage4BoundaryCapPrintabilitySummary and Stage4DetailAuthoringPrintabilitySummary / Stage4DetailPrintabilitySummary, all None when disabled (CapSynthesisPlan fields, staged_artifacts.py:454-459).

Output CapSynthesisPlan (staged_artifacts.py:441) carries cap_boundary_top_mm, cap_height_mm, boundary_edge_guard_weight, detail_height_mm, the detail zone maps/summary, and final_visible_top_mm.

Two unrelated PrintabilityReport/printability classes. Stage 4’s printability summaries (Stage4*PrintabilitySummary) and the optional plan-level BlueprintPrintabilityDiagnostic (staged_artifacts.py:502, run via staged_printability.run_blueprint_printability_diagnostic at :11583) live in this pipeline. They are distinct from the mesh-side and blueprint_triage printability types — do not cross-reference them. The blueprint diagnostic and geometry-attribution passes are opt-in, gated by emit_blueprint_printability (:11569) and emit_geometry_attribution (:11513); they are read-only diagnostics that never change geometry.

Stage 5 — Plan bridge

build_compatibility_bundle(...) (pipeline/staged_bridge.py:100) is the read-only adapter that projects the staged artifacts back into the legacy thickness-map shape the rest of the generator (mesh export, previews, dE diagnostics) expects.

It builds one (h, w) float32 thickness map per palette filament by painting each recipe’s thickness_by_filament onto its recipe_label_map mask (staged_bridge.py:124-130), then adds three white-channel maps: __white_cap__ (full cap height), __white_boundary_cap__ (cap-above-ceiling, floored at 0), and __white_detail_cap__ (:140-148). It also exports the __gamut_mask__ diagnostic and a dictionary of debug maps (zone labels, recipe labels, color ceiling, cap tops, detail maps, etc., :151-236). Output CompatibilityBundle (staged_artifacts.py:566) plus the per-pixel image-domain extents.

Back in the runner, _finalize_staged_backend_state (pipeline/runner.py:677) copies bundle.thickness_maps into state.thickness_maps (:702-705), routes bundle diagnostics into state.diagnostics (never into thickness maps, :710-711), merges debug maps (:713), sets state.color_committed = True (:719), and — separately — builds the export-facing SolvedMaterialPlan via build_solved_material_plan_for_export (:686). That is the true Stage 5 handoff to mesh generation; see Thickness map and From solve to mesh the export pipeline.

Diagnostics, receipts, and performance

Throughout, the orchestrator records:

  • Timings per stage into StagedPerformanceProfile.timings_s (_record_timing, :283) — stage0_compile_directives_s, stage1_zone_plan_s, the Stage 2 sub-timings (stage2_beam_seed_s, stage2_coord_descent_s, stage2_pair_repair_s), stage3_filler_s, stage4_cap_s, stage5_bridge_s, and staged_backend_total_s (:11822-11826).
  • Counters for grid sizes, zone counts, frontier sizes, detail accept/reject tallies, and printability findings (_set_counter, :288).
  • Receipts (DirectiveReceiptBook) and a diagnostics stream (PlanningDiagnosticsStream) of human-readable PlanningDiagnosticEntry notes — Stage 1 zone count, Stage 2 seam/pressure notes, printability summaries.

These are what the Color Ceiling / Recipe Viewer UI and the run-record JSON read from; the per-recipe rollups shown in the app derive from the recipe_table and the color_recipe_breakdown artifact, not from re-solving.
