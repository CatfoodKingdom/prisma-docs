Staged artifacts and the SolvedMaterialPlan contract

Staged artifacts and the SolvedMaterialPlan contract

Properties1
tagsgenerator, solver

Jul 12, 202610 min read

In one sentence: the live webapp solve runs the six passes numbered Stage 0–5 and emits a StagedBackendResult lineage, then a small bridge projects its final recipe map into the canonical solve-owned SolvedMaterialPlan (immutable segment geometry + mutable stack assignment + cap heights) from which downstream rasters — labels, per-filament thickness, predicted render — are one-way derived, never authored.

This page is the data-shape reference for the Solver output. It serves two readers: a USER who wants to know what a “solve” actually produces, and a DEVELOPER who has forgotten how the backend’s artifacts fit together. It is built from the four contract modules, not their docstrings (several of which are stale — e.g. solved_material_plan.py:11-14 still claims the plan “remains None at runtime”, which is false; see Liveness below).

Related: generator.pipeline.staged_runner · generator.pipeline.runner · The staged backend (Stage 0-5) · Blueprint triage the unwired engine · Color-region geometry (dormant) · Fixed-budget layer scheduling (experimental)

Two layers of artifact, one direction of truth

A finished solve produces artifacts at two altitudes:

LayerLives whereOwnsMutability
Stage plans (Stage 0–5)StagedBackendResult on state.staged_resultthe staged backend’s internal raster blueprintbuilt once per stage, then read-only downstream
Canonical planSolvedMaterialPlan on state.solved_plansegment geometry + stack assignment + cap heightsgeometry frozen, stack assignment mutable

The rule that holds the whole system together: truth flows one way. The staged backend authors raster blueprints; the bridge condenses the final blueprint into the canonical plan; the derived-views layer projects the plan back out into legacy rasters for consumers that still want them. Nothing downstream writes truth back into the plan’s geometry. This is the “one-way ownership” pattern documented in pipeline/derived_views.py:1-20.

The five stage plans

The staged backend (run_staged_backend_path, pipeline/staged_runner.py:11163) builds one authoritative plan object per stage. Each is a dataclass in pipeline/staged_artifacts.py. They are assembled in order inside the runner:

Stage 5 is not a geometry plan — it is the legacy-raster projection of stages 2–4 (see The staged_bridge).

The Stage 2 recipe table — the color blueprint

Stage 2 is where the color decision is made. Its recipe_table is a tuple of VisibleRecipe (staged_artifacts.py:72), each a frozen thickness_by_filament tuple. The per-pixel recipe_label_map (staged_artifacts.py:295) indexes into that table — preferring the fine_recipe_label_map when present, otherwise expanding zone_recipe_labels[zone_label_map]. This recipe map is the seed for the canonical plan.

Disambiguation trap. VisibleRecipe (Stage 2, staged_artifacts.py:72) and StackDefinition (canonical plan, solved_material_plan.py:27) are near-duplicates — both are frozen (filament_id, thickness_mm) tuples normalized to drop zeros. They are NOT the same class. VisibleRecipe is the staged backend’s currency; StackDefinition is the canonical plan’s. The bridge converts one to the other at staged_bridge.py:67.

The lineage object: StagedBackendResult

All nine artifacts are bundled into a single StagedBackendResult (staged_artifacts.py:580) returned by run_staged_backend_path (staged_runner.py:11828) and parked on state.staged_result by _finalize_staged_backend_state (runner.py:682).

StagedBackendResult
├── compiled_directives    : QuantizedDirectiveSet       (Stage 0)
├── receipts               : DirectiveReceiptBook        (per-directive status)
├── planning_diagnostics   : PlanningDiagnosticsStream   (zone-level notes)
├── performance_profile    : StagedPerformanceProfile    (timings_s, counters)
├── lateral_zone_plan      : LateralZonePlan             (Stage 1)
├── visible_plan           : VisibleRecipeRawGeometryPlan (Stage 2)
├── filler_plan            : FillerGeometryPlan          (Stage 3)
├── cap_plan               : CapSynthesisPlan            (Stage 4)
└── compatibility_bundle   : CompatibilityBundle         (Stage 5)

receipts, planning_diagnostics, and performance_profile are bookkeeping, not geometry: DirectiveReceiptBook (:40) records per-directive status/stage/detail; PlanningDiagnosticsStream (:57) holds zone-scoped notes; StagedPerformanceProfile (:64) is timings_s + counters (the solve writes e.g. stage5_solved_plan_segments at runner.py:696 and stage5_bridge_s at staged_runner.py:11811 into it).

The canonical artifact: SolvedMaterialPlan

This is the solve’s authoritative output and the input to export. Triage, scheduling, and region-geometry modules can consume the plan, but their production wiring is not established by the current caller graph. Defined at solved_material_plan.py:74.

Shape

FieldTypeMeaning
segment_id_map(H, W) intimmutable geometry identity; dense ids 0..n_segments-1
segment_stack_id(n_segments,) intmutable assignment: which stack_table entry each segment uses
stack_tabletuple[StackDefinition, ...]canonical, de-duplicated set of color stacks
cap_height_map(H, W) float32fine-grid white-cap height, mm
image_domain_width_mm / height_mmfloatphysical extent
image_sample_pitch_mm / solver_fine_pitch_mmfloatobservation-grid and solve-grid cell sizes
color_region_target_mmfloatcolor-region geometry target

The central design move (solved_material_plan.py:74-91): geometry identity and material assignment are separated. A segment is a region of pixels that share an id; which material that region prints is a separate, mutable indirection through segment_stack_id → stack_table. A downstream stage that wants to reassign material (e.g. triage shortening a stack) rewrites segment_stack_id — it must never rewrite segment_id_map.

Invariants (enforced in __post_init__, :104)

These raise ValueError/TypeError at construction, so any plan you hold is already valid:

  1. segment_id_map is 2-D (:105).
  2. cap_height_map shares the (H, W) footprint of segment_id_map (:109).
  3. segment_stack_id is 1-D (:115).
  4. Segment ids are dense and contiguous 0..n_segments-1 — np.unique(segment_id_map) must equal arange(n_segments); a gap raises “missing dense segment ids” (:137-146).
  5. Every segment_stack_id entry is a valid index into stack_table (:152-159).
  6. Every stack_table entry is a StackDefinition (:161-166).
  7. Geometry is frozen structurally: segment_id_map.flags.writeable = False (:169). Attempting to mutate the raster raises at the NumPy level — this is what makes the “geometry is immutable” claim a runtime guarantee, not a convention.

StackDefinition (:27)

One unique committed color-layer stack: a frozen, sorted color_thickness_mm tuple of (filament_id, thickness_mm). Color content only — base-white (d_wb config scalar) and cap-white (cap_height_map) are modeled separately on the plan (:29-39). from_mapping (:43) drops zero-thickness entries so two mappings that differ only in absent-vs-zero entries hash equal; being frozen + content-sorted makes stacks hashable and de-duplicable into the canonical stack_table.

Convenience accessors on the plan: n_segments, n_stacks, shape, stack_at(segment_id) (:185), and filament_ids() (:189, deterministic sorted union across all stacks).

Where it is carried

The plan rides on the runtime state objects:

  • PipelineState.solved_plan (state.py:254) — populated by the solve path, “consumed by export, triage, and scheduling” per the in-code comment (state.py:251-253).
  • SolveResult.solved_plan on the facade (facade.py:253).

The derived-views layer (one-way)

pipeline/derived_views.py turns a SolvedMaterialPlan back into legacy rasters for consumers that haven’t migrated onto the plan. Every helper is pure: reads plan fields, returns a fresh array the caller may mutate, never writes back (derived_views.py:10-14).

committed_stack_label_map is the keystone: because the label is segment_stack_id[segment_id_map], pixels in one segment are guaranteed to share a stack id, and per_filament_thickness_maps builds every thickness raster by gathering a stack-indexed lookup through this label map (:69-90). Mutate segment_stack_id and re-derive, and the rasters update — the plan stays the single source of truth.

project_observation_to_solve_grid is OWNED here

Despite being a target-grid resampler rather than a plan view, project_observation_to_solve_grid lives in and is exported from derived_views.py (:125, :172). It maps observation-grid target OKLab onto the solve grid. The contract (:134-164):

  • When image_sample_pitch_mm == solver_fine_pitch_mm (the common case) it is a zero-cost identity pass — it returns the same object (:154-155).
  • When the pitches differ, it bilinearly resamples (scipy.ndimage.zoom, order=1) by the pitch ratio to the solve-grid shape (:157-164).

Its live caller is target_cloud.py:84, which feeds it the image_to_target OKLab cloud to produce the solve_oklab used by the solver. So this single function is the boundary between the observation grid (what the camera sampled) and the solve grid (what the solver optimizes).

The staged_bridge build

pipeline/staged_bridge.py is the read-only Stage 5 adapter with two exported builders (:442).

build_solved_material_plan_for_export (:27) — staged plans → canonical plan

This is how a SolvedMaterialPlan actually comes into being on the live path. Called by _finalize_staged_backend_state (runner.py:686) with the Stage 2 visible_plan and Stage 4 cap_plan. Algorithm (:42-97):

  1. Take visible_plan.recipe_label_map (the final fine recipe map). Validate it is 2-D, non-empty, non-negative (:44-51).
  2. For each distinct recipe label present, convert its VisibleRecipe into a StackDefinition (:67) and de-duplicate into a canonical stack_table keyed by stack identity (:70-74) — two different recipe labels with identical color content collapse to one stack.
  3. Each distinct recipe label becomes one dense segment; segment_id_map paints the segment id onto every pixel of that label (:75), and segment_stack_id[segment] points at the de-duplicated stack (:76).
  4. Adopt Stage 4’s cap_height_mm as cap_height_map (shape-checked against the recipe map, :78-84), and set the pitch/domain scalars from solver_fine_pitch_mm (:86-97).

The result satisfies every SolvedMaterialPlan invariant by construction (dense segments, valid stack indices, matching cap footprint).

Note: here a “segment” is one whole connected-label footprint — all pixels of a given recipe label share one segment id, regardless of spatial connectivity. Spatial connected-component splitting is a later concern handled by Color-region geometry (dormant) (geometry/extract.py:210), not the bridge.

build_compatibility_bundle (:100) — staged plans → legacy raster bundle

Called at staged_runner.py:11790 to populate Stage 5. It projects visible_plan + filler_plan + cap_plan into the flat raster world the legacy preview/export code expects (:116-439):

  • thickness_maps: per-palette-filament (H, W) rasters painted by recipe label (:121-130), plus white-layer channels "__white_cap__", "__white_boundary_cap__" (cap-boundary minus color ceiling, floored at 0), "__white_detail_cap__" (:132-148).
  • diagnostics: "__gamut_mask__" (:150-152).
  • debug_maps: a large named dictionary of zone/recipe/ceiling/cap/detail rasters plus optional Stage 2 recipe-pressure, geometry attribution, printability-gate, substrate-repair, boundary-mutation, exterior-white-guard, and blueprint-printability maps — each guarded by a None check and copied (:193-428).
  • compatibility_label_map / boundary_label_map: copies of the recipe and zone label maps (:435-436).

This bundle is the legacy compatibility surface; the canonical plan (above) is the forward-looking one. Export can recover connected same-stack regions from the plan and avoid the per-pixel raster mesh path (staged_bridge.py:34-41).

Liveness — what is actually wired

Grepped, not assumed (a prior audit was burned by missing callers):

  • The staged backend is the live solve. runner.py:1222-1225 imports and calls run_staged_backend_path; this is the webapp solve, NOT solve.py’s legacy CLI “6-step” engine. Confirmed live.
  • SolvedMaterialPlan is populated at runtime. runner.py:686 assigns state.solved_plan on every solve. The solved_material_plan.py:11-14 docstring saying it “remains None at runtime” is stale — disregard it; trust the assignment.
  • Only the current caller-confirmed derived views are production-live. committed_stack_label_map is used by server.py and cap_quality.py; project_observation_to_solve_grid is used by the live target-cloud path. The per-filament/cap/compatibility helpers are reachable from the blueprint-triage application module but no production caller to that application was found. scheduling/model.py is also test-covered with no production caller found.
  • extract_regions (geometry/extract.py:210) is exported from the geometry package and consumes state.solved_plan, but I found no production call site inside Prisma/generator/ — it is exercised only by tests/generator/test_phase4_region_extraction.py. Status: wired-by-export, test-covered, no production caller found (unconfirmed whether export currently routes through it).
  • scheduling/model.py consumes the plan (committed_stack_label_map, cap_height_map) but its derive_*/build_* case functions (model.py:375/505/526/589) are reached only from tests/generator/test_layer_scheduling.py in my grep — no production caller found. Status: plan-consumer, test-covered, production wiring unconfirmed.

Both unconfirmed items are plan consumers downstream of a populated plan — they are not dead in the contract sense; I simply could not trace a production call edge and am flagging that explicitly rather than guessing.
