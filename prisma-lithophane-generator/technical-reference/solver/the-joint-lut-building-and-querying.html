The Joint LUT building and querying

The Joint LUT building and querying

Properties1
tagsgenerator, lut

Jul 12, 202611 min read

In one sentence: the joint LUT enumerates every printable (cap + color) stack under a height budget, stores each stack’s OKLab color in a chroma-weighted KD-tree, and the solver answers “which stack reproduces this pixel?” with a nearest-neighbor query.

This page covers Prisma/generator/lut.py (the spline path, the query functions, the disk cache, the convex hull, and the legacy cap-curve helpers) and Prisma/generator/photo_stack_lut.py (the vectorized photo-stack build path). For the surrounding solve flow see The Joint LUT and Staged Solve and the The Joint LUT and Staged Solve concept note. Architecture nodes: generator.lut, generator.photo_stack_lut, generator.appearance_model.

What “joint” means

Older designs solved cap thickness (luminance) and color thickness in two separate steps. The joint LUT folds them together: a single LUTEntry enumerates combinations of (d_wc, d_c1, …, d_ck) jointly and stores oklab(T_wb × T_wc(d_wc) × ∏ T_ci(d_ci)) for each (LUTEntry at lut.py:161, with the builder formula documented in build_luts). White base (d_wb) is fixed and baked into every entry, so the entries already include it. The cap dimension is carried per-entry in cap_thicknesses, and the chosen cap comes back to the caller under the reserved '__white_cap__' key.

A LUTEntry is one filament subset (size 1..k_max), not one filament. The build loops over itertools.combinations(filament_ids, k) for each k (the spline builder begins at lut.py:463, with the subset loop shortly below), so a 3-filament palette with k_max=3 produces 7 entries (3 singles + 3 pairs + 1 triple). Each entry owns its own KD-tree.

Entry enumeration under a height budget (stars-and-bars)

For each subset and each cap step, the remaining height budget caps how many color layers fit. The spline builder computes this in build_luts after the current builder entry point (lut.py:463), and the provider builder performs the same calculation in build_luts_with_provider (lut.py:1348). _enumerate_combos_budget(k, remaining_steps) produces all non-negative integer tuples of length k summing to ≤ remaining_steps (lut.py:260–287). This is a direct recursive stars-and-bars generation rather than itertools.product + filter. k=0 returns a single empty row and k=1 returns arange(max_steps+1).

photo_stack_lut.py keeps a local copy of this function to avoid importing lut.py from this helper module. The two implementations are independent and must stay in lockstep; the photo-stack copy is the one used when building provider LUTs.

The budget itself: if t_max is None, the builders default it to d_wc_max + max_layers * layer_height (build_luts and build_luts_with_provider). The live runner passes the post-white-base budget to the active builder; the provider path is visible around runner.py:1156–1160.

Transmission → OKLab → pruning

Both build paths share the same post-processing tail:

  1. Compose transmission. The spline path multiplies precomputed fixed white-base, cap-step, and color-layer transmission tables in build_luts (lut.py:463 onward). The provider path either consumes the vectorized photo-stack arrays or batches StackRequest predictions in build_luts_with_provider (lut.py:1348 onward). Products are clipped to [1e-9, 1.0] before OKLab conversion.
  2. OKLab. to_oklab converts the linear-RGB transmission array to OKLab.
  3. Prune near-duplicates. _prune_entries bins OKLab space at bin_width=0.005 (lut.py:440 onward) and keeps one entry per bin. Per bin it keeps the entry with lowest total color thickness (less material), tiebroken by lowest cap thickness (brighter), via _prune_entry_indices.
  4. Build KD-tree (see below) and append the LUTEntry.

OKLab indexing with chroma weighting

The KD-tree is built from OKLab, but when chroma_weight != 1.0 the L* channel is divided by the weight before tree construction. Dividing L* shrinks lightness distances in the search metric, so nearest-neighbor matching prioritizes color (a, b) over lightness. A chroma_weight > 1 therefore tolerates more lightness error to nail hue/chroma. The stored oklab array stays unscaled — only the tree sees the scaled copy — so reported dE can be recomputed in true (unweighted) OKLab space.

Every query mirrors this: the target’s L* is divided by cw = luts[0].chroma_weight before tree.query, and the returned distance (which is in scaled space) is replaced with the true unweighted Euclidean OKLab distance against the stored oklab whenever cw != 1.0 (query_luts lut.py:1651 onward; query_luts_batch lut.py:1691 onward). See OKLab and Chroma weight.

Querying

All query functions take the List[LUTEntry] and scan every entry’s tree, keeping the global best per pixel. There is no subset pre-filtering — the nearest stack across all subsets wins.

query_luts_batch — the live webapp query

This is the function the running webapp actually calls. It is imported and invoked in the staged backend (staged_runner.py), from the Stage-2 pixel-stack query at staged_runner.py:784 (query_luts_batch(state.luts, targets)). It is the LUT query reachable from run_staged_backend_path — the webapp solve runs the staged backend, not solve.py’s engine.

  • Input: (N, 3) OKLab targets. Output: a dict filament_id → (N,) float32 thickness array plus '__white_cap__', and a (N,) dE array (lut.py:1691 onward). Filaments not used for a pixel get 0.0.
  • Parallelism: when parallel=True, n_luts > 1, and n > 1000, each entry’s tree.query runs on a ThreadPoolExecutor; SciPy’s cKDTree releases the GIL so this is real parallelism. The reduction (picking the winning LUT per pixel) is sequential NumPy.
  • An optional on_lut_done(done, total) callback fires per entry for progress reporting.

query_luts — single-target

Scalar version of the above for one OKLab target; returns (thicknesses_dict, dE) (lut.py:1651 onward). Live in the legacy solve.py engine only (solve.py:106).

query_luts_fixed_cap — two-pass cap smoothing (legacy)

Re-solves color layers with the cap pinned per pixel, used by the legacy two-pass smoothing. For each pixel it queries the min(20, len) nearest neighbors, then among those keeps the best whose cap_thickness matches the supplied fixed_cap within 0.5 × layer_height, falling back to the unconstrained best if none match (lut.py:1814 onward). The returned '__white_cap__' is set to the fixed cap, not the LUT entry’s. Liveness: called only from the legacy CLI engine — solve.py:617 and pipeline_cli.py:619 (inside the solve_regions smoothing branch). Not reachable from the staged webapp path — see below.

query_cap_fixed_color / query_cap_fixed_color_batch — test-facing only

The duals of query_luts_fixed_cap: pin the color stack and sweep the cap to minimize dE (lut.py:1915 and lut.py:1976). They do not use the LUTs (the luts arg is accepted for API symmetry); they recompose transmission directly via compose_stack/predict_transmission. Liveness: unwired in product code. A repo-wide grep finds no caller inside Prisma/generator/ — the only caller is tests/generator/test_query_cap_fixed_color.py. Treat them as a tested-but-dormant utility.

Two build paths

The runner selects the path by the appearance provider’s model_kind (the active builder call is in runner.py:1156–1160):

model_kind == "historical_spline"  →  build_luts(...)
otherwise                          →  build_luts_with_provider()

See Appearance provider for what supplies model_kind.

Path A — build_luts (spline + pair corrections)

build_luts(color_profiles, wb_profile, wc_profile, …) is the historical spline path (lut.py:463 onward). It requires wb_profile and wc_profile, auto-derives d_wc_max via derive_d_wc_max if not given, precomputes transmission tables, enumerates combos per subset/cap, and builds entries.

Pair corrections (k=2 only). When corrections is supplied and k_max ≥ 2, _build_pair_corr_cache restructures the fitter’s correction dict into per-(overlay, base) arrays interpolated to each layer count. Only single-base pairs are kept; multi-base correction entries are dropped. During build, for each 2-filament subset the A-on-B and B-on-A correction curves are looked up; if both exist they are averaged, otherwise the available one is applied, indexed by the overlay filament’s layer count. Corrections never touch k=1 or k=3 subsets.

Live caller: the historical-spline branch in the pipeline runner and pipeline_cli.py:545 (CLI). The current default photo-stack provider uses the provider builder below.

Path B — build_luts_with_provider (live photo-stack model)

build_luts_with_provider(provider, …) is the provider-backed path and returns ordinary LUTEntry objects so the query code stays shared (lut.py:1348 onward). It has two internal sub-paths:

  • model_kind == "photo_stack_bundle" (the current default model): it iterates iter_photo_stack_lut_arrays(provider, …) from photo_stack_lut.py, prunes, chroma-weights, and builds trees. This is where the heavy vectorized appearance model runs.
  • Generic provider fallback: for any other non-spline provider it builds StackRequest objects per combo and calls provider.predict_stack_linear_rgb_batch(all_requests) in one batch. Pair corrections are not applied on this path (no corrections argument exists in this function).

Live caller: the normal provider branch in the pipeline runner — the webapp’s path whenever the active model is not the historical spline. This is the path exercised by typical solves today.

The vectorized photo-stack evaluator (photo_stack_lut.py)

iter_photo_stack_lut_arrays (photo_stack_lut.py:1110 onward) yields one PhotoStackLUTArrays (raw, pre-prune) per subset. It builds cap steps, instantiates a _PhotoStackGridEvaluator, and for each subset/cap enumerates combos and calls evaluator.predict_subset(subset, combos, cap_indices) to get model-domain linear RGB, then projects to appearance via provider.project_model_linear_rgb_to_appearance before OKLab conversion. _PhotoStackGridEvaluator is a NumPy mirror of the frozen photo-stack equations — white context, cap attenuation, multicolor interaction, ordered-tint retention, single-color cap transfer / profile blend, two-color endpoint corridor, and a kernel-weighted correction residual. Its physics is owned by lib.photo_stack_model.predictor and is out of scope here; the contract is “grid-aligned counts → OKLab, identical to the row predictor” (verified by the module’s comparison helper and tests).

Note: project_model_linear_rgb_to_appearance and the appearance-named provider methods are pass-throughs that return model-domain values after the projection-slot retirement (appearance_model.py:429–432; predict_stack_linear_rgb_batch aliases the model-domain batch, appearance_model.py:424–427). See Model-domain ingress.

predict_combo_model_linear_rgb (photo_stack_lut.py:925) and predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:998) are sibling entry points to the same evaluator used at solve time (Stage-4 cap planning), not during LUT build. predict_unique_stack_cap_oklab_grid is imported and called by the staged cap planner (staged_solver_helpers.py); it internally calls predict_combo_model_linear_rgb. The appearance provider’s deduplicated row predictor also reaches the same combo predictor. They share the evaluator so hot paths never pay the row predictor’s per-row cost.

Disk cache (npz, trees rebuilt)

LUTs are cached to data_paths.LUT_CACHE_DIR = <cache>/luts/ (data_paths.py:54). KD-trees are never serialized — only the arrays are saved, and trees are rebuilt on load (_save_luts_to_cache lut.py:321 onward; _load_luts_from_cache lut.py:348 onward). Because the tree is rebuilt at load, chroma_weight is re-applied at load time, so the same cached npz can serve different chroma weights — but the cache key includes chroma_weight, so in practice each weight gets its own file.

Two cache-key schemes:

Pathkey functionfilenameversion/metadata
spline (build_luts)_cache_key (lut.py:298 onward)lut_<16hex>.npzSHA-256 over sorted filament IDs, all geometry params, per-profile checksums, and a corrections checksum; no stored metadata block
provider (build_luts_with_provider)_provider_cache_key (lut.py:1320 onward)lut_provider_<16hex>.npzincludes a builder_version string and writes a cache_metadata dict (schema provider_lut_v2) into the npz, validated on load

The provider cache’s builder_version is PHOTO_STACK_LUT_BUILDER_VERSION (photo_stack_lut.py:65) for photo-stack bundles, else "provider_generic". On load, _load_luts_from_cache rejects the file if any expected_metadata key mismatches or if the metadata block is missing entirely — so a builder-version bump auto-invalidates stale provider caches. The provider path also fills a diagnostics dict (cache key/path/hit, LUT/entry counts) for observability.

The spline path’s _save_luts_to_cache is called with no metadata, and _load_luts_from_cache is called there without expected_metadata, so its only guard against staleness is the hash in the filename.

Convex hull construction

build_hull_from_luts(luts) stacks every entry’s oklab, deduplicates by rounding to 4 decimals, and returns a scipy.spatial.ConvexHull of all achievable OKLab colors (lut.py:2064 onward). It is the achievable-gamut surface used for hull-mode gamut projection: out-of-gamut targets are pushed onto the nearest hull facet. Live callers: the runner’s hull-mode gamut mapping path and solve.py’s legacy engine. The hull feeds solve.gamut_map_hull_batch, which the runner calls during target mapping. See Gamut mapping.

Legacy cap-curve helpers

A separate 1-D structure predates the joint LUT and is retained “for dual-resolution cap refinement”:

  • CapCurve (lut.py:152–158): maps OKLab L* → cap thickness d_wc, holding d_wc_steps, L_values, and a T_wc_table.
  • build_cap_curve (lut.py:201): builds it by stepping cap thickness and recording L*.
  • cap_curve_lookup_batch (lut.py:232): vectorised nearest-L* lookup with a broadcast-floats chunking guard.
  • derive_d_wc_max (lut.py:180): finds the cap thickness where mean transmission drops below a threshold (default 0.05) — beyond this the cap is effectively opaque. This one is not legacy: it is used by both build_cap_curve and build_luts to auto-derive d_wc_max.

Liveness of the cap-curve trio: build_cap_curve and cap_curve_lookup_batch are used by the legacy engine only. build_cap_curve is called by the CLI at pipeline_cli.py:665; cap_curve_lookup_batch is called by solve.py:434. The live webapp goes through run_staged_backend_path and queries LUTs with query_luts_batch. So CapCurve/build_cap_curve/cap_curve_lookup_batch are live in the CLI path, dormant in the webapp path.

Driving it (for users)

You never call these functions directly — the generator does. What you control maps to build parameters:

  • Palette → filament_ids / subsets (more filaments ⇒ more subsets ⇒ bigger LUT, longer first build).
  • k_max → how many colors may stack per pixel (1–3). Higher k_max multiplies subset count combinatorially.
  • Height budget (t_max, d_wb, layer height) → how many layers fit, hence how many combos per subset.
  • Chroma weight → favor color accuracy over lightness in matching.

First solve of a new palette pays the build cost; subsequent solves hit the npz cache. Changing a filament’s measured profile, the pair corrections, or the photo-stack model version (builder_version) invalidates the relevant cache automatically.
