Stage 1 and 2 solver kernels

Stage 1 and 2 solver kernels

Properties1
tagsgenerator, solver

Jul 14, 20269 min read

In one sentence: staged_solver_helpers.py is a bag of stateless NumPy kernels that the staged solver uses to carve an image into color zones (Stage 1) and to turn the per-pixel color stacks into a scored grid of cap-thickness color predictions (Stage 2).

What this page is

pipeline/staged_solver_helpers.py holds the shared, side-effect-free math kernels for the two early stages of the live solve. They do not own any solver policy — no commitment logic, no zone graph traversal, no budgeting decisions. They take arrays in and hand arrays back. The orchestration that calls them lives in generator.pipeline.staged_runner; this module is the low-level toolbox.

These kernels run on every webapp solve. The webapp solve runs the staged backend (pipeline/runner.py:1222 imports and calls run_staged_backend_path, defined at pipeline/staged_runner.py:11163), not the legacy “6-step” engine in solve.py. So everything below is on the hot path for a real generate.

Origin note (stale-docstring defuse)

The module docstring claims these functions “used to live in the retired dual-resolution solver wrapper” (pipeline/staged_solver_helpers.py:1-8). That is a historical note about where the code moved from, not about its current status. The functions are live — every public name in __all__ (pipeline/staged_solver_helpers.py:339-348) has at least one in-tree caller (see Liveness below). Do not read “retired … legacy … dead solver wrapper” in that header as a claim that this code is dead; the wrapper is gone, the kernels were lifted out and kept.

Stage 1 — zone-label generation

generate_stage1_zone_labels (pipeline/staged_solver_helpers.py:287) produces a 2-D integer label map the same height/width as the planning image, where each integer is a color zone. It is “dense Stage 1 zone-label map without solver commitment logic” (:297) — it only segments; the runner decides what to do with the zones.

Cell size. If scale is not passed, it is derived as round(color_region_target_mm / solver_fine_pitch_mm), floored to ≥1 (:299-302). pixels_per_cell = scale * scale (:305). In the live path the runner passes an explicit scale override (coarse_scale_override, derived from the stage-1 coarsening factor) when staging is active (staged_runner.py:720-736), so the internal derivation is mostly a fallback.

Three cell modes (:307-331), selected by cfg.cell_mode:

cell_modeMechanismNotes
"grid"Plain scale × scale square tiling via np.repeatDeterministic axis-aligned cells; default-ish
"felzenszwalb"skimage.segmentation.felzenszwalb, scale = max(1, pixels_per_cell*0.8), sigma=0.8, min_size=pixels_per_cellContent-aware blobs
anything elseskimage.segmentation.slic, n_segments = (h*w)//(pixels_per_cell*4), compactness=10SLIC superpixels; the catch-all branch

After segmentation the labels are forced contiguous (:333), optionally boundary-smoothed if cfg.smooth_boundaries is set (:334-335, radius from cfg.boundary_smooth_radius), then relabeled contiguous again on the way out (:336).

_smooth_label_map (:249) iterates radius passes; each pass finds 4-neighbor boundary pixels and replaces each with the majority label in its 3×3 window (np.bincount(...).argmax(), :274-275). It short-circuits when a pass finds no boundary (:265-266) and finishes with a contiguous relabel (:277). _relabel_contiguous_labels (:280) is the trivial “unique + inverse-index reshape” that guarantees ids are 0..n-1 as int32.

The radius/boundary_smooth_radius plumbing here is the same smooth_boundaries feature noted as bug-fixed 2026-04-12 in project memory; this kernel is where the majority vote actually happens.

Stage 2 — from per-pixel stacks to a scored cap grid

Stage 2 (entry at staged_runner.py:6221) turns LUT-queried per-pixel thicknesses into a compact, scorable representation. The kernels do three jobs: encode, predict, score.

Encode — _vectorized_stack_ids

_vectorized_stack_ids (:21) collapses the per-pixel thickness dictionary into a small set of unique stacks. Mechanics:

  1. Round each filament’s thickness to an integer layer count: rint(raw / layer_height) per palette entry (:31-34).
  2. Pack the per-pixel layer-count vector into a single integer using a positional base of max_layers + 1 (:36-38) — a mixed-radix encoding where each filament occupies one “digit”. max_layers defaults to 50 but the live caller passes cfg.effective_max_layers() (staged_runner.py:6312).
  3. np.unique(..., return_inverse=True) gives pixel_stack_ids (per-pixel index into the unique table) and the unique codes (:40-41).
  4. Decode each unique code back into a {filament_id: thickness_mm} dict, dropping zero-layer entries (:43-53).

Returns (pixel_stack_ids, unique_codes, unique_stack_dicts). This is the key compression step: a megapixel image with a handful of distinct stacks becomes a few hundred unique-stack dicts the rest of Stage 2 reasons over.

Palette order is cfg.palette for both lanes. The caller builds the palette as cfg.palette order before encoding (staged_runner.py:6304-6313); config materialization already canonicalizes color-filament order, and stack ids inherit it exactly for both appearance lanes. The order matters especially for the photo-stack model, whose layers are physically stacked. (Earlier revisions sorted the palette for the order-insensitive spline model; current code does not — it hands the same cfg.palette order to both.) The kernel itself just encodes whatever ordered palette it is handed.

Predict — _predict_transmission_batch

_predict_transmission_batch (:58) evaluates the spline transmission model for a whole array of thicknesses at once. It pulls the per-channel splines via lib.transmission._get_splines (:60-62) and:

  • thickness ≤ 0 → transmission 1.0 (:68, :72);
  • thickness within knot range → clipped [0,1] spline eval per R/G/B (:74-78);
  • thickness beyond the last knot → per-element lib.transmission._extrapolate (:80-82).

Returns an (N, 3) RGB transmission array. This is the spline-model batch evaluator; see lib.transmission for the underlying PchipInterpolator splines and the transmission contract T_total = T_wb · ∏ T_fi · T_wc.

Cap-OKLab precompute — the two grids

Stage 2 needs, for every unique stack, the OKLab color it would show at each possible white-cap thickness. There are two implementations, picked by model kind at staged_runner.py:6335.

Spline model — _precompute_cap_oklabs

_precompute_cap_oklabs (:87) builds the cap grid for the historical spline model:

  1. Cap steps 0 .. d_wc_max at layer_height spacing (:101-105); d_wc_max = cfg.effective_boundary_d_wc_max().
  2. White-cap transmission for all cap steps via _predict_transmission_batch (:107-109).
  3. For each unique stack: compose white-base + color layers with compose_stack (:114-132, from generator.model), multiply by every cap transmission, convert to OKLab with to_oklab (:134-135).
  4. Over-budget inf sentinel (:142-152): the cap headroom left by this stack’s color thickness is computed with max_cap_height_for_color_thickness from generator.pipeline.height_budget (remaining = t_max - d_wb - color_thickness, clamped to d_wc_max). Any cap step beyond that headroom has its OKLab row set to np.inf (:150-151). Because the downstream scorer takes a Euclidean distance and then .min() over cap steps, an inf row can never be the chosen cap — so the optimizer is structurally forbidden from selecting an unprintable cap. This is the mechanism that keeps the solve inside the ~3 mm total-height budget.

Returns (cap_values, all_oklabs) where all_oklabs is (unique_stacks, n_steps, 3).

Photo-stack model — _precompute_cap_oklabs_vectorized

_precompute_cap_oklabs_vectorized (:157) does the same job for the photo-stack provider, but returns two views (:168-177):

ViewBudget handlingUsed for
scoring_oklabsover-budget cells masked with inf (:208-209)zone scoring — the optimizer can’t pick unprintable combos
dense_oklabsfinite at every cellStage-4 cap lookup always gets a color answer; budget enforcement is the cap planner’s job

Cap steps come from the LUT cap grid (deduped from each LUT’s cap_thicknesses, :183-192) — never scavenged from the pruned LUT, never routed through the row-shaped predictor (docstring :170-177, behavior :183-210). The actual grid evaluation is delegated to predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:998), which returns (dense_oklabs, within_budget); the budget mask is applied here at :208-209 with budget_mm = t_max - d_wb (:203).

The caller binds the dense view to dense_cap_oklabs and the scoring view to all_oklabs (staged_runner.py:6337); the spline branch sets dense_cap_oklabs = all_oklabs since it has no separate dense view (:6358).

Score — _score_candidates_batch

_score_candidates_batch (:223) scores a set of candidate stacks against a zone’s pixels. For each candidate it computes, per pixel, the OKLab distance to the candidate’s best cap step, then averages over the zone’s pixels — “mean optimal-cap dE” (:213-220). It has two code paths:

  • Vectorized (:237-241): if the pixels × candidates × steps × 3 tensor is under 50 M elements, it broadcasts the whole thing, squares-sums-sqrts to dE, takes min over cap steps then mean over pixels.
  • Per-candidate fallback (:243-245): above that size it loops candidates and calls _score_stack_for_cell (:213) one at a time to cap peak memory.

Both return a (candidates,) array of scores; lower is better. This is the kernel the zone-candidate machinery calls in two places: enumerating each zone’s own candidates (staged_runner.py:816) and scoring borrowed neighbor candidates during augmentation (staged_runner.py:911). The candidate ids being scored are unique-stack ids, and the cap grid passed in is the scoring view (all_oklabs), so the inf sentinel rows propagate into these scores as “never selected”.

Reuse by the luminance handler

_predict_transmission_batch is also imported and used outside Stage 2 by generator.pipeline.luminance_handler (pipeline/luminance_handler.py:19). In _sample_white_luminance_curve’s spline branch it computes white-cap transmission for an array of cap thicknesses (luminance_handler.py:526-531), then converts to OKLab. So this one kernel serves both the Stage 2 cap precompute and the white-cap luminance handling — a single source of truth for “spline transmission of many thicknesses at once.” (The photo-stack branch of that same method bypasses the kernel and asks the provider’s own sample_white_cap_oklab directly, luminance_handler.py:519-523.)
