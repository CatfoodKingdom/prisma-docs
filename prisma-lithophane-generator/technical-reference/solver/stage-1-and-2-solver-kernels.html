Stage 1 and 2 solver kernels

Stage 1 and 2 solver kernels

Properties1
tagsgenerator, solver

Jul 16, 20268 min read

In one sentence: pipeline/staged_solver_helpers.py contains the array-oriented segmentation, stack encoding, cap-color precomputation, and candidate-scoring helpers used by the live staged solver.

The module is a low-level toolbox, not a complete Stage 1 or Stage 2 implementation. pipeline.staged_runner owns orchestration, zone analysis, LUT querying, candidate enumeration and augmentation, recipe optimization, printability gates, diagnostics, and the final artifacts. The helpers nevertheless encode real policy: the segmentation algorithms and constants, height-budget masks, and the candidate-score definition all live here.

Most helpers do not own workspace or job state. They are not literally side-effect-free, however: _predict_transmission_batch reaches lib.transmission._get_splines, which lazily caches built splines inside the supplied profile dictionary.

pipeline.runner always dispatches a product solve through run_staged_backend_path; the old engine in solve.py is not the web application’s backend. The helper module participates in that live path, although individual prediction helpers are model- and data-dependent.

Stage 1 zone-label generation

_build_stage1_zone_plan prepares the inputs before it calls the helper. It can downsample the runner’s prepared image and OKLab target cloud by stage1_coarsening_factor, apply a configured lattice offset, resolve the effective physical color-region target, and sometimes supply an explicit cell scale. generate_stage1_zone_labels receives that planning image and returns a same-height-and-width integer label map; it does not compute zone means, adjacency, pixel counts, or commitment decisions.

The helper supports three implementation branches:

The current settings UI supplies the intended SLIC value through that final branch, but the helper itself does not reject an unknown string; an invalid direct caller value also falls through to SLIC.

Labels are made contiguous after segmentation. When boundary smoothing is enabled, _smooth_label_map performs up to boundary_smooth_radius passes. Each pass identifies four-neighbor boundary pixels, chooses the most frequent label in the corresponding 3×3 window from a snapshot of the prior pass, and stops early if there are no boundaries. The result is relabeled contiguously again.

Stage 2 stack encoding

Stage 2 first queries query_luts_batch for a visible color recipe at every solve-grid target. _vectorized_stack_ids compresses those per-filament thickness arrays:

  1. Iterate filaments in the supplied palette order.
  2. Quantize each thickness with rint(thickness / layer_height).
  3. Encode the layer counts as base-(max_layers + 1) digits in a signed 64-bit integer.
  4. Use np.unique(..., return_inverse=True) to produce the per-pixel unique-stack id map.
  5. Decode each unique integer into a thickness dictionary, omitting zero-layer filaments.

The runner passes the already-canonicalized cfg.palette order in both appearance-model lanes. That order is physically significant to photo-stack v2. The helper returns the unique integer codes as well as the pixel ids and decoded dictionaries, but the live runner ignores the raw codes.

The positional encoding assumes that the full code fits in int64. The product’s swap-band planner currently rejects palettes over ten colors, which keeps the normal supported route inside that bound for current layer budgets; the helper itself does not perform an overflow check.

Historical-spline cap grid

_precompute_cap_oklabs constructs cap steps from zero through cfg.effective_boundary_d_wc_max() at the configured layer height. _predict_transmission_batch evaluates the white-cap spline over those steps:

  • thickness at or below zero returns unit transmission;
  • thickness inside the measured knot range uses clipped PCHIP evaluations; and
  • thickness above the last knot uses the shared Beer–Lambert extrapolator.

For each unique color stack, the cap-grid helper composes the fixed white base and color layers, multiplies that transmission by every variable-cap transmission, and converts the result to OKLab.

An ordinary run computes the legal cap ceiling from the stack’s total color thickness, white-base thickness, total-height limit, and boundary-cap maximum. A banded run instead prices the band’s derived fixed white fill in the optical stack and bases cap headroom on the fixed sum of band-layer budgets. Cap rows above the applicable ceiling are set to inf, preventing the Stage 2 score minimization from selecting them.

The returned grid is both the spline scoring grid and the later dense lookup grid. Unlike the v2 branch, spline processing does not keep a separate unmasked color grid.

Photo-stack v2 cap grids

_precompute_cap_oklabs_vectorized derives a deduplicated, layer-indexed cap grid from the current LUT entries and calls photo_stack_lut.predict_unique_stack_cap_oklab_grid once for the unique Stage 2 stacks.

It returns:

ArrayContract
cap_valuescap thickness corresponding to each cap-grid column
scoring_oklabscopy of the dense predictions with cells outside the height budget set to inf
dense_oklabsmodel prediction for every representable stack/cap cell, including cells that Stage 2 may not select

Stage 2 candidate scoring receives the masked view. Stage 4 receives the dense view so its own cap planner can enforce cap authority without needing another prediction call. A cell remains non-finite even in the dense view if its stack cannot be represented on the evaluator’s per-filament max_layers grid; live unique stacks originate from compatible LUT recipes.

For a banded solve, the evaluator uses the fixed band-layer budgets for the height mask and folds the derived commutative white fill into each stack’s predicted transmission. For an ordinary solve, the budget uses the actual sum of color layers.

The cap grid is not reconstructed from only the LUT rows that survived color pruning. It is freshly evaluated on the LUT’s cap-step domain. This normally uses the vector evaluator, but zero-cap rows deliberately fall back to the canonical row provider because a missing cap changes the physical evidence class. The previous blanket claim that this route never invokes the row-shaped provider was therefore false.

Candidate scoring

For one proposed stack and a set of zone pixels, _score_stack_for_cell computes each pixel’s Euclidean OKLab distance at every cap step, retains the best cap distance for that pixel, and then averages those minima. It is a mean per-pixel optimal-cap distance; it does not force the entire zone to share one cap value.

_score_candidates_batch applies the same calculation to several candidates. A single-pixel fast path avoids constructing a pixel axis. Otherwise it broadcasts the full pixels × candidates × cap_steps × 3 difference tensor when that tensor contains fewer than 50 million scalar elements. At or above that threshold it loops over candidates through _score_stack_for_cell to bound peak memory.

The runner uses the scorer when a zone has multiple local candidate stacks and when it prices selected neighboring zones’ local-best stacks for augmentation. A zone with only one local candidate is assigned a local score of zero without invoking the helper.

Because the scorer minimizes over the cap axis, the inf cells in the scoring grid act as structural exclusions. The later runner—not this helper—owns neighbor selection, beam/local optimization, fine override, seam/printability repair, and final recipe commitment.

Live Stage 2 sequence

The runner records separate timings for LUT query, stack encoding, cap-grid precompute, candidate enumeration, and neighbor augmentation under the stage2_*_s performance keys. These are diagnostic fields, not separate user-visible jobs or cancellation boundaries.

Secondary luminance-handler use

LuminanceHandler._sample_white_luminance_curve also calls _predict_transmission_batch when the active appearance lane is historical spline. It combines the fixed base transmission with each sampled cap transmission and converts both full white-stack and cap-only colors to OKLab. A non-spline provider instead uses provider.sample_white_cap_oklab and does not call this helper.
