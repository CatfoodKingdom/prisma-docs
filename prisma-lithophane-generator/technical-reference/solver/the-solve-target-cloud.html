The solve target cloud

The solve target cloud

Properties1
tagsgenerator, target

Jul 15, 20264 min read

In one sentence: the solve target cloud is the shared lower-level conversion that takes an already prepared source raster into model-domain OKLab on the observation and solve grids; the solve runner calls it after F1 preprocessing, while palette suggestion calls it without running F1.

What it owns

pipeline.target_cloud.compute_solve_target_cloud centralizes three operations that solving and palette suggestion must interpret identically:

  1. source sRGB to the active model’s target linear-RGB domain;
  2. linear RGB to OKLab; and
  3. observation-grid to solve-grid projection.

It deliberately does not load, crop, adjust, or preprocess an image. Its input is whatever raster the caller has already prepared.

The returned frozen SolveTargetCloud carries:

FieldMeaning
observed_oklab(H*W, 3) targets on the input raster’s observation grid
solve_oklabtargets projected onto the configured solve grid
observation_shapeinput raster height and width
solve_shapeprojected solve-grid height and width
domainalways "model_oklab"
model_domain_ingresswhether Camera Transform ingress was requested

The caller boundary

The two live direct consumers do not supply identical pixels:

  • pipeline.runner.run_pipeline loads profiles, resolves and executes the enabled F1 preprocessing chain, and then builds the target cloud from the resulting raster. With no enabled preprocessors, it passes the ordinary loaded/adjusted raster through unchanged.
  • palette.suggest.solve_target_oklab_for_signature builds the same kind of cloud for palette scoring. The server supplies a framed, resampled, ordinarily adjusted source raster capped to an 80 mm longest dimension, but it does not execute the F1 module chain.

This means the two paths share the color-domain conversion, grid projection, and optional white rescale. It does not mean an enabled noise-reduction, smoothing, tone-fit, or saturation-fit module changes automatic palette suggestions.

Preview and compare solves reach this helper indirectly through the same facade and runner as a full solve. There is no separate direct “gamut preview” caller.

Conversion steps

1. Source pixels enter the model domain

model.image_to_target performs the ingress conversion selected by model_domain_ingress:

  • On, as forced by the current product path: load the Camera Transform inverse LUT and apply its trilinear source-sRGB-to-model-domain mapping.
  • Off, for lower-level legacy callers: apply the historical gamma-2.2 srgb_to_linear conversion.

The normal runtime resolves the LUT from the active published model library’s camera_transform directory. _build_solve_config replaces stale saved/profile paths with that active-library path.

image_to_target still defaults its own ingress argument to False, but the server and typed runtime configuration explicitly use True. Its wb_profile and d_wb parameters remain for API compatibility and are unused: the modeled white sandwich is already represented in the gamut/LUT data to which the target will be compared.

2. Linear RGB becomes model OKLab

model.to_oklab converts the flattened target array with lib.transmission.linear_to_oklab. solve_target_domain always reports MODEL_OKLAB_DOMAIN, regardless of which ingress branch produced the target.

The ingress flag therefore selects a source conversion, not a second nearest-neighbor comparison domain. Solver targets and palette gamuts are both tagged as model OKLab.

3. Observation pixels project to the solve grid

pipeline.derived_views.project_observation_to_solve_grid compares image_sample_pitch_mm with solver_fine_pitch_mm:

  • when they agree within tolerance, it returns the original flat array object;
  • otherwise it reshapes the OKLab array and bilinearly resamples it with scipy.ndimage.zoom(order=1) using the physical-pitch ratio.

The helper and the separately recorded solve_shape use the same rounded dimensions. The normal Settings contract couples these two pitch fields, so ordinary browser-driven solves normally take the identity branch.

Optional paper-white rescale

apply_gamut_white_rescale_to_targets is a separate helper, not part of compute_solve_target_cloud. It returns the targets unchanged when gamut_white_rescale is off, the targets are absent, the provider is absent, or the computed paper white makes the operation a no-op.

When enabled:

  1. solve.compute_paper_white_rgb asks the active appearance provider for the thinnest printable white-only stack: configured white base plus one minimum-cap thickness of the effective cap filament.
  2. solve.rescale_oklab_targets converts targets back to linear RGB, multiplies each channel by that paper-white RGB, and returns to OKLab.

The runner applies this only to state.solve_target_oklab; state.observed_target_oklab remains the unrescaled observation-grid cloud. Palette suggestion applies the same helper to its solve-grid cloud before clustering.

The web-app default is gamut_white_rescale=False.

ConsumerStable source anchorResult
Solve runnerPrisma/generator/pipeline/runner.py: run_pipeline, _apply_target_white_rescaleowns observation- and solve-grid targets for the staged solve

The server’s suggestion route calls the palette helper; preview, compare, and full solves call the facade, which delegates to the runner. No production path calls the legacy six-step engine in pipeline_cli.run for this work.
