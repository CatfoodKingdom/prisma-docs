SolveConfig and SolveResult reference

SolveConfig and SolveResult reference

Properties1
tagsgenerator, solver

Jul 14, 202610 min read

In one sentence: SolveConfig is the current 100+-field dataclass that specifies one solve, and SolveResult is the compatibility container the facade returns — thickness maps, staged/export artifacts, diagnostics, stats, and the predict_image reconstruction methods.

Both live in generator.facade (Prisma/generator/facade.py). The module header still calls itself lith_facade.py (facade.py:2) — that name is stale; cite line anchors, not the header. This page covers the two dataclasses a caller hands in (SolveConfig) and gets back (SolveResult), the effective_* helpers that derive runtime values, and the two forward-prediction methods (predict_image, predict_image_color_only).

For the functions that consume a SolveConfig — solve_preview, solve_full, solve_compare — see The solve facade. For the pipeline they delegate into, see The staged backend (Stage 0-5) and generator.pipeline.runner.

SolveConfig

@dataclass SolveConfig (facade.py:46) — “All parameters needed for a single solve invocation.” Two required fields (palette and white_base), the rest defaulted. The web server builds one in _build_solve_config (server.py:976, return at :1008); the CLI builds its own.

How it is driven

A caller constructs a SolveConfig, then passes it to a facade entry point. The same object flows through _to_pipeline_config (facade.py:497), which copies the supported fields into a PipelineConfig for the runner. Almost every runtime field below is forwarded there — SolveConfig is the public shape, PipelineConfig the internal one. SolveConfig does not hold an image: the image is a separate argument to solve_full(img, config, ...).

__post_init__ — the resolution backstop

__post_init__ (facade.py:153) first canonicalizes palette order through the filament-order registry (:156-:160), then calls _apply_resolution_backstop(self) from config/resolution_schema.py:153. The backstop applies the default pitch pair when both fields are absent, rejects a half-specified pair, and rejects mismatched values (resolution_schema.py:167-185). It also ensures color_region_target_mm has its independent default (:187-:190).

Resolution (canonical pitch fields)

image_sample_pitch_mm (0.20), solver_fine_pitch_mm (0.20), stage1_coarsening_factor (1), stage1_lattice_offset_y_px / _x_px (0). These are the only resolution channel — there are no legacy alias fields on the runtime dataclass (resolution_schema.py:157). See generator.config.resolution_schema.

Cap shaping

cap_mode ("smooth_variable" | "appearance_bounded_smooth"; the server rejects retired "fixed" at request normalization), boundary_cap_de_budget (0.008, the Appearance dE budget within which appearance_bounded_smooth holds the structural boundary cap), cap_continuity_cleanup (True, fills single-pixel cap pinholes), plus the detail-cap family detail_cap_pitch_mm / detail_cap_enabled (True) / detail_cap_max_layers (5). The server rejects detail_cap_enabled=False and the facade-to-pipeline translation forces detail_cap_enabled=True (facade.py:619-625).

Solver behavior

de_threshold (0.01), gamut_mode ("hull" convex hull, or "chroma" legacy), gamut_white_rescale, chroma_weight (1.0, >1 prioritizes color over lightness in the KD-tree), and the luminance_handler_* family governing the optional generator.pipeline.luminance_handler. Luminance handling influences cap guidance; Stage 2 candidate scoring has no separate luminance near-tie control.

Model-domain ingress — model_domain_ingress (True) and model_domain_ingress_lut_path (the camera_transform directory inside the launcher’s active immutable model library) thread the Camera Transform inverse LUT into image ingress. See Model domain ingress.

Staging / printability — a large stage2_* family (continuity weight, fine override, boundary mutation, printability gates/repair), stage4_printability_gate_detail, luminance_detail_authoring_printability, and the printability_* / enforce_printability / color_region_* group. These feed the staged backend and optional staged printability diagnostics. emit_blueprint_printability defaults True; allow_print_despite_hazards defaults False. The web server forces product printability settings through _force_mandatory_product_settings before constructing the config (server.py:982-998).

Smoothing & cells — smooth_kernel (7.5), smooth_iters (3), cell_mode ("felzenszwalb"), smooth_boundaries (False), boundary_smooth_radius (1), and the v2_* cleanup family.

AMS slots — ams_slots (4), white_slots (1). Color slots are derived (see color_slots).

Swap banding — there is no grouping field or grouping module in the current SolveConfig. ams_slots and white_slots determine color_slots(); the runner automatically requests swap banding for a full-preset solve when the palette exceeds that budget. The plan is stored on PipelineState.swap_grouping and copied to SolveResult.swap_grouping.

Preprocessing — preprocessing_params (per-operator kwargs keyed by module name; every registered operator’s params block materializes here at its default). Enablement is resolved separately from module state; there are no current protect_subject_* or protect_mask_* fields in SolveConfig. See Preprocessing pipeline.

Printer / resample — nozzle_diameter (0.20), printer_min_line_width_mm, source_resample_kernel ("lanczos" default, bit-exact with pre-B7 behavior; "area" selects cv2.INTER_AREA).

Cloning

_replace_solve_config(config, **changes) (facade.py:651) shallow-clones a SolveConfig from config.__dict__ with overrides. solve_compare uses it to swap in each palette (facade.py:939-:942). Because it rebuilds via the constructor, __post_init__ re-runs — palette canonicalization and the resolution invariant are re-checked on every clone.

SolveResult

@dataclass SolveResult (facade.py:234) — “Complete result of a solve operation.” Built by _state_to_solve_result (facade.py:785), which converts a PipelineState back into the public result shape after the runner finishes. Direct tests may construct partial SolveResult objects with many optional fields None.

__post_init__ — thickness-map normalization

__post_init__ (facade.py:270) wraps a raw dict into the typed ThicknessMaps if it is not already one (:276-:277). This is a no-op when the runner already handed over a wrapped container (the webapp path), so it preserves exact object aliasing there. ThicknessMaps (thickness_maps.py:77) is a compatibility-first MutableMapping whose keys normalize to plain strings, so every serializer and frontend payload sees the exact legacy strings. The reserved sentinel keys are the MapKey enum (thickness_maps.py:40): __white_cap__, __white_boundary_cap__, __white_detail_cap__, __de__, __gamut_mask__. Dynamic filament IDs are plain strings, distinguished by not starting with __.

Diagnostics-vs-thickness_maps accessor fallback

The de_map and gamut_mask properties (facade.py:281-291) each prefer the diagnostics dict and fall back to thickness_maps:

This dual lookup exists for a reason spelled out at facade.py:255-260: the staged/webapp runner populates diagnostics (from PipelineState.diagnostics: __de__, __gamut_mask__, __target_gamut_*__), so production results take the first branch. The fallback to thickness_maps serves only diagnostics-less legacy results — the separate legacy CLI engine, and tests that build a SolveResult straight from thickness_maps without a diagnostics dict. The same prefer-then-fall-back pattern appears in _compute_palette_fit_diagnostics (facade.py:679-687).

The other map accessors read thickness_maps directly (no fallback needed — caps are always part of the thickness output): cap_map → WHITE_CAP (facade.py:293), boundary_cap → WHITE_BOUNDARY_CAP or None (facade.py:298), detail_cap → WHITE_DETAIL_CAP or None (facade.py:303), filament_ids → the dynamic keys (facade.py:308).

Best-case palette-fit diagnostics

palette_fit_image / palette_fit_de / solver_loss_map are computed by _compute_palette_fit_diagnostics (facade.py:666) and only for preset.name == "full" (returns {} otherwise, :668-:670). It re-queries the LUTs for the per-pixel best achievable match and computes the solver’s loss as max(final_de - best_de, 0) — i.e. how far the actual solve fell short of the palette’s theoretical best. See Solve diagnostics and dE maps.

predict_image and predict_image_color_only

These are the forward reconstruction methods: given solved thickness maps, recompose the predicted backlit image. This page owns the cap-zeroing explanation.

predict_image

predict_image(max_layers=None, *, thickness_maps=None) (facade.py:313) returns an (H, W, 3) uint8 image. Two backends, selected by the appearance provider’s model_kind (facade.py:328-364):

  • historical_spline (the spline provider — no longer the default) and any diagnostics-less result fall to predict_image_fast (solve.py:674), the vectorised spline composition: T = T_wb · Π T_color(d) · T_cap(d) per pixel, then gamma-2.2 to sRGB uint8 (solve.py:714).
  • non-spline providers (e.g. photo_stack_bundle, appearance_model.py:224) route to provider.predict_thickness_maps_srgb(...) (facade.py:460).

The thickness_maps= keyword overrides the solved maps for the prediction. Default None uses the solved maps, preserving historical behavior (facade.py:326-327). This override is the hook predict_image_color_only rides on.

max_layers defaults to config.effective_max_layers() (facade.py:326).

Callers (confirmed live): server.py:4061 (preview/gamut-check reconstruction), :4172 (per-palette reconstruction inside the solve_compare loop), :5028 (the full-solve reconstruction), plus evaluation/scripts and tests. predict_image is the live image-reconstruction path for the generator UI.

predict_image_color_only — and white-cap zeroing as multiplicative identity

predict_image_color_only(max_layers=None) (facade.py:406) reconstructs the base + color image with the white cap omitted, so the cap’s luminance shaping does not drown out the color story. The base stays in — it is the substrate. Output is the same model-domain gamma-2.2 sRGB uint8 as predict_image, so it can be baked through the display transform F.

It is a thin wrapper: it calls self.predict_image(max_layers, thickness_maps=self._cap_zeroed_thickness_maps()) (facade.py:415-:417). All the interesting work is in _cap_zeroed_thickness_maps (facade.py:386):

It shallow-copies the maps (ThicknessMaps.copy(), arrays shared) and replaces every white-cap term — total cap and its boundary/detail components — with an all-zero array.

Why zeroing the cap thickness cleanly drops the term: a zero cap thickness is the multiplicative identity in the transmission model. The composition multiplies a per-channel cap transmission T_cap(d_wc) into the stack (solve.py:710-712; spline provider appearance_model.py:205-206). The transmission of any profile at thickness 0 is [1, 1, 1] — confirmed at lib/transmission.py:107-108:

So T_cap(0) = [1,1,1], and multiplying the stack by [1,1,1] leaves base × color untouched. This holds in both spline-composition backends (predict_image_fast and the spline appearance provider both call predict_transmission → predict), exactly as the method’s docstring asserts (facade.py:483-485). The cap term is dropped without touching the composition math — no special-casing, just feeding it the identity input.

Liveness: predict_image_color_only and _cap_zeroed_thickness_maps are defined at facade.py:406 / :386 and are live. The full-solve path invokes result.predict_image_color_only() at server.py:5077, saving the color-only predicted render for the Recipe viewer’s color-region view. The behavior is exercised directly by tests/generator/test_predict_color_only.py, including the non-spline backend cap-zeroing check.
