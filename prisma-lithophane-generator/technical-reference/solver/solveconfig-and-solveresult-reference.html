SolveConfig and SolveResult reference

SolveConfig and SolveResult reference

Properties1
tagsgenerator, solver

Jul 26, 202610 min read

In one sentence: facade.SolveConfig is the public solve-request dataclass, while facade.SolveResult is the compatibility-facing result that carries material maps, staged/export artifacts, diagnostics, statistics, and forward-reconstruction helpers.

config.solve_settings.SolveSettings declares the 81 settings shared by facade requests and pipeline execution. SolveConfig inherits those fields and adds only preprocessing_params, for 82 fields total. Only palette and white_base are required; all other fields have dataclass defaults. Those defaults are not always the product defaults: for example, the dataclass uses cap_mode="smooth_variable" and smooth_kernel=7.5, while the server’s ordinary session defaults use Detail Aware cap mode and smooth_kernel=5.0.

PipelineConfig is the sibling execution wrapper. It inherits the same settings and adds the resolved preprocessor list, quality preset, and a non-constructor runtime carrier. Its bare de_threshold=0.05 remains an intentional lower-level compatibility override; facade compilation copies the request value, normally 0.01.

The source header still calls the module lith_facade.py. The file is now facade.py, and prediction is invoked separately by server callers after a solve.

Both functions normalize a copy of the request, resolve the preprocessing module state, compile the shared fields into PipelineConfig, and call pipeline.runner.run_pipeline. The image is a separate argument; it is not stored on SolveConfig.

There is no separate batch-solver entry point: all supported solves use the solve facade, pipeline.runner, and the stage-owned backend reached through the thin pipeline.staged_runner compatibility facade.

Construction and resolution normalization

The inherited SolveSettings.__post_init__ performs two actions:

  1. canonicalize palette order through the active published library’s filament registry; and
  2. invoke config.resolution_schema._apply_resolution_backstop.

The backstop treats image_sample_pitch_mm and solver_fine_pitch_mm as one coupled pair. If both are absent it assigns 0.20; if only one is present or their values disagree it raises a schema conflict. color_region_target_mm remains independent and defaults to 0.60 when absent. Retired external aliases such as pixel_size_mm, mesh_xy_pitch_mm, and color_pixel_mm are rejected earlier by the ingress schema and do not exist on either runtime dataclass.

Resolution and Stage 1 regions

The canonical pitch fields are image_sample_pitch_mm and solver_fine_pitch_mm, both 0.20. Stage 1 additionally uses stage1_coarsening_factor, lattice offsets, color_region_target_mm, color_region_target_from_printability, its width multiplier, cell_mode, smooth_boundaries, and boundary_smooth_radius.

The server forces printability-derived color-region sizing on for product solves. The user-facing Region Method selects felzenszwalb, slic, or grid; the low-level helper treats any unrecognized direct value as SLIC.

Gamut and color objective

de_threshold defaults to 0.01, chroma_weight to 1.0, and gamut_white_rescale to false.

The product server accepts:

  • hull: convex-hull projection; and
  • hue_preserving: hue-preserving chroma contraction.

pipeline.runner._apply_target_gamut_mapping accepts chroma as a compatibility alias for hue_preserving, and direct lower-level callers can disable mapping with none/off/disabled. The server normalizes chroma to hue_preserving, but rejects the three mapping-disabled values. The legacy solve.py engine’s separate chroma implementation is not the product route.

Stage 2 and printability

The stage2_* family covers zone continuity, area weighting, pressure/frontier rescue, source-edge subzones, fine overrides, seam handling, boundary mutation, and printability gating/repair. emit_pressure_diagnostics and emit_geometry_attribution gate expensive developer diagnostics.

Printability inputs include the active nozzle diameter, minimum extrusion width, minimum line length, enforce_printability, and emit_blueprint_printability. The server forces product safety settings including enforcement, fine-override gate/repair, final substrate repair, Stage 4 detail gating, and blueprint diagnostics. It does not force the optional fine-override feature or boundary mutation themselves on; those remain settings.

Preprocessing

preprocessing_params defaults to an empty dictionary. It stores only parameter overrides that have been supplied, keyed by preprocessing module id. The UI materializes descriptor defaults when it builds or normalizes settings; a direct facade call with a missing or empty parameter block constructs an enabled operator with that class’s constructor defaults. Module enablement lives separately in the Workspace module-state file. The facade consumes the dictionary while constructing the resolved ordered operator list; PipelineConfig receives the instantiated operators, not another parameter copy.

AMS and swap bands

ams_slots defaults to four and white_slots to one. A distinct base and cap force at least two white slots through effective_white_slots; color_slots subtracts that value from the AMS capacity without clamping.

SolveConfig contains no grouping object. For a full-preset solve whose palette exceeds the ordinary color-slot budget, the runner chooses a swap-band plan and stores it on PipelineState.swap_grouping; result conversion deep-copies that plan to SolveResult.swap_grouping.

Resampling

source_resample_kernel is a live session/profile setting, not a SolveConfig field. It defaults to lanczos; area chooses cv2.INTER_AREA. The server consumes it while preparing the source raster before the facade solve begins, so it does not need a later SolveConfig or PipelineConfig carrier.

Facade compilation

PipelineConfig.from_solve_settings copies every canonical field using the authoritative SolveSettings dataclass inventory, so adding a shared field cannot silently omit it from the handoff. This includes max_layers. The facade still applies its explicit mandatory-detail policy to a copy of the request before compilation, leaving the caller’s object untouched.

The preset is an additional execution ceiling: FULL_PRESET imposes no extra limit, while PREVIEW_PRESET limits the configured or physically derived budget to at most 15 layers. The server does not expose an ordinary max_layers setting.

SolveResult

_state_to_solve_result converts the finished PipelineState into a facade result. SolveResult.__post_init__ wraps a raw thickness-map mapping in ThicknessMaps; when the state already supplies a ThicknessMaps, the exact object is retained.

Diagnostics and export fields

diagnostics is annotated as Dict[str, np.ndarray], but runtime state also stores nested metadata dictionaries such as solve identity, provider/cache information, and swap-plan diagnostics. Result conversion shallow-copies the dictionary, so contained arrays/dicts remain shared with state.

debug_maps is also shallow-copied as a dictionary; its arrays remain shared. preprocessing_metrics and cap_quality receive shallow dictionary copies. By contrast, result export_maps receive new float32 arrays, export_metadata is deep-copied, and swap_grouping is deep-copied.

The read-only blueprint printability diagnostic lives on staged_result.cap_plan and in derived debug/counter fields.

ThicknessMaps and convenience accessors

ThicknessMaps normalizes enum and string keys to the exact historical strings. Current reserved keys are:

  • __white_cap__
  • __white_boundary_cap__
  • __white_detail_cap__
  • __de__
  • __gamut_mask__

The live staged result keeps dE and gamut in diagnostics, not in material maps. de_map and gamut_mask prefer the diagnostics dictionary and fall back to thickness-map sentinels for diagnostics-less legacy/test objects. cap_map, boundary_cap, and detail_cap read the material container directly. filament_ids returns keys that do not begin with __.

Palette-fit diagnostics

_compute_palette_fit_diagnostics runs only for FULL_PRESET. It re-queries the LUTs for the best independently attainable recipe at each target and produces:

  • palette_fit_image
  • palette_fit_de
  • palette_fit_rms_de
  • solver_loss_map = max(final_de - best_de, 0)
  • solver_loss_rms_de

The best-fit rendering uses the active appearance provider and includes derived swap-band white fill when the solve is banded. The preview preset returns these fields as None.

Forward reconstruction

predict_image

predict_image(max_layers=None, *, thickness_maps=None) returns an (H, W, 3) uint8 reconstruction. An override mapping lets diagnostics reuse the exact prediction path with modified material maps.

For a historical spline result, predict_image_fast composes the base, color, final cap, and optional band-fill transmissions. For a non-spline provider, the provider predicts from thickness maps; banded v2 results additionally fold the derived fixed white fill into model-linear RGB before the common gamma-2.2 uint8 conversion.

When max_layers is omitted, this method uses resolved_max_layers populated from the finished pipeline. Directly constructed legacy/test results without that value fall back to the facade config’s effective_max_layers(). An explicit method argument remains the highest-priority override.

The live server calls this method after a full solve to create UI reconstruction artifacts. Repository evaluation and focused-test callers may also reconstruct results from solve_preview; there is no live compare-solve path. Display Camera Transform baking happens after this method; the method itself returns the model-domain encoded reconstruction.

predict_image_color_only

_cap_zeroed_thickness_maps shallow-copies the ThicknessMaps container and replaces total, boundary, and detail final-cap arrays with zeros. Color arrays remain shared. predict_image_color_only passes that override to predict_image.

The backend meaning differs slightly:

  • In the historical spline lane, zero thickness gives [1,1,1] transmission, so the final cap is a multiplicative identity.
  • In photo-stack v2, zero cap changes the evidence geometry. The vector evaluator deliberately delegates those rows to the canonical row provider; the model predicts the base-plus-color, no-final-cap stack rather than relying on a generic multiplicative-identity assumption.

For a swap-banded solve, fixed band white fill remains because it is part of the printable color-band plan and is derived from swap_grouping, not stored in the final-cap keys. “Color only” therefore means without the final luminance-shaping cap, not without mandatory band fill.

The full-solve server path saves this reconstruction for the Recipe viewer’s color-region presentation.
