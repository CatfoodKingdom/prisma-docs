The vectorized photo-stack LUT evaluator

The vectorized photo-stack LUT evaluator

Properties1
tagsgenerator, evaluator

Jul 25, 20266 min read

In one sentence: photo_stack_lut.py mirrors the photo-stack v2 equations over NumPy grids so bulk LUT, palette-gamut, cap-grid, banded-fill, and image-prediction work can reuse the calibrated model without paying the DataFrame row-provider cost for every candidate.

The canonical row-shaped implementation is PhotoStackBundleAppearanceProvider.predict_stack_model_linear_rgb_batch. It turns StackRequests into pandas rows, invokes the published bundle predictor, and optionally applies the learned correction artifact. That route remains the oracle for isolated and unsupported-grid cases.

The vectorized implementation is _PhotoStackGridEvaluator. It uses the same provider bundle, predictor object, material classifier, correction artifact, imported model constants, and low-level color/OD helpers, but reorganizes the equations around array columns. Local vector helpers handle row normalization, hue math, grouping, and broadcasting.

PHOTO_STACK_LUT_BUILDER_VERSION is part of ordinary provider cache identity. It must change when evaluator behavior changes in a way that invalidates cached colors.

Precomputed model tables

The evaluator constructor validates that configured base and cap are model-white, then precomputes:

  • base OD at the fixed base thickness;
  • cap OD for every supplied cap value;
  • a combined base-plus-cap OD table when both whites are the same filament;
  • per-filament OD tables at every integer color-layer count through max_layers; and
  • compiled correction groups and lazy single-color profile grids.

predict_subset groups rows by an active-filament bitmask. Every row in one group therefore has the same present color IDs and takes the same distinct-color branches, while its layer counts and cap index remain vectorized.

OD composition and OKLab refinements

For nonzero-cap rows, the evaluator first builds optical density:

It clips OD to [0, 20], converts once to linear RGB with the predictor’s transmission floor, and converts that RGB to OKLab. Later refinements operate in OKLab rather than by adding OD:

The underlying OD terms also use the predictor’s material gates, tint-authority scales, overlayer attenuation, cap response, and interaction parameters. Three-or-more-color rows receive the general multi-color and ordered-tint behavior but not the exactly-two endpoint corridor.

Learned correction parity

_compile_correction_artifact validates the artifact’s model-white classifier and groups training rows by canonical unordered colors, canonical white pair, and evidence class. _apply_corrections builds the same scaled feature vector used by the correction layer, performs distance-cutoff Gaussian local averaging inside the matching group, and limits the residual by support, authority, and norm.

The residual can change L, a, and b. Only L is explicitly clipped to [0, 1] before conversion back to RGB.

Evidence classes are white_only, single_color_sandwich, and cross_color_multilayer_sandwich.

Model domain and the retired projection seam

predict_combo_model_linear_rgb returns model-domain linear RGB. LUT and cap-grid callers then invoke provider.project_model_linear_rgb_to_appearance before OKLab conversion, but that provider method is currently an exact array pass-through retained for compatibility. It is not an active camera conversion.

Camera Transform ingress maps source pixels into the model domain. Forward Camera Transform baking maps solved model-domain predictions to display appearance. See Model-domain ingress and display conversion.

Zero-cap and same-white correctness guards

Rows whose selected cap is zero bypass the vector equations and are sent to the canonical row provider. Zero cap changes the evidence geometry from a white sandwich to color-over-white, so delegating avoids extrapolating cap-transfer and white-context behavior across the absent-cap boundary. This route is particularly relevant to color-only reconstruction, which deliberately asks for zero variable cap.

When no color separates a same-filament white base and cap, _latent_parts samples the nonlinear white OD curve at their combined thickness rather than summing two independently sampled white curves. That mirrors the provider’s physical-layer collapse.

Dense versus budgeted cap grids

predict_unique_stack_cap_oklab_grid returns two arrays:

  • dense: (n_stacks, n_caps, 3) OKLab, finite for every representable stack/cap cell;
  • within_budget: a boolean mask marking which representable cells also fit the current height rule.

A stack is unrepresentable if any color’s layer count exceeds max_layers; those dense cells remain inf. For an ordinary solve, the budget mask compares total color layers with the height left after each cap. For a banded solve, it uses the plan’s fixed total band layers and separately folds each stack’s computed white fill into the optical prediction.

pipeline.staged_solver_helpers._precompute_cap_oklabs_vectorized keeps the dense view for Stage-4 cap lookup and creates a scoring copy with disallowed cells set to inf. Candidate scoring cannot choose an over-budget cap, while later cap planning still has model colors for every representable cell and enforces its own cap authority.

Commutative band white fill

apply_commutative_white_fill multiplies provider model-RGB rows by the historical cap spline’s transmission at the total white-fill thickness. This represents the fixed white occupying unused layers across swap bands without asking the photo-stack predictor to treat separated fill as another ordered color layer.

It is live in:

  • provider banded-LUT pricing;
  • banded cap-grid precomputation;
  • final dE recomputation;
  • palette-fit diagnostics; and
  • full and color-only solved-image reconstruction.

The helper validates RGB shape, scalar/per-row fill cardinality, and nonnegative thickness, and returns the original values unchanged when every fill is zero.

On-grid acceleration and fallback

PhotoStackBundleAppearanceProvider._predict_unique_combo_model_linear_rgb deduplicates image recipes before prediction. Color thicknesses that are nonnegative, within max_layers, and aligned to layer_height use predict_combo_model_linear_rgb. Off-grid or out-of-range color thicknesses fall back to row-shaped StackRequests.

Cap values are not subjected to that color-grid check: the vector evaluator builds a local cap OD table from the supplied unique cap values, so an otherwise valid row can use an arbitrary cap thickness.
