The live staged printability diagnostic

The live staged printability diagnostic

Properties1
tagsgenerator, printability

Jul 12, 202610 min read

In one sentence: after the staged solve builds the white cap, the generator re-derives the layered plan, grades every connected component on every layer against the printer’s physical min-feature thresholds, and records a read-only diagnostic (per-pixel fail maps + worst-component facts) that the UI overlays — while a separate, always-on audit counts any color filament left exposed to air.

The live staged printability diagnostic

This is the plan-level printability check that runs as part of a production solve. It does not repair geometry — it measures it. Two distinct things live here, both wired into the live solve path:

  1. The blueprint printability diagnostic — a layer-by-layer grade of every connected component against resolved physical thresholds (min extrusion width, min line length, plus a neck, clearance, and vertical-support audit). Built in generator.pipeline.staged_printability.
  2. The material exposure audit — a 3D face-count of color filament left touching air, plus the mandatory white boundary-shield floor implied by color-height cliffs. Built in generator.pipeline.material_exposure.

The diagnostic is read-only. The enforcement passes inside generator.pipeline.staged_runner (Stage 4 boundary-cap and detail repair) reuse the same grading helpers so a component the diagnostic flags is the same component the gates repair — see Reuse by the enforcement passes. For the stage that owns those gates see The staged backend (Stage 0-5).

How to drive it

You do not call any of this directly. It runs automatically inside run_staged_backend_path (the live webapp solve engine, pipeline/staged_runner.py:11163; the only caller is the runner at pipeline/runner.py:1222–1225 — not the legacy solve.py CLI engine). The diagnostic stage is gated on one flag and bounded by a handful of physical settings you set per run:

KnobDefaultWhere setEffect
emit_blueprint_printabilityTruefacade.py:59, server.py:398, state.py:106, app.js:335Master on/off for the diagnostic stage (staged_runner.py:11569).
printability_minimum_extrusion_width_mmNone → 0.40resolver staged_printability.py:79Min printable feature width; from the active nozzle’s min_line_width (app.js:6544).
printability_minimum_line_length_mmNone → derivedresolver staged_printability.py:84-88Min printable feature length; defaults to max(0.40, width + 0.10).

When emit_blueprint_printability is off the diagnostic stage is skipped entirely; the exposure audit (below) still runs on every solve.

Step 1 — Resolving physical thresholds

resolve_blueprint_printability_settings (staged_printability.py:71) collapses the user/printer config into a frozen BlueprintPrintabilitySettings (staged_printability.py:20) carrying four numbers in millimeters: minimum_extrusion_width_mm, minimum_line_length_mm, pitch_mm, layer_height_mm.

The resolver is forgiving — each field falls through a chain of candidates via _first_positive (staged_printability.py:58), which returns the first strictly-positive value:

  • Width: printability_minimum_extrusion_width_mm → printer_min_line_width_mm → hard floor 0.40 (staged_printability.py:78-83).
  • Min line: explicit value, else max(0.40, width + 0.10) (staged_printability.py:84-88).
  • Pitch: the pitch_mm argument → solver_fine_pitch_mm → image_sample_pitch_mm → 0.20 (staged_printability.py:89-94). The live call passes pitch_mm=solver_fine_pitch_mm (staged_runner.py:11434) so grading happens at the true fine solve resolution.
  • Layer height: layer_height → 0.08 (staged_printability.py:95).

Pitch is the linchpin: every pixel-count is converted to physical area/width/length by multiplying by pitch_mm, so the thresholds are compared in millimeters regardless of solve resolution.

Step 2 — The layered blueprint view

build_layered_blueprint_view (staged_printability.py:163) derives a read-only per-layer occupancy view (LayeredBlueprintView, staged_printability.py:31) from two staged artifacts: the VisibleRecipeRawGeometryPlan (color recipes per zone) and the CapSynthesisPlan (white cap + detail heights). It splits the plan into three surface families:

  • Color layers — each visible recipe’s per-filament thickness is quantized into integer layer counts (_positive_layer_counts, staged_printability.py:125; note ≥ 1 layer for any positive thickness, staged_printability.py:131), expanded into an ordered label stack per recipe (_recipe_color_layer_table, staged_printability.py:135), then scattered across the image via the recipe label map (staged_printability.py:184-186). Material ordering follows the declared palette, with any stragglers appended (_ordered_material_ids, staged_printability.py:106).
  • Cap layers — the boundary cap, computed as cap_height_mm − detail_height_mm clamped at 0 (staged_printability.py:192-196), sitting on top of the color ceiling (color_ceiling = cap_boundary_top_mm − boundary_cap_height, staged_printability.py:198-201).
  • Detail layers — the detail cap, stacked on color_ceiling + boundary_cap_height (staged_printability.py:241-248).

Each surface is materialized into a stack of boolean layer masks anchored to an absolute Z grid (absolute_layer_masks, staged_printability.py:204), so the support audit (Step 4) can look downward through the stack.

Step 3 — Grading a component

grade_blueprint_component (staged_printability.py:264) is the atomic check. Given a connected component’s pixel count and bounding-box height/width in pixels, it computes three physical measures and returns a grade:

MeasureFormula (staged_printability.py)Compared against
area_mm2pixel_count · pitch² :272min_extrusion_width · min_line_length :275-278
width_mmmin(h, w) · pitch :273minimum_extrusion_width_mm :283
length_mmmax(h, w) · pitch :274minimum_line_length_mm :285

Grades and their reason flags:

  • hard_fail if area below min_area (tiny_component), or width below min (narrow_width), or length below min (short_length) — any one trips it (:281-288).
  • pass otherwise (:289).

Bounding-box width/length alone cannot catch a fat blob joined by a one-pixel neck, so the diagnostic adds two more per-component checks on top of the bbox grade.

The opening-width neck criterion

grade_blueprint_component only sees the bounding box; a dumbbell shape (two wide lobes joined by a sub-width neck) passes its width test. The neck is caught by a morphological opening with a square structuring element sized to the minimum printable width:

  • _minimum_width_px (staged_printability.py:292) → ceil(min_extrusion_width / pitch) pixels; _opening_width_structure (:298) builds an N×N all-ones kernel.
  • _opening_width_loss (:303) opens the component and returns the pixels the opening removed — the kernel cannot fit there, i.e. sub-width features. A 1×1 kernel is a no-op (:311-312).
  • _opening_width_loss_is_structural (:317) decides whether the loss matters: opening also rounds harmless exterior corners. The loss is structural only if removing the lost pixels destroys the component or splits it into more than one piece (:333-340). Only structural loss escalates to hard_fail with narrow_width (:530-538); harmless corner rounding is ignored.

These three helpers are public re-exports (opening_width_structure :349, opening_width_loss :353, opening_width_loss_is_structural :361) precisely so the enforcement passes apply the identical criterion — the comment at :343-348 spells out why.

Step 4 — The full diagnostic run

run_blueprint_printability_diagnostic (staged_printability.py:401) walks every layer of every surface and accumulates per-pixel fail maps plus component-level facts. The inner consume_mask closure (:449) does the work for one (surface, layer, material) mask:

  1. Connected-component labeling with 4-connectivity (ndi.label, structure from :446), iterating bounding boxes via find_objects (:489-493).
  2. Bbox grade via grade_blueprint_component (:500).
  3. Center clearance — a distance transform in mm gives each pixel’s clearance to the nearest edge (_component_center_clearance_mm, :368; applied :514-521). Recorded as max_center_clearance_mm, not itself a fail.
  4. Opening-width neck — structural loss escalates to hard_fail and marks width_loss_map (:523-538).
  5. Vertical support — see below. Any unsupported pixel escalates to hard_fail with low_vertical_support (:551-560).

Every non-pass component becomes a BlueprintPrintabilityComponentFacts (:564, dataclass at staged_artifacts.py:477) carrying its bbox, physical measures, grade, reason flags, clearance, width-loss pixels, and support fraction. The full set is sorted hard-fail-first then by pixel count (:683-694) and the worst max_worst_components (default 128) are kept (:776).

Support-fraction checks

A color pixel printed with nothing under it overhangs. _support_fraction_for_layer (staged_printability.py:383) measures, for layer k, the mean occupancy of the window of layers below it (window_layers=3, :388; layer 0 is treated as fully supported on the base, :391-392). Inside consume_mask, the per-pixel support map is sampled over the component; the mean is its support_fraction (:540-546), and any pixel with support < 1.0 is unsupported (:551).

Support sources differ per surface (:628-671):

SurfaceSupport mapSource (staged_printability.py)
colorrolling 3-layer occupancy below_support_fraction_for_layer(color_occupancy, …) :632-636
cap (boundary)full support (sits on the color ceiling)full_support :656

Projected clustering

Beyond per-component facts, the run projects all hard-fail pixels down to a 2D map and clusters them (projected_cluster_summary, :695) at two radii: tight (:716-718) and dilated by a cluster_radius_px derived from min_line_length / pitch (:719-730). This surfaces “many small fails packed into one region” as a single large-cluster fraction — the color_hard_fail_largest_cluster_fraction family on the result.

The result object

The run returns a BlueprintPrintabilityDiagnostic (staged_artifacts.py:501): the resolved hard thresholds, per-surface layer/mask/fail counts, the tiny/narrow/short tallies, the projected-cluster summaries, the worst-component tuple, and a stack of float32 per-pixel maps (hard_fail_map, narrow_width_map, short_component_map, color_hard_fail_map, cap_hard_fail_map, detail_hard_fail_map, center_clearance_map, width_loss_map, low_support_map).

Where it goes

In the live solve the diagnostic is attached to the cap plan (cap_plan.blueprint_printability_diagnostic = blueprint_printability, staged_runner.py:11447) and its scalar counts are timed/recorded into the run’s performance profile (staged_runner.py:11448+). The bridge (Step 5 of the staged backend) copies the float maps into the solve’s debug-map dict under blueprint_printability_* keys (pipeline/staged_bridge.py:383-427), which is how they reach the generator’s overlay viewer. A subset of the scalar counts is also promoted into run_metadata["stats"] for display (server.py:2336-2349). This is purely diagnostic — it gates nothing and raises nothing.

Reuse by the enforcement passes

The diagnostic is the measurement; the Stage 4 boundary-cap and detail repair passes are the enforcement, and they reuse the diagnostic’s grading helpers so the two stay in lockstep:

  • grade_blueprint_component is imported by staged_runner.py:74 and called from the enforcement graders — e.g. _stage2_component_physical_grade (staged_runner.py:3383), _component_physical_grade_with_opening (:3404), a local growth grader (:3810), and the vectorized layer-failure scan _stage4_layer_failures_vectorized (:5849).
  • opening_width_structure / opening_width_loss / opening_width_loss_is_structural are imported (staged_runner.py:75-77) and applied in those same passes (:3435-3438, :5901-5905) so the neck criterion is identical. The header comment at staged_printability.py:343-348 is explicit that bbox/area/length-only gates would let a 1-pixel neck slip past.

The material exposure audit

This page owns material_exposure.py. It is a separate, always-on audit (independent of emit_blueprint_printability) that asks one question: does any color filament touch air in the final print? It is geometry-agnostic — it audits the raster material occupancy the export path will use, and it never smooths or repairs (material_exposure.py:1-7 header; trust the line behavior, not the prose).

The boundary-shield floor

lateral_boundary_shield_floor_layers (material_exposure.py:72) computes, per pixel, how many white cap layers are mandatory to shield internal color-height cliffs. For each 4-neighbor pair it compares color-layer counts: the lower side must carry enough white cap to cover its neighbor’s color-height excess; the higher side needs none for that pair (:88-102). This floor is enforced in the live solve — lateral_boundary_shield_floor_layers (staged_runner.py:7178) runs unconditionally on every staged solve, and the result feeds the implied cap heights as minimum_cap_height_mm (staged_runner.py:7186-7193). With the fixed cap mode retired, the non-fixed gate is gone and the shield floor is now always computed.

The color-air exposure count

audit_colored_filament_exposure_from_layer_counts (material_exposure.py:106) counts exposed color faces in 3D without building a voxel stack, given color and white-cap layer-count maps:

Face typeWhat it countsCode
lateral_internal_face_countcolor stack on one side taller than the total (color + cap) stack of a 4-neighbor:122-127
top_face_countpixels with color but zero white cap on top:129
exterior_face_countcolor layers on the four image borders (no neighbor to shield them):130-135

A MaterialExposureAudit (material_exposure.py:29) bundles these counts plus the exposed-color pixel count and stack maxima. Its passes property (:51) is True only when the total exposed face count is zero (:53). The height-based entry point audit_colored_filament_exposure_from_heights (:177) just quantizes mm → layer counts first; audit_colored_filament_exposure_from_thickness_maps (:189) sums every exposure-relevant material map (exposure_relevant_material_keys, :222 — everything not prefixed __, minus explicit exclusions, :248-251) and resolves the white cap from WHITE_CAP or WHITE_BOUNDARY_CAP + WHITE_DETAIL_CAP (:258-269).

How the audit is wired

In the live solve, server.py calls the non-raising _run_material_exposure_audit (server.py:2408, invoked during solve completion around :5427) once per solve. It excludes the white base/cap ids (_white_ids, server.py:768). The summary lands in run_metadata["material_exposure_audit"] and the boolean white_cap_exposure_safe for display — it records, it does not block.

A second, assert-form gate _assert_material_exposure_safe_for_product (server.py:2369) does raise PrintabilityError on exposure, but per the in-code note at server.py:2361-2368 it is suspected inert on the live solve path (no confirmed live caller found; appears exercised only by tests/generator/test_material_exposure_product_gate.py). Treat that as unconfirmed — the note itself asks for a full reference re-check before relying on it.

Disambiguation (do not confuse)

  • The blueprint BlueprintPrintabilityDiagnostic here is unrelated to the mesh-side PrintabilityReport classes. There are two unrelated report types in the codebase (blueprint-triage vs mesh) — this page is strictly the blueprint/plan-level one.
  • VisibleRecipe (staged_artifacts.py:73) is the per-zone recipe the layered view consumes; it is a near-duplicate of StackDefinition but not the same type — the view reads recipe.to_mapping() (staged_artifacts.py:105) and recipe.thickness_by_filament (:76).
