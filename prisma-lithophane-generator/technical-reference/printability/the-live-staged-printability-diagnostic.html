The live staged printability diagnostic

The live staged printability diagnostic

Properties1
tagsgenerator, printability

Jul 15, 20266 min read

In one sentence: every normal Generator solve enforces physical feature rules while building its color and white-cap plans, then runs a read-only layer-by-layer diagnostic over the finished staged blueprint; a separate non-blocking audit records whether any solved color material remains exposed to air.

This page separates three related mechanisms that are easy to conflate:

  1. Solve-time enforcement changes Stage 2 color assignment and Stage 4 white-cap/detail geometry so they satisfy mandatory printer-derived rules.
  2. BlueprintPrintabilityDiagnostic measures the finished staged blueprint and records remaining findings. It does not change or reject that blueprint.
  3. MaterialExposureAudit counts color-to-air faces in the final thickness maps. The live caller records its result but does not reject the solve.

The legacy interval-based blueprint_triage package and the dormant high-level mesh.printability report are different systems; see Printability three layers.

Product configuration and liveness

For a normal web-app solve, _build_solve_config in server.py forces both product enforcement and blueprint diagnostics on. These are not user-facing switches. The printability width and line-length values come from the currently selected printer/nozzle:

Resolved valueProduct sourceFallback in resolve_blueprint_printability_settings
minimum extrusion widthactive nozzle min_line_width0.40 mm
minimum line lengthactive nozzle min_line_lengthmax(0.40 mm, width + 0.10 mm)
diagnostic pitchlive runner passes solver_fine_pitch_mm explicitlyconfig solve pitch, image pitch, then 0.20 mm

emit_blueprint_printability still exists in the internal config contract, so tests and non-product callers can disable the final diagnostic. The browser and server both pin it on for ordinary solves.

The diagnostic runs near the end of run_staged_backend_path: after the color, filler, boundary-cap, and detail plans have been built and enforced, but before the Stage 5 compatibility bundle is emitted.

Deriving the layered blueprint

build_layered_blueprint_view reads the final VisibleRecipeRawGeometryPlan and CapSynthesisPlan and produces a read-only LayeredBlueprintView with three surface families:

  • Color layers are reconstructed from each VisibleRecipe in declared palette order. Positive thickness is rounded to a layer count and is never allowed to become zero layers.
  • Boundary-cap layers use cap_height_mm - detail_height_mm, floored at zero, and begin at the color ceiling inferred from cap_boundary_top_mm.
  • Detail layers begin at the boundary-cap top and use detail_height_mm.

The result is a material-label stack for color and boolean mask stacks for boundary cap and detail. It is a diagnostic reconstruction, not the mesh-export representation.

Component grading

For every material mask on every reconstructed layer, run_blueprint_printability_diagnostic labels 4-connected components and grades each component in physical units.

grade_blueprint_component calculates:

MeasureCalculationMinimum
areapixel count × pitch²extrusion width × line length
widthshorter bounding-box side × pitchminimum extrusion width
lengthlonger bounding-box side × pitchminimum line length

Any failed check produces a hard_fail with tiny_component, narrow_width, or short_length reason flags.

Two additional checks catch conditions a bounding box cannot describe:

  • A square morphological opening sized to the minimum extrusion width finds sub-width material. Exterior-corner rounding is ignored; the loss is structural only when it destroys or splits the component.
  • A vertical-support map checks the three preceding color layers. Any component pixel with support below one is marked low_vertical_support. The diagnostic treats the boundary cap as fully supported and detail as supported wherever any boundary-cap layer exists.

The diagnostic also records center-clearance values and clusters projected hard-fail pixels so many nearby findings can be summarized as one affected region.

Diagnostic result and product visibility

The frozen BlueprintPrintabilityDiagnostic contains:

  • resolved physical thresholds and layer/mask counts;
  • component and pixel counts by failure type and surface;
  • worst-surface and worst-layer summaries;
  • up to 128 BlueprintPrintabilityComponentFacts records; and
  • float maps for hard failures, narrow/short components, center clearance, structural opening loss, low support, and color/cap/detail subsets.

The runner attaches this result to CapSynthesisPlan.blueprint_printability_diagnostic. Stage 5 copies its maps into CompatibilityBundle.debug_maps, and the server persists selected counters and debug-map files with the run.

Those debug maps are not exposed as normal Preview modes. The old printability diagnostic views are explicitly removed from the browser’s accessible view set. Treat the maps as persisted diagnostic/developer artifacts, not as a current user-facing overlay workflow.

The diagnostic appends an informational or warning planning entry, but it raises no exception and gates no later stage.

Relationship to solve-time enforcement

The diagnostic runs after enforcement, but its low-level physical graders are deliberately shared with the enforcement passes:

  • Stage 2 uses the same component and opening-width rules while gating and repairing fine recipe assignments.
  • Stage 4’s boundary-cap gate may grow structural cap coverage or suppress optional cap material while preserving the mandatory floor.
  • Stage 4’s detail gate suppresses optional detail material that fails its physical checks.

This shared implementation keeps “what the diagnostic flags” aligned with “what enforcement tries to prevent.” The two workflows still have different ownership: enforcement mutates plans while they are being authored; the final diagnostic is read-only.

Mandatory lateral shield floor

lateral_boundary_shield_floor_layers in pipeline/material_exposure.py computes a structural white-cap minimum before Stage 4. For every horizontal or vertical neighbor pair, the lower color stack must receive enough white layers to cover the taller neighbor’s color-height excess.

The live Stage 2 path computes this floor from the selected color-layer counts and passes the resulting millimeter map into _infer_implied_cap_heights as minimum_cap_height_mm. It is therefore enforced on every normal staged solve; it is not merely a diagnostic statistic.

Material exposure audit

After the solve result has been converted to final thickness maps, the server calls _run_material_exposure_audit. The audit sums every non-special, non-excluded material map as color and resolves white cap from either the combined white-cap map or the boundary-plus-detail pair.

It quantizes both to layer counts and reports three kinds of exposed color face:

CountMeaning
lateral internal facesa color stack rises above the total color-plus-cap height of a 4-neighbor
top facesa pixel contains color but has no white cap above it
exterior facescolor layers touch an outer edge of the image domain

MaterialExposureAudit.passes is true only when the total exposed-face count is zero. The live server stores the summary in run metadata and exposes the convenience boolean white_cap_exposure_safe.

The live audit is record-only. _assert_material_exposure_safe_for_product would raise PrintabilityError, but an exhaustive caller search currently finds only its focused tests, not a production solve or export caller. It must not be described as a live product gate.
