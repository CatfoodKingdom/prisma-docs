Model-domain ingress and display conversion

Model-domain ingress and display conversion

Properties1
tagsgenerator, color, camera-transform

Jul 14, 20265 min read

In one sentence: the live solver converts source display-sRGB pixels through the committed Camera Transform inverse LUT into model-domain RGB before target-cloud construction, while generated preview artifacts convert model-domain predictions forward through the same transform for display.

This page is the implementation reference for the two domain boundaries. The conceptual explanation lives in Model-domain ingress and Camera Transform; this page records the actual runtime ownership, artifact contract, and failure behavior.

The domains and the boundary

The calibrated appearance model and the staged solver compare colors in model-domain RGB, then convert those values to OKLab for target matching and dE calculations. A source image arrives as display-encoded sRGB. The live product path therefore has this boundary:

The reverse boundary is used only for display-facing artifacts:

The names predicted.png and target_transmission.png are consequently important: they are model/transmission-domain views encoded as PNG, not necessarily what a viewer would see on screen. predicted_appearance.png and predicted_color_only_appearance.png are the forward-transformed display-appearance views.

Ingress: source image to solve targets

The live solve calls compute_solve_target_cloud (pipeline/target_cloud.py:64) during the Load phase (pipeline/runner.py:1034). It calls image_to_target (model.py:128), then to_oklab (model.py:155), and finally projects the observation-grid OKLab values onto the solve grid with project_observation_to_solve_grid (target_cloud.py:80-90). The resulting SolveTargetCloud carries both observed_oklab and solve_oklab, their shapes, the fixed domain name model_oklab, and whether ingress was applied (target_cloud.py:18-28, :91-106).

image_to_target uses the configured inverse LUT when model_domain_ingress is true (model.py:148-151). The current server forces that setting on at product ingress and again while building SolveConfig (server.py:817-835, :1008-1018, :1104-1107). The False branch remains compatibility code: it returns ordinary sRGB-to-linear values (model.py:152) and is not a selectable current webapp product mode.

The image is already framed, resampled, and adjusted before this boundary. F1 preprocessing also runs before target-cloud construction. Therefore “ingress” is not the first operation on the raw upload: it is the domain conversion after source loading/adjustment and preprocessing, immediately before OKLab target construction.

Camera Transform artifact contract

The generator loads the transform through lib.camera_transform.load_camera_transform (lib/camera_transform.py:201) and the inverse LUT through load_inverse_lut (:333). A directory with a CURRENT pointer resolves to one generation; the loader verifies that generation’s manifest.json hashes before accepting camera_transform.json and inverse_lut_33.npz (lib/camera_transform.py:70-96, :142-176).

The accepted payload is camera_transform_v1 with model_version="v2", used_lattice=false, exactly 48 finite parameters, and ten monotone-curve knots per channel (lib/camera_transform.py:20-28, :178-199). The inverse LUT must have shape (33, 33, 33, 3) and finite values (:325-331).

Missing, malformed, schema-incompatible, or hash-mismatched artifacts raise CameraTransformError with the actionable instruction to rebuild through Calibration → Camera Transform (lib/camera_transform.py:44, :136). The generator does not silently fall back to gamma-only ingress when the product path requests the transform.

apply_inverse_lut performs trilinear interpolation over the 33³ table, accepts integer sRGB input by scaling it from [0,255] to [0,1], clamps coordinates, and returns float32 model-domain values (lib/camera_transform.py:356-389).

Display conversion and generated artifacts

After the staged solve produces a SolveResult, the server writes the normal model-domain predicted.png and then calls bake_view_domain_images (server.py:5028-5058). That helper:

  1. recovers model-domain linear RGB from the gamma-2.2 encoded predicted.png;
  2. applies the forward Camera Transform through apply_appearance_transform (model_domain_display.py:37-44); and
  3. writes predicted_appearance.png as display-encoded sRGB.

For the source-side comparison, the same helper applies the inverse ingress LUT to the source image and writes target_transmission.png using the model-domain PNG encoder. Its return value contains the display-transform path and transform SHA-256, which the server stores under run_metadata["model_domain_display"] (server.py:5452).

The color-only recipe-viewer render follows the same forward transform through bake_appearance_png (model_domain_display.py:47-70, invoked at server.py:5075-5084). SolveResult.predict_image_color_only first zeroes white-cap terms and reuses the model-domain composition path (facade.py:406-417); the server then bakes that result into predicted_color_only_appearance.png.

The raw predicted.png remains available for transmission/model-domain inspection. The UI’s predicted-print view uses the appearance artifact when it is present, while the technical artifact bundle retains both domains so a run can be diagnosed without guessing which conversion occurred.

Provenance and current-path boundaries

  • The transform parameters and inverse LUT are one committed calibration generation selected by CURRENT; the loader caches them by resolved path and modification time (lib/camera_transform.py:201-224, :333-354).
  • The solve target cloud records domain="model_oklab"; gamut mapping and dE calculations operate on that cloud, not directly on display-sRGB values (pipeline/target_cloud.py:18-28, pipeline/runner.py:232-325, :327-445).
  • appearance_model.py prediction methods are model-domain pass-through APIs after the retired projection-slot conversion; display conversion belongs at the generator ingress/display boundary (appearance_model.py:218-221, :425-430).
  • The legacy CLI and compatibility constructors still expose model_domain_ingress=False defaults in lower-level helpers. That is not evidence of a live product fallback; the web server’s product configuration forces ingress on.
