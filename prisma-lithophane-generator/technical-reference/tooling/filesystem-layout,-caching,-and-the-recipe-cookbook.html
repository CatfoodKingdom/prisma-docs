Filesystem layout, caching, and the recipe cookbook

Filesystem layout, caching, and the recipe cookbook

Properties1
tagsgenerator, filesystem

Jul 13, 202610 min read

In one sentence: runtime_layout.py establishes Generator’s portable visible folders, immutable-library store, and app-owned Workspace before data_paths.py binds server constants to them; cache_admin.py clears only Workspace cache without escaping through a Windows junction, run_naming.py mints chronological collision-free ids for exports and saved runs, and recipe_cookbook.py rolls each solve’s per-recipe color breakdown into the family → combo → recipe tree the recipe viewer browses.

This page covers the portable layout boundary plus four small, pure-ish Generator modules that consume it. See generator.server for the endpoints that wire them together, and The interactive recipe viewer for the UI the cookbook feeds.

Filesystem layout (runtime_layout.py → data_paths.py)

The packaged launcher resolves and prepares the portable tree before it imports the Generator server. resolve_runtime_layout anchors normal state to the folder containing the executable and produces four distinct Generator-owned roots (runtime_layout.py:127-184). Frozen launch ignores inherited developer path overrides; source-maintenance launches may deliberately supply them.

The cache vs. persistent split

The governing rule is ownership plus visibility: source images and completed exports are plainly visible, installed published libraries are a separate immutable store, and mutable implementation state stays inside the app-owned Workspace.

OUTPUT_DIR receives only complete export directories. The server builds each export in a hidden sibling .export-stage-* directory and publishes it with one same-filesystem directory rename after every deliverable and manifest update succeeds. Failure and cooperative cancellation remove the stage; read/download routes do not create missing export directories. The clear-cache endpoints remain deliberately unable to touch either completed exports or an active export stage.

GENERATOR_DATA_DIR (data_paths.py:100) is the Workspace, the parent of both cache/ and persistent mutable siblings. The structural safety of “clear cache never deletes saved runs” rests on saved_runs/ being a sibling of cache/, not a child — see the caching section below.

One active immutable model library

initialize_generator_runtime creates/reconciles the installed-library store, installs the bundled seed only when no active selection exists, and resolves one complete active library (runtime_layout.py:322-383). The selection record lives inside Generator’s Workspace; the payload lives under Generator/Model Libraries/{library_id}. If the active library cannot be validated, the launcher supplies a separate recovery root and the server starts in Library Recovery mode instead of falling back to Calibration data or combining partial libraries.

The launcher then applies explicit environment paths before importing data_paths.py (runtime_layout.py:390-430). resolve_data_dir now requires PRISMA_MODEL_LIBRARY_ROOT; Workspace, Images, Exports, and config resolution likewise fail with “Start it through the Prisma launcher” rather than guessing a repository path (data_paths.py:30-96). DATA_DIR is therefore the selected published library for compatibility with older consumers—not a shared Calibration/Generator data root.

Boot: ensure_dirs()

prepare_generator_runtime creates and write-probes Generator/Images, Generator/Exports, Generator/Model Libraries, and Generator/Workspace before the Workspace lock is acquired (runtime_layout.py:207-220). After the launcher applies those roots, ensure_dirs() creates the server’s managed cache/save/log descendants (data_paths.py:115-118). It is called once at server import. LOG_DIR is created on boot but is not swept by either clear endpoint.

Run, export, and save ids (run_naming.py)

Three different id schemes coexist; do not conflate them.

Run-cache id = the request’s card_id

A per-solve working directory is cache/runs/{card_id}. The card_id is client-supplied (the UI’s run/card identifier), not minted by run_naming.py. _current_out_dir() (server.py:1910) builds the path; with no card_id it falls back to the literal "current" (server.py:1910–1919). Before use the id is passed through _validate_card_id() (server.py:1902), which rejects anything not matching ^[a-zA-Z0-9_-]+$ — this is the traversal/slug guard for run-cache and export dirs alike (_export_out_dir reuses it, server.py:1929).

Export id and save id (minted by run_naming.py)

Both make_export_id (run_naming.py:34) and make_save_id (run_naming.py:54) produce a Windows-safe, chronologically-sortable name of the form {timestamp}-{image-stem} — the timestamp leads so listings sort by time, and the image stem follows for readability (run_naming.py:37-38, run_naming.py:57-58). Neither encodes the palette/label: the palette is recorded in the export manifest (run_naming.py:39-40), and the save’s display label is deliberately excluded so renaming never changes identity (run_naming.py:58-59).

Both run their parts through _slugify (run_naming.py:16), which: normalizes / and \ to spaces before the regex so palette dots aren’t eaten by Path.stem (run_naming.py:22-24); lowercases and collapses any non-[a-z0-9] run to a single - (run_naming.py:25); truncates to _MAX_LEN = 64 (run_naming.py:7, applied run_naming.py:26); falls back to "export" if empty (run_naming.py:8, run_naming.py:27-28); and appends -x to Windows reserved device names like con/nul/com1 (run_naming.py:9-13, run_naming.py:29-30).

Collision handling differs by what counts as “taken”:

MintsCollision checkCaller
make_export_idexport folder nameoutput_root/{candidate} directory exists (run_naming.py:46)server.py:5841
make_save_idsaved-run id{candidate}.zip or {candidate}.json exists (run_naming.py:66)server.py:6609, auto_run_store.py:74

Both append -2, -3, … as a same-second backstop, trimming the base so the suffix stays within _MAX_LEN (run_naming.py:47-50, run_naming.py:67-69).

Timestamp formats (set by the callers, not run_naming.py)

The timestamp is passed in by the caller, so the format lives in server.py:

  • Export: datetime.now().strftime("%Y%m%d-%H%M%S") (server.py:5838) → e.g. 20260621-143005-steve.
  • Manual save: same %Y%m%d-%H%M%S (server.py:6607), then make_save_id during archive packing.
  • Auto save: saved_at or datetime.now().strftime("%Y%m%d-%H%M%S") (server.py:6642).
  • Promotion (auto → saved) reuses the auto record’s original saved_at as the timestamp unless overridden (auto_run_store.py:73), re-minting a fresh save_id against the saved-runs root (auto_run_store.py:74).

Saved-run and auto-run archives are stored as a {save_id}.zip + {save_id}.json sidecar pair, validated on every access by run_store.resolve_save_paths against _SAVE_ID_RE = ^[A-Za-z0-9_-]+$ (run_store.py:14, run_store.py:31-33) — the same character class as card_id, enforced independently. Listings sort newest-first by (saved_at, save_id) reversed (run_store.py:69). See generator.run_store / generator.auto_run_store.

Caching (cache_admin.py)

cache_admin.py exists to answer one question safely: “delete the contents of this cache directory, and under no circumstances follow a link out of the cache to delete something else.” On Windows that “link” includes directory junctions (reparse points), which pathlib/shutil.rmtree will happily traverse.

The clear endpoints

Two POST endpoints in server.py call into it (grep-confirmed; these are the only callers):

EndpointSweepsSparesCode
POST /api/cache/clear-runsRUN_CACHE_DIR, AUTO_RUNS_DIR + in-RAM solve cacheLUTs, output, saved_runsserver.py:6508
POST /api/cache/clear-allRUN_CACHE_DIR, LUT_CACHE_DIR, AUTO_RUNS_DIR + in-RAMoutput, saved_runsserver.py:6525

Both first call _assert_no_active_job() (server.py:6500), which raises HTTP 409 if any solve/export/compare job is running, then clear the in-RAM solve_cache. Every directory is cleared with root=data_paths.CACHE_DIR, so the boundary is the cache root itself.

Why saved_runs/ is structurally safe: it lives under Generator/Workspace, as a sibling of cache/. safe_clear_dir refuses any target not under its root, and the clear endpoints always pass root=CACHE_DIR. There is no code path that would point a clear at saved_runs/; it is outside the permitted root by construction.

safe_clear_dir(target, *, root) — the containment contract

safe_clear_dir (cache_admin.py:47) deletes the contents of target (keeping target itself) and returns the count of top-level entries removed (cache_admin.py:89-90). It refuses anything questionable by raising OutsideRootError (cache_admin.py:9). The guard is layered, and all of it runs on lexical absolute paths — os.path.normpath(os.path.abspath(...)) resolves .. but does not resolve symlinks/junctions (cache_admin.py:57-59). This is the whole trick: lexical paths can’t be redirected by a junction, so the checks below see the intended tree, not a relocated one.

  1. Containment — target must equal root or have root among its lexical parents, else OutsideRootError (cache_admin.py:60-61).
  2. Root + every ancestor must be real dirs — it walks root and all its parents up to the filesystem anchor; if any is a link/junction it refuses (cache_admin.py:66-70). A junction anywhere above the cache would physically relocate the whole tree, so deletion can’t be allowed to start.
  3. Every component root→target must be real — each path part between root and target is checked the same way (cache_admin.py:72-76).
  4. Missing target is a no-op returning 0 (cache_admin.py:77-78).

Junction/symlink-aware deletion

Detection is _is_link_or_junction (cache_admin.py:13): it os.lstats the path (never following), treats S_ISLNK as a link, and additionally checks st_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT (0x400) to catch Windows junctions (cache_admin.py:19-23). When the walker hits a link/junction entry it unlinks the entry itself without recursing through it via _unlink_link (cache_admin.py:26), which tries os.rmdir (junction-to-dir / dir symlink) and falls back to os.unlink (file symlink) (cache_admin.py:29-31). Real subdirectories are recursed with _rm_tree (cache_admin.py:34), which uses os.scandir + is_dir(follow_symlinks=False) so it likewise never crosses a reparse point (cache_admin.py:36-44). Net effect: a junction sitting inside the cache is removed as a single entry; its target is left untouched.

This behavior is exercised by tests/generator/test_cache_admin.py (junction-root refusal at lines 83-84, mid-path component refusal at 113-116) and tests/generator/test_cache_clear_endpoints.py.

The recipe cookbook (recipe_cookbook.py)

The recipe viewer needs to answer “which filament combinations make up this image, and in what proportions?” The cookbook is the aggregator that turns the flat per-recipe breakdown into a browsable tree. It is a pure module — no I/O, no numpy, no server deps (recipe_cookbook.py:14), unit-tested in isolation by tests/generator/test_recipe_cookbook.py.

Input, caller, and what’s already been stripped

build_recipe_cookbook (recipe_cookbook.py:35) is called once, from the artifact-saver in server.py:1665 (grep-confirmed sole caller). It consumes the same per-recipe entries that get written to the *_recipe_breakdown.json artifact, feeding it two scalars from that payload’s totals block:

  • all_plan_pixels= the breakdown’s all_plan_pixels (sourced from segment_id_map.size in the artifact builder) — the denominator for every area fraction.
  • base_only_pixels= the breakdown’s excluded_empty_recipe_pixels — pixels whose stack has no colored filament.

Crucially, each entry’s recipe is the ordered stack of colored filaments only — the white base and white cap are excluded upstream before the cookbook ever sees them (recipe_cookbook.py:4-6). The cookbook does no color/optics; it is pure counting. The result is written next to the breakdown as {base}_cookbook.json by the same artifact-saver and reported back as cookbook_filename.

The output tree

The taxonomy is three nested levels plus a flat rollup:

N-color family   →   unordered filament combo   →   specific thickness recipe

Walking the build (recipe_cookbook.py:65-89): each entry is bucketed by n_colors = len(recipe) (recipe_cookbook.py:70) and by an order-insensitive combo = the sorted tuple of filament ids (recipe_cookbook.py:71). Entries with pixel_count <= 0 are skipped (recipe_cookbook.py:68-69). The recipe_key is taken from the entry if present, else recomputed by _recipe_key (recipe_cookbook.py:28), whose "{id}:{thickness:.6g}" join is kept byte-identical to the breakdown’s own key format (the matching format string is server.py:1504-1505; the cookbook’s own comment cites it as server.py:1565) (recipe_cookbook.py:29-32) — so cookbook keys match the breakdown’s.

The returned dict (recipe_cookbook.py:165-172) has:

FieldMeaningAnchor
schema"prisma-recipe-cookbook-v1"recipe_cookbook.py:21, :166

Every node carries pixel_count and area_fraction, the latter via _frac (recipe_cookbook.py:24), which is numerator/denominator or 0.0 when the denominator is 0 (recipe_cookbook.py:25) — so a zero-pixel image yields all-zero fractions instead of dividing by zero.

The 0-color “Base only” family

If base_only_pixels > 0, a synthetic family is prepended with n_colors: 0, label "Base only", and a single collapsed combo/recipe whose recipe_key is the literal "base-only" and whose filaments list is empty (recipe_cookbook.py:95-119). It “collapses” because there is nothing to slice — family combo recipe. When base_only_pixels == 0 the family is omitted entirely (the if at recipe_cookbook.py:95).

Sort order (stable, deterministic)

Ordering is fixed so the UI renders deterministically:

  • Families: 0-color first (prepended), then ascending n_colors (sorted(families), recipe_cookbook.py:121).
  • Combos within a family: by descending pixel count, ties broken by the combo tuple — key=lambda c: (-combos[c]["pixels"], c) (recipe_cookbook.py:124).
  • Recipes within a combo: descending pixel count, ties by recipe_key (recipe_cookbook.py:126-128).
  • Filament rollup: descending pixel count, ties by filament_id (recipe_cookbook.py:158). Each rollup row also reports recipe_count = the number of distinct recipe keys the filament appears in, tracked via a set (filament_recipe_keys, recipe_cookbook.py:63, :89, counted :154).

Relationship to the viewer

This cookbook JSON is what powers the recipe viewer’s “Recipe cookbook” and “Color Regions” surfaces — see The interactive recipe viewer. The viewer ships both the recipe tree and the filament rollup; which one a user leans on is decided by interaction, not by the backend picking for them. The cookbook is the aggregation; it does not render color — the color-only predicted render is a separate path in generator.server.
