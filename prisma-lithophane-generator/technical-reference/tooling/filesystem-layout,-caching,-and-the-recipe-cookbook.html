Filesystem layout, caching, and the recipe cookbook

Filesystem layout, caching, and the recipe cookbook

Properties1
tagsgenerator, filesystem

Jul 26, 20268 min read

In one sentence: the launcher owns Generator’s portable visible folders, immutable model-library store, private Workspace, and recovery startup; cache clearing is constrained to Workspace cache, while recipe artifacts preserve the physical banded stack but classify and roll it up by colored filaments.

This page covers the ownership boundary shared by lib/runtime_layout.py, generator/data_paths.py, generator/cache_admin.py, generator/run_naming.py, and generator/recipe_cookbook.py.

Portable filesystem contract

Generator does not discover its files relative to server.py. The launcher first resolves a RuntimeLayout, prepares the folders, selects a published library, and supplies every required root through an explicit environment contract before importing the server.

Packaged launches anchor the tree beside the executable and ignore inherited developer path overrides. Source launches use the --app-root passed to Prisma.launcher and may deliberately use supported environment overrides. The application root itself must already exist; the launcher creates its owned descendants, not an arbitrary missing root.

data_paths.py requires the launcher-supplied model library, Workspace, Images, and Exports roots. Importing it without those paths raises a clear “Start it through the Prisma launcher” error instead of guessing a checkout-relative or %LOCALAPPDATA% location.

Startup and recovery

Before server import, the launcher:

  1. creates and write-probes Generator’s visible folders and Workspace;
  2. acquires the Workspace lock, reopening an already-running instance instead of starting a second owner;
  3. removes only exact ordinary .export-stage-* directories whose trees contain no links or reparse points, preserving and reporting unrecognized/unsafe lookalikes;
  4. removes only staging names recognized as abandoned model-library installation/state stages;
  5. installs the bundled seed library only when no active selection exists and a seed is present; and
  6. resolves and validates the selected library.

If the active selection is absent, unreadable, incompatible, or invalid, Generator starts against Generator/Workspace/Recovery/No Active Model Library. That root exists only to let the UI and model-library manager start. Model-dependent routes remain blocked until the user installs/selects a valid library and restarts. Generator never falls back to Calibration’s live model data and never combines partial libraries.

The selection record is Generator/Workspace/active-model-library.json; it contains the selected library id for the next launch. The currently running process keeps its original active library. Activating another library validates and records the choice, then requires a launcher-managed restart. The store will not remove either the library in use by the process or the library selected for the next launch.

An installed directory name must be the same canonical lower-case UUID as the manifest’s library_id. Manually copying a valid library under a different folder name therefore produces an invalid store entry; installing the ZIP through the manager stages, validates, and names it correctly.

Export publication boundary

Completed export directories appear directly under Generator/Exports. Export first writes to a hidden sibling .export-stage-* directory, updates every deliverable and manifest there, and publishes it with a same-filesystem rename only after preparation succeeds. Ordinary failure or cooperative cancellation attempts to remove the stage; cleanup failure is logged without exposing the directory under a final export id. A process kill may prevent cleanup, so the next launcher run performs the same conservative stage reconciliation after it owns the Workspace lock.

Read and download routes do not create missing export directories. Cache clearing does not touch completed Exports or export staging.

Run, export, and save identifiers

Three related ids have different owners:

  • A run-cache directory is cache/runs/{card_id}. The UI supplies the card id; the server accepts only letters, digits, _, and -. A request without one uses current.
  • make_export_id creates a timestamp-first, Windows-safe export directory name from the source-image stem.
  • make_save_id creates the corresponding stable id for a saved or automatic run archive. Its display label is metadata and does not determine identity.

Slugging lowercases names, replaces separator/punctuation runs with -, avoids Windows device names, caps the result at 64 characters, and appends -2, -3, and so on when the relevant destination already exists. Save collisions check both the .zip archive and .json sidecar. Export and ordinary manual-save callers use %Y%m%d-%H%M%S; promotion from automatic to saved normally preserves the original automatic-run timestamp while minting an id in the saved tier.

Saved and automatic runs are {save_id}.zip plus {save_id}.json pairs. Their publication, deletion, and promotion limits are documented in Saving, loading, and auto-capturing runs.

Source-image identity cache

SourceImageService keeps its disposable manifest and normalized working PNGs under Generator/Workspace/cache/source-images. Normalized entries already record the digest of the original HEIC/HEIF/HIF/AVIF bytes. Native JPEG, PNG, TIFF, BMP, and WebP entries also record a SHA-256 digest plus size, modification time, change time, dimensions, and detected source format.

Library discovery validates and indexes a native file once. Later discovery and saved-run matching reuse that entry while all three filesystem identity values remain unchanged; a changed file is inspected and hashed again before it can be considered ready. Exact saved-run lookup first selects digest-index matches, then applies same-name-first deterministic ordering. It does not rehash every ready library image on each run load.

The manifest is an optimization, not user data. Clear Temp Files removes it and the normalized working PNGs; the next Library discovery rebuilds the index from the untouched originals in Generator/Images.

Cache administration

cache_admin.safe_clear_dir(target, root=CACHE_DIR) deletes a target’s contents without following a symlink or Windows junction outside the cache. It uses lexical containment checks, rejects linked/junction ancestors, removes an in-cache link itself rather than traversing it, and treats a missing target as an empty no-op. saved_runs is structurally outside the permitted cache root.

This is the only user-facing cache-clear action. If the current image is a private loaded-run source, the endpoint clears both image_path and the runtime-only image_source_ref; the UI explains that the saved run can be loaded again. Ordinary Image Library selections are preserved. The action is serialized behind pending configuration publication, returns the exact cleared source reference and authoritative configuration, and force-reconciles local history only after backend success. It is refused while solve, export, suggestion, or image preparation is active, and it is excluded from model-library mutation/restart transitions through the shared resource-coordination guard. This is an admission rule, not a claim that every different long-job kind is globally serialized; see Driving the Generator.

Recipe breakdown and cookbook

The solve artifact builder first converts the solved stack-label map into flat recipe-breakdown entries. build_recipe_cookbook then rolls those entries into the tree used by the recipe viewer:

colored-filament count → unordered colored-filament combination → exact physical recipe

The distinction between classification and physical content is important for banded solves.

What a recipe contains

An ordinary recipe contains its ordered color-filament entries. A banded recipe can additionally contain white-cap filament entries whose material_role is white_fill, because empty space in a fixed-height color band is physically filled with white. The recipe node and its recipe_key preserve those white-fill intervals. Banded keys include their band index so two physically different band placements are not collapsed.

The white base and final variable white cap are not recipe entries. Swap-band white fill is different: it is part of the fixed banded color-stack structure and remains in the physical recipe.

How taxonomy and rollups treat white fill

For the family and combination taxonomy, the cookbook filters material_role == "white_fill" and counts only colored filaments:

  • n_colors is the number of colored recipe entries;
  • the combination key is the sorted colored-filament id tuple;
  • the per-filament rollup counts only colored filament participation; and
  • the nested recipe still exposes the full ordered recipe, including white fill.

This lets the UI describe a recipe as, for example, a two-color family without pretending that its necessary white-filled band intervals do not exist.

Base-only pixels

The breakdown calls a pixel base-only when its stack has no non-white-fill colored material. A banded stack that contains only white fill therefore contributes to excluded_empty_recipe_pixels rather than becoming a zero-color physical recipe entry. The cookbook exposes that count as a synthetic Base only family when it is nonzero.

total_image_pixels is the complete solved-plan pixel count. Every area_fraction divides by that same total, returning 0.0 for an empty image. color_pixels is the sum of nonzero-color family counts.

Stable ordering

  • Base only, when present, comes first.
  • Other families sort by ascending color count.
  • Combinations sort by descending pixel count, then id tuple.
  • Recipes sort by descending pixel count, then recipe key.
  • Filament rollups sort by descending pixel count, then filament id.

The cookbook performs counting only. The color-only prediction, contour maps, and interactive rendering are separate server/frontend artifacts.
