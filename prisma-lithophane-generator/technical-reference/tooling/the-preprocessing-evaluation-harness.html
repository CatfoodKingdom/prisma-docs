The preprocessing evaluation harness

The preprocessing evaluation harness

Properties1
tagsgenerator, evaluation

Jul 26, 20267 min read

In one sentence: an offline A/B bakeoff that solves two images through the production pipeline under one shared config and reports a fixed metric bundle (mean/p95 dE, out-of-gamut pixels, small-component count, cap total-variation), optionally dropping predicted-PNG + heatmap + report.json artifacts to disk.

This page documents the developer-only tools.generator.evaluation package: how to drive it from the CLI or a Python caller, and what each metric means. The package sits outside Prisma/generator and is not part of the shipped product or generated product-module graph. It exists to answer “did this preprocessing operator (or solver tweak) actually help?” with comparable numbers instead of eyeballing two renders.

What it is for

The harness compares two versions of an image — a baseline and a candidate — by running each through the full generator solve and diffing the results. It is corpus-agnostic: both images are passed in as explicit arrays, so the difference between baseline and candidate can be anything the caller wants (a preprocessing operator applied to one, a different denoise setting, etc.). It does not generate the candidate; you do that, then hand both to evaluate_pair.

Both arms run through the same SolveConfig, so any metric delta is attributable to the image difference, not config drift.

The contract: evaluate_pair

The single public entry point is evaluate_pair(request, *, modules_path=None, module_state=None) in tools/generator/evaluation/preprocessing_harness.py. It takes an EvaluationInput and returns an EvaluationResult.

SymbolRole
EvaluationInputFrozen dataclass: case_id, baseline_image, candidate_image, solve_config, optional out_dir.
EvaluationMetricsFrozen dataclass holding all 11 metric fields (see below).
EvaluationResultCarries both SolveResult objects, the metrics bundle, and artifact_paths.
EvaluationRunErrorRaised (not swallowed) when either arm’s solve fails; tags .arm ("baseline"/"candidate") and .original.
evaluate_pairRuns both arms, aggregates metrics, optionally renders artifacts.

Flow

  1. Two solves. _run_arm calls solve_full (from generator.facade) once per image. solve_full runs run_pipeline under FULL_PRESET, i.e. the staged production backend — not the legacy 6-step CLI engine in solve.py. If either solve raises, it is wrapped as EvaluationRunError(arm, exc) rather than crashing silently.
  2. Metric aggregation. _compute_metrics reads the two SolveResult objects and builds the EvaluationMetrics bundle.
  3. Optional artifacts. Only when request.out_dir is not None does it lazily import render_evaluation_artifacts and write files. The lazy import is deliberate: in-memory metric callers never pull in PIL.

Metrics are always returned in memory; artifacts are opt-in.

Where the metrics come from

_compute_metrics reads these SolveResult accessors (defined in generator.facade):

Source fieldAccessorContract
dE mapresult.de_mapPrefers diagnostics[MapKey.DE], then falls back to thickness_maps.
Gamut maskresult.gamut_maskReads the standardized gamut diagnostic.
Per-filament thicknessresult.thickness_mapsReturns the color-material maps exposed by the facade.
White-cap mapresult.cap_mapReads MapKey.WHITE_CAP.
Predicted renderresult.predict_image()Reconstructs the predicted image through the active appearance provider.

The solver pitch used for area scaling is config.solver_fine_pitch_mm, read off the baseline’s SolveResult.config.

The metric bundle

EvaluationMetrics holds eleven fields — for the five base metrics, both arms plus one delta where relevant:

MetricBaseline / candidate fieldsHow computed
Mean dEbaseline_mean_de, candidate_mean_de, delta_mean_dede_map.mean() per arm; delta = candidate - baseline. Empty map → 0.0.
p95 dEbaseline_p95_de, candidate_p95_de95th percentile of the dE map via _p95 and np.percentile(arr, 95.0). Empty → 0.0.
Out-of-gamut pixelsbaseline_oog_pixels, candidate_oog_pixels_oog_pixels counts True cells in the boolean gamut_mask with int(mask.sum()).
Small-component countbaseline_small_component_count, candidate_small_component_countcount_small_components over the thickness maps (see below).
Cap total-variationbaseline_cap_total_variation, candidate_cap_total_variationcap_total_variation over cap_map (see below).

Note dE is the only metric with a precomputed delta_* field; for the rest the caller diffs the two arms themselves (the bakeoff runner does exactly this).

Metric primitives — preprocessing_metrics.py

Two metrics are non-trivial and live in tools/generator/evaluation/preprocessing_metrics.py:

count_small_components in preprocessing_metrics.py counts speckle. For each per-filament thickness map (keys starting with __ are diagnostics and skipped):

  • Mark a pixel “occupied” if its thickness exceeds 5% of that map’s max (_SMALL_COMPONENT_REL_THRESHOLD = 0.05).
  • Run 8-connectivity connected-component labeling with a 3×3 structuring element of ones through scipy.ndimage.label.
  • Convert each component’s pixel count to physical area as pixel_count × pixel_pitch_mm².
  • Accumulate the count of components whose area is below min_area_mm2.

The min_area_mm2 threshold is derived in the harness, not hard-coded: feature_scale_mm², where feature_scale_mm comes from resolve_feature_scale_mm. That helper returns 2.0 × nozzle_diameter (_FEATURE_WIDTHS_PER_NOZZLE = 2.0), i.e. 0.40 mm at the default 0.20 mm nozzle, so min_area = 0.40² = 0.16 mm². This is the value the retired cleanup_min_area_mm2 carried.

cap_total_variation measures how “busy” the white-cap surface is. It returns the anisotropic L1 total variation Σ(|Δx| + |Δy|) over the 2-D cap map: abs(diff(axis=1)).sum() + abs(diff(axis=0)).sum(). It is a grid-space sum, not a per-mm integral; a non-2-D or empty map returns 0.0. Lower means a smoother cap.

Artifacts — preprocessing_render.py

When out_dir is set, render_evaluation_artifacts in tools/generator/evaluation/preprocessing_render.py writes exactly four files:

FileContent
baseline_predicted.pngBaseline predict_image() as RGB PNG.
candidate_predicted.pngCandidate predict_image().
delta_de_heatmap.pngSigned candidate − baseline dE heatmap.
report.json{"case_id": ..., **asdict(metrics)}.

The heatmap (_save_delta_de_heatmap) is signed: it normalizes delta = candidate − baseline by its peak absolute value, then puts positive delta (candidate worse) in the red channel and negative delta (candidate better) in the green channel. Mismatched shapes are defensively cropped to the smaller grid, though they are expected to match.

report.json’s schema is locked to the EvaluationMetrics dataclass via asdict; the drift-regression test in tests/generator/test_preprocessing_evaluation_metrics.py guards it.

How to drive it

CLI wrapper status

tools/generator/evaluation/preprocessing_eval_cli.py contains a thin parser that loads two images, builds a shared SolveConfig, calls evaluate_pair, and prints the report. Required parser fields are --case-id, --baseline, --candidate, --profiles, --palette, and --white-base; artifacts are optional through --out-dir, and --solver-preset accepts only full.

The canonical developer invocation is python -m tools.generator.evaluation.preprocessing_eval_cli .... Package import and --help are runtime-independent: Generator and harness imports are deferred until after argument parsing. An actual evaluation still enters the live facade and therefore needs an intentionally selected developer runtime plus an explicit published-library profile directory; the old checkout-relative Prisma/data/filaments/profiles example no longer exists. This remains a developer tool, not an end-user launch path.

From Python

The namespace package markers are intentionally inert. Import explicit submodules such as tools.generator.evaluation.preprocessing_harness or tools.generator.evaluation.preprocessing_metrics; there is no compatibility package or eager re-export surface under Prisma.generator or bare evaluation.

Historical bakeoff scripts

scripts/evaluate_preprocessing_first_bakeoff.py records the earlier F4 corpus experiment: it applies A1/B1/B3/C1/C2 offline, calls evaluate_pair, and writes per-case artifacts plus summary.json/summary.csv. The script is now stale and not runnable against the current facade. _make_config still passes the removed cleanup_enabled and solver_backend arguments to SolveConfig, and its parser/help still advertises retired backend choices and A2. It also assumes historical checkout-local profile data.

evaluate_b1_b3_preservation.py and evaluate_b1_parameter_sweep.py import private harness/render helpers for narrower historical studies. They are research artifacts, not product entry points; their current runnability has not been established by the production test suite.

Liveness

  • evaluate_pair / tools.generator.evaluation — live developer/test API. It is imported by the wrapper and historical scripts and exercised by focused tests, but not called by a normal web-app request.
  • render_evaluation_artifacts — live harness implementation, reached when out_dir is supplied and exercised end to end by tests.
  • count_small_components / cap_total_variation — live evaluation primitives called by _compute_metrics and covered independently.
  • preprocessing_eval_cli.py — developer parser retained under tools.generator.evaluation; namespace import and --help are clean without runtime selection, while real evaluation still requires an explicit runtime/profile context.
  • first-bakeoff script — historical and incompatible with current SolveConfig.
  • B1 sibling scripts — historical research tooling whose current runnability is unverified.

Caveats

  • Production solve path. Both arms go through solve_full → run_pipeline / FULL_PRESET — the staged backend, the same engine the webapp uses. The metrics reflect production solver behavior, including grouping/cleanup, not the legacy solve.py CLI engine.
  • Wrapper surface versus implementation. preprocessing_eval_cli.py exposes --solver-preset, but accepts only full and does not pass the value separately because evaluate_pair always selects solve_full. Argument parsing and help are runtime-independent; solve execution is not.
  • Historical script drift. The first-bakeoff parser and SolveConfig construction refer to retired settings. Do not use its results or instructions as evidence of the current production path without first porting and revalidating the script.
  • Shapes must match. Metrics assume baseline and candidate solved to the same grid (same config, same image dimensions). The heatmap renderer crops defensively, but the dE mean/p95 do not align grids — feed same-sized images.
  • Cap-TV is grid-space. cap_total_variation is a raw grid sum; it is only comparable between two solves at the same resolution. Do not compare TV across differing solver_fine_pitch_mm.
