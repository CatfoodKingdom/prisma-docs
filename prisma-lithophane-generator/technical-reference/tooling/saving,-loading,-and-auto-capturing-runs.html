Saving, loading, and auto-capturing runs

Saving, loading, and auto-capturing runs

Properties1
tagsgenerator, runs

Jul 25, 202613 min read

In one sentence: Prisma can package a completed solve as a self-contained ZIP, keep it deliberately as a saved run or temporarily as one of the 20 newest autosaves, and either restore the whole run into a new card or load only its captured settings.

This page describes the current saved-run archive, its two storage tiers, the browser workflows that consume it, and the actual interruption guarantees. The archive is portable; the neighboring JSON file is local list metadata. See also Run cache and per-card artifacts, The staged backend (Stage 0-5), generator.run_archive, generator.run_store, generator.auto_run_store, and generator.run_naming.

Both tiers use the same {save_id}.zip plus {save_id}.json layout. auto_run_store delegates ordinary storage work to run_store, then applies autosave retention. GET /api/runs/saved merges both lists and sorts them newest-first.

The ZIP and its sidecar

For each run:

  • {save_id}.zip is the portable artifact. It contains the source image, solve data, and cached review artifacts.
  • {save_id}.json is local list metadata. list_saves discovers runs from these sidecars without opening every ZIP; renaming edits only this file.

The sidecar records save_id, display label, saved_at, source_image_name, palette, compact mean_de and max_de statistics, archive schema version, and tier.

Per-file replacement is safe; the pair is not transactional

run_store.write_save first writes .zip.tmp and .json.tmp, then calls os.replace for the ZIP followed by the sidecar. Each published file is therefore replace-safe: readers do not observe a partially written ZIP or partially written JSON file. The two replacements are not one atomic transaction and there is no recovery journal.

A hard process stop can consequently leave:

  • hidden temporary files if it occurs before publication; or
  • a published ZIP with no listed sidecar if it occurs between the two replacements.

Because the sidecar drives the list, an orphan ZIP is not shown in the Saved Runs window. This is an interruption boundary, not evidence that archive bytes were partially written.

Stable identity and labels

make_save_id derives a Windows-safe identifier from the timestamp and source-image stem. It caps the identifier at 64 characters and adds -2, -3, and so on when either candidate file already exists. The display label is independent of that identifier, so renaming does not rename the on-disk pair.

The store accepts only identifiers matching ^[A-Za-z0-9_-]+$ before building a path. The Save dialog requires a nonblank display name. Names matching ^run\s+\d+$ after trimming, case-insensitively—such as Run 7, run 7, or Run 007—are reserved for Generator’s automatic live-card labels. Save and Rename reject new writes using that form in both the UI and API. Existing or uploaded archives with a legacy Run N label still load and display normally. The backend still falls back to the generated identifier if another caller sends an empty label.

Archive contents

run_archive.pack_run_archive builds the ZIP from supplied bytes and arrays without changing server state.

MemberRequiredContents
run.jsonyesSchema header, identity, full config and palette, image-domain dimensions, result/statistics, sanitized export metadata, and optional durable run_metadata
thickness_maps.npzyesCompressed tm__* thickness maps, dbg__* debug maps, and ex__* export maps
image/<file>yesExactly one nonempty source image; conversion-required sources are embedded as their solve-time normalized PNG
solve_state.jsonoptionalThe solve-owned fingerprint used by review-tier state
run_cache/<relpath>optionalThe portable per-card cache subtree, including review images/data and any export bundle already present; Prisma’s private loaded-source namespace is excluded

When the per-card run.json is readable, the packer also copies it into the optional top-level run_metadata field. This preserves newer solve-start diagnostics and recipe/profile snapshots while keeping older schema-version-1 archives loadable. The original file is still present inside run_cache/ because the whole cache tree is copied.

For HEIC, HEIF, HIF, and AVIF sources, solve start snapshots the exact normalized PNG used by that solve. Save and autosave embed that snapshot rather than re-reading a possibly changed original or disposable cache. Optional source_asset provenance records the original filename/format, source digest, normalized member name, and normalization version. Schema version remains 1: older readers ignore the optional provenance and consume the ordinary PNG member.

The packer applies the same 4,096-member and 512 MiB total-uncompressed-size ceilings as the reader. Save therefore cannot intentionally create an archive that violates those two reader limits.

Saved Runs window

The Load action on the Solve and Export sidebars opens one combined list of saved runs and autosaves. Each row includes:

  • a preview derived from the archive-owned source image;
  • display label and Saved/Autosave tier;
  • source filename; and
  • saved timestamp.

The preview routes read and validate the archive, apply EXIF orientation, convert the image to RGB, fit it within 320 × 320 pixels, and return a JPEG. Preview generation does not extract files into the Generator workspace.

The selected row controls these actions:

  • Load restores the complete run into a fresh solve card.
  • Load Settings reads the archive’s captured configuration into a session-only TEMP settings profile without restoring its image or run cache.
  • Download streams the original ZIP.
  • Rename changes a saved run’s sidecar label; autosaves cannot be renamed.
  • Delete removes either tier after the UI’s two-click confirmation.
  • Save promotes an autosave into the durable saved tier.

The ordinary Saved Runs mode can also load an uploaded ZIP. Upload is hidden in settings-only mode because uploaded archives currently use the whole-run rehydration route rather than the read-only settings route.

Saving and auto-capture

Explicit save

POST /api/runs/save requires a completed solve still present in the in-memory solve cache. The card’s Save action remains disabled until completion and becomes busy during the request so repeated clicks cannot create duplicate submissions. The live card is renamed only after a successful response, using the server-returned label as authoritative; card identity and persisted identity remain card_id and save_id, never the display label. Native source images from an ordinary live solve must still exist in Generator Images. Conversion-required sources use the solve-owned normalized snapshot, so their archive remains stable if the original changes after the solve. A card loaded from an archive instead reads the exact private archive snapshot retained for that card; changing or deleting a same-content library match cannot change a re-saved archive’s embedded image name or bytes. The server packages the current cached solve and writes it to saved_runs/.

Best-effort autosave

After a successful staged solve has populated the completed-solve cache, _maybe_write_auto_run packages the same archive shape under auto_runs/. Failures are logged and do not turn a successful solve into a failed solve.

After writing, evict_old_auto_runs lists sidecars newest-first and deletes entries beyond the retention limit of 20. Retention and the full Clear Cache action treat autosaves as disposable cache.

Promotion

POST /api/runs/auto/{id}/promote is refused while a solve, export, or palette-suggestion job is active or cancelling. Promotion:

  1. validates that both autosave files exist;
  2. mints a fresh identifier in saved_runs/;
  3. stages a rewritten saved-tier sidecar;
  4. moves the unchanged ZIP into saved_runs/;
  5. publishes the saved sidecar; and
  6. removes the old autosave sidecar.

Ordinary exceptions during the ZIP or sidecar publication steps trigger compensating cleanup or a ZIP move back to the autosave directory. This is useful rollback, but it is not a process-kill transaction. A hard stop between filesystem operations can leave an orphan ZIP, a listed autosave whose ZIP has moved, or both old and new sidecars listed against the one moved ZIP. There is no startup promotion journal that converges those states automatically.

Loading a complete run

Both a selected local entry and an uploaded ZIP pass through read_run_archive. Loading is refused while a solve, export, or palette-suggestion job is active or cancelling. A successful load never overwrites the original card; it creates a fresh loaded-<timestamp> card.

The backend then:

  1. validates the archive and its current configuration contract;
  2. rejects retired preferred-length/soft-warning artifacts, configurations that disable the now-mandatory detail cap, contradictory native/normalized source metadata, and archive members in Prisma’s reserved private-source cache namespace;
  3. stores the exact archived image bytes under _loaded_source/ inside the fresh card’s private run cache;
  4. compares a verifiable archived source digest with the persistent Image Library digest index, preferring an exact same-name match and then the case-insensitively sorted first differently named exact match;
  5. separates the tm__, dbg__, and ex__ arrays;
  6. writes every portable archived run_cache/ member under the fresh card directory;
  7. recursively rebases cached ?run=<old> URLs to the new card identifier; and
  8. adds a synthetic complete solve entry to the current server session.

The synthetic cache preserves the archived maps, result, export metadata, image-domain dimensions, and fingerprint. Objects that were not serialized as reconstructable runtime objects—such as solved-plan, grouping, and live profile objects—are left None. Review consumers use the restored cache files and rebased result URLs.

The exact archive snapshot always remains attached privately to the loaded card. If the digest search found a library match, the frontend selects that ordinary library item for new work. Otherwise it selects the private source through the opaque runtime reference loaded-run:<card_id> and shows Saved run source; the temporary source is not added to the Image Library or its count. The reference contains no filesystem path and is accepted only while the loaded card cache exists.

For native image members, the backend always derives identity from the embedded bytes. A schema-version-1 normalized member is a solve-time PNG, so it cannot prove which original HEIC/HEIF/HIF/AVIF bytes produced it. Local saved and automatic runs may use the Prisma-authored original-source digest retained with their managed archive; uploaded schema-version-1 normalized archives do not trust that editable provenance and therefore remain private. This is a deliberate false-negative match rather than a risk of activating an unrelated Library image.

The frontend creates a new history card using the archive label, selects the resolved active image, applies the captured frame and image-adjustment state, uses the archived config as the basis of the live session, and restores the palette by reusing a matching deck card, loading a matching saved palette, or creating an ad-hoc card. The loaded card keeps its historical resolved printability values, but live synchronization overlays the currently active printer’s nozzle-derived width and length before any new solve. It never writes archived thresholds into the printer profile.

A new solve uses the currently selected library match or private source. Preview, palette suggestion, and luminance recommendation use that same selection. The loaded result and any later re-save continue to use the private snapshot even if a matched library file changes or disappears. Client application is compensating-transactional: if final configuration synchronization fails, the prior card list, image, frame, adjustments, palette deck, and live configuration are restored and Prisma attempts to republish that restored configuration before reporting the load failure.

Rehydration interruption boundary

Whole-run rehydration writes the private image and cache files before publishing the in-memory solve-cache entry. Image validation failures remove the fresh private directory, but later write errors and hard process stops have no filesystem journal. They can therefore leave a partial run-cache directory that is not attached to a live card. Clear Temp Files removes that cache. Rehydration never writes the archive image into Generator/Images, so repeated loads do not create visible loaded-* images. Legacy loaded-* files made by older versions remain ordinary user-managed library files and are not moved, hidden, or deleted.

Loading settings only

POST /api/runs/settings validates the selected saved/autosave ZIP and returns its config, palette, label, optional durable metadata, and solve-start diagnostics. The route itself does not write the archived image, restore run-cache files, or add a solve card, and it does not use the active-job gate. The frontend subsequently applies the resulting TEMP profile through the ordinary live config and module-state synchronization paths.

The frontend reconstructs a settings snapshot with explicit compatibility fallbacks:

  1. broad archived config;
  2. optional run_metadata.config;
  3. server-resolved solve-start settings; and
  4. the durable recipe/profile settings snapshot, when present.

Later sources in that sequence override earlier ones. Diagnostic module parameters are merged into preprocessing parameters. Module toggles prefer the durable recipe/profile snapshot, fall back to diagnostic module state, and use older active-module diagnostics only as a compatibility fallback.

The result is a single session-only profile identified in the UI with a TEMP badge and the source run’s label. Loading another run’s settings replaces the prior TEMP profile. TEMP can be modified and used for solves, but cannot become the startup profile or be overwritten in place; Save routes to Save As to create a normal named profile. The same TEMP flow is available from a live solve card’s display-only Settings panel.

Applying a profile is coordinated but not one backend transaction. The frontend first applies settings and module state locally, sends the config, and then sends the module snapshot. If either synchronization step fails, it tries to restore the previous local state and, once config publication has begun, sends compensating config/module updates. A rollback request can itself fail, in which case the console records the failure and the next server refresh is authoritative.

Rename and delete interruption behavior

rename_save stages a new sidecar and replaces that one file atomically. It does not edit the ZIP.

delete_save unlinks the ZIP and then the sidecar. Missing files are benign; an ordinary Windows file-lock error becomes a clean HTTP 409. The two deletions are not journaled. If the ZIP is removed and the process stops or sidecar deletion fails, the list can retain a sidecar whose download/load target no longer exists. Autosave eviction uses the same deletion primitive.

Untrusted-archive checks

The reader never calls extractall; it reads explicitly named members after validation. It rejects:

  • more than 4,096 members;
  • duplicate member names;
  • more than 512 MiB total declared uncompressed data;
  • names outside the closed archive allow-list;
  • empty, absolute, drive-letter, backslash, ./.., or traversing paths;
  • symlinks and other explicitly marked non-regular members;
  • missing required JSON/NPZ members;
  • archive schemas outside accepted version 1; and
  • anything other than exactly one nonempty source image;
  • non-boolean normalized-source provenance; and
  • source display/member formats that contradict their declared native or normalized state.

The upload route separately reads multipart data in 1 MiB chunks and rejects compressed uploads beyond 512 MiB before parsing. This does not trust the client’s Content-Length.
