Saving, loading, and auto-capturing runs

Saving, loading, and auto-capturing runs

Properties1
tagsgenerator, runs

Jul 13, 20269 min read

In one sentence: a completed solve can be packed into a portable, self-contained zip archive (plus an authoritative JSON sidecar) and either deliberately saved by the user or silently auto-captured into a 20-slot ring buffer, then later loaded back into a fresh card — with the loader treating every archive (including uploaded ones) as untrusted input.

This page covers how the generator persists a finished solve so you can come back to it later or hand it to someone else. There are two storage tiers, one archive format, and a careful loader. See also Run cache and per-card artifacts, The staged backend (Stage 0-5), and generator.run_archive / generator.run_store / generator.auto_run_store / generator.run_naming.

Both tiers use the same on-disk pair ({save_id}.zip + {save_id}.json) and the same archive format. auto_run_store is a thin re-root of run_store: it just points run_store at AUTO_RUNS_DIR and adds eviction (auto_run_store.py:19-28). The list endpoint merges both tiers and re-sorts newest-first (server.py:6666-6672).

Disk layout: zip + authoritative JSON sidecar

For each run, run_store.write_save writes two sibling files under the store root, named by save_id (run_store.py:46-55):

  • {save_id}.zip — the portable, self-contained archive (see below). This is the only thing you’d hand to another machine.
  • {save_id}.json — the sidecar: a small dict that is the authoritative source for the run list and its display label. list_saves reads only the sidecars, never opening a zip (run_store.py:64-66), and rename_save edits only the sidecar label, leaving the zip untouched (run_store.py:104, :99).

Both files are written atomically — to .tmp siblings first, then os.replace swaps them into place (run_store.py:51-55) — so a crash mid-write never leaves a half-written run in the list.

The sidecar carries: save_id, label, saved_at, source_image_name, the palette, a trimmed stats block (mean_de / max_de only), schema_version, and tier (server.py:6622-6633). list_saves sorts entries newest-first by (saved_at, save_id) (run_store.py:69).

save_id identity is stable across renames

make_save_id mints the id as {timestamp}-{image-stem}, slugified and Windows-safe, capped at 64 chars, with same-second collisions getting a -2, -3, … suffix; a candidate collides if either {id}.zip or {id}.json already exists (run_naming.py:54, :66). The display label is deliberately not part of the id (run_naming.py:58-60) — renaming changes the sidecar label but never the identity, so existing zip/sidecar paths stay valid. The id is also a strict allow-list ^[A-Za-z0-9_-]+$ (run_store.py:14); anything else raises SaveNotFoundError before any path is built (run_store.py:32-33).

What’s inside the archive

run_archive.pack_run_archive (run_archive.py:98) builds the zip from already-extracted pieces — it touches no disk and no server state. Members:

MemberRequiredContents
run.jsonyesheader + full config + palette + image-domain dims + stats + result + sanitized export_metadata (server.py:6589-6601)
thickness_maps.npzyesnp.savez_compressed of tm__<key> thickness arrays, dbg__<key> debug arrays, and ex__<key> export arrays (server.py:6577-6584)
image/<file>yesexactly one source-image member; required, non-empty (run_archive.py:110-111)
solve_state.jsonoptional{ solve_owned_fingerprint } review-tier state (server.py:6603)
run_cache/<relpath>optionalthe entire per-card run-cache subtree (png/bin/json/csv + export bundle), nesting allowed (server.py:6581-6588)

The run_cache/ subtree is copied verbatim so that instant review (contours, surface explorer, recipe viewer) works on a loaded run without re-solving (server.py:6581-6583). Because the per-card cache can be large, pack_run_archive enforces the same member-count (MAX_MEMBERS = 4096) and total-uncompressed-byte (MAX_TOTAL_UNCOMPRESSED_BYTES = 512 MB) ceilings the loader checks, so Save can never produce an archive the loader would reject (run_archive.py:121-133, :37-38). JSON members are serialized to the exact bytes that get written so the byte total matches what the reader later sees (run_archive.py:115-118).

Driving it: the user-facing flows

All flows live behind /api/runs/* in server.py and thin wrappers in app/api.js.

Save a completed solve

The Save button calls saveRun(cardId, label) → POST /api/runs/save (api.js:254-255). Server side (server.py:6653): it requires a completed cached solve for that card or returns 409 (server.py:6545-6550); the source image must still exist on disk or it refuses to write a “hollow” archive (409, server.py:6567-6572); then it packs and writes the pair with tier="saved", returning {save_id, label}. An empty label defaults to the save_id (server.py:6610).

Browse, load, download, rename, delete

The Saved Runs browser lists both tiers via GET /api/runs/saved (api.js:258, server.py:6666). Each row is tagged "Saved" or "Autosave" (app.js:6846-6848) and offers:

  • Load → loadSavedRun(saveId, tier) → POST /api/runs/load with {save_id, tier} (api.js:262-263, server.py:6938).
  • Download → a direct link to /api/runs/saved/{id}/download or /api/runs/auto/{id}/download (app.js:6866-6869, server.py:6675, :6686) streaming the raw zip.
  • Rename (saved only) → POST /api/runs/saved/{id}/rename (api.js:278, server.py:6707) — sidecar label only.
  • Delete → DELETE /api/runs/saved/{id} for saved runs or DELETE /api/runs/auto/{id} for autosaves (api.js:270-276, server.py:6715, :6727).
  • Save (auto only) → promote (next section).

You can also load an uploaded zip that didn’t come from this machine: uploadSavedRun(file) → POST /api/runs/load-upload (multipart) (api.js:282-288, server.py:6952).

Delete is idempotent but surfaces locked files

run_store.delete_save removes both files with missing_ok=True, so deleting an already-gone run is a benign no-op (run_store.py:91). But a file that exists yet can’t be removed — e.g. a zip locked open on Windows — raises the typed SaveDeletionError (run_store.py:92-95), which the endpoint converts into a clean 409 telling the user to close the program holding it (server.py:6715-6724), rather than crashing.

Auto-capture and promotion

Capture happens automatically on every solve

At the end of a successful solve, once the completed-solve cache entry is written, the staged backend calls _maybe_write_auto_run(card_id, solve, config) (server.py:5689-5690). This packs the identical archive Save would (same _pack_completed_run_archive), but with tier="auto" and an auto-generated label Auto <timestamp> (server.py:6638-6647). The whole thing is wrapped in a try/except that only logs on failure (server.py:6648-6649) — auto-capture is best-effort and must never break a solve. (This is the live The staged backend (Stage 0-5) path, not the legacy CLI engine in solve.py.)

write_auto_run forces tier="auto" onto the sidecar regardless of what the caller passed (auto_run_store.py:40-42), then immediately evicts.

Ring-buffer eviction keeps the newest 20

After each write, evict_old_auto_runs lists the auto sidecars newest-first and deletes everything past index limit (default AUTO_RUN_RETENTION_LIMIT = 20) (auto_run_store.py:46-54, :12). A negative limit is clamped to 0 (:48-49). Because auto runs share run_store’s newest-first ordering, “past index 20” is reliably the oldest records.

Promote an auto run to a saved run

The auto row’s Save button calls promoteAutoRun(saveId) → POST /api/runs/auto/{id}/promote (api.js:266-267, server.py:6697). auto_run_store.promote_auto_run (auto_run_store.py:57):

  1. resolves the auto pair via run_store.resolve_save_paths (no raw f-string paths from endpoint-controlled ids — auto_run_store.py:66-68);
  2. mints a fresh saved-tier save_id under SAVED_RUNS_DIR, preserving the original timestamp (auto_run_store.py:73-74);
  3. rewrites the sidecar with the new id, tier="saved", and a promoted_from_auto_id breadcrumb (auto_run_store.py:75-80);
  4. moves the zip bytes unchanged into saved_runs/, then publishes the new sidecar. A failed initial ZIP move removes the staged sidecar; if sidecar publication fails after the ZIP moved, promotion rolls the ZIP back and removes the stage so the auto record survives for a retry.

Promotion is gated by _assert_no_active_job so it can’t race a running solve/export/compare. The endpoint returns the rewritten sidecar, and promoteSelectedSavedRun derives its new saved:<new save_id> selection key from that response before refreshing the list. The newly promoted row therefore remains selected even when collision handling gave it a suffixed id. Once promoted, the run lives under saved_runs/ and survives a cache clear.

How loading works

Loading a run never restores into the original card; it builds a fresh “loaded-” card and replays the archive into it.

load_run (server.py:6938) and load_run_upload (server.py:6952) both gate on _assert_no_active_job (server.py:6943, :6954), then funnel into _load_from_bytes → read_run_archive → _rehydrate_loaded_archive:

  1. Untrusted parse — run_archive.read_run_archive validates the zip (see safety section) and returns a ParsedArchive (run_archive.py:149). On any ArchiveError, the endpoint returns HTTP 400 (server.py:6448-6449).
  2. Fresh card id — _fresh_loaded_card_id mints a collision-free loaded-<timestamp> card (server.py:6743-6751).
  3. Image — written to a save-scoped unique path {card_id}-{name} under the images dir; config.image_path is rewritten to it (server.py:6872-6875).
  4. Thickness/debug/export maps — the npz is split into thickness_maps (tm__), debug_maps (dbg__), and export_maps (ex__) (server.py:6876-6883).
  5. Run-cache subtree — the whole run_cache/ tree is restored under the fresh card’s dir, so /api/run-cache/files serves contours/explorer/recipe (server.py:6884-6890); relpaths were already validated safe during parse.
  6. URL rebasing — every ?run=<old> in the result payload (top-level and nested url maps/lists) is rewritten to the new card id by _rebase_run_urls (server.py:6754-6764, :6892).
  7. Cache entry — a synthetic status="complete" solve entry is written into session["solve_cache"], with grouping / solved_plan / profiles / material-exposure audit set to None (server.py:6895-6915). The loader also rejects retired preferred-length/soft-warning artifacts and disabled detail-cap configurations before rehydration (server.py:6776-6856).

The frontend then applies the loaded run and (best-effort) restores its palette to the deck (app.js:7260, :7270-7320).

Safety: the loader assumes archives are hostile

read_run_archive is built to be safe on untrusted zips — uploaded archives go through the exact same path as locally-saved ones. It never calls extractall; every byte is read by explicit member name. The guards (run_archive.py:149-194):

  • Member-count ceiling — > MAX_MEMBERS (4096) → reject (run_archive.py:158-159).
  • No duplicate member names (run_archive.py:161-162).
  • Total-uncompressed-byte ceiling — sum of file_size > 512 MB → reject before decompressing (zip-bomb guard) (run_archive.py:163-165).
  • Closed allow-list of member names — only run.json, thickness_maps.npz, solve_state.json, one image/<leaf>, and run_cache/<relpath> are permitted; everything else is rejected (_member_is_safe, run_archive.py:70-82).
  • Path-traversal refusal — empty / absolute / drive-letter (:) / backslash / . / .. / ../-escaping relpaths are all rejected, including each nested run_cache/ path (_is_safe_relpath, run_archive.py:56-67).
  • Symlink / non-regular refusal — any member whose external-attr type field is set and isn’t a regular file is rejected; Windows writestr members (no type field) correctly pass (_zipinfo_is_symlink, run_archive.py:85-95).
  • Required members present — run.json and thickness_maps.npz must exist (run_archive.py:172-174).
  • Schema gate — run.json.schema_version must be in ACCEPTED_SCHEMA_VERSIONS = {1} or reject (run_archive.py:176-177, :29).
  • Exactly one image, non-empty (run_archive.py:180-188).

The upload route adds a compressed-upload cap on top: it reads the multipart body in 1 MB chunks and aborts with HTTP 413 once it passes MAX_UPLOAD_BYTES (512 MB), before the full read and the uncompressed zip-bomb check, and never trusts a client Content-Length (server.py:6955-6965, run_archive.py:39).

Liveness notes

Every endpoint and helper below was confirmed wired front-to-back by grepping callers:

  • saveRun/loadSavedRun/promoteAutoRun/renameSavedRun/deleteSavedRun/uploadSavedRun are all defined in app/api.js:254-289 and the solve-run Save button calls saveRun at app.js:6978; the Saved Runs modal loads at app.js:7260, promotes at app.js:7180, and uploads at app.js:12914.
  • _maybe_write_auto_run is called from the live staged-solve completion path at server.py:5690.
  • clear_cache_runs (server.py:6508) sweeps AUTO_RUNS_DIR but not SAVED_RUNS_DIR, confirming auto-runs are cache and saved runs are durable.
