The Solve Facade

The Solve Facade

Properties1
tagsgenerator, facade

Jul 14, 202610 min read

In one sentence: the facade (generator.facade, facade.py) is the thin front door to the solver — it takes a typed SolveConfig, picks a quality preset, resolves the preprocessing chain, translates everything into a PipelineConfig, and hands off to the one orchestrator (run_pipeline) that runs the staged backend.

This page is about the handoff layer, not the solve itself. For the solve walked end-to-end, see How a Solve Works; for the inversion math, The Joint LUT and Staged Solve; for the stage-by-stage diagram, Pipeline Map. Here we stay at contract altitude: what the entry points are, what they translate, and which one is dormant.

Page boundary: this page owns the facade’s typed API and config translation. What Actually Runs is the liveness authority; Pipeline Map owns stage ordering; the LUT and staged-backend pages own numerical and artifact internals.

Why a facade exists

The module docstring (facade.py:2) names a stale filename (lith_facade.py) — ignore it. The real job, stated in the same header block (facade.py:4–10), holds up against the code: callers (chiefly the web server) should never reach into pipeline internals. They build one SolveConfig, call one of three functions, and get back a SolveResult. Everything between — module-state resolution, the SolveConfig → PipelineConfig translation, the conversion of the runner’s PipelineState back into a SolveResult — lives here so the rest of the app doesn’t have to know it exists.

The three live entry points

All three production entry points have the same shape: (img, config, progress=None, modules_path=None, module_state=None), returning a SolveResult (solve_compare returns a list). They differ only in the quality preset they pass and, for compare, the per-palette loop.

Entry pointDefinedUsed forPresetServer call site

Liveness is confirmed from callers, not docstrings. solve_preview, solve_full, and solve_compare are all imported in server.py:79–81 and invoked at the call sites above. solve_full has a second live caller in the preprocessing evaluation harness (evaluation/preprocessing_harness.py:166). These are the production solve surface.

Each one does the same four-step dance:

  1. Resolve the preprocessing chain — _resolve_pipeline_slots (facade.py:475) loads module state and returns a (module_state, preprocessors) pair — just the ordered preprocessor chain. There is no grouping slot anymore; swap grouping is now an automatic banded solve inside the runner (see Grouping is now an automatic banded solve).
  2. Translate config — _to_pipeline_config (facade.py:497) maps SolveConfig → PipelineConfig.
  3. Run — run_pipeline (runner.py:736) executes the staged backend.
  4. Convert back — _state_to_solve_result (facade.py:785) turns the returned PipelineState into a SolveResult.

solve_compare (facade.py:915) wraps steps 1–4 in a loop over palettes: it loads module state once (facade.py:927), then for each palette clones the config with the new palette via _replace_solve_config (facade.py:651), runs the four steps with palette_index/palette_count threaded into the runner for progress reporting (facade.py:959), and catches per-palette exceptions — a failing palette becomes a {"error": ..., "palette": ...} dict in the result list rather than aborting the whole batch (facade.py:972). Empty palettes short-circuit to an error dict before solving (facade.py:936).

Quality presets

A QualityPreset is a tiny named record — just name and max_layers (state.py:29-33). The old grouping_enabled flag is gone. Three are defined as module constants:

Presetnamemax_layersDefined
PREVIEW_PRESET"preview"15state.py:36
FULL_PRESET"full"None (auto)state.py:41
COMPARE_PRESET"compare"15state.py:46

The preset is the only thing distinguishing the three entry points. It is passed through _to_pipeline_config onto PipelineConfig.preset (facade.py:647) and read back inside the runner. Two effects:

  • Layer ceiling. max_layers=15 caps preview/compare solves to a cheap low-resolution height stack; None means full solve lets the config derive it from t_max (see SolveConfig.effective_max_layers, facade.py:165).
  • Banded-solve gate. The preset name also decides whether swap grouping runs. There is no preset flag for it; instead the runner triggers a two-pass banded solve only for the full preset and only when the palette overflows the color slots — _swap_banding_requested (runner.py:50-55) requires preset.name == "full" and len(palette) > color_slots(). Preview and compare never band. See Grouping is now an automatic banded solve.

Note the preset name also drives diagnostics: the palette-fit best-case diagnostics in _compute_palette_fit_diagnostics only compute when preset.name == "full" (facade.py:666-669), so the “solver loss” overlay is a full-solve-only artifact.

The dormant fourth entry point

solve_preview_progressive (facade.py:849) is the one to know about. Its own docstring (facade.py:857–865) says the progressive-solve HTTP feature and its mid-solve snapshot emitter were removed in the “Stage 3 cleanup,” and that the function survives only to thread an optional SnapshotPublisher (generator.pipeline.snapshot) into the preprocessing preview hook. This docstring is accurate — and verified independently from callers, not taken on faith:

  • No production code imports or calls it. A repo-wide grep finds it imported/called only in two tests: tests/generator/preprocessing/test_facade_threading.py:286 and tests/generator/preprocessing/test_f1_smoke.py:169.
  • The server’s only remaining mention of “progressive” is a static-file route comment (server.py:6476) that serves cached diagnostic/preview PNGs — there is no progressive solve endpoint.
  • The one other hit is a stale traceback in Prisma/output/generator.log (a log artifact, not live code).
  • A removal plan exists for it: Prisma/generator/docs/legacy_audit/12_WEBAPP_DEAD_BACKEND_CANDIDATES_REMOVAL_PLAN.md:59 lists removing solve_preview_progressive from facade.py.

So: DORMANT in production, retained only as a test vehicle. It runs FULL_PRESET (facade.py:873), and unlike the three live entries it forwards a snapshot_publisher into run_pipeline (facade.py:882; the runner accepts it at runner.py:742 and attaches it to the state at runner.py:1220). The _progressive suffix is, per its docstring, a historical artifact and a rename candidate. Do not wire new code to it without reviving the publisher path.

Resolving the preprocessing chain

_resolve_pipeline_slots (facade.py:475) returns a (module_state, preprocessors) pair — grouping is no longer a resolved slot. It first loads module state via _load_module_state (facade.py:425) — which prefers an in-memory module_state dict, else reads modules_path through load_module_state, else returns None. The server passes modules_path=_MODULES_PATH so the live solve reads the on-disk module configuration.

Preprocessing — _resolve_preprocessing_from_state

_resolve_preprocessing_from_state (facade.py:438) builds the ordered list of enabled preprocessing operator instances (legacy callers with no module state simply get an empty list, facade.py:452-453). It walks the operator registry (generator.pipeline.registry), keeps each operator whose module-state flag is on (falling back to the operator’s default_enabled, facade.py:460), passes the operator’s params block from config.preprocessing_params as constructor kwargs, then sorts by each operator’s order with ties broken by import path (facade.py:466-471). The chain is threaded into the runner’s preprocessing slot. Class defaults are disabled, but persisted module state may enable operators; the current checked-in state enables C2. See How a Solve Works for where the chain runs inside the pipeline.

Grouping is now an automatic banded solve

The pluggable grouping slot was removed. GroupBudgetGrouping, GreedyGrouping, and _resolve_grouping_from_state no longer exist, and grouping/ now holds only band_plan.py and banded_export.py. Grouping is not something the facade resolves — the runner performs it automatically whenever a full-preset solve’s palette overflows the color slots. Inside run_pipeline (generator.pipeline.runner):

  1. _swap_banding_requested (runner.py:50-55) fires for preset.name == "full" with len(palette) > color_slots().
  2. A bounded-resolution scout solve runs first (_run_swap_banding_scout, runner.py:84) to measure per-filament color usage.
  3. choose_band_plan (generator.grouping.band_plan, called runner.py:940) partitions the canonical dark-first palette into consecutive exact-height swap bands from those scout maps.
  4. The plan is stored as a swap_grouping dict on the state (_swap_grouping_metadata, runner.py:130; assigned runner.py:947) — keys include groups, band_layers, canonical_palette, pause_z_mm, and cap_limit_mm.
  5. The real solve then runs with that band structure fixed; the per-band white fill comes from band_fill_maps (generator.grouping.band_plan), which the facade calls when reconstructing images (facade.py:334, facade.py:367, facade.py:717, facade.py:753).

The full banded story — slot budget, band planning, and export-time swap instructions — is AMS grouping and swap planning.

Disambiguation: the experimental beam-search / greedy schedulers under generator.scheduling.policies are unrelated to swap grouping and were not removed. They quantize an already-solved plan into per-layer orderings and are wired only into one offline eval script — see Fixed-budget layer scheduling (experimental).

The config translation — _to_pipeline_config

_to_pipeline_config (facade.py:497) is the big, boring, load-bearing function: it copies the dozens of fields from a SolveConfig (generator.facade) into a PipelineConfig (generator.pipeline.state) and attaches the resolved preprocessors, preprocessing_params, and preset (facade.py:645-647). A few translation facts worth knowing:

  • Resolution is canonical-pitch only. The translation passes image_sample_pitch_mm and solver_fine_pitch_mm (facade.py:580–581) plus the stage-1 coarsening/lattice-offset fields; there are no legacy resolution fields. The SolveConfig.__post_init__ applies a resolution backstop first (facade.py:153–154, via config.resolution_schema). See Settings, resolution, and the config contract and generator.config.resolution_schema.
  • Color-model ingress passes through verbatim. model_domain_ingress and model_domain_ingress_lut_path ride along (facade.py:529) to the Model-domain ingress step; appearance_model_provider selects the Appearance provider (facade.py:575).
  • de_threshold defaults differ across layers. SolveConfig.de_threshold defaults to 0.01 (facade.py:97) while PipelineConfig.de_threshold defaults to 0.05 (state.py:72) — but the translation always copies the SolveConfig value through (facade.py:523), so the config you build wins; the PipelineConfig default only matters for direct construction.
  • Everything else is a near-mechanical 1:1 copy — whites, layer height, t_max/k_max, gamut mode, chroma weight, the full luminance-handler block, the staged-backend stage-2/stage-4 knobs, cap mode, and the printability fields. The list is long because SolveConfig is the kitchen-sink settings object; the translation is where it narrows to what the runner reads.

What comes back — SolveResult

run_pipeline returns a PipelineState; _state_to_solve_result (facade.py:785) converts it into the SolveResult dataclass (facade.py:234) that callers actually consume. The result carries the thickness maps (normalized to a typed ThicknessMaps in __post_init__, facade.py:277), the color/white profiles, aggregate SolveStats, the original SolveConfig, the appearance provider, diagnostics (dE map, gamut mask — preferred from the diagnostics dict, falling back to thickness maps, facade.py:282–290), grouping result, the canonical SolvedMaterialPlan, and the blueprint-triage printability report.

Disambiguation: SolveResult.blueprint_triage is the blueprint-triage PrintabilityReport (generator.pipeline.blueprint_triage.report), imported at facade.py:37. That is a different class from the mesh-side printability report (generator.mesh.printability). Don’t conflate them.

Two reconstruction methods live on SolveResult and matter for the UI’s color views:

  • predict_image (facade.py:313) composes the full backlit sRGB image (base × colors × white cap) — routing through the appearance provider when it isn’t the historical spline, else predict_image_fast (generator.solve).
  • predict_image_color_only (facade.py:406) composes base + colors with the white cap dropped (every cap term zeroed via _cap_zeroed_thickness_maps, facade.py:386) so the cap’s luminance shaping doesn’t drown out the color story. A zero cap thickness is the multiplicative identity in the transmission model, so this cleanly removes the term without touching the composition math. This is what feeds the recipe viewer’s color-only render.

What this layer does not do

  • It does not run the legacy solve.py “6-step” engine. run_pipeline always dispatches to run_staged_backend_path (generator.pipeline.staged_runner) at runner.py:1222, for every preset. The 6-step engine in generator.solve is the separate CLI engine; the webapp path is the staged backend. (predict_image_fast from solve.py is still used for fast forward prediction — that is just the composition helper, not the solve engine.)
  • It does not decide resolution, gamut mode, or which operators are enabled — those come in on the SolveConfig / module state. The facade only resolves and translates.
  • It does not persist anything. Saving runs, naming, archives, and caches are the server’s job (generator.server, generator.run_store).

Progress reporting

The facade no longer defines a progress-tracker class — progress is delegated to the generator.progress module. The facade imports coerce_progress_reporter from it (facade.py:34), and the reporting split is:

  • The three simple entry points thread the caller’s raw progress callback straight into run_pipeline; the runner is what emits the per-stage updates the UI shows.
  • solve_compare wraps the caller’s callback with coerce_progress_reporter once up front (facade.py:929) so it can thread each palette’s palette_index/palette_count alongside the runner’s stage updates — those two fields are what solve_compare populates per palette.

See generator.progress for the reporter’s structure (stage key/label/index/count, percent, ETA).
