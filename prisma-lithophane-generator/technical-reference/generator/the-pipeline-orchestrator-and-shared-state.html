The pipeline orchestrator and shared state

The pipeline orchestrator and shared state

Properties1
tagsgenerator, pipeline

Jul 15, 202612 min read

In one sentence: pipeline/ is the small framework layer — a single orchestration function (run_pipeline) that loads profiles, runs an optional preprocessing chain, optionally scouts a swap-banding plan when the palette overflows the AMS color slots, builds LUTs, hands the heavy solve to the staged backend, and finalises one shared PipelineState carrier, with one pluggable slot (preprocessing operators) that self-registers from disk and persists its on/off state to JSON.

This is the developer companion to the generator.pipeline.runner package. It covers the data carriers, the fixed-spine design, the preprocessing plugin base class, parameter self-description, registry auto-discovery, and module on/off persistence. It also flags two seams (revalidate() and snapshot.py) that are wired but dormant in production.

What changed: the old pluggable grouping slot (GreedyGrouping / GroupBudgetGrouping, a grouping_enabled preset flag, a grouping registry) was deleted. Swap grouping is now the built-in two-pass swap-banding path in the runner, engaged purely on AMS overflow — no module, no toggle. The full story lives in AMS grouping and swap planning; this page describes only where it plugs into the spine.

Related: generation_pipeline (narrative walkthrough) · generator.facade (the entry layer above this) · generator.pipeline.staged_runner (the solve engine below it) · The staged backend (Stage 0-5) · AMS grouping and swap planning · Module management and settings.

How to drive it (users)

You never call this package directly — you change its behavior through the Generator’s Settings drawer. The launcher prefers port 8010 but may choose another free local port. Two settings families land here:

  • Preprocessing operators — a chain of optional image-cleanup / gamut steps that run on the source raster before color solving. Several can be on at once. This is the only module-toggled slot.
  • Quality preset — preview vs full vs compare; controls how many layers. (Swap banding is not a knob — it fires automatically on FULL_PRESET when the palette overflows the AMS color slots.)

Toggling a preprocessing module in the UI writes to a JSON file (modules.json) so the choice survives a restart. The contract is enforced server-side: see Module on/off persistence below.

The shared carriers (pipeline/state.py)

Everything the pipeline produces is accumulated on one mutable object that is threaded through every stage. There are four dataclasses, all defined in pipeline/state.py.

PipelineState — the bag of solve state

pipeline.state.PipelineState is the object passed through all stages. run_pipeline constructs it once and mutates it in place. Fields, grouped by who fills them:

The diagnostics dict is load-bearing: on the staged/webapp path __de__ and __gamut_mask__ live in state.diagnostics, never mirrored into thickness_maps. _compute_stats reads diagnostics first and only falls back to thickness_maps for legacy/CLI-style states.

PipelineConfig — the mutable per-run carrier

pipeline/state.py defines the full parameter set for one solve. The production path builds it through the facade’s _to_pipeline_config; tests and evaluation code can construct it directly. It is an ordinary mutable dataclass, and the runner attaches a few runtime-derived authority values during execution. Beyond its plain fields it carries the preprocessing-slot members and a set of effective_* resolver methods:

  • preprocessors: List[Any] — the ordered list of enabled operator instances. Sorting happens in the facade resolver, not here.
  • preprocessing_params: Dict[str, Dict] — supplied per-operator parameter overrides, which may be empty and ride along for fingerprinting. The UI can materialize descriptor defaults; direct facade resolution constructs an enabled operator with its class defaults when its block is absent or empty.
  • preset: QualityPreset — defaults to FULL_PRESET.

(There is no grouping field anymore — the pluggable grouping slot was removed. When swap banding fires, its plan lives on PipelineState.swap_grouping, not on the config.)

The effective_* methods compute derived values so callers never duplicate the arithmetic: effective_max_layers() lets the preset cap the physical/configured layer budget, effective_white_cap() falls back to the base white, effective_d_wc_max() / effective_boundary_d_wc_max() derive cap authority (the latter also clamps to the runtime swap-band cap limit when banding is active), and color_slots() = ams_slots - effective_white_slots() — the same threshold that gates swap banding. __post_init__ canonicalizes the palette order and applies the resolution backstop from config.resolution_schema.

ProfileSet and QualityPreset

ProfileSet is a three-field bundle of loaded filament profiles: color_profiles, wb_profile, wc_profile. QualityPreset now carries just name and max_layers — the old grouping_enabled flag was removed. Three named instances exist:

Presetmax_layers
PREVIEW_PRESET15
FULL_PRESETNone (no preset-imposed ceiling; the physical/configured budget still applies)
COMPARE_PRESET15

The record itself carries only a name and layer ceiling. Downstream code also branches on the preset name: _swap_banding_requested requires name == "full" and an overflowing palette, and full-only palette-fit diagnostics use the same name. There is no separate grouping flag on the preset.

The orchestrator: fixed spine plus two slots (pipeline/runner.py)

pipeline.runner.run_pipeline is the whole orchestration. The structure is a fixed spine of always-run stages, with the preprocessing slot woven into Load and an optional swap-banding two-pass inserted before LUT build on AMS overflow. Reading the function top to bottom:

#StageKindStable source anchor
1Load — validate palette, load profiles, create appearance provider, run the optional swap scout/band plan and preprocessing chain, then compute target cloudsspine + optional expansionsrun_pipeline; _run_swap_banding_scout; compute_solve_target_cloud
—Swap-banding two-pass — scout solve → choose_band_plan → write state.swap_groupingAMS overflow only_swap_banding_requested; _swap_grouping_metadata
—F1 Preprocessing — run the enabled operator chain, overwrite state.imageslotpreprocessing.runner.run_preprocessing_pipeline
—Target clouds + white-point/luminance setupspine detailcompute_solve_target_cloud; _apply_target_white_rescale; configure_luminance_handler_runtime
2Build LUTs — spline or provider path, plain or bandedspinelut builder functions selected by run_pipeline
3Gamut — _apply_target_gamut_mapping + final luminance-authority passspine_apply_target_gamut_mapping; configure_luminance_handler_runtime
4Solve — run_staged_backend_path then _finalize_staged_backend_statespinethose two named functions
5Stats — _compute_statsspine_compute_stats

Two facts that the stale module header hides (trace the live symbols, not the header):

  • The webapp solve is the STAGED backend. The Solve stage calls run_staged_backend_path from pipeline.staged_runner. It does not run solve.py’s legacy CLI engine. _finalize_staged_backend_state copies one staged result bundle’s thickness, diagnostic, debug, and export contracts onto state, derives the separate SolvedMaterialPlan, and recomputes dE straight into state.diagnostics.
  • The preprocessing slot and the banded two-pass are the only optional orchestration expansions. The preprocessing slot is a legal no-op when config.preprocessors is empty. The swap-banding two-pass runs only when _swap_banding_requested(config) is true; when it does, the spine’s five reported stages expand to eight (load, scout, band_plan, prepare, lut, gamut, solve, stats). There is no post-solve grouping stage. Individual stages still branch on their many solve settings and provider type.

Observation vs solve grid

The runner is the single owner of target-cloud computation through compute_solve_target_cloud. observed_target_oklab lives on the observation grid (image_sample_pitch_mm); solve_target_oklab is projected onto the solve grid (solver_fine_pitch_mm) and is what the solve path and dE recomputation both consume. _apply_target_white_rescale and _apply_target_gamut_mapping replace solve_target_oklab, so it is not necessarily the original projection array.

Progress reporting

Progress is delegated to the generator.progress module — the old facade-level _ProgressTracker class is gone. run_pipeline calls coerce_progress_reporter(progress, stage_count=…) (a plain callback, an existing ProgressReporter, or None all coerce cleanly) and then carves per-stage child reporters through its local _phase helper. Each stage’s emit(...) sends a dict with stage, stage_index, stage_count, overall_pct, elapsed_s, and palette index/count; the reporter enforces monotonic overall progress and cooperative cancellation checkpoints. No callback means no reporter and no emissions. The per-run phase_specs select five versus eight stages and tune weights for spline versus photo-stack LUT work.

The module plugin contract (pipeline/base.py)

One abstract base class defines what a pluggable module is: PreprocessingModule. (The old GroupingModule ABC was deleted along with the pluggable grouping slot.) It is an ABC with one abstract method and a describe() that serializes the module for the UI.

PreprocessingModule (F1)

pipeline.base.PreprocessingModule represents one image preprocessing operator. Class attributes the slot runner reads:

AttributeMeaning
name, descriptionidentity / UI text
params: Dict[str, ParamDef]self-described tunables
default_enabled: booldefault on/off
input_domain / output_domain (ColorDomain)color-domain contract; the slot runner inserts conversions between adjacent operators whose domains differ
order: floatposition in the chain; conventional bands Wing A 100–199, B 200–299, C 300–399, D 400–499; ties resolve by fully-qualified class name
required_context: FrozenSet[ContextKey]optional shared services (e.g. palette metadata) the runner resolves before apply()

(There is no longer a supports_protect_mask attribute — the subject-protect-mask feature was removed.)

Abstract method: apply(image, *, context, progress) -> PreprocessingResult. The live operators all live under preprocessing/operators/ and self-register — a1_bilateral_denoise, b1_printscale_bilateral, b3_tv_flatten, c1_achievable_tonemap, and c2_soft_gamut_compress. See generator.preprocessing.

Swap grouping is no longer a module

There is no GroupingModule base class, no greedy_optimize/group_budget implementations, and no grouping entry in the registry. AMS swap grouping is now the built-in two-pass swap-banding path run directly by run_pipeline (scout solve → choose_band_plan from grouping/band_plan.py → state.swap_grouping), engaged purely on AMS overflow. It is not toggled and not registered. The full mechanism is documented in AMS grouping and swap planning.

Worth knowing: pipeline.__init__ re-exports ParamDef, ProgressCallback, the state classes/presets, and run_pipeline / revalidate — but not PreprocessingModule or the preprocessing registry helpers. Preprocessing operators import the registry decorator directly from pipeline.registry.

ParamDef — parameter self-description

pipeline.base.ParamDef is a dataclass that lets a module describe one tunable to both the solver and the frontend renderer in one place. Core fields: name, label, type ("int" | "float" | "bool" | "choice" | "html" | "computed_text"), default, plus choices/choice_labels/min/max/description. UI-only fields include unit, tooltip, group, show_when (conditional visibility keyed on another parameter’s value), and order. to_dict() emits the JSON the API/UI consumes, omitting None-valued optional keys. This is why the Settings drawer can render preprocessing parameter forms without hand-written controls for each operator.

Registry and auto-discovery (pipeline/registry.py)

The registry is now a single module-level dict — _PREPROCESSORS — populated by @register_preprocessing at import time. The decorator stores each class under cls.name and adds its name to PREPROCESSING_MODULE_IDS. The grouping registry was removed with the grouping slot.

Preprocessing discovery is filesystem-driven. _discover_preprocessing_operators walks preprocessing.operators with pkgutil.iter_modules and imports every public, non-package submodule in lexicographic module-name order. That makes registration/listing deterministic; execution ties are separately resolved by fully-qualified class name in the facade. An empty operators/ package is legal — the slot becomes a no-op. Discovery runs lazily: _ensure_preprocessing_populated re-discovers whenever _PREPROCESSORS is empty, and _ensure_registry_populated is its wrapper.

Public accessors all call _ensure_registry_populated first: get_preprocessing, list_preprocessings, and list_all_modules, which instantiates each class via cls.__new__ and returns its describe() dict. _clear_registry is testing-only.

Module on/off persistence (pipeline/modules.py)

pipeline/modules.py reads and writes the JSON file of {module_name: enabled} flags. This is fully live — the generator server wires every endpoint to it. It now handles preprocessing operators only.

FunctionBehavior
load_module_state(path)read JSON, fill missing keys with defaults, normalize
save_module_state(path, state)normalize then write
toggle_module(path, id, enabled)flip one flag, validate the id against _PREPROCESSORS, normalize, persist, return full state

One normalization rule remains, since preprocessing is the only slot:

  • Preprocessing is non-exclusive. _normalize_module_state fills defaults for every registered operator and drops retired keys; _get_all_defaults collects each module’s default_enabled. Operators each contribute independently and several may be on at once. The zero-enabled case is a legal no-op.

The server’s module-list, toggle_module_endpoint, and bulk-save endpoints all use the configured _MODULES_PATH; solve paths snapshot load_module_state into the run record. The facade’s _load_module_state feeds _resolve_pipeline_slots, turning the flag dict into the resolved preprocessors chain for PipelineConfig.

Dormant and test-only seams

Two seams in this package are wired but not exercised by the production webapp solve. Both confirmed by grepping callers.

revalidate() — a test/compatibility seam with no production caller

pipeline.runner.revalidate(state) recomputes __de__ from the current thickness maps against the solve-grid target, writing straight into state.diagnostics['__de__'] and not touching thickness_maps. It is a thin wrapper over _recompute_de_diagnostics.

Liveness: run_pipeline never calls the wrapper. The production solve path calls _recompute_de_diagnostics directly during staged finalisation. With the pluggable grouping slot deleted there is no post-grouping dE branch left. The public revalidate symbol is still re-exported, but its only current callers are tests. Status: test/compatibility seam; no production caller.

snapshot.py / SnapshotPublisher — one live hook, one dormant field

pipeline.snapshot.SnapshotPublisher writes preprocessed source-image preview PNGs and their URLs into a shared progress dict via publish_image_preview. Liveness, two halves:

  • The preview hook is implemented but only reachable through a production-dormant facade entry. The preprocessing runner calls publish_image_preview per enabled operator when it receives a publisher. A publisher reaches run_pipeline only through facade.solve_preview_progressive, which has no production caller; the webapp uses solve_full, which passes none. Tests exercise this path.
  • The state.snapshot_publisher field is write-only and dead. The runner assigns it but nothing reads it back; the operative preview path threads the publisher as a function parameter. The progressive-solve snapshot emitter was removed. Status: publish_image_preview hook = implemented but production-dormant; state.snapshot_publisher field = dead.
