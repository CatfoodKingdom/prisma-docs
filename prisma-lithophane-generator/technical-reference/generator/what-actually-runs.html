What Actually Runs

What Actually Runs

Properties1
tagsgenerator, liveness

Jul 15, 20265 min read

In one sentence: every product solve enters through the facade and unconditionally reaches the staged backend; the older six-step solver, blueprint-triage package, geometry/scheduling research packages, and progressive-solve entry remain outside the production web-app path even though some of their helpers or result fields survive.

This is the liveness map for Generator. Status is based on current callers rather than module names, headers, or historical design documents.

  • LIVE — reached during an ordinary launched Generator workflow.
  • LEGACY — working compatibility or CLI code, but not the web app.
  • DORMANT — constructable and tested or script-driven, but without a production caller.
  • REMNANT — a retained hook/field from a removed product feature.
  • SUSPECTED INERT — no production caller was found, but the area should be re-audited before deletion.

Production solve path

The server has three live facade calls:

Facade entryProduct usePreset
solve_previewsynchronous one-palette gamut previewpreview
solve_fullbackground production solvefull
solve_comparebackground comparison batchcompare

Each resolves preprocessing, translates SolveConfig to PipelineConfig, and calls pipeline.runner.run_pipeline. After load, target, appearance-model, LUT, gamut, optional band-scout, and preprocessing preparation, run_pipeline imports and calls run_staged_backend_path without selecting among alternative solve engines. The staged result is finalized onto PipelineState and then converted by the facade.

solve_compare adds a loop and per-palette error containment, but each successful palette still enters the same staged backend. solve_preview_progressive also enters the staged backend with the full preset, but it has no production caller; it is retained for snapshot-publisher tests.

Legacy solver versus live helpers

The six-step orchestration in solve.py/pipeline_cli.py is not the product pipeline. Its only normal entry is the legacy parser. Several low-level functions from those files remain load-bearing:

  • pipeline_cli.load_image and apply_adjustments prepare the product source raster;
  • pipeline_cli.validate_palette protects the staged runner;
  • gamut-mapping helpers from solve.py remain part of target preparation; and
  • predict_image_fast remains the v1 forward-composition helper.

Deletion decisions must therefore be symbol-specific. Declaring an entire historical-looking module dead would break the live product.

Blueprint triage and the two report types

pipeline/blueprint_triage/ contains analysis, hazard, planning, and repair machinery with its own PrintabilityReport. Current runner finalization sets the state field to None, and the facade/server merely preserve/read that compatibility field. The suite is exercised by its dedicated tests and evaluation carriers, not by an ordinary solve.

Do not confuse that dormant package with the live staged diagnostic whose similarly named BlueprintPrintabilityDiagnostic is produced by staged_printability.run_blueprint_printability_diagnostic. The normal server posture forces that read-only diagnostic on and stores it on staged_result.cap_plan; it does not populate state.blueprint_triage or invoke the dormant analysis/planning/repair engine.

mesh/printability.py defines a different mesh-side report and measurement toolkit. The shared class name does not imply a shared lifecycle. An exhaustive current search finds its high-level build_printability_report classification ladder only in focused tests. Live export instead calls mesh.quality.check_mesh_quality and path-specific validation/fallback code in mesh.post_solve_export and the white-cap/color builders. Lower-level helpers still require symbol-by-symbol review before removal. Printability three layers and the Output pages own that distinction.

Dormant scheduling and geometry packages

The scheduling package explores fixed-budget per-layer ordering policies. It is not automatic AMS grouping. Live grouping is the runner’s two-pass band planner under grouping/band_plan.py and grouping/banded_export.py.

The geometry package builds/simplifies vector ColorRegion containers. No Generator production module imports it. Mesh policy/serialization modules and third-party shapely.geometry imports are different systems.

Snapshot remnant

The removed progressive-solve feature used to publish intermediate solver snapshots. What remains is narrower:

  • solve_preview_progressive can pass a SnapshotPublisher into the runner;
  • preprocessing can call publish_image_preview after enabled operators; and
  • tests exercise that preview hook.

There is no progressive-solve HTTP endpoint and no current maybe_publish solver-snapshot emitter. The remnant should not be described as a live user workflow.

Published model ingress

The live appearance providers receive explicit artifacts from the launcher-selected published library:

  • v1 uses the library’s validated spline profiles and optional pair corrections;
  • v2 receives the validated published deployment directory/runtime bundle and optional correction layer; and
  • the library contract also requires a valid Camera Transform deployment.

Generator does not select a “live Calibration candidate,” read Calibration’s Workspace, or use a reference bundle as a fallback. Switching complete libraries is a launcher/restart operation.

Stale headers and ports

Several module headers still use historical lith_* or lithophane_generator/* names. The server header also contains an old port example. Neither is runtime truth. The launcher binds loopback and prefers 8010, but may select any free port through 8029. Liveness and startup claims must be traced from callers and launcher code, not copied from those headers.
