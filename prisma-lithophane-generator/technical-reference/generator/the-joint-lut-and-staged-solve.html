The Joint LUT and Staged Solve

The Joint LUT and Staged Solve

Properties1
tagsgenerator, inversion

Jul 26, 20265 min read

In one sentence: the transmission model only runs forward (recipe → color), so the generator inverts it by precomputing a table of achievable recipes and, for each target pixel, picking the recipe whose color is the nearest neighbor in OKLab.

This page is the conceptual bridge between the color you want and the print recipe that makes it. It deliberately stays at that altitude — how the table is built and queried lives in The Joint LUT building and querying, and how the per-pixel ideal recipes become a printable plan lives in The staged backend (Stage 0-5).

Page boundary: this page explains why the inversion is joint and how it connects to the staged solve. It is not the liveness authority or a second LUT implementation reference; use What Actually Runs for caller status and The Joint LUT building and querying for builder/query mechanics.

The inversion problem

The forward model is easy: give it a stack of filament thicknesses and it returns a color (model.compose_stack). Solving needs the reverse — given a color, find a stack — and there is no clean closed-form inverse. Too many filament/thickness combinations can land near the same color, and the achievable set is a discrete, budget-constrained lattice, not a smooth function you can analytically invert.

The generator sidesteps this entirely. It enumerates the achievable recipes once, records the color each produces, and at solve time treats inversion as a nearest-neighbor lookup: the target color goes in, the closest precomputed entry’s recipe comes out. That table is the The Joint LUT and Staged Solve.

”Joint” — cap and color together

Each entry fixes both a white-cap thickness and a color-layer recipe at once, and stores the OKLab of the full stack:

oklab( T_wb × T_wc(d_wc) × ∏ T_ci(d_ci) )

Cap and color are represented in one lookup entry rather than in two independent tables — that is what “joint” means. Two consequences follow directly from lut.LUTEntry and the LUT builders:

  • The white base T_wb is baked into every entry. The solve target is therefore the full-stack color, and T_wb is never divided back out at query time (model.image_to_target states this explicitly). The module-level prose near the top of lut.py still contains the contradictory historical target = T_source / T_wb description; the live builders and model-domain ingress use full-stack color.
  • An entry carries its color filament subset, the per-filament color thicknesses, the cap thickness, and the unscaled OKLab color — so the batch nearest-neighbor query returns complete recipes, with the cap surfaced under __white_cap__ by query_luts_batch.

Nearest neighbor in OKLab

The match runs in OKLab, a perceptually-uniform space, so “closest color” means “closest to how the eye sees it.” Each LUT subset holds a SciPy KDTree over its OKLab points; query_luts_batch queries every tree for k=1 and keeps the global best across subsets. The returned ΔE is plain Euclidean OKLab distance.

One twist worth knowing as a user: chroma weight. When chroma_weight != 1.0, the L* (lightness) axis is divided by the weight before the tree is built and before each query, so the nearest-neighbor search prioritizes the chromatic axes over exact lightness. The reported ΔE is always recomputed unweighted so quality numbers stay comparable.

The live product’s SolveConfig.de_threshold defaults to 0.01 (the lower-level PipelineConfig retains a 0.05 direct-construction default). Before Stage 2, pipeline.runner._apply_target_gamut_mapping uses the unweighted distance to the nearest raw LUT sample to identify unreachable targets and optionally remap them. Stage 2 then queries the mapped targets and records its own post-mapping __gamut_mask__; that later mask is a result diagnostic, not the input that drove gamut mapping.

From “ideal per-pixel recipe” to a printable plan

The nearest-neighbor lookup gives the ideal recipe for each pixel in isolation. A lithophane printed that literally would be unmanufacturable — single-pixel color islands, sub-nozzle features. So the webapp solve does not stop at the lookup. pipeline.staged.orchestration.run_staged_backend_path coordinates the stage-owned implementation: Stage 1 forms color regions, Stage 2 uses the per-pixel Joint-LUT results to construct and score regional candidates and apply visible-material gates, and Stage 4 plans the white cap under the active printer’s limits. pipeline.staged_runner is only the stable compatibility import through which the outer runner reaches that orchestrator.

That is the division of labour this page bridges:

Liveness note for developers. query_luts_batch is the sole LUT recipe-query surface and is called by staged.stage2.candidates._query_stage2_pixel_stacks plus live diagnostics. The obsolete scalar, fixed-cap, and cap-curve query variants have been removed. build_hull_from_luts remains live through pipeline.runner._apply_target_gamut_mapping when hull mapping is selected.
