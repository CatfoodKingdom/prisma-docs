Pipeline Map

Pipeline Map

Properties1
tagsgenerator, pipeline

Jul 23, 20268 min read

In one sentence: one webapp solve runs a fixed five-step spine (run_pipeline) with one pluggable slot (preprocessing, inside Load) plus an optional two-pass swap-banding path that fires before LUT build when the palette overflows the AMS color slots — and the heavy lifting in the Solve step is the staged Stage 0–5 backend (run_staged_backend_path).

This is the wiring diagram for one full solve. For the narrative walk-through read How a Solve Works; for the optics read The Transmission Model and The Joint LUT and Staged Solve; for the overflow two-pass read AMS grouping and swap planning. The Mermaid below renders natively in Obsidian and in a Quartz-published site, so it travels with the docs.

Page boundary: this page owns the one-run wiring diagram and nested stage order. What Actually Runs owns liveness classifications; The Solve Facade owns entry-point/config translation; The Joint LUT building and querying owns LUT construction/query implementation. Details below are included only where they explain a connection in this graph.

Two layers: the spine, and the staged backend inside the Solve step

There are two nested orchestrators, and it matters which one you are looking at:

  1. The spine — pipeline.runner.run_pipeline. Five fixed steps: load → build LUTs → gamut → solve → stats, always in this order. When a full solve’s palette has more colors than PipelineConfig.color_slots(), _swap_banding_requested inserts a scout → band-plan → prepare expansion between Load and Build LUTs; the full story is in AMS grouping and swap planning.
  2. The staged backend — pipeline.staged_runner.run_staged_backend_path. This is the spine’s Solve step. Internally it runs its own Stage 0–5 sequence. Every facade preset takes this path; solve.py supplies only focused gamut and prediction helpers, not a competing solve engine.

Fixed spine vs. the two optional expansions

The orange nodes are the only parts of the spine that vary per run: the preprocessing slot (module-toggled) and the swap-banding two-pass (fires by palette size, no toggle). Everything else is hard-wired.

Optional expansionWhere it plugs inWhat it isEmpty / off behavior
F1Preprocessing slotInside step 1, after profile load and before the target cloudAn ordered chain discovered from preprocessing.operators and resolved from saved module stateEmpty chain is a legal no-op; the original raster passes through and state.source_image stays None
—Swap-banding two-passBefore step 2, between Load and Build LUTsA bounded scout solve followed by grouping.band_plan.choose_band_plan, which writes state.swap_grouping and switches LUT construction to a banded variantSkipped unless _swap_banding_requested: full preset, not already a scout, and len(palette) > color_slots()

Preprocessing resolution happens once, in the facade: _resolve_pipeline_slots reads saved module state and returns the preprocessing chain. There is no pluggable grouping module and no grouping_enabled preset flag anymore; swap grouping is the built-in banded two-pass, engaged by AMS overflow. See AMS grouping and swap planning.

Disambiguation (do not confuse these): the swap-banding two-pass in grouping.band_plan chooses AMS swap groups before the solve. The optional Stage 2 _seed_zone_recipe_labels_with_beam search instead seeds regional recipe labels; it is unrelated to swap banding.

Inside the Solve step — the staged Stage 0–5 backend

run_staged_backend_path is a strict pipeline of artifact builders. Each stage consumes the prior artifacts and emits a new one; the whole lineage is returned as a StagedBackendResult. The stage titles below are short paraphrases; the literal progress labels are “Planning solve directives…”, “Planning color regions…”, “Solving visible color stacks…”, “Planning filler support…”, “Solving white cap structure…”, and “Building solved material maps…”.

Two read-only diagnostic passes can run between Stage 4 and Stage 5 — they emit reports/counters, not geometry. Geometry attribution remains config-gated by emit_geometry_attribution. The blueprint printability diagnostic still has an emit_blueprint_printability field, but the normal web-server solve posture forces it on; it is not a user-facing optional switch. Neither report changes the already-built plan, and the old blueprint debug maps are not exposed as normal browser views.

What lands on PipelineState

After the staged result returns, _finalize_staged_backend_state copies one bundle onto the legacy-facing state exactly once:

  • state.staged_result = the full StagedBackendResult
  • state.solved_plan ← build_solved_material_plan_for_export(...) (historical function name; the resulting plan currently drives Explorer/recipe artifacts, not mesh construction)
  • state.thickness_maps ← float32 copies of the bundle thickness maps
  • state.export_maps / state.export_metadata ← the Stage 5 canonical mesh-export contract
  • state.diagnostics[...] ← bundle diagnostics; __de__ is recomputed here by _recompute_de_diagnostics, never read from thickness_maps
  • state.cap_quality ← _summarize_staged_cap_quality(...)

The later STL/3MF request consumes the cached thickness maps plus export_maps/export_metadata. It does not derive its geometry from state.solved_plan.

Appearance provider — the color oracle on the side

The Appearance provider is not a stage; it is built once in spine step 1 and queried by spine step 2 (LUT build) and prediction paths inside the staged solve. model_kind == "historical_spline" is Color Model v1; the live SolveConfig default is "photo_stack_bundle", which triggers the provider-LUT path and the cap range resolved by _provider_lut_d_wc_max. See The Transmission Model.
