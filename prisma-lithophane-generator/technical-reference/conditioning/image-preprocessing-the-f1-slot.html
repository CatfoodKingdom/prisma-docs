Image preprocessing the F1 slot

Image preprocessing the F1 slot

Properties1
tagsgenerator, preprocessing

Jul 12, 20269 min read

In one sentence: the F1 slot takes the loaded image, runs an ordered, contract-enforced chain of preprocessing operators (each declaring its own color domain), and hands the result forward to target computation — inserting color-space conversions at every domain boundary and refusing to start if the chain is mis-wired.

Image preprocessing — the F1 slot

The F1 preprocessing slot is the stage that conditions the source image after filament profiles are loaded and before the solve target is computed. It is a pure function over image data: raster plus read-only context in, transformed raster plus an audit trace out. The actual operators that do the conditioning live on Preprocessing operators; the F2 shared service (palette metadata) that some operators consume lives on Palette metadata and protect masking. This page is about the runner that drives the chain and enforces the contract.

The slot runner is preprocessing/runner.py; its public types are preprocessing/types.py; the boundary converters are preprocessing/color_convert.py.

Where the slot sits in a solve

The slot is driven from the staged-backend pipeline runner, not the legacy CLI engine. run_pipeline (pipeline/runner.py:736) loads profiles, resolves preprocessing state, builds the LUTs and target cloud, and then hands off to the staged backend via run_staged_backend_path (pipeline/runner.py:1222–1225). The F1 slot executes inside run_pipeline, in between:

Before the slotThe slotAfter the slot
Profiles loaded into state.profiles; appearance provider created during the Load phase.run_preprocessing_pipeline(...) called at pipeline/runner.py:1016.compute_solve_target_cloud(image, ...) at pipeline/runner.py:1034 computes the OKLab solve target from the post-preprocess raster.

Profiles load first so palette-aware operators can resolve their F2 context (pipeline/runner.py:997, resolve_palette_metadata_for_chain); the slot runs before target computation so the target OKLab reflects whatever conditioning the chain applied. This ordering is documented inline at pipeline/runner.py:985.

Liveness. The slot is live on the webapp solve path. The chain is resolved from live module state by _resolve_preprocessing_from_state (facade.py:438) and threaded into PipelineConfig.preprocessors (facade.py:645), which the webapp facade hands to run_pipeline (facade.py:845, facade.py:965). The whole F1 block is gated on if config.preprocessors: (pipeline/runner.py:991) — when no operators are enabled, the block is skipped entirely and the original raster flows through unchanged.

The runner contract — five things it does

run_preprocessing_pipeline (preprocessing/runner.py:210) does exactly five things, in order:

  1. Sort enabled operators (preprocessing/runner.py:232).
  2. Validate the chain shape before any work (preprocessing/runner.py:233).
  3. Convert the raster at each operator’s input boundary (preprocessing/runner.py:247).
  4. Run each operator and validate its output per-boundary (preprocessing/runner.py:252–253).
  5. Preview: emit a per-operator snapshot frame, view-only (preprocessing/runner.py:273).

It returns (image, trace, accumulated_debug_maps) (preprocessing/runner.py:217): the post-preprocess raster in the last operator’s declared output domain, a list of one PreprocessingTraceStep per executed operator, and a dict of debug maps keyed <module_name>:<map_name> (preprocessing/runner.py:266).

1. Sort: (order, class qualname)

_sort_operators (preprocessing/runner.py:111) does a stable sort keyed on (float(getattr(op, "order", 1000.0)), f"{type(op).__module__}.{type(op).__qualname__}") (preprocessing/runner.py:117–123). So the primary key is the operator’s declared order (default 1000.0 on the base class, pipeline/base.py:93), and ties break deterministically on the fully-qualified class name — matching the registry’s lexical import-path discovery order.

Operators advertise their position with conventional order bands (documented at pipeline/base.py:80): Wing A 100–199, Wing B 200–299, Wing C 300–399, Wing D 400–499. For example, c2_soft_gamut_compress declares order = 330.0 (operators/c2_soft_gamut_compress.py:381), placing it in the Wing C band.

2. Validate the chain before running anything

_validate_chain (preprocessing/runner.py:126) enforces one rule: the last enabled operator must emit an sRGB output domain. It checks getattr(tail, "output_domain", None) against SRGB_OUT_DOMAINS (preprocessing/runner.py:136) and raises PreprocessingContractError otherwise (preprocessing/runner.py:137). SRGB_OUT_DOMAINS is frozenset({"srgb_u8", "srgb_f32"}) (types.py:35).

This check runs before any apply() call (preprocessing/runner.py:233, ahead of the loop at :243), so a mis-wired chain fails loudly with zero partial work. The error message is actionable — it names the offending operator and tells you to disable it or add a tail converter (preprocessing/runner.py:138–142). An empty chain is a legal no-op: _validate_chain returns immediately when not operators (preprocessing/runner.py:132), and the runner short-circuits with return image, [], {} for an empty sorted chain (preprocessing/runner.py:235–236).

3 & 4. Convert at boundaries, then run + validate per operator

The run loop (preprocessing/runner.py:243) carries a current raster and a current_domain. The ingress domain is inferred from the input raster’s dtype by _infer_ingress_domain (preprocessing/runner.py:189): uint8 → srgb_u8, float32 → srgb_f32 (preprocessing/runner.py:200–203); any other dtype raises PreprocessingContractError (preprocessing/runner.py:204). In practice the slot is entered from the post-load srgb_u8 raster, while many direct tests feed srgb_f32 (preprocessing/runner.py:194–197).

For each operator, the runner reads its declared input_domain (preprocessing/runner.py:244) and, if current_domain != in_dom, converts the raster to match (preprocessing/runner.py:247–248). The runner owns every boundary, including the very first one — the first enabled operator receives its declared input domain without normalizing inside apply().

After op.apply(...) (preprocessing/runner.py:252), _validate_apply_result (preprocessing/runner.py:146) enforces the per-boundary contract on what came back:

CheckRaises if…Anchor

_DOMAIN_DTYPE (preprocessing/runner.py:60) is the canonical dtype-per-domain map: srgb_u8 → uint8, the three *_f32 domains → float32. Every failure carries the offending operator’s name.

After validation the runner records one PreprocessingTraceStep (preprocessing/runner.py:256) with the operator’s name, input/output domains, cache_hit=False, and a copy of its metrics; then it merges the operator’s debug_maps into the accumulator (preprocessing/runner.py:265). Finally current and current_domain advance to the operator’s output (preprocessing/runner.py:287–288).

Note: PreprocessingTraceStep.cache_hit is hard-wired False here (preprocessing/runner.py:262); the runner itself does not cache operator outputs.

5. Preview emission — view-only

When a snapshot_publisher is supplied (preprocessing/runner.py:273), the runner canonicalizes the operator’s output to srgb_u8 via _to_srgb_u8_for_preview (preprocessing/runner.py:274) and publishes it under stage key preprocess/<module_name> (preprocessing/runner.py:281–283). This is view-only: the raster handed forward to the next operator stays in the declared domain (preprocessing/runner.py:287 advances current to result.image, not the previewed copy).

If the operator is palette-aware — "palette_metadata" in its required_context and the context actually carries metadata — the preview’s cache key folds in palette_metadata.request_fingerprint (preprocessing/runner.py:277–280) so the same module name under a different palette does not collide in browser cache. request_fingerprint is a real field on PaletteMetadata (palette_metadata.py:157).

The four color domains

The slot speaks exactly four color domains, defined as a Literal type (types.py:26) and enumerated in VALID_COLOR_DOMAINS (types.py:29):

Domaindtype / rangeMeaning
srgb_u8uint8 [0, 255]sRGB primaries (Rec.709), D65, IEC 61966-2-1 transfer (types.py:5)
srgb_f32float32 [0, 1]Same encoding as srgb_u8, normalized (types.py:7)
linear_rgb_f32float32, nominally [0, 1]Same primaries + D65, linear light (no transfer); may exceed [0,1] for HDR-style ops (types.py:8)
oklab_f32float32Ottosson OKLab, D65; L in [0,1], a/b in ~[−0.5, 0.5] (types.py:10)

Each operator declares an input_domain and output_domain from this set on the PreprocessingModule base class (pipeline/base.py:91–92, both default "srgb_u8"). The runner’s job is to bridge any mismatch between an operator’s output_domain and the next operator’s input_domain.

Per-boundary conversion

_convert (preprocessing/runner.py:70) is the boundary bridge. It is a no-op when src == dst (preprocessing/runner.py:76), routes the six adjacent pairs directly (preprocessing/runner.py:79–90), and two-hops every other pair through srgb_f32 (preprocessing/runner.py:92). So srgb_f32 is the single conversion hub; e.g. linear_rgb_f32 → oklab_f32 goes linear → srgb_f32 → oklab.

The conversion math lives in color_convert.py, and the runner imports exactly six helpers (preprocessing/runner.py:34–41):

HelperDirectionNotes
srgb_u8_to_srgb_f32u8 → f32divide by 255 (color_convert.py:22)
srgb_f32_to_srgb_u8f32 → u8clamp [0,1], ×255, round half-to-even (color_convert.py:27)
srgb_f32_to_linear_rgb_f32sRGB → linearIEC 61966-2-1 piecewise, sign-preserving, no clamp (color_convert.py:45)
linear_rgb_f32_to_srgb_f32linear → sRGBpiecewise inverse, sign-preserving, no clamp (color_convert.py:62)
srgb_f32_to_oklab_f32sRGB → OKLabtwo-hop via linear (color_convert.py:92)
oklab_f32_to_srgb_f32OKLab → sRGBtwo-hop via linear (color_convert.py:97)

Two precision-relevant choices in color_convert.py:

  • It uses the true IEC 61966-2-1 piecewise transfer, not the **GAMMA approximation in model.py (color_convert.py:8), because round-trips through linear light must not bleed shadow precision near the project’s T_floor=0.003 noise floor (color_convert.py:11).
  • The sRGB↔linear helpers are sign-preserving and unclamped (color_convert.py:54, color_convert.py:70): HDR-style operators may temporarily exceed [0,1], and only the final emit to srgb_u8 clamps (color_convert.py:35). The OKLab conversions delegate to lib.transmission.linear_to_oklab / oklab_to_linear (color_convert.py:17), tying the slot’s color math to lib.transmission.

The runner inserts at most one converter per boundary, and operators never call these helpers directly except in tests (color_convert.py:5).

Read-only context handed to each operator

Every apply() receives a frozen PreprocessingContext (types.py:50). The runner builds it once per solve at pipeline/runner.py:1009 with:

  • config — the PipelineConfig (types.py:59)
  • image_fingerprint — from _fingerprint_preprocessing_image(image) (pipeline/runner.py:996)
  • source_path — None on the solve path (types.py:61)
  • source_image — the pre-slot raster (pipeline/runner.py:1013)
  • palette_metadata — the F2 service result, or None (types.py:63)

An operator only sees palette_metadata populated if it opts in via required_context (pipeline/base.py:94) — otherwise it stays None. palette_metadata is resolved exactly once per solve and only when at least one operator requests it (pipeline/runner.py:997, resolve_palette_metadata_for_chain). This service is documented on Palette metadata and protect masking. A concrete consumer: c2_soft_gamut_compress declares required_context = frozenset({"palette_metadata"}) (operators/c2_soft_gamut_compress.py:328).

The slot’s public types

All in preprocessing/types.py:

  • PreprocessingContractError (types.py:37) — the single exception type for every contract violation (wrong type/shape/dtype, non-finite output, illegal end-of-chain domain, ingress-dtype mismatch).
  • PreprocessingContext (types.py:50) — frozen, read-only, handed to every apply().
  • PreprocessingResult (types.py:67) — an operator’s return value: image, output_domain, optional debug_maps, optional metrics (types.py:74–77). Mutable (not frozen).
  • PreprocessingTraceStep (types.py:81) — one frozen audit row per executed operator; the list lives on PipelineState.

How to drive it (users)

You do not call the runner directly — you enable/order operators through the generator’s module management UI, which writes the live module state that _resolve_preprocessing_from_state reads (facade.py:438). Practical consequences of the contract above:

  • Order matters and is explicit. Operators run in order order, not enable order. If two operators tie, the class-name tiebreaker decides — see the Wing bands above.
  • A disabled chain is free. With no operators enabled, the whole F1 block is skipped (pipeline/runner.py:991) and the image passes through untouched.
  • The last operator must end in sRGB. If you build a custom chain whose final operator emits linear_rgb_f32 or oklab_f32, the solve aborts at chain-build time with a clear message (preprocessing/runner.py:137) — add a tail converter or reorder so an sRGB-emitting operator is last.
  • Previews are per-operator. Each enabled operator publishes a preprocess/<name> snapshot you can inspect; the previews are color-canonicalized to srgb_u8 for display but do not affect the data flowing downstream.
