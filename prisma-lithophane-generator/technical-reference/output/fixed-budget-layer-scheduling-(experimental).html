Fixed-budget layer scheduling (offline research)

In one sentence: generator/scheduling quantizes selected fields from an already-solved material plan, tries deterministic ordering policies, and scores their setup/activity characteristics; it is used only by tests and an offline evaluation script, not by the live solve, mesh, or export path.

This package does not change a solve, write an STL/3MF, or control swap grouping. The current automatic banded solve is a different subsystem; see AMS grouping and swap planning.

Liveness

No server, facade, staged-runner, or mesh/export module imports this package. Current runnable consumers are:

  • tests/generator/test_layer_scheduling.py; and
  • scripts/evaluate_layer_schedules.py, an offline report generator.

PipelineState.solved_plan has a source comment naming scheduling as a consumer, but no product caller implements that relationship. The package is therefore research/test code, not an experimental product mode.

What the budget includes—and omits

derive_fixed_budget_schedule_case reads:

  • color thicknesses from each SolvedMaterialPlan.stack_table entry; and
  • final cap thickness from SolvedMaterialPlan.cap_height_map.

It does not build a complete printer layer plan. In particular, it does not include the fixed base-white thickness, does not distinguish base-white and cap-white filament identities, does not incorporate derived swap-band white-fill maps, and does not emit spatial geometry or tool-change instructions. Every scheduled white layer is collapsed to None (or __white__ in metric dictionaries).

“Fixed budget” therefore means preservation of the quantized color-stack and final-cap amounts represented by this research case—not every material layer in the exported object.

Case derivation

quantize_thickness_to_layers uses Python round(thickness / layer_height) and rejects a nonzero thickness whose reconstructed value differs by more than 1e-6 mm. Negative thickness beyond that tolerance and nonpositive layer height also fail.

derive_fixed_budget_schedule_case then:

  1. validates that the global ordering has no duplicates and contains every positive color in every stack;
  2. quantizes each stack’s positive color thicknesses in that ordering;
  3. quantizes every unique final-cap value;
  4. expands the plan’s committed stack labels to the solve grid;
  5. computes color-plus-cap total layer height per cell;
  6. derives an anisotropic high-side white reserve around four-neighbor height drops; and
  7. groups identical (stack, cap, effective reserve, sidewall reserve, sidewall-band) cells into signatures with support area.

When no explicit flat reserve is supplied, it uses ceil(d_wc_min_mm / layer_height_mm), then clamps each signature’s base, sidewall, and effective top reserve to that signature’s available white layers. The sidewall band width is ceil(min_printable_line_width / solver_fine_pitch), with a minimum of one cell.

The plan is read-only to this function. Its segment_id_map is structurally read-only, but the plan as a whole is not a deeply immutable object.

Core records

RecordPurpose
LayerBudgetSignatureQuantized color counts, final-cap white count, ordering, and top-white reserve metadata for one unique case
LayerScheduleBottom-to-top tuple of filament ids or None plus its originating signature and policy name
FixedBudgetCaseEntryOne signature plus pixel count and physical support area
FixedBudgetScheduleCaseOrdering, physical constants, shape, and all unique entries
ScheduleEvaluationBudget/reserve checks and case-level activity/setup metrics

These are frozen dataclasses, but contained objects are not recursively frozen.

Policies

POLICY_REGISTRY contains six deterministic policies:

PolicyBehavior
baseline_top_white_onlyGlobal color order followed by all final-cap white layers
white_envelopeBuries surplus cap white below the color block and retains only the required reserve on top
absorber_strength_global_orderOrders colors by one-layer modeled attenuation, then places all cap white on top
layer_sparse_greedyAligns area-weighted color demand across absolute layers, using white slack and a budget-repair fallback
setup_beam_searchWidth-12 bounded search over preferred per-layer families, ranked by setup, chromatic activity, tiny presence, and prefix length
setup_beam_guardedUses beam output only when its evaluation tuple strictly beats baseline

The absorber policy can use supplied profiles. Otherwise it loads profiles from the active Generator model-library context; a load/prediction exception silently assigns that filament zero strength. That fallback keeps the policy running but can reduce the ordering to its original tie order.

Baseline and absorber put all cap white on top. The envelope, greedy, and beam families explicitly reserve the required top run and may place surplus white below it. It is therefore incorrect to describe every policy as appending exactly the minimum reserve.

Metrics

evaluate_case_schedules aligns schedules by signature and reports:

  • exact quantized-budget deltas and an aggregate preservation flag;
  • per-signature and aggregate top-white-reserve checks;
  • non-white active filament count per absolute layer;
  • white-inclusive active family count per layer;
  • adjacent non-white set-transition cost;
  • minimum unit-cost family changes with loaded-family carry-over; and
  • a tiny-presence penalty, defaulting to a 1.0 mm² threshold.

Setup-change and tiny-presence metrics include the collapsed white family. Chromatic activity and adjacent-set metrics exclude white.

Callable surfaces and the offline script

The package provides build_schedule_case(payload), named policy lookup, and evaluate_policy(case, policy_name), plus lower-level constructors, policies, and metrics. Synthetic equal-budget and swap-pressure fixtures support testing without a solve.

These APIs are not clean-shell standalone tools: importing the package reaches launcher-bound Generator modules and requires the same active model-library/Workspace environment as other internal Generator code.

scripts/evaluate_layer_schedules.py is also not currently a supported CLI:

  • it imports launcher-bound facade/server modules before argument parsing, so even --help fails without runtime bootstrap;
  • its recommended_v2 posture still writes retired solver_backend, grouping_mode, and old module-state keys that no longer select the current staged backend or grouping policy;
  • it uses hardcoded filament ids and real-photo discovery assumptions; and
  • its adapter still probes several nonexistent module names and says the scheduling package has not landed.

With an explicitly bootstrapped compatible runtime, the script can still find the real scheduling package, solve its cases, evaluate requested policies, and write Markdown/JSON plus diagnostic images. It requires cleanup before being documented as a user-ready command.

Verification

The focused scheduling suite covers quantization, signature derivation, anisotropic reserve behavior, all policies, and metrics. The production-liveness classification comes from caller tracing, not the stale PipelineState comment.
