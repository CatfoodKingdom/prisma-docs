Fixed-budget layer scheduling (experimental)

Fixed-budget layer scheduling (experimental)

Properties1
tagsgenerator, scheduling

Jul 12, 20269 min read

In one sentence: the scheduling/ package is a deterministic research harness that quantizes an already-solved material plan into per-layer filament/white assignments and scores competing ordering policies, but it is wired only into one offline eval script and its tests — nothing in the live solve or export path calls it.

This page is the status note for the fixed-budget layer scheduler. It exists to answer two questions a future reader will have: does the print I export actually use this? (no), and what does it compute if I run it by hand? (per-layer schedules plus setup/tiny-presence metrics). The aliasing target [[Fixed-budget layer scheduling (experimental)]] resolves here.

Liveness: NOT in the live solve/export path

The package lives at Prisma/generator/scheduling/ with three implementation modules plus a re-export shim:

FileRole
scheduling/model.pydataclasses + quantization, derives cases from a SolvedMaterialPlan
scheduling/policies.pysix deterministic ordering policies + a registry
scheduling/metrics.pybudget/reserve checks + setup-change / tiny-presence costs
scheduling/__init__.pyre-exports everything, adds build_schedule_case / evaluate_policy convenience entry points

Grepping the whole tree for importers of the package, the only non-package, non-test caller is one offline script: scripts/evaluate_layer_schedules.py. That script’s own header states it does not export STL / 3MF geometry and does not mutate repo-tracked configuration or pipeline state (scripts/evaluate_layer_schedules.py:7-8).

Confirmed by grep — these live entry points contain zero references to scheduling, LayerSchedule, setup_beam_search, etc.:

The state.py:256 comment is aspirational wording, not a wiring. The schedule outputs are never meshed: the live mesh/export path is documented in From solve to mesh the export pipeline and the staged backend in The staged backend (Stage 0-5); neither touches this package.

Disambiguation: the experimental setup_beam_search / layer_sparse_greedy policies here belong to this offline scheduler and are unrelated to swap grouping. The pluggable grouping beam-search/greedy modules that once lived under grouping/ have been deleted; grouping is now the automatic banded solve that The Solve Facade describes (generator.grouping.band_plan / generator.grouping.banded_export). Do not confuse this offline scheduler with that live path.

What “fixed-budget” means

The scheduler never decides how much of each filament a region gets — the solve already committed that. It only decides layer order within a fixed material budget. A budget is committed material thickness; quantization turns thickness into an integer layer count via round(thickness_mm / layer_height_mm), rejecting any non-zero thickness whose reconstruction error exceeds a 1e-6 mm tolerance (scheduling/model.py:65-73, tolerance QUANTIZATION_TOLERANCE_MM at :34). White is tokenized as WHITE_LAYER_TOKEN = "__white__" (scheduling/model.py:35); in an absolute schedule, white is represented as None (scheduling/model.py:195-196).

Deriving a case from a solved plan

derive_fixed_budget_schedule_case(plan, ordering, layer_height_mm, d_wc_min_mm, ...) (scheduling/model.py:375) reads an immutable SolvedMaterialPlan (generator.pipeline.solved_material_plan) and produces a FixedBudgetScheduleCase. Steps:

  1. Quantize each stack’s color budgets into ordering-stable positive (filament_id, count) tuples (scheduling/model.py:407-422 calling _ordered_positive_color_layers at :77). Any stack filament with positive thickness that is missing from ordering raises (scheduling/model.py:411-415).
  2. Quantize the per-pixel cap-height map into integer white-cap layer counts (scheduling/model.py:424-433).
  3. Label each pixel by stack via committed_stack_label_map(plan) (scheduling/model.py:435, defined in generator.pipeline.derived_views at derived_views.py:33), and build a total_layers_map = stack_total_layers[labels] + cap_levels (scheduling/model.py:440).
  4. Derive an anisotropic white surface reserve from cliff geometry (see below) and take the elementwise max against the flat d_wc_min-derived reserve (scheduling/model.py:441-448).
  5. Group identical (stack_index, cap_layers, effective_reserve, sidewall_reserve, sidewall_band) pixels into unique signatures with their pixel counts and area_mm2 (scheduling/model.py:450-490).

If top_white_reserved_layers is not given, it defaults to ceil(d_wc_min_mm / layer_height) (scheduling/model.py:393-394) — i.e. the minimum white cap implied by the solve’s d_wc_min. min_printable_line_width_mm defaults to the plan’s solver_fine_pitch_mm (scheduling/model.py:397-401), and the sidewall band width in pixels is ceil(line_width / fine_pitch) clamped to ≥1 (scheduling/model.py:402-405).

derive_unique_layer_budget_signatures(...) (scheduling/model.py:505) is the thin wrapper returning just the signatures tuple.

The anisotropic sidewall reserve

derive_anisotropic_white_surface_reserve(total_layers, band_width_px=...) (scheduling/model.py:355) returns (reserve_layers, sidewall_band_mask). It finds, per pixel, the local positive height drop to its lower 4-neighbors (_internal_cliff_drop_layers, :317), then propagates that reserve inward only across the high side of a cliff for band_width_px - 1 steps (_propagate_sidewall_reserve, :329). The intent: a tall region adjacent to a short one exposes a vertical wall that needs a white shell, and that reserve should not spill onto the lower face. This is the only geometry-aware part of the model; everything else is pure integer bookkeeping.

The signature dataclass (the unit of work)

LayerBudgetSignature (scheduling/model.py:94) is a frozen dataclass holding one committed (stack, cap) combination:

FieldMeaning
stack_indexwhich committed color stack (:107)
orderingthe global filament order tuple (:108)
color_layers((fid, count), ...), all counts > 0 (:109)
white_layersquantized white-cap layer count (:110)
top_white_reserved_layerscontiguous white run the schedule must keep on top (:111)
base_top_white_reserved_layersthe flat d_wc_min-derived component (:112)
sidewall_white_reserved_layersthe cliff-derived component (:113)
sidewall_bandwhether this signature sits in a sidewall band (:114)

__post_init__ enforces non-negativity, ordering membership, no duplicate filaments, positive counts, and that the effective top-white reserve covers both the base and sidewall reserves (scheduling/model.py:116-158). Convenience: total_color_layers (:165), total_layers (:169), full_layer_budget_map() which adds the __white__ token (:185).

A LayerSchedule (scheduling/model.py:191) pairs a signature with absolute_layers — a bottom→top tuple of filament-id-or-None, plus the policy_name that produced it (:199-201).

The six policies

All policies take a FixedBudgetScheduleCase and return one LayerSchedule per entry. They are deterministic and bounded. The registry is POLICY_REGISTRY (scheduling/policies.py:640); get_policy_registry() returns a copy (:650).

Policy nameFunctionBehavior
baseline_top_white_only:470Control: fixed global ordering, all white on top (_fallback_schedule, :43).
white_envelope:484Same color order, but bury surplus white below the color block, keep only the reserved run on top (_white_envelope_schedule, :79).
absorber_strength_global_order:491Re-order colors strongest-absorber-first, then fixed top-white (absorber_strength_order, :108).
layer_sparse_greedy:514Greedy case-level scheduler: pick one area-weighted-preferred filament per absolute layer; signatures take it when they can, else white, with a repair pass that re-fills white slots to preserve totals exactly (:603-625).
setup_beam_search:344Bounded beam search (width _DEFAULT_BEAM_WIDTH = 12, :28) over per-layer family templates, ranked by (setup_cost, active_count, tiny_penalty, prefix_len) (_BeamState.rank_key, :70). Falls back to baseline if the beam empties (:422-423).
setup_beam_guarded:445Runs beam search and baseline, evaluates both, and keeps the beam result only if it strictly beats baseline on (setup_change_cost, total active, tiny_penalty, transition_cost) (_report_rank_key, :436; comparison :465-467).

absorber_strength_order (scheduling/policies.py:108) ranks filaments by 1 - mean(predict_transmission(profile, layer_height)) — i.e. how much a single layer of that filament darkens — loading profiles via the shared model.load_profile / predict_transmission (generator.model, imported policies.py:20), with an lru_cache on per-filament strength (:93-105).

Every policy enforces the white-on-top reserve by appending exactly min(white_layers, top_white_reserved_layers) None layers at the top (_top_white_layers_used, scheduling/policies.py:31).

The metrics

metrics.py scores a (case, schedules) pair. The headline costs:

MetricFunctionWhat it counts
Budget preservationbudget_preserved (metrics.py:81) / budget_preservation_deltas (:49)Whether observed layer counts exactly match the signature’s full_layer_budget_map(); deltas list any mismatch. A correct schedule has zero deltas.
Top-white reserve OKtop_white_reserve_ok (metrics.py:89)Whether the schedule’s own top reserve layers are all white (:100).
Setup-change costsetup_change_cost (metrics.py:218)Minimum family-change cost with carry-over loaded state across adjacent layers — a tiny DP over which family is “loaded” after each layer (:231-248). Start family defaults to white.
Adjacent-layer transition costadjacent_layer_filament_set_transition_cost (metrics.py:206)Symmetric-difference size of the active non-white filament set between neighboring layers (:213-214).
Tiny-presence penaltytiny_presence_penalty (metrics.py:251)For each family/layer whose total area is below min_area_mm2 (default 1.0, :255), adds threshold - area (:262-266).

Area is aggregated per absolute layer either including white (family_area_by_absolute_layer_mm2, :103) or excluding it (filament_area_by_absolute_layer_mm2, :134 — note: white is deliberately dropped here because the metric tracks chromatic activity, :140-142). Setup/tiny costs use the white-inclusive aggregation; “active filament” counts use the white-exclusive one.

evaluate_case_schedules(case, schedules, ...) (metrics.py:270) bundles all of the above into a frozen ScheduleEvaluation (scheduling/model.py:285), aligning schedules to entries by signature first (_align_schedules, metrics.py:22). The tiny-presence threshold here defaults to 1.0 mm² (metrics.py:275).

Driving it by hand

There is no UI and no CLI flag. Two ways to exercise it:

1. Package convenience API (scheduling/__init__.py):

  • build_schedule_case(payload) (:68) — dispatches to a synthetic fixture (build_swap_pressure_case / build_synthetic_equal_budget_case) or, given a solve_result carrying a solved_plan, calls derive_fixed_budget_schedule_case (:91-103).
  • evaluate_policy(case, policy_name) (:117) — runs one named policy and returns a flat dict of costs (setup_change_cost, active_count, tiny_presence_penalty, top_white_penalty, budget_ok, the schedules, etc., :124-145). Policy-name aliases map short names to canonical ones (POLICY_NAME_ALIASES, :54).

2. The offline eval script (scripts/evaluate_layer_schedules.py):

python scripts/evaluate_layer_schedules.py --out-dir <dir> \
    --cases synthetic_swap steve cafe \
    --policies baseline white_envelope absorber_strength_order \
               layer_sparse_greedy setup_beam_search setup_beam_guarded

It performs a real bounded solve per case (solve_full, :441) under a fixed recommended_v2 posture (dual_resolution_v2 + greedy grouping, :68-73), builds a scheduling case through a defensive adapter (SchedulerAdapter, :181; module discovery _load_scheduler_adapter, :482), evaluates every policy, and writes report.md + summary.json plus per-case stack_strips.png / layer_activity.png visuals (:1612-1616, _write_case_visuals :1492). It picks a “winner” with a weighted chooser whose weights (setup_change_cost 40, active_count 25, tiny_presence_penalty 20, top_white_penalty 10, printability_proxy 5) live in CHOOSER_COMPONENTS (:98-104) — note these chooser weights are the script’s, not the package’s. The adapter tries module names ("scheduling", "layer_scheduling", "schedule_evaluation", "evaluation.scheduling") (:106-111); only scheduling exists, so the others are dead fallbacks.

The synthetic fixtures build_swap_pressure_case (scheduling/model.py:589) and build_synthetic_equal_budget_case (:526) are also the basis of much of the test suite (tests/generator/test_layer_scheduling.py, 12 tests).

Stale-header warnings

  • The module docstrings are accurate here, but the package-status framing in scripts/evaluate_layer_schedules.py:12-15 (“expected to land separately from this runner”) and the adapter’s import-failure message (scripts/evaluate_layer_schedules.py:578-579, “once the new scheduling package lands”) are stale — the package has landed; the adapter’s multi-name probing is now vestigial.
  • The pipeline/state.py:256 comment listing scheduling as a plan consumer overstates reality: no live code path consumes scheduling output.
