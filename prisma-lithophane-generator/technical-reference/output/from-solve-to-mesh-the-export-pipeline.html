From solve to mesh: the export pipeline

In one sentence: export_solve_bundle loads a canonical solved-material bundle, builds a format-neutral set of base/color/cap mesh objects with exact-raster or field-derived cap geometry, audits and reports those objects, optionally writes STLs, and returns the in-memory bundle that the server can package as 3MF before directory publication.

This page describes the geometry/manifest integration point in generator/mesh/post_solve_export.py. HTTP target selection, background polling, private output staging, swap-instruction writing, and the final directory rename belong to Export request lifecycle and artifact ownership.

The format-neutral boundary

generator.mesh.export_mesh_bundle defines two frozen dataclasses.

MeshObject

A MeshObject contains:

  • unique object_key;
  • material_key used for filament/package assignment;
  • semantic role;
  • mesh_style describing its construction;
  • copied float64 vertices and int64 triangle faces;
  • optional 4×4 transform; and
  • free-form metadata.

MeshObject.from_trimesh copies arrays from a trimesh.Trimesh. to_trimesh reconstructs with process=False and applies the optional transform. A border shift is represented as an object transform and is therefore baked when a serializer calls to_trimesh.

object_key is an export-object identity, not always a source thickness-map key. Unsplit color objects commonly use the filament id, but quarantine/slab/adaptive parts receive distinct suffix-bearing keys while retaining the parent’s material_key.

ExportMeshBundle

An ExportMeshBundle groups all objects with physical dimensions, layer height, XY quantum, coordinate-frame name, build report, per-object quality, color-export details, and mesh-style metadata. object_by_key performs a linear lookup.

The dataclasses are structurally frozen: code creates replacement bundles for report or border changes rather than assigning fields. This is not deep immutability; contained NumPy arrays and mapping objects remain ordinary mutable Python objects if a caller deliberately modifies them.

The shared coordinate frame is x-left-to-right_y-bottom-to-top_z-build-plate-mm.

Input bundle contract

The web server first materializes a clearable cache bundle containing:

  • arrays.npz;
  • stageA_field_bundle_summary.json;
  • prediction_replay_metadata.json; and
  • run_template.json.

export_solve_bundle accepts an arrays.npz path, its directory, or a parent that resolves to exactly one bundle. NumPy loads with allow_pickle=False. The replay names the ordered color filaments; run/summary metadata carries the physical and white-cap contracts.

Required arrays include the color map stack and canonical white-cap data. Required metadata includes solve-grid pitch, layer height, white-base thickness, explicit solve mode, and the canonical white-cap field-target policy. Border values are read through a metadata-priority chain unless the caller overrides them. When border is disabled its resolved width and height are zero.

detect_solve_mode_from_metadata searches the top-level and nested export_metadata / physical_geometry / white_cap_field_target records for luminance_mode. The current implementation maps the canonical standard string to SolveMode.STANDARD and any other present value to SolveMode.LUMINANCE; absence raises ExportPreparationError. It no longer infers mode from array keys.

The ten internal stages

DEFAULT_EXPORT_STAGES drives ExportProgressReporter:

#StageCurrent ownership
1load_bundleResolve and load arrays plus JSON metadata.
2detect_solve_modeResolve mode, physical dimensions, and border.
3prepare_material_mapsUnpack the ordered color stack, validate any band plan/fill maps, and construct the base rectilinear config.
4build_geometry_sourceLoad exact cap data or reconstruct the field-derived cap.
5build_color_base_meshesBuild one flat base and one or more same-material objects for each nonempty color.
6build_white_cap_meshesBuild exact-raster or hybrid cap objects and merge band white fill into the cap material.
7validate_banded_geometryAudit a persisted banded plan; explicit no-op event for an unbanded solve.
8serialize_outputsWrite STL objects when requested; 3MF remains server-owned.
9validate_meshesOptionally reload written STLs; otherwise record why disabled.
10write_manifestBuild and write the initial export manifest.

The separate prepare_export_material_maps module is called by the server before this function. It now only shallow-copies the map dictionary and ordering. Internal stage 3 does different work: it unpacks and validates the already materialized arrays/config.

Geometry configuration and policy

RectilinearExportConfig carries white-base thickness, actual geometry XY pitch, canonical solve-grid pitch, layer height, optional physical image dimensions, numerical/welding controls, border settings, a test/internal forced-slab switch, and a cooperative cancellation callback.

Its export_policy() creates a GeometryExportPolicy with:

  • canonical solve-grid pitch;
  • actual geometry pitch;
  • layer height;
  • white-base thickness; and
  • a GeometryPrintabilityPolicy whose default minimum widths/areas derive from the solve-grid pitch.

For exact raster the actual and solve pitches match. For a field-derived cap the cap geometry pitch is solve pitch / field_scale, while printability thresholds remain anchored to the solve grid. Color objects use the solve-grid config in both modes.

Shared base and color construction

_base_and_color_objects owns the common lower stack.

  1. generate_flat_plate creates __white_base__ from Z=0 through d_wb_mm.
  2. A floor array begins at the base top.
  3. Each ordered non-internal color map is meshed over that floor.
  4. The floor advances by the material thickness before the next color.

For a banded solve, fixed band-white-fill volumes are also built according to the persisted plan. They belong to the white-cap material, not to a synthetic color filament, and are merged into the cap material objects later.

Each color first attempts one rectilinear interval body. It must pass both the ordinary build-time check and a strict processed/welded check. A failing nonempty body tries a topology-risk quarantine partition. If no tested partition is ready, constant-Z slab parts are emitted instead. The fallback report and every part’s quality remain in the bundle; a failed leaf is not silently reclassified as good.

Exact-raster white cap

build_exact_raster_mesh_bundle reads the combined cap thickness on the solve grid and places it over the final color floor.

The ordinary ladder is:

  1. one rectilinear interval body;
  2. topology-risk quarantine parts if strict quality fails; and
  3. recursive adaptive Z partitions if the quarantine is not ready.

force_exact_white_cap_slabs=True selects a separate constant-Z slab route directly; the web request does not expose that config switch. Adaptive terminal ranges are emitted even when a one-level leaf still fails, with failure recorded in quality/report metadata.

After the cap route, band-white-fill meshes are concatenated or represented as cap-material objects as required, then _bundle_from_objects records the bundle report and optional border wrapping runs.

Field-derived white cap

The field path calls reconstruct_field_white_cap_from_arrays with the metadata-authorized target and requested scale. The result must be a 2D integer uniform multiple of the color grid. Export derives the actual scale from the returned shape rather than trusting the request blindly.

build_field_derived_mesh_bundle_mixed_resolution then:

  1. builds base and colors at exact solve-grid pitch;
  2. derives the final color-top witness, including persisted band fill when present;
  3. nearest-neighbor upsamples only that witness to field resolution; and
  4. calls build_overlap_white_cap_mesh with matching field/hybrid policies.

The hybrid builder emits guard and freeform cap geometry while preserving coverage over the color stack. Its validation and build time are copied into mesh_build_report["overlap_white_cap"]. The field reconstruction report is stored separately under field_white_reconstruction.

Banded geometry audit

When a valid persisted plan exists, audit_banded_export_geometry compares it with the emitted color floors/ceilings, pause planes, band fill, and total non-border upper surface. Failure raises ExportPreparationError, so that staged export is not published.

For field-derived geometry, the expected cap maximum is taken from the reconstructed field actually used for meshing rather than from the coarser solve-grid cap. This keeps the band/pause checks exact without rejecting a deliberately different field-derived top surface. The audit is embedded in the build report and manifest validation; no duplicate audit JSON is written.

Format serialization boundary

With write_stls=True, export_solve_bundle calls write_export_mesh_bundle_as_stls, which skips empty objects, derives a safe filename from each object key, converts the positioned object to trimesh, and writes one file. Returned output_paths map object keys to those paths.

With write_stls=False, no mesh file is written inside this function. The web server’s 3MF branch reuses the returned in-memory bundle, optionally coalesces same-material color quarantine objects, assigns package-local material numbers/display names, and calls write_export_mesh_bundle_as_3mf. Therefore 3MF construction, its manifest amendment, swap instructions, and the final directory publication are outside the ten internal stages and outside PostSolveBundleExportResult.output_paths.

Quality and manifest semantics

check_mesh_quality records watertightness, open edges, pinch/non-two-valence edges, winding consistency, and mesh counts. Rectilinear acceptance additionally processes/welds a copy and requires that strict representation to have no non-two-valence edges.

Stage 9 is a second, optional operation only for written STLs. If validate_written_meshes is true, each STL is reloaded and recorded under reload_quality; otherwise the manifest records disabled_by_default. With no written meshes (the 3MF path), it records no_written_meshes.

build_export_manifest writes schema post-solve-export-manifest-v1. Its top-level status is ready only when every recorded object is watertight and has no open or pinch edges; otherwise it is mesh_quality_failed. The manifest still exists in the latter case and the server may publish it with the files, allowing the UI to report the failure rather than hiding it.

The manifest also contains content/export footprints, border, grid/policy, objects and any STL paths, quality, build report, bundle identity, validation, and a performance block. Those timings cover export_solve_bundle itself. They do not include later 3MF packaging, swap-instruction generation, response assembly, or the final rename; the background job’s elapsed time is the end-to-end measure for those steps.

Return value and progress boundary

PostSolveBundleExportResult returns:

  • the in-memory ExportMeshBundle;
  • initial manifest dict and path;
  • written STL output_paths;
  • internal progress events; and
  • optional STL reload-quality results.

ExportProgressReporter.emit checks cancellation before constructing each event, and lower mesh/serializer loops receive the same callback for finer checkpoints. The web server converts the internal stage index/fraction into its polling payload.

The server emits additional events around 3MF packaging and final publication. Current source stamps 3MF packaging as stage 7/10 even though internal serialization is stage 8/10, and stamps publication as stage 10/10; this can make the displayed percentage regress during a 3MF export. That is a frontend/backend progress-index discrepancy, not a change in geometry order. The completed state ultimately sets progress to 100%.
