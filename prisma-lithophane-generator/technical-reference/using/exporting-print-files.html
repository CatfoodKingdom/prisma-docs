Exporting Print Files

Exporting Print Files

Properties1
tagsgenerator, export

Jul 16, 20268 min read

In one sentence: export converts one completed solve card’s physical thickness maps into STL or 3MF geometry, a manifest and mesh report, and printer-capacity-specific swap instructions, then publishes the complete artifact set under Generator/Exports.

The browser workflow

The Export page is card-oriented. Select a completed solve in the left sidebar, inspect its solve preview and solved dimensions, choose the export settings, and press Generate Print Files.

The preview reports the solved image area in millimetres and solve-grid pixels. When the solve has a border, it separately reports the total physical footprint, including the border on both sides. These values come from the solved card, not the original source image dimensions.

Three settings define the ordinary export identity:

  • Output format: one 3MF package (default) or separate STLs;
  • Mesh method: field-derived white cap (default) or exact solved raster; and
  • Mesh detail: 2x, 4x, 8x, or 16x for a field-derived cap. Exact raster ignores this scale.

The browser always sends the selected card id. This means changing current Settings after a solve does not silently reinterpret that card; export uses the config and arrays captured for the selected solve. A card whose cached arrays disappeared after Generator restarted cannot be exported until the user loads its Saved Run archive or solves again.

Export is a polled background job. Its progress bar can request cancellation, which remains in a cancelling state until the backend reaches a safe checkpoint. The format and mesh controls remain locked while the job is active. See Export request lifecycle and artifact ownership for job identity, cancellation, private staging, and process-kill recovery.

Multiple exports of one solve

Finishing an export appends a record to the selected solve card. Generating the same solve with another format, mesh method, or field scale does not replace the earlier record. Select a record in Generated Exports to change all three subordinate views together:

  • Generated Files;
  • Swap Instructions; and
  • Mesh Report.

Each record shows its completion time and export duration. Open Folder opens that record’s published directory; per-file Download links and Download .zip serve the durable artifacts.

The record list itself is browser-session state. Generator does not reconstruct it by scanning Generator/Exports after a restart, although the completed folders remain plainly accessible on disk.

What a published export contains

The permanent folder is Generator/Exports/{export_id}. It contains:

  • either {export_id}.3mf or an stls/ directory;
  • export_manifest.json; and
  • swap_instructions.txt when a swap payload is available.

The object set always includes a flat white base, the color material volumes, and the white-cap material volume. An enabled border adds a white-cap-material frame. A difficult color or cap volume may be split into multiple same-material objects to avoid welded topology failures, so there is not necessarily exactly one mesh object per filament.

The manifest records the geometry source and detected solve mode, content and total footprint, border, coordinate frame, material/role for every object, build reports, quality summaries, validation details, and performance timings. It is the authority for interpreting the object files.

Field-derived versus exact-raster geometry

Both methods use the same exact solve-grid white base and color thickness maps. The setting changes how the white cap is created.

Field-derived white cap

The default path reconstructs the solve’s canonical white-cap field target at an integer multiple of the solve-grid resolution. field_scale controls that multiple. The color-top witness surface is nearest-neighbor lifted to the finer grid, while the hybrid cap builder creates the guard/freeform cap geometry there. Color material is never invented at the finer cap resolution.

This produces a smoother, potentially more detailed viewing surface. Increasing the scale can greatly increase work and output size; the UI asks for confirmation above 4x.

Exact solved raster

Exact raster meshes the combined white-cap thickness directly on the solve grid. It first tries one rectilinear interval body. If strict post-weld quality fails, it tries a topology-risk quarantine split and then recursive adaptive Z partitions. A forced constant-Z slab mode exists for internal/test use but is not the ordinary fallback selected by the web UI.

Color bodies follow a related policy: one interval body first, then same-material topology quarantine, then constant-Z slabs if the quarantine report is not ready. All of these preserve the physical thickness field while changing the object partition.

The detailed algorithms are in From solve to mesh the export pipeline and Robust rectilinear meshing.

Export contract and geometry ownership

Export reads the solved material plan; it does not run the color solver again. The server validates and materializes:

  • ordered color thickness maps;
  • total, boundary, and detail white-cap maps;
  • the canonical white-cap field target and its policy metadata;
  • solve-grid pitch, layer height, and white-base thickness;
  • physical image dimensions; and
  • the persisted swap-grouping plan when present.

Missing or obsolete canonical fields return HTTP 409. prepare_export_material_maps currently only shallow-copies the maps and order; the retired translucent-underfill promotion is not part of export. Mandatory product settings are normalized on the config/solve path, not retroactively applied as new geometry during export.

Solve mode is detected from required metadata. Standard and Luminance Detail are not user-selectable export modes, and current export does not infer the mode from whichever array names happen to exist.

Border geometry

If the solved card has a border, export translates all content objects inward by the configured border width and appends a __border__ frame object printed with the white-cap material. The content-domain dimensions remain the solved image area; the export footprint grows by twice the border width in X and Y. The border height participates in total print height but does not alter the solved content maps.

Mesh quality and fallbacks

Each built mesh receives a check_mesh_quality summary: watertightness, open edges, pinch/non-two-valence edges, winding consistency, and counts. Rectilinear color/cap paths also test a strictly processed, welded representation because a mesh that is clean before welding can acquire a non-manifold pinch when duplicate vertices merge.

Fallback partitioning attempts to turn a failing single body into clean same-material bodies. The manifest does not pretend success if a fallback still contains a problem: its top-level status becomes mesh_quality_failed whenever any recorded object is non-watertight or has open/pinch edges. The Export page’s Mesh Report displays those results. Export can therefore produce files with an explicit failed-quality report; publication itself is not a guarantee that every mesh passed.

validate_written_meshes optionally reloads written STL files and records that second check. It is false by default and the current browser has no control for enabling it. 3MF packaging may coalesce same-material color quarantine bodies; the package manifest explicitly records that the post-coalescence package mesh is not revalidated.

STL and 3MF ownership

  • STL writes one file per nonempty mesh object under stls/. Material and role mappings live in the manifest, so the slicer assignment is manual.
  • 3MF writes one package directly from the in-memory mesh bundle without creating temporary STLs. Object transforms are baked into vertices. Package-local material slots are one-based and share a slot when base and cap use the same filament.

Those 3MF material numbers are packaging metadata. They are not the active printer’s AMS slot table and do not replace the separate swap instructions.

Swap instructions and M600

Swap geometry belongs to the solve. Export reads the persisted consecutive band plan and validates it against the printer selected at export time:

  • ams_slots determines total slots;
  • white_slots reserves the fixed white capacity; and
  • the remaining color slots must hold every persisted band.

Export assigns current slot tables but never regroups the solved palette or changes pause heights. A changed printer profile can therefore make an old solved plan unexecutable and produce HTTP 409. If the solve records that no valid swap plan was available, the export carries an unavailable explanation rather than inventing one. A non-banded solve receives a one-load table and is still capacity-checked.

For a banded solve, each pause is the preceding band’s stored upper Z plane. N bands require N-1 pauses. The response includes human instructions and generated M600 G-code; the published text file contains the human instructions. When everything fits in one load, there are no pause commands.

Routes

RouteOwnership
POST /api/export/files/startStart the browser’s background export and return its job id.
GET /api/export/files/statusPoll job identity, state, progress, elapsed time, and terminal result.
POST /api/export/files/cancelRequest cooperative, job-scoped cancellation.
GET /api/export/files-zip?dir={export_id}Download the selected final directory’s known deliverables.
GET /api/export/files/{path}?dir={export_id}Serve one contained exported file.
POST /api/export/files/open-folderOpen one existing final export directory in the system file manager.
