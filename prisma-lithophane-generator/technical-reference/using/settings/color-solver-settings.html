Color Solver settings

Color Solver settings

Jul 15, 20267 min read

The Color Solver section governs the core of a solve: the color model, how target colors are prepared and matched to filament recipes, and how the image is partitioned into color regions. Two closely related controls — Solve Pitch (resolution) and Solve Mode — sit at the top of the Essentials section in the app but are documented here, since they set the solve’s resolution and cap strategy. For the mechanism behind these stages, see The Solve.

Solver core

Solve Pitch — default 0.20 mm; the displayed minimum follows the active nozzle diameter. This is the physical spacing of the solve grid: the distance between points for which the solver chooses recipes. Smaller values preserve more detail but increase solve and export cost roughly with the square of the resolution. Prisma does not silently raise this value after a nozzle change. Instead, both the frontend preflight and the backend solve-start gate reject a solve whose pitch is smaller than the active nozzle diameter.

Solve Mode — Color (default) or Luminance. It changes how the white cap is built and — indirectly — the color recipes. In Color, the cap realizes the brightness the color solve already chose. In Luminance, the cap is reconstructed from the image’s own luminance and carries the photo’s tone and fine detail as white relief; because that reserves part of the height budget for the cap, the recipe table is built over a narrower range of cap thicknesses, so the solver can pick different per-filament recipes than in Color mode. Solve Mode is a preset: selecting Luminance reconfigures several White Cap fields at once — it reveals Shading balance and forces the boundary cap to its smooth form. See Solve Modes and White Cap settings.

Appearance Model — Color Model v1 or Color Model v2 (default). The forward color model used to predict stacks, build the recipe table, render previews, and score accuracy. Color Model v1 is the spline/multiplicative transmission model. Color Model v2 is the interaction-aware photo-stack model and requires the corresponding runtime bundle from the active published model library. A valid published library supplies the artifacts Prisma needs for the offered models. See Appearance provider.

Recipe Search

This subsection controls how target colors are prepared and matched to filament recipes. Most fields are advanced.

Out-of-gamut handling (advanced) — Nearest reachable color (default) or Preserve hue. How target colors the palette cannot reproduce are moved before recipe lookup. Both modes use the same unweighted distance to the nearest discrete recipe-table sample to decide whether a target exceeds Color mismatch tolerance. Nearest reachable color moves geometrically outside targets toward the reachable color hull in full three-dimensional OKLab, so lightness and hue can shift before the final recipe lookup. Preserve hue scales the target’s two chroma axes together toward neutral, preserving hue while reducing chroma and moving lightness only as needed to enter the printable range. See Gamut mapping.

White-point rescale (advanced) — default off. Rescales every target so the source’s white maps to the print’s actual paper white (the thinnest white stack), keeping pale tints in gamut instead of clipping them to white. Predicted previews read slightly darker and warmer when it is on.

Color corrections — default on. Applies calibrated correction data while the recipe table is built — pair corrections for Color Model v1, the correction layer for Color Model v2. For Color Model v1 it only takes effect when Max colors per region is at least 2.

Max colors per region — 1–7 in the browser, default 3. The most distinct colored filaments a single region’s recipe may stack. Higher values can match colors more closely but multiply the recipe search; the effective cap is the smaller of this and the palette size. The frontend enforces the 1–7 range, but the backend’s generic config payload accepts an arbitrary integer and does not repeat that upper-bound check for direct API callers.

Color mismatch tolerance (advanced) — default 0.01, in OKLab color difference. A target farther than this from the nearest discrete recipe-table sample is flagged as out of gamut. Preserve hue then searches its hue-preserving path for an improvement. Nearest reachable color projects the target only when it is also geometrically outside the continuous hull; a flagged point already inside the hull stays in place and the final recipe lookup handles the remaining discrete mismatch. Lower is stricter. The 0.01–0.20 shown is a guide, not an enforced limit.

Chroma weight (advanced) — default 1.0. Weights chroma against lightness when matching recipes: above 1 favors hue and saturation over brightness, below 1 favors brightness. It changes which recipe is chosen, not the reported color error, which is always measured in unweighted OKLab. The current logarithmic slider spans 0.125–8.0.

Region Construction

This subsection controls how the image is divided into color-planning regions and how those regions are refined. Every field except Color region target is advanced.

Region method (advanced) — Image regions (default), Superpixels, or Fixed grid. How the image is partitioned into initial color regions before recipes are chosen. The image-aware modes follow image structure; Fixed grid uses uniform square cells.

Region planning scale (advanced) — 1–4× in the browser, default 1. Plans the regions on a grid coarsened by this factor. Higher values make broader, simpler regions that solve faster but follow fine edges less closely. The staged helper clamps direct values only to a minimum of 1, so the browser’s upper bound is not a generic backend constraint.

Color region target — default 0.60 mm. The target physical width of the initial regions: smaller follows image structure more closely, larger makes broader, simpler regions. Note that this value is raised to a printability-derived minimum, so entering a value below that minimum has no further effect. This is the only always-visible field in the subsection.

Local recipe corrections (advanced) — default on. Lets individual grid cells inside a broader region adopt a better-matching recipe when the color improvement is strong enough. This preserves fine detail at the cost of more small recipe patches.

Boundary mutation (advanced) — default on in the current product configuration. Lets the solver redraw recipe boundaries between neighbors when borrowing a neighbor’s recipe lowers local color error. Turning it off disables that refinement. When enabled, the UI reveals four tuning fields:

  • Mutation passes — 1–16, default 1. Each pass can move a boundary by one more solve-grid cell. Prisma stops early when a pass accepts no pixels.
  • Mutation current-dE percentile — empty/off by default. When set, only boundary candidates whose current color error is at or above this percentile are eligible. The threshold is recomputed from the current candidates on each pass.
  • Mutation min gain — empty by default, which uses 0.010 dE. Candidate pixels are grouped into connected patches that share the same original and borrowed recipes; the patch’s mean improvement must exceed this threshold.
  • Mutation min contact — empty by default, meaning at least one solve-grid pixel of shared boundary with the donor recipe. A supplied millimeter value is converted to ceil(value / Solve Pitch) contact pixels.

The older Mutation grouping control is not present in the current UI or config contract. Boundary mutation already evaluates four-connected patch components and records its component/contact diagnostics internally.

The result of this section is the per-cell recipe map that the white cap, grouping, and export stages build on.
