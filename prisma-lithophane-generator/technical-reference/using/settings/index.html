Settings

Settings

Jul 26, 20265 min read

The settings page configures how a solve runs — print geometry, image conditioning, the color solver, the white cap, and material grouping. These are the parameters that rarely change between runs; per-image choices (the source photo, palette, image adjustments, export format) live on the workflow tabs, not here.

Settings are organized into four editable sections, in pipeline order:

  • Essentials — the print’s physical envelope (total thickness, layer height, base thickness) and the white base/cap filament, plus the two headline solver controls, Solve Mode and Solve Pitch (detailed under Color Solver).
  • Pre-processing — how the source image is conditioned before solving: resampling onto the solve grid, plus optional smoothing and palette-fit modules.
  • Color Solver — the color model, the recipe search, and how the image is partitioned into color regions. (Solve Mode and resolution now live in Essentials.)
  • White Cap — the white layer over the colors: minimum thickness, the boundary cap, and the detail relief. (The white filament is shared with the base, set in Essentials.)

AMS swap grouping is not an editable settings section in the current build. It is created automatically during a full solve only when the palette exceeds the available AMS color slots; see Grouping settings and AMS grouping and swap planning.

Settings profiles

A settings profile is a saved bundle of every editable settings-profile field, the preprocessing parameter map, and the complete current preprocessing-module toggle snapshot. Palette membership, source image, frame/crop state, image adjustments, and export options are not settings-profile fields.

The profile bar names the loaded profile and adds badges for its state:

  • system is the built-in Basic profile;
  • startup is the profile selected to load when the app starts;
  • TEMP is a session-only profile reconstructed from a solved run; and
  • modified means a profile field or module toggle differs from the snapshot that was loaded.

Save updates a named profile after confirmation. Save As… writes the current values as a new named profile. Profiles… lists profiles and can load, rename, choose a startup profile, delete, restore the system profile, or open Load Settings from Run….

The built-in Basic profile is regenerated from current product defaults when necessary. It cannot be renamed, overwritten, or deleted. Saving a draft based on Basic therefore uses Save As. Named profile names are case-insensitively unique and cannot be blank, carry leading/trailing whitespace, end in a period, use Windows-forbidden filename characters, or reuse the reserved name Basic. If the selected startup profile is missing or invalid at launch, the backend resets the startup selection to Basic.

Loading a profile changes both the flat session config and the separately persisted preprocessing-module state. The frontend applies both locally, sends the config, then sends the module snapshot. If synchronization fails, it attempts to restore the previous local state and sends compensating backend updates once publication has begun. Those calls are coordinated but are not one atomic backend transaction; a failed compensation is logged and a subsequent server refresh is authoritative.

Settings captured by solved runs

Every live solved-run card has a display-only Settings panel. It preserves the same section order as the editable drawer, renders values as text rather than disabled controls, and has its own Advanced: On/Off view. Clicking the card’s Settings button again closes it.

Load Settings in that panel reconstructs a session-only profile from the solve. The Saved Runs window and Settings Profiles window provide the same operation for a saved run or autosave without loading its image or restoring the solve card. Prisma uses the archived config plus newer solve-start diagnostics and durable recipe/profile metadata when those are present; this keeps current archives exact while retaining compatibility with older archives that recorded less metadata.

Only one reconstructed run profile exists at a time. It is marked TEMP, identifies its source run, and is replaced when settings are loaded from another run. It can be modified and used immediately, but it is not written to the profile store and cannot be selected as the startup profile. Saving it uses Save As to create a normal named profile.

When switching away from a modified profile, Prisma offers to save the draft, discard it, or cancel the transition. A TEMP profile is subject to the same guard.

Persistence and backend contract

Persistent profiles live as individual JSON records under Generator/Workspace/settings_profiles/. system-default.json is the canonical Basic record; named profiles use generated identifiers rather than display names as filenames. state.json stores the selected startup-profile identifier. Each JSON update is staged and replaced as one file, but a profile update and a separate startup-state change are not a multi-file transaction.

The backend enumerates named JSON files, skips records it cannot normalize, ignores later records that duplicate an already loaded profile identifier, and sorts valid named profiles by display name. It canonicalizes the resolution fields, supplies current defaults for missing profile fields, normalizes the complete module-toggle map against current module descriptors, and drops explicitly retired compatibility keys. This means an older profile can acquire current defaults for settings it never recorded; it is not treated as a byte-for-byte historical solve record.

The profile API separates list/create/update, startup selection, Basic restoration, and deletion. Basic is rejected by update and delete routes. Deleting the selected startup profile resets startup state to Basic. The frontend additionally prevents deletion of the profile currently loaded into the editable drawer until another profile is loaded.

Showing advanced settings

Many fields are hidden by default as advanced. The drawer’s Advanced: On/Off button reveals them across every section. It changes only visibility; it does not alter solve settings and is not stored inside a settings profile. Its state is saved separately in browser local storage, so the editable drawer normally remembers the user’s choice across launches in that browser profile.

The display-only solved-run Settings panel has a separate Advanced toggle. That panel starts with advanced rows hidden each time it is opened and does not change the editable drawer’s stored preference. Throughout this reference, fields noted as advanced are the fields controlled by these views.
