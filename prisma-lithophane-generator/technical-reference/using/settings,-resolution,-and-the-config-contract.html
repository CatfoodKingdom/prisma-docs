Settings, resolution, and the config contract

Settings, resolution, and the config contract

Properties1
tagsgenerator, config

Jul 27, 202610 min read

In one sentence: the Generator keeps a mutable session dictionary, accepts partial updates through a POST endpoint, normalizes its coupled solve-pitch fields, force-restores mandatory product safeguards, snapshots the resolved dictionary at solve start, and translates that snapshot into SolveConfig and then PipelineConfig.

This page describes the contract between the Settings UI, settings profiles, the server session, and the staged solver. For the user-facing controls, see the pages under Settings. For the solve path, see Pipeline Map and generator.facade.

The three live representations

LayerTypeOwnerRole
Frontend configJavaScript objectapp.state.settings.config, initialized in app/core/application-context.js and synchronized by app/features/settings/profiles.jsMirrors the current Settings UI and the last server response.
Session configplain Python dictsession["config"] in server.pyMutable state for the running server process.
Typed solve configshared SolveSettings, wrapped by SolveConfig then PipelineConfigconfig/solve_settings.py, facade.py, pipeline/state.pyOne canonical setting inventory plus request-only and execution-only data.

POST /api/session/config has partial-update semantics: fields omitted from the request retain their current session values. The endpoint validates the submitted ConfigPayload, merges it over the existing session dictionary, normalizes resolution, applies the selected luminance preset, reapplies mandatory product settings, stores the result, and returns the complete resolved config. The frontend serializes config writes so an older request cannot arrive after a newer one and silently revert the session.

The frontend and backend use two names for the shared support filament. The visible control owns base_filament and forces cap_filament to "__same__"; every frontend sync also mirrors that selection into the older solver-facing white_base field and sends white_cap: null. _build_solve_config resolves those solver-facing fields. Settings-profile and saved-run normalization accepts either representation and reconstructs the shared-filament rule.

At POST /api/solve/start, the server copies the resolved session dictionary before starting the background worker. Later Settings changes therefore do not alter a solve already in progress. SolveConfig and PipelineConfig are ordinary mutable dataclasses, not frozen types; their isolation comes from this per-solve snapshot, facade copy, and pipeline compilation. Pipeline runtime limits are declared separately on PipelineRuntime, and swap-scout replacement creates a fresh carrier.

Printer-owned printability

Printer configuration is a separate Workspace contract at Generator/Workspace/config/printers.json; it is not owned by session["config"] or Settings Profiles. Each nozzle profile stores its diameter, layer-height and nominal-line-width data, and an integer min_line_length_multiplier from 2 through 10. It does not store a separate minimum width or physical minimum length.

The backend resolver derives and canonicalizes:

GET /api/printers/active and successful printer writes return those resolved values under printability. The frontend uses that response to refresh its display and session mirror, but the server overlays the active printer’s values again on every session update and solve-start snapshot. A stale or hand-written printability_minimum_* client value therefore cannot override the current printer.

Changing the active printer or nozzle updates the session mirror and solve-owned fingerprint. The selected nozzle diameter also remains the solve-admission floor described below. Physical printability checks retain their existing solve-grid quantization; this schema change does not introduce fractional occupied cells or alter the component grader.

Resolution schema

config/resolution_schema.py owns three canonical schema fields:

FieldDefaultMeaning
image_sample_pitch_mm0.20Physical pitch of the source raster sampled for the solve.
solver_fine_pitch_mm0.20Physical pitch of the solver grid.
color_region_target_mm0.60Target physical width of initial color-planning regions.

The first two are one user-facing Solve Pitch under two internal names. They must both be present and agree within the schema tolerance. When they agree, the normalizer writes the accepted value back to both fields. color_region_target_mm is independent.

Solve-pitch constraints

The Settings UI always writes the same value to image_sample_pitch_mm and solver_fine_pitch_mm. It does not silently change the pitch when a user selects a different nozzle. Instead:

  • the UI displays the active nozzle diameter as the minimum;
  • solve preflight refuses to start when Solve Pitch is below that diameter; and
  • _validate_solve_pitch_for_nozzle repeats the check in the backend before a job is reserved.

The resolution schema itself only checks field presence, finite numeric values, and agreement. The nozzle constraint belongs to solve admission.

Retired aliases

The following aliases are retired:

Retired fieldCanonical replacement
pixel_size_mmimage_sample_pitch_mm and solver_fine_pitch_mm
mesh_xy_pitch_mmimage_sample_pitch_mm and solver_fine_pitch_mm
color_pixel_mmcolor_region_target_mm

A non-null retired alias raises ResolutionSchemaLegacyFieldError. An alias present with null is dropped. ConfigPayload deliberately permits extra keys long enough for _payload_model_fields to identify retired fields and return a useful HTTP 422 response; unrelated unknown extras are ignored. Egress removes all three aliases defensively.

Canonical config also excludes eight retired no-op fields: smooth_iters, allow_print_despite_hazards, detail_cap_pitch_mm, v2_cleanup_de_budget, v2_enable_cliff_closure, v2_enable_cap_topology_cleanup, v2_max_cleanup_rounds, and v2_full_cap_quality_report. Old Settings Profiles and saved-run config carriers are normalized when they enter or leave the live state model, so these names do not reappear as active settings. Unrelated metadata dictionaries are not recursively rewritten.

Where normalization runs

normalize_resolution_schema runs at the external dictionary boundaries that can persist settings:

  • merged session updates in POST /api/session/config;
  • Settings Profile creation;
  • Settings Profile update; and
  • Settings Profile file loading.

For a profile payload or direct call to the normalizer, submitting only one member of the pitch pair is a conflict. The session endpoint first merges a partial request with the current session, so an omitted member can come from existing state; the merged pair must still agree.

Both typed config dataclasses call _apply_resolution_backstop in __post_init__. This backstop does not inspect legacy dictionary keys. It defaults the pitch pair only when both are absent, rejects a missing or disagreeing member, and defaults/coerces the independent color-region target.

The two schema exceptions are translated to structured HTTP 422 responses:

Exceptiondetail.errorAdditional fields
ResolutionSchemaLegacyFieldErrorlegacy_resolution_fieldfield, replacements
ResolutionSchemaConflictErrorresolution_schema_conflictboth field names and values

Other explicitly retired config fields use retired_config_field. Some deliberately quiet-dropped historical residue is logged and discarded instead.

Mandatory product settings

_force_mandatory_product_settings is applied on session updates, profile normalization/egress, and solve construction. _build_solve_config also passes several of the same values as literals, so a stale or hand-edited profile cannot turn them off.

SettingForced valueConsequence
model_domain_ingressTrueSource targets use the active library’s Camera Transform path.
enforce_printabilityTrueProduct printability enforcement runs.
cap_continuity_cleanupTrueCap continuity cleanup remains enabled.
color_region_target_from_printabilityTrueThe effective region target cannot fall below the nozzle-derived printability floor.
detail_cap_enabledTrueThe detail-cap stage cannot be disabled, although detail_cap_max_layers = 0 permits no optional detail height.
stage2_final_printability_gate_fine_overrideTrueThe final Stage-2 gate runs.
stage2_printability_gate_fine_overrideTrueThe Stage-2 gate runs.
stage2_printability_repair_fine_overrideTrueStage-2 repair runs.
stage4_printability_gate_detailTrueStage-4 detail authoring is gated for printability.

The same gate rounds d_wc_min upward to a whole number of layer-height steps. The normal UI expresses it directly as Min Cap Layers.

The Camera Transform path is not trusted from an archived run or stale Settings Profile at solve time. _build_solve_config resolves the path from the active published model library owned by the launcher.

Selecting Luminance mode also expands a preset. It forces the smooth boundary-cap mode, enables the luminance handler, sets its boundary-ceiling path, enables detail residual handling, and selects the final-gate luminance authoring policy. Returning to Color mode disables the luminance handler; the frontend restores its separately remembered Color-mode boundary-cap selection.

Settings Profiles and module state

Settings Profiles persist only _SETTINGS_PROFILE_KEYS, plus a separate snapshot of module enablement. They do not persist printer profiles, the active printer/nozzle selection, resolved minimum-width or minimum-length values, the selected image, palette deck, frame/crop state, image adjustments, border/export settings, or solve history. See Settings for Basic, named, and TEMP profile behavior.

The distribution ships two revisioned named-profile records under Prisma/data/generator/settings_profiles/refinement/: refinement-balanced and refinement-strong. On the first launch after this profile revision, the server removes the retired wing-c-minimal and wing-c-standard ids, installs the current bundled records into the Workspace profile store, and records bundled_profile_revision in state.json. The revision marker makes this a one-time migration, so a user may subsequently delete either optional profile without it reappearing on every launch.

Loading a profile is a two-part frontend/backend transition:

  1. write the profile’s config fields to the session; then
  2. replace the persisted module-state snapshot.

If the second write fails, the frontend attempts compensation with the prior config and module snapshot. This is not one backend transaction, so ordinary error compensation is stronger than hard-process-kill convergence.

Module toggles live in the Generator Workspace at config/modules.json, not inside session["config"]. server._MODULES_PATH resolves that file through data_paths.CONFIG_DIR; the checked-in generator/app/modules.json is not the production state file. Preprocessing parameter blocks do live in config. Cache identity includes all module enablement, but includes parameter blocks only for preprocessing modules that are enabled.

Solve-owned cache identity

_solve_owned_fingerprint hashes the settings and external state that can change solved output. This includes:

  • the coupled pitch pair, color-region target, and cap parameters;
  • palette, stack geometry, solver, gamut, correction, luminance, and region-refinement settings;
  • the selected image plus its frame and image adjustments;
  • active-nozzle printability data;
  • module enablement and enabled preprocessing parameters;
  • the selected appearance provider, configured model paths, and photo-stack predictor/domain contract versions.

Presentation/export-only settings such as the border are intentionally outside the solve fingerprint. Retired resolution aliases are absent because ingress rejects or removes them.

preprocessing_params remains canonical settings state and contributes to the fingerprint only for enabled preprocessing operators. The facade consumes each enabled operator’s block when it constructs the ordered instances; the pipeline receives those instances rather than another parameter copy.

Saved runs are different from Settings Profiles: a completed card and its archive may retain the resolved millimeter thresholds as historical solve provenance. Loading that result preserves those values on the loaded card. Any new solve uses the current active printer resolver and does not copy archived thresholds into printers.json.

Research and compatibility residue

Normal UI sync explicitly keeps emit_pressure_diagnostics and emit_geometry_attribution off; scripts or direct API callers may enable those heavier diagnostic products. emit_blueprint_printability remains on for product solves.

Several lower-level dataclass defaults differ from the web-app defaults because those constructors also serve tests and compatibility paths. Documentation of normal Generator behavior should begin with _DEFAULT_CONFIG, the UI serializer, and _build_solve_config, then follow pipeline.runner into pipeline.staged.orchestration—not infer product behavior from a dataclass fallback or the thin pipeline.staged_runner facade in isolation.
