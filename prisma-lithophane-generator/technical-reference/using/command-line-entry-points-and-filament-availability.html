Command-line entry points and filament availability

Command-line entry points and filament availability

Properties1
tagsgenerator, cli

Jul 16, 20266 min read

In one sentence: the supported way to run Generator from source is the Prisma launcher, which establishes the portable filesystem and active-library contract before importing the server; evaluation and palette-suggestion CLIs are internal developer tools, while new palette and solve work is gated by the active published library and the user’s per-library filament selection.

This page distinguishes three things that are easy to conflate: starting the actual product from source, invoking internal command-line modules, and deciding which published filaments may enter new work.

Related: Driving the Generator · Settings, resolution, and the config contract · How a Solve Works · generator.facade · generator.filament_policy

Supported source entry point

The product entry point is Prisma.launcher, not uvicorn server:app and not either of the solver-oriented scripts below. The launcher:

  1. resolves and prepares a portable application root;
  2. acquires the Generator Workspace lock;
  3. conservatively removes exact, ordinary abandoned export stages while preserving unrecognized or link-like lookalikes;
  4. validates the selected published model library or enters Library Recovery;
  5. supplies the explicit Images, Exports, Workspace, model-store, and active-library environment contract;
  6. starts the local FastAPI server on the first available port beginning at 8010; and
  7. connects the in-app restart action to a fresh launcher process.

Use the current commands in the repository README.md. The --app-root directory must already exist; the README creates it before invoking the launcher. Directly importing generator/server.py, running Uvicorn from the Generator folder, or importing data_paths.py from a clean shell fails deliberately because no launcher-selected Workspace or published library has been supplied.

In a normal source launch, switching libraries can use the in-app restart action because the launcher installs the restart callback. A hand-started Uvicorn server has no callback and can only tell the user to close and reopen Prisma.

Internal command-line modules

The repository contains two command-line-shaped developer modules, but neither is an alternative end-user distribution path.

ModulePurposeProduction status
tools.generator.evaluation.preprocessing_eval_cliA/B evaluation wrapper around the live facade/staged solverDeveloper/evaluation harness only
generator/palette/suggest.pyPalette-suggestion development CLIDeveloper tool; the web app calls the suggester through server routes

The evaluation module defers Generator imports until after argument parsing, so python -m tools.generator.evaluation.preprocessing_eval_cli --help works from a clean repository shell without selecting or writing a runtime. A real evaluation still imports the live facade and needs an intentionally selected developer runtime and explicit published-library profiles. The palette-suggestion module likewise remains developer tooling rather than an alternative product launch path.

Shared product helpers

The shared helpers formerly embedded in the retired batch CLI now have product-specific owners:

OwnerLive role
image_ingress.load_imageEXIF-aware image load, framing, transforms, and resampling for solves and palette suggestion
image_ingress.apply_adjustmentsExposure, contrast, saturation, tint, highlight, shadow, and temperature adjustments
filament_policy.validate_paletteProfile-presence and generation-availability validation in the staged runner

The obsolete batch parser and its alternate solve orchestration have been removed. The sole product solve path is facade.solve_full() → pipeline.runner.run_pipeline() → the staged backend.

Preprocessing evaluation harness

tools.generator.evaluation.preprocessing_eval_cli builds a real SolveConfig and delegates to tools.generator.evaluation.preprocessing_harness.evaluate_pair. It solves a baseline and candidate image under one configuration and can optionally write predicted images, a delta-dE heat map, and report.json. The harness itself is tested and is also called by evaluation scripts; the wrapper is a developer leaf outside the shipped product package, not a UI or release entry point.

Published-library filament contract

Generator reads one immutable published library selected by the launcher. A standard library is valid only when its manifest, exact file set, hashes, filament registry, v1 spline artifacts, v2 photo-stack deployment, and Camera Transform deployment all validate together. A profile file copied into some other folder is not enough to make a filament usable.

Each public filament record currently carries both:

  • exclude_from_model, the calibration/publication policy flag; and
  • generation_available, a public convenience field emitted as the inverse of that flag.

The current Generator policy implementation still treats exclude_from_model as authoritative and derives the API’s generation_available value from it. In libraries produced by Calibration the two values agree. The stored convenience field is therefore redundant today; it is not an independent override.

Backend gate for new work

filament_policy.py defines the common rule used by validation, suggestion, and solving:

  • exclude_from_model: true means unavailable for new Generator work;
  • profile presence is checked separately;
  • an unavailable fixed white base or cap is a hard error for suggestion and solving; and
  • color candidates that are unavailable are removed from suggestion before search.

POST /api/palette/validate reports missing profiles and policy-unavailable filaments separately, but it is only an advisory pre-check. The staged solve validates again before doing work. Existing saved-run arrays are not destroyed merely because a filament later becomes unavailable; any new solve is evaluated against the currently active library.

Unknown filament ids are not made safe by the policy helper’s permissive default. They still fail the profile and active-library checks before a solve can use them.

Browser-side Active Filaments gate

The Active Filaments control is a second, user-owned filter over the library’s eligible color filaments. It determines which filaments appear in palette-building and suggestion surfaces; it does not mutate the published library.

The browser stores this choice in localStorage, keyed by the runtime active library id:

  • the first time a library is seen, all eligible filaments are enabled;
  • a user’s disabled subset persists through reloads and relaunches for that library;
  • if a previously seen runtime library id presents additional eligible ids, those newly eligible ids are enabled by default; and
  • ids no longer eligible are removed from the saved selection.

The frontend accepts a color filament only when it has a profile, is not excluded, is not reported unavailable, and is in the enabled set. The base/cap selectors are stricter: their candidates must additionally have white_cap_eligible: true. The backend remains authoritative and revalidates when work starts, so stale browser storage cannot bypass the model policy.

Two unrelated exclusion helpers

Generator’s filament_policy.excluded_filament_ids(registry) gates new generation from a published registry. Calibration’s fitting.filament_exclusions.excluded_filament_ids(store) removes excluded evidence from model fitting. They read the same conceptual flag but accept different inputs and protect different workflows.

Source-truth boundary

  • Use Prisma.launcher to run the application from source.
  • Treat evaluation wrappers as developer harnesses: clean help is runtime-independent, but actual evaluation requires an explicitly bootstrapped runtime.
  • Treat the active published library as model truth.
  • Treat Active Filaments as a per-browser, per-library palette filter, not as a model mutation.
  • Expect every new solve and suggestion to be revalidated by the backend.
