Driving the Generator

Driving the Generator

Properties1
tagsgenerator, webapp

Jul 14, 202613 min read

In one sentence: the generator web app (port 8010) is a four-step wizard backed by a FastAPI server that runs every long job — solve, palette suggest, palette compare, export — in a background thread on a single module-level session dict, which the browser drives by start-then-poll and which makes the whole app strictly single-user, one-job-at-a-time.

This page serves two readers: the user who wants to drive the app end to end (pick an image, build a palette, solve, review, compare, export), and the developer who has forgotten the backend’s job model — how a click becomes a background thread, how progress reaches the screen, and why two browser tabs will fight each other. It stays at endpoint-contract altitude; for what happens inside a solve see How a Solve Works and The Joint LUT and Staged Solve.

Related: How a Solve Works · Pipeline Map · Exporting Print Files · Settings, resolution, and the config contract · Command-line entry points and filament availability · generator.facade · generator.filament_policy

Starting the app

In a packaged Generator-only release, double-click Prisma.exe. In the shared Suite, double-click Prisma Generator.exe. The launcher creates the portable folder layout, selects and validates the active immutable model library, starts the local server on port 8010, and opens the browser. Keep the console window open while using Prisma; closing it stops the server. See Launching Prisma for the user-facing procedure.

server.py builds one FastAPI instance (server.py:333) titled “Prisma — Lithophane Generator API”, wide-open CORS for development (server.py:340), and — as the last mount so it doesn’t shadow the API — serves the single-page app from generator/app/ with html=True so / resolves to index.html (server.py:6276). All JSON routes live under /api/...; everything else is the static frontend (app.js, style.css, data.js).

Developers running from source may still invoke Uvicorn directly, but that is not the distribution path and the Generator’s data-path contract expects the launcher-provided environment. The stale command in the server.py module header is not end-user guidance.

The wizard at a glance

The frontend is a four-step bar (index.html:64-77): 1 Image → 2 Palette → 3 Preview → 4 Export. The steps map to backend route families like this:

Step (UI label)What you doPrimary endpoint(s)
1 ImagePick / upload a source imageGET /api/images, POST /api/images/upload
2 PaletteAuto-suggest, compare, or hand-build a palettePOST /api/palette/suggest, POST /api/palette/compare, POST /api/gamut-preview, POST /api/palette/validate
3 PreviewKick off the full solve and review the resultPOST /api/solve/start, GET /api/solve/status
4 ExportGenerate STL/3MF print files + AMS swap planPOST /api/export/files/start, GET /api/export/swap-instructions

A persistent Palette Deck, Model Library, Active Filaments, and Printer configuration area lives in the left rail and is separate from the linear workflow. Use Model Library → Manage to manage complete published model libraries; that remains separate from choosing which filaments appear in palette tools.

The job model (read this if you are the developer)

One global session, one process

All mutable app state is a single module-level dict, session (server.py:474), created once at import. It holds the live config, the current solve slot, an in-RAM solve_cache keyed by card_id, and one slot each for compare, suggest, and export. Each long-running slot is a small state machine on a status string: idle | running | complete | error | cancelled (e.g. server.py:477).

Because this state is process-global and not keyed by user or browser session, the app is single-user by construction. Two tabs share the same session; a solve started in one tab is visible (and cancellable) from the other, and GET /api/session (server.py:2634) returns the same config and solve status to everyone.

Start, then poll

No endpoint blocks for the duration of a long job. The pattern is always: a POST .../start validates inputs, sets the slot’s status to "running" synchronously before returning (so an immediately-following request sees the job as active), spawns a daemon threading.Thread, and returns {"job_id": ..., "status": "running"}. The browser then polls a matching GET .../status on an interval until status leaves "running".

Each /status route reads the slot and returns status, a progress string (the current stage_label), a richer progress_detail dict, elapsed_s, and — once finished — the result payload (e.g. server.py:5383-5394). The status endpoint is a pure read; it never advances the job.

One job at a time

Each start endpoint refuses to run on top of itself with HTTP 409: solve guards on if session["solve"]["status"] == "running" (server.py:4656), and suggest/compare/export do the same on their own slots (server.py:3758, :4058, :5670). There is no global “only one of any kind” lock at start time, but the cache-management and run-load endpoints call _assert_no_active_job() (server.py:5926), which raises 409 if any of solve/export/compare is running — so you cannot, for example, clear the cache or load a saved run mid-solve.

Internally each background worker grabs a module-level lock (_solve_lock, _compare_lock, _suggest_lock, server.py:521-523) for the body of its run, so the heavy numeric work is serialized even if the 409 guard were bypassed.

Cancellation is cooperative

Cancel endpoints don’t kill the thread — they set a cancel_requested flag on the slot (server.py:5403). The worker’s progress callback checks that flag and raises a sentinel (SolveCancelled / ExportCancelled) on the next progress tick, which the worker catches and turns into status = "cancelled" (e.g. server.py:5364). So a cancel only lands at the next progress checkpoint, not instantly. Compare has a cancel_requested flag honored in its progress callback (server.py:4086) but, as of this code, no dedicated cancel route.

Step 1 — Picking an image

GET /api/images (server.py:2554) lists files in the images dir filtered to a fixed extension allow-list — .png .jpg .jpeg .tif .tiff .bmp .webp (server.py:2551). POST /api/images/upload (server.py:2566) accepts a multipart upload, rejects unsupported suffixes with 400, sanitises the filename to its basename (path-traversal guard), auto-suffixes _1, _2, … to avoid overwriting, then re-opens the saved file with Pillow to confirm it is a real image (deleting it and returning 400 if not). GET /api/images/preview/{filename} (server.py:2610) streams an EXIF-transposed, max-800px JPEG thumbnail for the gallery.

Selecting an image writes image_path into the session config (via the config endpoints — see Settings, resolution, and the config contract); the solve later resolves it against the images dir and 404s if it has gone missing (server.py:4666-4668).

Step 2 — Building a palette

There are three ways to arrive at a palette, plus a cheap validity pre-check. All of them respect the exclude_from_model generation-availability gate documented in Command-line entry points and filament availability and generator.filament_policy.

Validate (instant, advisory)

POST /api/palette/validate (server.py:3487) is a synchronous pre-check: it returns missing (no spline profile on disk) and unavailable (flagged exclude_from_model) as separate lists, plus a combined valid boolean (server.py:3502). It is advisory only — the solve path re-validates regardless.

Gamut preview (synchronous, one palette)

POST /api/gamut-preview (server.py:3972) is the one palette operation that runs inline rather than as a background job. It accepts an optional palette override so the UI can probe a non-active deck palette without mutating the session (server.py:3972-3979), runs a preview-quality solve, and returns coverage %, out-of-gamut count, mean/max dE, and URLs to freshly-baked preview PNGs (dE map, gamut overlay, source, predicted) with a cache-busting ?t= suffix (server.py:4013-4027).

Auto-suggest (background job)

POST /api/palette/suggest (server.py:3746) launches the suggester in a thread. Suggestion is always thorough now — the old fast/quality switch was removed, and unknown legacy fields are rejected loudly with 422 (server.py:3511-3515). Two modes:

  • Plain top-K (max_swaps unset): returns the best top_k palettes of n_filaments colors.
  • Swap-aware tiers (max_swaps set): sweeps AMS swap tiers honoring ams_slots, n_ams_units, and reserved white_slots from config (server.py:3891-3908).

Before any model loads, the endpoint hard-rejects (400) if the configured white base/cap is itself excluded from generation, because the suggester can drop color candidates but not the fixed whites (server.py:3766-3774). Excluded color candidates are filtered up front via excluded_filament_ids (server.py:3886). The start response supplies a job id used by status polling and cancellation. Cancel is a durable request for that active job: the UI stays attached and keeps polling until the worker reports cancelled, complete, or error.

Compare (background job, N palettes side by side)

POST /api/palette/compare (server.py:4044) takes a list of palettes and solves each at preview quality via solve_compare (server.py:4094, defined facade.py:992), then writes per-palette diagnostic PNGs (compare_<idx>_predicted.png, cap maps, surface maps) into the shared run-cache dir. A palette that errors comes back as an {"error": ...} entry rather than failing the whole batch (facade.py:1031). Poll GET /api/palette/compare/status (500 ms). This is how you A/B several candidate palettes before committing one to the full solve.

Preview ≠ full. Suggest and compare use the COMPARE_PRESET / preview path; the Step-3 solve uses the FULL_PRESET path. Numbers from compare are directional, not the final solve’s metrics.

Step 3 — Solving

Kicking it off

POST /api/solve/start (server.py:4653) validates that an image and a palette exist (the palette can be overridden in the body, else it comes from config; server.py:4662), snapshots the config so mid-solve setting changes can’t perturb the running thread (server.py:4671), mints an 8-char job_id, sets solve.status = "running" synchronously, and spawns the worker. The body may carry a card_id (for per-run caching), a profile_ref / recipe_snapshot (provenance recorded into the run metadata), and a palette override (SolveStartPayload, server.py:4398).

What the worker actually runs

The worker (_run_solve, server.py:4688) resets the solve slot, loads the source image through the shared loader, then calls solve_full(...) (server.py:4740, defined facade.py:967).

The product solve is the staged backend, not the CLI engine. solve_full → run_pipeline (facade.py:988) → run_staged_backend_path (pipeline/runner.py:846, defined pipeline/staged_runner.py:10310). It does not use pipeline_cli.run()’s legacy “6-step” engine — that engine is unwired from the product (see Command-line entry points and filament availability and Pipeline Map).

Progress detail

Inside the worker, a _progress(msg) closure (server.py:4732) both checks the cancel flag and writes the latest stage into solve["progress"] — accepting either a bare string or a dict carrying stage_label/stage_pct. That dict is exactly what GET /api/solve/status surfaces as progress_detail, so the UI’s progress bar is driven by whatever the staged backend reports. On completion the worker logs a one-line SOLVE_PHASE_TIMINGS JSON of coarse phase durations (server.py:5352).

What lands when it finishes

On success the worker writes a large pile of diagnostic artifacts into the run-cache dir (predicted/source/reference PNGs, dE maps, per-filament thickness maps, white-cap and color-ceiling/total-surface maps, contour blobs, recipe-breakdown artifacts), then assembles a JSON-safe solve["result"] dict of metrics plus /api/run-cache/files/... URLs (built from server.py:5148). The headline metrics include mean_de, source_rms_de, max_de, coverage_pct, out-of-gamut count, image dimensions, and max_height. Every URL carries a cache-bust query (?run=<card>&t=<epoch>, server.py:5007) so the browser fetches fresh images for each run. The worker also records a solve_owned_fingerprint (server.py:5344) — a hash of the solve-coupled settings — which export later checks for staleness.

Reviewing the result

The frontend reads solve["result"] from the status poll and renders the predicted render, the dE heatmaps, the per-filament thickness maps, the color-ceiling / total-surface views, and the recipe breakdown (which colors compose which regions — the Color Ceiling / Recipe Viewer sub-tab). The blocky look of the predicted render is intentional: it honors the true solve resolution and never fakes smoothness the print won’t have. Binary .bin blobs of the thickness/surface fields are served alongside the PNGs for the interactive viewers.

Auto-archiving

If the solve carried a card_id, on completion the worker writes a completed-solve cache entry and then _maybe_write_auto_run(...) (server.py:5357, defined :6059) silently packs the run into the auto-runs archive tier (labeled Auto <timestamp>). This is best-effort — failures are logged and swallowed, never failing the solve.

Step 4 — Exporting print files

The full mesh + serialization details live in Exporting Print Files; this is the driver’s view.

Two export entry points

POST /api/export/files (server.py:5651) runs the export synchronously and is retained for direct API callers and tests. The UI uses the background variant POST /api/export/files/start (server.py:5666), which threads the same _perform_export_files worker with a progress callback, then polled via GET /api/export/files/status (500 ms) and cancellable via POST /api/export/files/cancel.

What export needs from the solve

_perform_export_files (server.py:5432) refuses with 400 if there is no complete solve to export, and — when exporting the current solve (no explicit card_id) — refuses with 409 if the solve is stale: it recomputes _solve_owned_fingerprint(cfg) and rejects if it differs from the fingerprint captured at solve time, telling you to re-solve first (server.py:5443-5450). Export options come from ExportFilesPayload (server.py:742): geometry_source (default field_derived), field_scale (one of 2/4/8/16, default 4), and output_format (stls or 3mf, default 3mf).

Swap instructions and downloading

GET /api/export/swap-instructions (server.py:5774) returns the AMS swap plan — grouped filament bands with z-ranges and slot assignments, human-readable instructions, and OrcaSlicer pause G-code (server.py:5848). It reads the currently selected AMS capacity (ams_slots/white_slots) rather than whatever was active at solve time, since AMS capacity is export-time printer state (server.py:5797-5802). Generated files are downloaded as a zip via GET /api/export/files-zip (server.py:5855), or served individually under GET /api/export/files/{path} (server.py:5897). Run-cache diagnostics are served by GET /api/run-cache/files/{path} (server.py:5912); both use _safe_path to reject traversal.

Saving, loading, and comparing runs

Beyond the per-job state there is a small archive layer (Stage 9b) for keeping runs around:

ActionEndpointNotes
Save current runPOST /api/runs/save (server.py:6073)packs the cached solve into the user-curated saved tier
List runsGET /api/runs/saved (server.py:6086)merges saved + auto tiers, newest first, each tagged tier
DownloadGET /api/runs/saved/{id}/download, .../auto/{id}/download (server.py:6095, :6106)streams the run zip
Promote auto → savedPOST /api/runs/auto/{id}/promote (server.py:6117)guarded by _assert_no_active_job()
Rename / deletePOST .../rename, DELETE .../{id} (server.py:6127, :6135)delete returns 409 if the file is locked
Load by idPOST /api/runs/load (server.py:6242)tier is "saved" or "auto"; both rehydrate via the same path
Load from uploadPOST /api/runs/load-upload (server.py:6256)multipart zip, size-capped before the full read

Loading rehydrates the archive into a fresh card_id, restores the whole run-cache subtree to disk, rewrites every ?run= URL to the new card, and installs a complete entry into session["solve_cache"] (_rehydrate_loaded_archive, server.py:6176) — so a loaded run behaves like a just-finished solve for review and re-export. Both load routes are gated by _assert_no_active_job() so you cannot load over a running job.

Caches you can clear

POST /api/cache/clear-runs (server.py:5933) sweeps the run-cache and auto-run archives plus the in-RAM solve_cache, keeping LUTs, output, and user-curated saved runs. POST /api/cache/clear-all (server.py:5950) additionally drops the LUT cache. Both first call _assert_no_active_job().

Single-user caveats (what will bite you)

  • Two browser tabs share one backend. The session dict is process-global (server.py:474); there is no per-client isolation. A second tab sees and can cancel the first tab’s solve.
  • One job per kind at a time. Starting solve/suggest/compare/export over a running one of the same kind returns 409 (server.py:4656, :3758, :4058, :5670). Cache-clear and run-load return 409 if any of solve/export/compare is running (server.py:5926).
  • Cancellation is deferred, landing only at the next progress checkpoint (server.py:4733-4734).
  • Mid-solve setting changes are ignored for the running solve — config is snapshotted at start (server.py:4671) — but they will make the result stale, and export/swap-instructions will 409 until you re-solve (server.py:5443).
  • Local desktop server, not a hosted multi-user service. Single process, daemon threads, and in-RAM state are lost when the packaged launcher restarts the server (saved-run archives on disk survive). The launcher binds locally and opens the browser; it is not intended for network hosting.
