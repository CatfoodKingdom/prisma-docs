Driving the Generator

Driving the Generator

Properties1
tagsgenerator, webapp

Jul 26, 20269 min read

In one sentence: Generator is a local, single-process four-step web app whose launcher establishes one portable runtime and one active model library, while the server keeps process-global UI/job state and coordinates independently admitted solve, suggestion, export, and model-library workflows.

This page follows the browser-to-server contract. For the staged solve itself see How a Solve Works and The Joint LUT and Staged Solve; for export internals see Exporting Print Files.

Starting the application

In a packaged Generator release, start Prisma.exe on Windows or Prisma on Linux; in the Suite, start Prisma Generator.exe on Windows or Prisma Generator on Linux. The platform-specific executables enter the same Python launcher contract:

  • anchors the portable Generator tree beside the executables;
  • takes the Workspace lock;
  • reconciles interrupted export/model-install stages;
  • validates the selected immutable model library or enters Library Recovery;
  • starts FastAPI on loopback only; and
  • opens the browser.

Port 8010 is preferred, not guaranteed. If it is occupied, the launcher reserves the first available port through 8029 and prints/opens the actual 127.0.0.1 address. A second launch against the same Workspace reopens the owned instance rather than starting a second server.

From source, use python -m Prisma.launcher --app-root <existing-runtime-folder> after installing the declared Generator runtime group. The repository README gives the exact Windows and POSIX commands. Do not start uvicorn server:app as the normal source path: the server imports require launcher-provided model-library, Workspace, Images, and Exports roots, and direct Uvicorn also lacks the in-app restart callback.

Current evidence is platform-qualified: the source launcher and active-library selection have been health-smoked under Ubuntu 24.04/WSL2 as well as Windows, and the Linux x86-64 package is built in that environment. The POSIX lock, loopback socket, browser fallback, and macOS open branches have been statically audited, but no Mac has run Prisma and no macOS support is claimed.

The launcher treats Ctrl+C as a normal shutdown and prints Prisma stopped.. Closing the console stops the server. The app is bound to the local host and is not designed as a remotely hosted multi-user service.

Interface structure

The main workflow is:

  1. Image — choose or upload source artwork.
  2. Palette — enable candidate filaments, request suggestions, or build one manually.
  3. Preview — run the full solve and inspect predicted, cap, surface, thickness, contour, and recipe data.
  4. Export — select a solved run and generate one or more print-file variants.

The left rail owns infrequent configuration and persistent working controls: Palette Deck, Model Library, Active Filaments, and Printer/nozzle configuration. Model Library → Manage installs complete published bundles and selects the library for the next launch. Active Filaments is only a per-browser filter over eligible filaments in the runtime library.

The static shell loads one native-module entrypoint and an ordered stylesheet manifest. Feature modules own their state, events, and asynchronous lifecycles; the Theme controller is browser-local and does not enter server configuration. See Frontend architecture for the maintained browser-code map.

Process-global state

server.py creates one module-level session dictionary. It contains the editable config, current solve, in-memory solved-run cache, and separate job slots for suggestion and export. This state is not keyed by browser or user.

Consequences:

  • two tabs see and mutate the same session;
  • a job started in one tab is visible from the other;
  • in-memory current/solved-run state disappears when the process restarts; and
  • disk-backed settings, caches, Images, Exports, and saved-run archives survive according to their own lifecycles.

This makes Generator single-user, but it does not mean the backend globally serializes every different long-job type.

Background jobs and admission

The UI uses start-then-poll workflows for solve, palette suggestion, and export. A start route validates input, reserves its job slot synchronously, assigns a job id, launches a daemon worker thread, and returns. A status route is a read-only snapshot; it does not advance work.

Image preparation uses one worker, and repeated folder refreshes coalesce into the active scan. It pauses queued conversion work while solve, export, suggestion, or model-library operations need priority. Each numeric job kind refuses another active job of the same kind. Solve and suggestion also use separate worker locks to prevent two workers of that same implementation from executing simultaneously. There is no one global numeric-work lock across different kinds: for example, the current admission model can allow a solve and a suggestion to overlap.

All three registered background-job kinds reserve against model-library mutation/restart. Conversely, installing, activating, removing, or restarting refuses to begin while solve, export, or suggestion is running or cancelling. Cache clearing and saved-run loading use the same active-job check. This protects those registered jobs and their filesystem ownership without claiming broader serialization than the code provides.

Cancellation

Cancellation is cooperative. It does not terminate a Python thread:

  • Solve and suggestion cancel requests are tied to the active job id and set a flag checked at progress/safe checkpoints. The browser remains attached until a terminal status arrives.
  • Export changes immediately from running to cancelling, reports Cancelling after current safe point, and becomes cancelled after the worker acknowledges it. If publication finished before the request could land, it may validly report Completed before cancellation took effect.

The practical latency is therefore bounded by the next checkpoint, not the button click. Export cancellation also owns cleanup of its hidden stage; hard process termination is recovered on the next launcher start.

Step 1 — Images

GET /api/images lists only ready files in Generator/Images. Native sources are PNG, JPEG/JPE/JFIF, TIFF, BMP, and WebP. HEIC/HEIF/HIF and AVIF are conversion-required sources: generator.source_images validates their signatures, applies EXIF orientation and supported ICC/NCLX color information, then atomically caches a lossless 8-bit sRGB PNG under Workspace/cache/source-images. Originals are never rewritten. Animated AVIF and HDR-only PQ/HLG sources are rejected.

The UI sends multi-file additions to POST /api/images/import; uploads stream into private staging, are validated independently, and are published into Images only after successful preparation. Collision suffixes preserve every accepted original. POST /api/images/refresh discovers copied files, while GET /api/images/imports/{batch_id} exposes the bounded single-worker batch status. The legacy POST /api/images/upload remains a synchronous single-file compatibility route.

Previews are JPEG thumbnails made from the resolved working image. The selected original filename remains the session identity; preview, suggestion, solve, and archive creation all resolve it through the same service. Cache entries are keyed by source stat, SHA-256, and normalization version, recover from corruption, and are capped by LRU size. The UI can open the visible Images folder through the local-only folder-opening route.

Step 2 — Palette work

All new palette work is limited by the active published library and the user’s Active Filaments subset. See Command-line entry points and filament availability.

Validation

POST /api/palette/validate separates missing profiles from policy-unavailable filaments. It is advisory; suggestion and solve validate authoritatively again.

Suggestion

Suggestion is a background job. Plain mode returns top palettes of the requested size; swap-aware mode explores additional color-load tiers against AMS/white-slot capacity. An unavailable fixed base/cap is rejected before search, while unavailable color candidates are filtered out. Cancellation is durable at the job level: the UI polls until the backend reports a terminal state.

Step 3 — Solve and review

POST /api/solve/start requires a valid active library, source image, and nonempty palette. It snapshots the current config before starting so later UI edits cannot mutate the running solve. It also blocks a solve whose pitch is smaller than the active nozzle diameter.

The server canonicalizes filament order, constructs a typed SolveConfig, assigns the card/job identity, and runs facade.solve_full() through the staged backend. Structured progress covers source preparation, pipeline stages, and artifact publication.

On success, the run cache receives predicted/reference/source images, error and gamut maps, per-filament and cap/surface fields, contour binaries, recipe breakdown/cookbook data, and export-owned solved arrays/metadata. The result payload exposes cache-busted URLs plus physical and diagnostic metadata. A completed card is also best-effort auto-archived; failure to auto-save does not fail the solve.

The server captures a solve-owned settings fingerprint. Changing solve-owned settings after completion does not mutate the solved arrays, but it can make the current result stale for actions that require the current settings to match. A selected saved/loaded solved card owns its archived solve data separately.

Step 4 — Export

The browser uses the background export start/status/cancel workflow. Export operates on a selected completed solve, stages all output outside the visible completed-export namespace, then publishes one completed directory. Different format/method/detail variants of the same solved run remain separate export records in the session UI.

The export result owns its generated files, mesh report/checks, and swap instructions. The UI can open the visible Exports folder or download the selected export as a ZIP. Full geometry, 3MF/STL, cancellation, and process-kill semantics are audited in Exporting Print Files and the Output reference pages.

Model-library lifecycle

GET /api/model-libraries distinguishes:

  • the library loaded by this running process;
  • the library selected for the next launch;
  • whether restart is required; and
  • installed-but-invalid directories with their validation errors.

Install uploads to Workspace cache, extracts/copies into a hidden UUID staging directory, validates compatibility and the complete standard-library contract, then renames it to its manifest UUID. Activating a library atomically writes the next-launch selection but does not hot-swap model objects. Restart is allowed only when the selected entry is valid and different from the runtime library.

The running library and selected-next-launch library cannot be removed. The frontend asks for confirmation before removal. Library Recovery opens the manager automatically because model-dependent work is unavailable until a valid selection has restarted successfully.

Saved runs and cache actions

Saved and automatic runs can be listed, previewed, downloaded, renamed, deleted, promoted, or loaded according to their tier. Whole-run loading validates and rehydrates archived arrays into a fresh session card; settings-only loading creates a non-persisted TEMP profile and does not restore solved arrays. Active long jobs block loading and promotion.

Clear Cache is the sole cache-administration action. It removes run cache, automatic runs, LUT files, prepared source-image PNGs, in-memory solved cards, and in-memory palette-backend cache while preserving user-curated saved runs, original Images, Exports, config, and logs. It is refused while any coordinated long job or image import is active. Prepared images rebuild on the next explicit refresh or on-demand resolution.

Operational caveats

  • Use one browser session; tabs share state.
  • Expect one job per kind, not one job globally.
  • Wait for terminal acknowledgement after cancellation.
  • Use the launcher so paths, locking, recovery, and in-app restart work.
  • Treat the local console as the lifetime of the server.
