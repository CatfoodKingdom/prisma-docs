The photo-stack v2 model

In one sentence: the photo-stack v2 model is the context-aware colour predictor the generator can use instead of the spline model — a calibration fitter writes a self-contained runtime bundle, the generator resolves the latest live bundle, and a multi-stage predictor (plus an optional residual correction layer) turns a physical layer stack into a backlit colour.

This is the model behind the photo_stack_bundle appearance backend. Where the spline model treats a stack’s colour as the product of independent per-filament curves (see The Transmission Model), photo-stack v2 is context-aware: the same blue layer predicts a different colour depending on what is above it, below it, how much white caps it, and which other colours sit alongside it. That context-sensitivity is exactly why it cannot be reduced to per-filament profile JSONs and must enter through the Appearance provider boundary.

If you just want to drive it, read “How to drive it” then skip to “Live vs reference”. If you are the developer who forgot how the backend works, read the whole thing.

How to drive it (for users)

You never call this model directly. You select it through the Appearance provider:

  • Set appearance_model_provider = "photo_stack_bundle".
  • Point photo_stack_bundle_path at a live calibration candidate directory (or its runtime_bundle.json). This is mandatory; there is no implicit default for a real solve.
  • Optionally set use_corrections (the direct-vs-corrected toggle — covered below under “The residual correction layer”).

The model comes from running a calibration fit, not from editing any file by hand. The fitter (Prisma/calibration/fitting/photo_stack_model/) photographs swatch stacks, fits the model, and publishes a candidate; the generator then resolves the newest published candidate automatically when you don’t pin an explicit path.

Producer → artifact → consumer

The model is a hand-off across two apps that share no runtime code:

RoleWhereWhat it does
Producer (fitter)Prisma/calibration/fitting/photo_stack_model/ (live_fit.py, fit_job.py, write_artifact.py)Fits the model from photographed swatch stacks and publishes a candidate run directory.
Artifact (bundle + siblings)Prisma/data/filaments/photo_stack_models/<run_id>/A self-contained, research-independent JSON payload the runtime can load without importing any fitter code.
Consumer (generator)generator/appearance_model.py → lib/photo_stack_model/predictor.pyResolves the latest live bundle and scores stacks during a solve.

The package header states the contract plainly: “the bridge between the research fitter and Prisma runtime code: research code may create it, but webapp/runtime code must be able to load it without importing any research package” (lib/photo_stack_model/bundle.py:3).

The candidate directory

A published run is a directory of fixed-named files (ARTIFACT_FILES, lib/photo_stack_model/artifacts.py:18):

FilePurpose
runtime_bundle.jsonThe validated bundle the predictor consumes.
model.jsonThe fitted model + manifest-level live-fit flags.
correction_layer.jsonThe residual kNN correction artifact (sibling, applied only when corrections are on).
metrics.json, fit_log.json, review_summary.json, evidence_summary.json, sample_predictions.jsonDiagnostics / review data.
manifest.jsonRun identity: model_family, model_version, run_id, timestamps, fingerprints.

Publishing is atomic: everything is written to a .tmp-<run_id> directory, every required file is validated, and only then is the directory renamed into place and latest.json advanced (write_candidate_artifact, artifacts.py:226–artifacts.py:332). A candidate without a validated runtime bundle is refused outright (artifacts.py:300). After a successful publish, superseded run directories are garbage-collected down to the survivor (_gc_superseded_runs, artifacts.py:178; keep=1, so only the live model survives — without it every ~63 MB run leaked forever, artifacts.py:182).

How the generator resolves “the live candidate”

latest.json is a pointer file holding the survivor run_id (artifacts.py:36, artifacts.py:306). The generator resolves it through latest_live_candidate_dir → latest_live_runtime_bundle_path (artifacts.py:124, artifacts.py:139). The server wraps this in _resolve_photo_stack_candidate_path_for_solve (server.py:959): an explicit photo_stack_bundle_path is validated; otherwise it falls back to latest_live_candidate_dir(_DATA_DIR) (server.py:979). This resolution runs live on every photo-stack solve — confirmed by grep, not assumed: the resolved path flows into the SolveConfig at server.py:1012 and then into the main create_appearance_provider(...) call at runner.py:670; the white-rescale pass also reconstructs the provider via a second create_appearance_provider(...) call (server.py:3803).

Live vs reference

There are two bundles, and the distinction is enforced in code, not just convention.

  • Live — a freshly fitted candidate carrying live_fit_source_of_truth: true and artifact_role: "live_calibration_fit" (set by the fitter at Prisma/calibration/fitting/photo_stack_model/live_fit.py:408, from LIVE_ARTIFACT_ROLE at live_fit.py:50). This is the only kind a real generator solve will accept.
  • Reference / replay — the checked-in default at lib/photo_stack_model/bundles/runtime_bundle.json, loaded by load_default_photo_stack_bundle (default_bundle.py:18). It is a point-in-time snapshot for replay/comparison and bootstrapping.

The guard validate_live_runtime_bundle_path (artifacts.py:80) rejects a bundle that is marked replay (live_fit_source_of_truth is False or artifact_role == "point_in_time_reference_replay", artifacts.py:73) or that is not positively marked live (artifacts.py:94); it also checks the candidate’s model.json carries live_fit_bundle_generated: true (artifacts.py:100). validate_live_candidate_dir (artifacts.py:107) additionally requires a valid correction_layer.json schema beside it.

Liveness check on the reference bundle: grep finds load_default_photo_stack_bundle used only in tests and the package README within the product tree — never in the live generator solve path or calibration runtime. So the checked-in default really is reference-only; the live solve always goes through a calibration candidate.

The runtime bundle contract

Before any runtime code trusts a bundle, validate_photo_stack_bundle_payload (bundle.py:125) checks its shape. The version knobs at the top of the bundle:

FieldValueMeaning
schema"prisma_photo_stack_v2_runtime_bundle" (bundle.py:16)Bundle format identity.
schema_version1 (bundle.py:17)Bundle format version.
runtime_constants_version"photo_stack_v2_2026_06_09" (bundle.py:18)The frozen-constants epoch; a mismatch is rejected (bundle.py:132).
fingerprintnon-empty string (bundle.py:137)Identity used in caching / fingerprints.

The bundle’s model object must contain a fixed key set (REQUIRED_MODEL_KEYS, bundle.py:22): the per-channel optical-density curves, the fallback curve, and one parameter block per prediction stage. Each stage block has a required-field contract (REQUIRED_PARAM_FIELDS, bundle.py:40) — e.g. white_context needs white_gamma/white_tau; endpoint_corridor needs ab_weight/l_weight/endpoint_tau/path_mode/… The color pair-correction sub-artifact is optional but, when present, must carry schema "prisma_photo_stack_v2_color_pair_corrections_v1" (bundle.py:192). The bundle also carries a source.prediction_reference_rows block and a verification block (prediction_reference_columns, prediction_reference) used for replay checking (bundle.py:200–bundle.py:212).

There is a separate, code-side version too: PHOTO_STACK_PREDICTOR_LOGIC_VERSION = 4 (predictor.py:34). This is the logic epoch of the predictor itself, distinct from the bundle’s data version. It is folded into the predictor cache key (predictor.py:1374) and the provider fingerprint, so a code-only change to the math invalidates cached solves even when the bundle bytes are unchanged.

How a colour is predicted

The predictor (PhotoStackPredictor, predictor.py:713) is compiled once from a bundle (from_bundle, predictor.py:736) and cached per (path, fingerprint, logic_version) (predictor_for_bundle, predictor.py:1377). Prediction works on rows — one physical stack per row — through predict_rows_rgb (predictor.py:1304). The unit of geometry is a canonical layer group: adjacent same-filament same-role layers are merged, and each group is tagged color, base_white (white below any colour), or cap_white (white above colour) (canonical_layer_groups, predictor.py:137).

Everything starts in per-channel optical density (OD = -log T, od_from_t / t_from_od, predictor.py:292), sampled from the bundle’s per-filament curves with a frozen high-thickness taper (channel_curve_od, predictor.py:309). The stages, in execution order:

#StageMethodWhat it adds / does
0Latent OD splitlayer_optical_arrays (predictor.py:504)Splits the stack into summed colour OD, white OD, cap OD, base OD, and the first/last ordered colour layers.
0White contextwhite_context_od (predictor.py:815)Re-adds attenuated white OD gated by colour strength (white_gamma, white_tau) — white behind colour darkens differently than white alone.
0Cap attenuationcap_attenuation_od (predictor.py:824)Extra OD from white on top of colour (the “surface white”), gated by colour strength and selectivity.
0Multi-colour interactionmulticolor_interaction_od (predictor.py:993)For ≥2 distinct colours, a directional OD term driven by colour-direction diversity, copresence, and layer order.
1(assemble)predict_row_od_parts (predictor.py:1138)Sums latent + white + white-context + cap + interaction OD → base RGB → base OKLab.
2Ordered tint retentionordered_tint_retention_lab (predictor.py:1075)Pulls the result back toward lower colour layers’ intrinsic tint that plain summed OD washes out.
3Single-colour cap transfersingle_color_cap_transfer_lab (predictor.py:845)For single-colour sandwiches, transfers hue/chroma/lightness from the bare colour through the white cap.
4Single-colour profile evidencesingle_color_profile_lab (predictor.py:964)If a measured single-colour sandwich profile matches the context, it is blended in and allowed to dominate.
5Endpoint corridorendpoint_corridor_lab (predictor.py:1246)For two-colour stacks, pulls the prediction toward the line between two physically-supported one-colour endpoints.
—Colour pair correctioncolor_pair_corrected_rgb (predictor.py:1199)For ordered two-colour / no-white stacks, replaces the result with OD-only × a calibrated per-channel curve.

The stage commentary in predict_rows_rgb (predictor.py:1309–predictor.py:1352) labels these Stages 1–5 inline. A few important wiring details:

  • Pair correction short-circuits the OKLab stages. If color_pair_corrected_rgb matches (an ordered two-colour, no-white stack with a calibrated pair), the predictor uses OD-only × correction and skips Stages 2–5 entirely (predictor.py:1311–predictor.py:1318), zeroing the suppressed context info (color_pair_suppressed_context_info, predictor.py:1230). The rationale: these pair rows are colour-only evidence excluded from white-stack context calibration (predictor.py:1201 comment).
  • The OKLab→RGB round-trip only happens if a later stage actually moved the colour — the predictor checks each stage’s reported weight before re-deriving RGB from final_lab (predictor.py:1338–predictor.py:1345), otherwise it keeps the cheap base RGB.
  • Every stage also emits a bag of *_info scalars (gates, weights, support) that ride along in the output frame for diagnostics.

Evidence classes

Each runtime stack is tagged with an evidence class (_runtime_evidence_class, predictor.py:1396) describing what kind of calibration evidence governs it. This drives both which stages have authority and which rows the correction layer trains on:

white_only, naked_single_filament, color_over_white, multicolor_over_white, single_color_sandwich, cross_color_multilayer_sandwich, and the catch-all unsupported_or_diagnostic (predictor.py:1414–predictor.py:1422).

Transmission-distance and material profiles

Two per-filament side-tables refine the stages:

  • Transmission-distance (TD) profiles (transmission_distance_profiles) provide per-filament channel weights, an over-layer attenuation scale, and a “tint authority” (how strongly a layer’s intrinsic tint survives under other layers). They are blended by an evidence-confidence factor so an unmeasured filament defaults to neutral behaviour (td_* methods, predictor.py:772–predictor.py:813).
  • Material profiles (material_profiles) carry each colour’s naked-chroma anchor, hue anchor, and various gates (bright-vivid relief, chroma gate). They are aggregated across a stack’s colours in material_gates_for_ids (predictor.py:475) and feed the cap/white/transfer stages.

The residual correction layer

The bundle prediction is the base model. An optional residual kNN correction sits on top (correction_layer.py), selected by the use_corrections toggle on the Appearance provider.

  • The fitter builds an all-evidence correction artifact (build_photo_stack_correction_artifact, correction_layer.py:217) carrying training rows: for each calibration sample, the base model’s OKLab residual (photo_oklab − photo_stack_v2, correction_layer.py:171). Only rows whose evidence class is in TRAIN_EVIDENCE are kept (correction_layer.py:25; note unsupported_or_diagnostic is excluded).
  • At runtime, correction_residuals_for_rows (correction_layer.py:254) looks up training rows in the same context — keyed on (unordered_color_key, white_key, evidence_class) (correction_layer.py:269) — and does a Gaussian-weighted nearest-neighbour average of residuals in a scaled feature space (FEATURE_COLUMNS/FEATURE_SCALES, correction_layer.py:41/correction_layer.py:55). The residual is norm-capped (max_norm) and scaled by a saturating authority that grows with local support (correction_layer.py:293).
  • apply_photo_stack_correction (correction_layer.py:298) adds the residual to the base OKLab and re-derives RGB, emitting the corrected prediction under the photo_stack_v2_corrected name plus per-row support, authority, and correction_norm columns.

The correction is schema-gated: requesting it when no valid correction_layer.json (schema "prisma_photo_stack_v2_correction") is present raises rather than silently using direct (predict.py:86, mirrored at appearance_model.py:261).

Two prediction shapes: row predictor vs LUT

The same equations are evaluated two ways, and they are kept in sync deliberately:

  • Row predictor — predictor.py scores one stack per DataFrame row. It is the source of truth for isolated predictions and calibration review, and the fallback for off-grid thicknesses.
  • Vectorized LUT — generator/photo_stack_lut.py mirrors the frozen equations with NumPy arrays to score the hundreds of thousands of grid-aligned candidate stacks a Joint LUT needs at interactive speed. The provider routes grid-aligned rows to the LUT and everything else to the row predictor (appearance_model.py:533), so callers never lose exactness — only speed. The LUT module imports the predictor’s frozen constants directly (photo_stack_lut.py:26) precisely so the two cannot drift.

The library exposes convenience entry points for one-off stacks too: predict_stack_from_layers (predictor.py:1476), predict_stack_rows_from_layers (predictor.py:1456), and the artifact-level predict_stack (predict.py:65, which applies corrections when present).

How it plugs into a solve

The webapp solve runs the staged backend (run_staged_backend_path, pipeline/staged_runner.py:10310, called from runner.py:846) — not solve.py’s legacy CLI engine. The staged runner branches on state.appearance_provider.model_kind, and when the provider is photo_stack_bundle it is the PhotoStackBundleAppearanceProvider (appearance_model.py:210) wrapping the predictor described here. Everything above is what produces a single backlit colour for one candidate stack inside that loop; see Appearance provider for the boundary contract and The Joint LUT and Staged Solve for how those colours become a LUT and a solved image.
