Colour-core library

Colour-core library

Properties1
tagsgenerator, colour

Jun 21, 202610 min read

In one sentence: the Prisma/lib/ colour core is the shared, framework-free toolbox of colour-space conversions, two non-interchangeable ΔE definitions, the spline transmission model (build / predict / compose / pair-correct), adjacent-layer collapsing, the filament-registry accessor, and the Camera Transform loader (forward fit, Newton inverse, trilinear LUT) that both the generator and calibration apps build on.

This page documents the modules under Prisma/lib/ that the generator solve path depends on. These are pure helpers — no FastAPI, no disk writes beyond reading JSON/.npz artifacts. If you are wiring a new solve stage, this is the layer you import from. For how these pieces compose into a render, see The Transmission Model and generator.model; for the colour-domain contracts, see Colour domain doctrine.

Related architecture nodes: lib.transmission, lib.color, lib.stack_geometry, lib.filaments, lib.camera_transform.

Two ΔE definitions — not interchangeable

The repo has two distinct colour-difference functions that live in different modules, use different colour spaces, and serve different consumers. Mixing them up is a real trap. (One wiring caveat: the generator’s deltaE_ok path is live, but the lib/color.py compute_dE_from_linear shown here is a dormant copy — the calibration app consumes an identical duplicate; details below.)

  • deltaE_ok operates on OKLab coordinates produced by linear_to_oklab (lib/transmission.py:40). It is the generator’s perceptual metric — the solver imports linear_to_oklab directly (generator/model.py:22, used at generator/model.py:160) and compares candidates in OKLab. The module docstring’s claim that OKLab is “faster than CIEDE2000” is a design note, not a guarantee — what matters is it is a different space from CIE76.
  • compute_dE_from_linear converts each linear-RGB triplet to CIE Lab via linear_to_lab (lib/color.py:77, an approximate D65 transform) and returns the plain CIE76 distance (lib/color.py:99). This is the calibration metric in spirit, but watch the wiring: the calibration app imports a byte-for-byte duplicate from calibration/fitting/color_math.py (defined at calibration/fitting/color_math.py:93), not the lib/color.py copy. Its consumers are calibration/server.py:104 (imports from fitting.color_math) and calibration/fitting/composition.py:176 (same). Grep finds no importer of lib/color.py anywhere in the codebase — see the liveness note below.

Practical rule: a “ΔE 3.3” reported by the generator’s OKLab metric and a “ΔE 3.3” from the calibration CIE76 metric are not the same number. Never compare them across the two systems. See Delta E definitions.

sRGB / linear / Lab helpers (lib/color.py)

These are the scalar, stdlib-only conversions (the module imports only math). They are the calibration-flavoured cousins of the vectorised numpy helpers above.

Liveness: lib/color.py is currently unwired. Grep finds zero importers of this module across Prisma/, the tests, or any caller — production or otherwise. It was created during the 2026-04-03 reorganization as an extraction from unified_calibration/pipeline/color_math.py, but the calibration app never switched to it: it imports a duplicate of these same functions from calibration/fitting/color_math.py instead. Spline transmission model (lib/transmission.py)

This is the heart of The Transmission Model: measured (thickness, T_rgb) knots interpolated with monotone cubic (Pchip), not Beer-Lambert. Composition is multiplicative and order-independent (the corrections term excepted).

Pair-correction key format (verify before constructing one): when len(layers) >= 2, compose builds the lookup key from the first layer as overlay and the rest as base (lib/transmission.py:168-179):

pair_key = f"{overlay_fid}|{base1_fid}@{d1:.2f}+{base2_fid}@{d2:.2f}..."

i.e. "overlay|base@0.20" with thicknesses formatted to two decimals. Each profile must carry a filament_id for this to match; absent it, the key uses an empty string and the correction silently no-ops.

compute_pair_corrections lives elsewhere. The compose/build_spline docstrings reference compute_pair_corrections(), but that producer is not in this module — it is defined in calibration/fitting/fitter_core.py (grep-confirmed) and writes data/filaments/pair_corrections.json. The generator only consumes the resulting dict: it loads the JSON (generator/server.py:152,880) and threads it through compose(..., corrections=...) via the solve config (generator/pipeline/runner.py:811, generator/facade.py:689). See Pair corrections.

Camera Transform artifact (lib/camera_transform.py)

The Camera Transform (CT) is the colour bridge between the model domain (predicted transmission RGB) and display sRGB. It has two directions:

  • Forward F — model RGB → camera-rendered display sRGB. A Finlayson degree-2 root-polynomial matrix (rp_features) followed by monotone PCHIP curves.
  • Inverse G — display sRGB → model RGB, used for image ingress. Baked once into a 33³ trilinear LUT.

The on-disk schema is camera_transform_v1 carrying a v2 fit model (camera_transform.py:20, :183-187). See Camera Transform and Colour domain doctrine.

Generation pinning. A CT directory holds dated gen-* subdirs plus a CURRENT file naming one of them. _read_current_generation (camera_transform.py:69) reads CURRENT, and rejects anything that is absolute or not a single local path component (camera_transform.py:80) — a guard against pointer traversal. _resolve_artifact_file (camera_transform.py:88) transparently follows CURRENT when the path is a directory, so callers pass the CT root and get the pinned generation’s file.

SHA-256 integrity. When a generation dir is resolved, _verify_generation_hashes (camera_transform.py:160) loads manifest.json, requires an artifact_hashes map containing both filenames, and recomputes each file’s SHA-256 (_sha256_file, camera_transform.py:139) — raising CameraTransformError on mismatch (:175). Both load_camera_transform and load_inverse_lut run this verification before reading (camera_transform.py:205, :337). Separately, load_camera_transform records the raw JSON bytes’ SHA-256 on the returned CameraTransform.sha256 (camera_transform.py:223) for downstream provenance.

Caching. Both loaders cache by (resolved_path, mtime_ns) and clear the cache on every miss (camera_transform.py:225, :351) — a deliberate single-entry cache, not an unbounded one.

Data-root indirection. _configured_data_root (camera_transform.py:105) reads Prisma/calibration/.data-root; _resolve_data_root_default (:118) re-roots a Prisma/data/... path under that pointer if present. This is how the CT loader finds artifacts when data lives outside the repo.

Where each runs — the load-bearing distinction. The generator’s image ingress does not call invert_forward. It loads the pre-baked LUT and trilinearly interpolates it:

  • generator/model.py:21 imports apply_inverse_lut, load_inverse_lut; calls them at model.py:120 / :125.
  • generator/model_domain_display.py:28 imports apply_forward, load_camera_transform; applies F at model_domain_display.py:44 (model RGB → display, for previews).

invert_forward (the Newton inverse) is called only at calibration bake time — calibration/fitting/camera_transform/lut.py:17 runs it over the 33³ grid to produce inverse_lut_33.npz. Grep finds no generator caller of invert_forward. So: the generator consumes the trilinear LUT; the Newton solve lives in the calibration bake. Do not expect invert_forward on a hot solve path.
