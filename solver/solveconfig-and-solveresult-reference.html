SolveConfig and SolveResult reference

In one sentence: SolveConfig is the ~80-field dataclass that fully specifies one solve, and SolveResult is the container the facade returns — thickness maps, diagnostics, stats, and the predict_image reconstruction methods.

Both live in generator.facade (Prisma/generator/facade.py). The module header still calls itself lith_facade.py (facade.py:2) — that name is stale; cite line anchors, not the header. This page covers the two dataclasses a caller hands in (SolveConfig) and gets back (SolveResult), the effective_* helpers that derive runtime values, and the two forward-prediction methods (predict_image, predict_image_color_only).

For the functions that consume a SolveConfig — solve_preview, solve_full, solve_compare — see The solve facade. For the pipeline they delegate into, see The staged backend and generator.pipeline.runner.

SolveConfig

@dataclass SolveConfig (facade.py:160) — “All parameters needed for a single solve invocation.” One required field, the rest defaulted. The web server builds one at server.py:1015 (return SolveConfig(...)); the CLI builds its own.

How it is driven

A caller constructs a SolveConfig, then passes it to a facade entry point. The same object flows through _to_pipeline_config (facade.py:612), which copies its fields one-for-one into a PipelineConfig for the runner. Almost every field below is forwarded verbatim there — SolveConfig is the public shape, PipelineConfig the internal one. SolveConfig does not hold an image: the image is a separate argument to solve_full(img, config, ...).

__post_init__ — the resolution backstop

__post_init__ (facade.py:283) calls _apply_resolution_backstop(self) from config/resolution_schema.py:153. This enforces the solve-coupled pitch pair invariant: if both image_sample_pitch_mm and solver_fine_pitch_mm are None, both default to the family default; if exactly one is set, it raises ResolutionSchemaConflictError (resolution_schema.py:170-177); if both are set they must agree (resolution_schema.py:178). So you cannot construct a SolveConfig with a half-specified pitch family — the dataclass refuses it at construction time. See Resolution schema.

Resolution (canonical pitch fields)

image_sample_pitch_mm (0.20), solver_fine_pitch_mm (0.20), stage1_coarsening_factor (1), stage1_lattice_offset_y_px / _x_px (0). These are the only resolution channel — there are no legacy alias fields on the runtime dataclass (resolution_schema.py:157). See Resolution schema.

Cap shaping

cap_mode ("smooth_variable" | "fixed"), cap_fixed_thickness_mm (0.0, 0 ⇒ use d_wc_min in fixed mode), cap_continuity_cleanup (True, fills single-pixel cap pinholes), plus the detail-cap family detail_cap_pitch_mm / detail_cap_enabled / detail_cap_max_layers.

Solver behaviour

de_threshold (0.01), gamut_mode ("hull" convex hull, or "chroma" legacy), gamut_white_rescale, chroma_weight (1.0, >1 prioritises colour over lightness in the KD-tree), the luminance_tiebreak_* pair, and the full luminance_handler_* family (~14 fields, facade.py:220-233) governing the optional Luminance handler.

Model-domain ingress — model_domain_ingress (True) and model_domain_ingress_lut_path ("Prisma/data/camera_transform") thread the Camera Transform inverse LUT into image ingress. See Model domain ingress.

Staging / printability — a large stage2_* family (continuity weight, fine override, boundary mutation, printability gates/repair), stage4_* detail-surface flags, and the printability_* / enforce_printability / color_region_* group. These feed the staged backend and blueprint printability. emit_blueprint_printability defaults True; allow_print_despite_hazards defaults False.

Smoothing & cells — smooth_kernel (15.0), smooth_iters (3), cell_mode ("felzenszwalb"), smooth_boundaries (False), boundary_smooth_radius (1), and the v2_* cleanup family.

AMS slots — ams_slots (4), white_slots (1). Colour slots are derived (see colour_slots).

Grouping (beam search) — grouping_max_iterations, grouping_beam_width, grouping_z_waste_weight, grouping_overflow_weight, grouping_swap_count_weight, grouping_slot_stability, grouping_de_scoring, grouping_de_cost_weight, grouping_in_group_sub. These instantiate the grouping module in _resolve_grouping_from_state (facade.py:513) — only consumed when module_state["group_budget"] is set; otherwise a plain GreedyGrouping runs. See Grouping and slot scheduling.

Preprocessing — preprocessing_params (per-operator kwargs keyed by module name; every registered operator’s params block materializes here at its default), plus protect_subject_* and protect_mask_* for subject protection. See Preprocessing pipeline.

Printer / resample — nozzle_diameter (0.20), printer_min_line_width_mm, source_resample_kernel ("lanczos" default, bit-exact with pre-B7 behaviour; "area" selects cv2.INTER_AREA).

effective_boundary_d_wc_max reads a private runtime attribute _runtime_luminance_boundary_cap_authority_mm via getattr (facade.py:303) — the luminance handler can stamp a tighter authority onto the config object mid-solve; absent that, only the static fields apply.

Cloning

_replace_solve_config(config, **changes) (facade.py:769) shallow-clones a SolveConfig from config.__dict__ with overrides. solve_compare uses it to swap in each palette (facade.py:1011). Because it rebuilds via the constructor, __post_init__ re-runs — the resolution invariant is re-checked on every clone.

SolveResult

@dataclass SolveResult (facade.py:359) — “Complete result of a solve operation.” Built by _state_to_solve_result (facade.py:864), which converts a PipelineState back into the public result shape after the runner finishes. Direct tests may construct partial SolveResult objects with many fields None.

__post_init__ — thickness-map normalisation

__post_init__ (facade.py:394) wraps a raw dict into the typed ThicknessMaps if it is not already one (facade.py:400-401). This is a no-op when the runner already handed over a wrapped container (the webapp path), so it preserves exact object aliasing there. ThicknessMaps (thickness_maps.py:77) is a compatibility-first MutableMapping whose keys normalise to plain strings, so every serializer and frontend payload sees the exact legacy strings. The reserved sentinel keys are the MapKey enum (thickness_maps.py:40): __white_cap__, __white_boundary_cap__, __white_detail_cap__, __de__, __gamut_mask__. Dynamic filament-IDs are plain strings, distinguished by not starting with __.

Diagnostics-vs-thickness_maps accessor fallback

The de_map and gamut_mask properties (facade.py:405-415) each prefer the diagnostics dict and fall back to thickness_maps:

This dual lookup exists for a reason spelled out at facade.py:382-387: the staged/webapp runner populates diagnostics (from PipelineState.diagnostics: __de__, __gamut_mask__, __target_gamut_*__), so production results take the first branch. The fallback to thickness_maps serves only diagnostics-less legacy results — the separate legacy CLI engine, and tests that build a SolveResult straight from thickness_maps without a diagnostics dict. The same prefer-then-fall-back pattern appears in _compute_palette_fit_diagnostics (facade.py:802-805).

The other map accessors read thickness_maps directly (no fallback needed — caps are always part of the thickness output): cap_map → WHITE_CAP (facade.py:417), boundary_cap → WHITE_BOUNDARY_CAP or None (facade.py:421), detail_cap → WHITE_DETAIL_CAP or None (facade.py:427), filament_ids → the dynamic keys (facade.py:431).

Best-case palette-fit diagnostics

palette_fit_image / palette_fit_de / solver_loss_map are computed by _compute_palette_fit_diagnostics (facade.py:784) and only for preset.name == "full" (returns {} otherwise, facade.py:787). It re-queries the LUTs for the per-pixel best achievable match (query_luts_batch, facade.py:824) and computes the solver’s loss as max(final_de - best_de, 0) (facade.py:853) — i.e. how far the actual solve fell short of the palette’s theoretical best. See Solve diagnostics and dE maps.

predict_image and predict_image_color_only

These are the forward reconstruction methods: given solved thickness maps, recompose the predicted backlit image. This page owns the cap-zeroing explanation.

predict_image

predict_image(max_layers=None, *, thickness_maps=None) (facade.py:437) returns an (H, W, 3) uint8 image. Two backends, selected by the appearance provider’s model_kind (facade.py:452-454):

  • historical_spline (the default provider) and any diagnostics-less result fall to predict_image_fast (solve.py:674), the vectorised spline composition: T = T_wb · Π T_colour(d) · T_cap(d) per pixel, then gamma-2.2 to sRGB uint8 (solve.py:714).
  • non-spline providers (e.g. photo_stack_bundle, appearance_model.py:224) route to provider.predict_thickness_maps_srgb(...) (facade.py:456).

The thickness_maps= keyword overrides the solved maps for the prediction. Default None uses the solved maps, byte-for-byte preserving historical behaviour (facade.py:451). This override is the hook predict_image_color_only rides on.

max_layers defaults to config.effective_max_layers() (facade.py:450).

Callers (confirmed live): server.py:4007 (preview/gamut-check reconstruction), :4117 (per-palette reconstruction inside the solve_compare loop), :4806 (the full-solve reconstruction), plus evaluation/preprocessing_render.py:64,68, scripts/validate_task3_real_images.py:199, and several tests. predict_image is the live image-reconstruction path for the generator UI.

predict_image_color_only — and white-cap zeroing as multiplicative identity

predict_image_color_only(max_layers=None) (facade.py:494) reconstructs the base + colour image with the white cap omitted, so the cap’s luminance shaping does not drown out the colour story. The base stays in — it is the substrate. Output is the same model-domain gamma-2.2 sRGB uint8 as predict_image, so it can be baked through the display transform F (facade.py:501).

It is a thin wrapper: it calls self.predict_image(max_layers, thickness_maps=self._cap_zeroed_thickness_maps()) (facade.py:503). All the interesting work is in _cap_zeroed_thickness_maps (facade.py:474):

It shallow-copies the maps (ThicknessMaps.copy(), arrays shared) and replaces every white-cap term — total cap and its boundary/detail components — with an all-zero array.

Why zeroing the cap thickness cleanly drops the term: a zero cap thickness is the multiplicative identity in the transmission model. The composition multiplies a per-channel cap transmission T_cap(d_wc) into the stack (solve.py:710-712; spline provider appearance_model.py:205-206). The transmission of any profile at thickness 0 is [1, 1, 1] — confirmed at lib/transmission.py:107-108:

So T_cap(0) = [1,1,1], and multiplying the stack by [1,1,1] leaves base × colour untouched. This holds in both spline-composition backends (predict_image_fast and the spline appearance provider both call predict_transmission → predict), exactly as the method’s docstring asserts (facade.py:478-481). The cap term is dropped without touching the composition math — no special-casing, just feeding it the identity input.

Liveness: predict_image_color_only and _cap_zeroed_thickness_maps are defined at facade.py:494 / :474 and are live. The full-solve path invokes result.predict_image_color_only() at server.py:4855, saving the result as predicted_color_only.png and baking it through the forward Camera Transform F into predicted_color_only_appearance.png (server.py:4859) — this is the colour-only predicted render for the Recipe viewer’s “Color Regions” tab (the cap-omitted “colour story” view). The behaviour is exercised directly by tests/generator/test_predict_color_only.py (including test_photo_stack_backend_receives_cap_zeroed_maps, which checks the non-spline backend receives a zeroed cap). (Confirmed by grep against the call site, not inferred from headers.)
