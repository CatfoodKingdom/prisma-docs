The staged backend (Stage 0-5)

The staged backend (Stage 0-5)

Properties1
tagsgenerator, solver

Jun 21, 202610 min read

In one sentence: the staged backend is the generator’s sole production solve engine — it turns a prepared image into per-filament thickness maps through six ordered passes (directives → zones → recipes → filler → cap → bridge), each handing a frozen artifact to the next.

The staged backend (Stage 0-5)

When you click Solve in the generator web app, the colour decomposition is performed by run_staged_backend_path in generator.pipeline.staged_runner, not by the older solve_image engine in solve.py (that is the legacy CLI region engine — solve.py:410 solve_image, solve.py:577 solve_regions — and is not on the webapp solve path). The webapp path is run_pipeline → the staged backend; the only caller of the staged entry point is the runner: pipeline/runner.py:843-846 imports and calls run_staged_backend_path(state, progress=progress).

The function lives at pipeline/staged_runner.py:10310. That one file is ~11,000 lines; this page stays at stage-contract altitude — what each stage consumes, what it produces, and which knobs you control — and deliberately does not narrate gate/beam/mutation internals.

How to drive it

You never call the stages directly. You configure a PipelineConfig (palette, layer height, budgets, region target, feature flags) and run a solve from the web app or pipeline_cli.py. The staged backend reads state.config and state.solve_target_oklab (the prepared OKLab targets on the solve grid) and returns a StagedBackendResult bundle. The runner then copies that bundle onto legacy-facing state (pipeline/runner.py:533 _finalize_staged_backend_state), after which filament grouping, statistics, and mesh export run as usual.

Two hard preconditions, enforced by the stages themselves:

  • state.solve_target_oklab must be set — Stage 1 and Stage 2 raise RuntimeError otherwise (pipeline/staged_runner.py:675-676, :760-761, :6132-6133).
  • The solve grid shape is taken from state.image.shape[:2]; everything downstream operates on that lattice.

The pipeline at a glance

run_staged_backend_path runs the six stages in strict order, timing each into a StagedPerformanceProfile and emitting progress callbacks (all reported under stage_index: 3, stage_count: 5, pipeline/staged_runner.py:10325-10326). Each stage is a single builder function whose output is a frozen artifact consumed by the next.

The artifact names are stable; some docstrings still call this an “experimental proof slice” (e.g. staged_artifacts.py headers, staged_runner.py:10311). That language is stale — this is the production path. Trust the caller at runner.py:846, not the docstring.

Stage 0 — Directives

_compile_directives(state) (pipeline/staged_runner.py:567) builds a tiny, explicit directive set rather than letting later stages re-derive geometry. It computes the planning lattice pitch as solver_fine_pitch_mm × stage1_coarsening_factor (:572) and quantizes the minimum visible cap (d_wc_min) to a whole number of layers (:586-591). The solver_shape it pins is the raw image shape (h, w) (:613).

Each directive is a CompiledDirective with a gate (here "require") and a scope ("image"); each gets a DirectiveReceiptEntry marked status="held", stage="stage0" (:593-607). The output QuantizedDirectiveSet (staged_artifacts.py:22) is consumed by Stage 2 as its evaluation lattice (:6159 reads compiled_directives.solver_shape). See concept-solve-lattice for how fine pitch, planning pitch, and coarsening relate.

Stage 1 — Lateral zone segmentation

_build_stage1_zone_plan(state, diagnostics) (pipeline/staged_runner.py:671) partitions the image into lateral colour zones — contiguous regions that will each receive one recipe in Stage 2.

What it does:

  1. Optionally coarsens the planning grid by stage1_coarsening_factor (_effective_stage1_coarsening_factor, :275), block-averaging both the RGB image (_downsample_rgb_image, :344) and the flat OKLab targets (_downsample_flat_oklab_targets, :399) onto the coarse lattice, with an optional lattice offset (_stage1_lattice_offset_px).
  2. Calls generate_stage1_zone_labels (imported from generator.pipeline.staged_solver_helpers, :709) to produce the integer zone-label raster, honouring cell_mode, the effective color_region_target_mm, smooth_boundaries, and boundary_smooth_radius.
  3. Derives per-zone bookkeeping: flat membership indices (_zone_flat_indices, :644), per-zone OKLab mean/variance (_summarize_zone_targets, :654), and 4-neighbour adjacency with shared-edge lengths (_build_zone_adjacency, :619).

The effective region target can be widened from the printability minimum width when color_region_target_from_printability is on (_effective_color_region_target_mm, used at :697 and :10360); the requested-vs-effective values are both recorded as counters (:10361-10394). Output LateralZonePlan (staged_artifacts.py:114) carries zone_label_map, zone_flat_indices, adjacency_edges, edge lengths, per-zone means/variances, and the coarse_to_fine_scale Stage 2 will reverse. See concept-colour-zones.

Stage 2 — Recipe assignment

_build_stage2_visible_plan(...) (pipeline/staged_runner.py:6122) is the heart of the solver: it chooses one visible filament recipe per zone while balancing local colour fidelity against seam continuity. This is the single largest stage in the file.

Projection back to fine grid. If Stage 1 coarsened, the zone labels are projected back onto the fine evaluation lattice (_project_zone_labels_to_fine, :6160), optionally refined into source-edge subzones (_split_stage2_source_edge_subzones, :6174, gated by stage2_source_edge_subzones). Adjacency and per-zone variance are recomputed on this evaluation lattice (:6181-6193).

Candidate query. _query_stage2_pixel_stacks (:757) runs query_luts_batch (from generator.lut) over the OKLab targets to get a per-pixel best stack plus a per-pixel ΔE; pixels above de_threshold form the gamut_mask (:763). _vectorized_stack_ids (:6214) quantizes those thickness vectors into a discrete set of unique stack ids under effective_max_layers(). Palette ordering matters here: for the photo-stack model the palette order is preserved as-is because layers are physically ordered, whereas the legacy spline model sorts ids (:6205-6212).

Enumeration + pruning. _enumerate_zone_candidates (:767) collects, per zone, the unique stack ids that appear among that zone’s pixels and scores each candidate against the zone’s targets with _score_candidates_batch (:794); a single-candidate zone gets score 0 (:790-791). Each candidate also carries its total visible thickness (:798-804). The candidate frontier is then enriched — neighbouring zones’ strong local-best stacks are injected as extra candidates (_augment_zone_candidates_with_neighbor_local_bests, :815) so a zone can match a neighbour it would not have considered alone. This frontier is what keeps the assignment search tractable instead of enumerating the full LUT.

Coordinate-descent + beam under continuity/seam. Selection is a two-step optimization over candidate indices:

  1. _seed_zone_recipe_labels_with_beam (:1440, called :6408) runs a small beam search (_STAGE2_BEAM_WIDTH = 12, :93) to build a good initial assignment that already respects neighbour continuity.
  2. _optimize_zone_recipe_labels (:1901, called :6496) takes that seed and refines it: _run_coord_descent (:1681, up to _STAGE2_MAX_COORD_DESCENT_PASSES = 4, :83) followed by _repair_worst_boundary_pairs pair repair (:1960).

The objective per zone/candidate is computed in _zone_objective_breakdown (:1594): local_cost + continuity_weight × boundary_cost + retaining_wall_weight × retaining_cost (:1624-1628), where boundary_cost is the edge-length-weighted squared visible-thickness step to each neighbour’s current choice (:1617-1621) and retaining_cost penalizes excess thickness above the zone’s thinnest candidate (:1622-1623). Defaults: _STAGE2_CONTINUITY_WEIGHT = 0.12, _STAGE2_RETAINING_WALL_WEIGHT = 0.02 (:81-82); the continuity weight is overridable via _stage2_continuity_weight. “Seam” quality is the mean shared-boundary thickness step, tracked before/after by _mean_boundary_step_mm (:1637).

Output VisibleRecipeRawGeometryPlan (staged_artifacts.py:264) carries the zone_recipe_labels, the recipe_table of VisibleRecipe entries, the raw colour ceiling, the gamut mask, an optional fine_recipe_label_map (when a within-zone detail override fires), and a Stage2ObjectiveSummary. Its recipe_label_map property (:295-299) returns the fine override if present, else the zone-level labels.

VisibleRecipe vs the photo-stack StackDefinition. VisibleRecipe (staged_artifacts.py:73) is the staged backend’s committed recipe — an ordered tuple of (filament_id, thickness_mm) pairs with from_mapping/to_mapping helpers. It is structurally near-identical to but distinct from the model-layer StackDefinition; do not conflate them.

Stage 3 — Filler

_build_stage3_filler_plan(...) (pipeline/staged_runner.py:8992) is the geometry-only filler pass. In current code it is effectively a pass-through: it sets filler_height = zeros_like(raw_color_ceiling) and therefore color_ceiling_mm == raw_color_ceiling_mm (:8998-9000). It still runs every solve (called unconditionally at :10413) and emits a FillerGeometryPlan (staged_artifacts.py:311) so Stage 4 has a uniform color_ceiling_mm field to build on. The stage exists as a wired seam for support/filler logic; today it adds no height. Confirmed live but no-op: the only writer of filler_height is the np.zeros_like at :8999.

Stage 4 — Cap and detail / printability

_build_stage4_cap_plan(...) (pipeline/staged_runner.py:9598) synthesizes everything above the colour layers: the white boundary cap, edge guards, an optional detail surface, and the printability gates.

Key contract points:

  • Budget. The remaining cap budget is t_max − color_ceiling, clamped to effective_d_wc_max() (:9610-9614); the boundary cap is further clamped to effective_boundary_d_wc_max() (:9615-9618). The minimum cap floor is quantized to layers via _quantized_cap_floor (:9609).
  • Requested cap & guards. _requested_stage4_cap_maps (:9619) returns the requested boundary cap, a detail reference cap, and a boundary_edge_guard_weight map. Stage 4 supports cap_mode ∈ {"fixed", "smooth_variable"} (_STAGE4_SUPPORTED_CAP_MODES, :186); any other mode does not raise — it falls back to smooth_variable and emits a stage4_cap_mode_fallback warning diagnostic (:8758-8770).
  • Lateral boundary shield. When printability is enforced and a non-fixed lateral shield is required, Stage 4 honours the mandatory shield floor handed off by Stage 2 (visible_plan.mandatory_lateral_boundary_shield_floor_mm, :9633), raising a ValueError if its shape disagrees with the cap (:9636-9639).
  • Detail surface. Optional, gated by detail_cap_enabled (:9629) plus stage4_optical_detail_surface / stage4_independent_detail_surface (:9679-9684). Detail candidates are scored per connected zone and accepted/rejected with explicit reasons (Stage4DetailZoneSummary, staged_artifacts.py:344); rejection categories include too-small, weak-optical-gain, and weak-signal (_STAGE4_DETAIL_REJECT_*, :198-201).
  • Printability gates. Two optional gate families run here and surface as Stage4BoundaryCapPrintabilitySummary and Stage4DetailAuthoringPrintabilitySummary / Stage4DetailPrintabilitySummary, all None when disabled (CapSynthesisPlan fields, staged_artifacts.py:454-459).

Output CapSynthesisPlan (staged_artifacts.py:441) carries cap_boundary_top_mm, cap_height_mm, boundary_edge_guard_weight, detail_height_mm, the detail zone maps/summary, and final_visible_top_mm.

Two unrelated PrintabilityReport/printability classes. Stage 4’s printability summaries (Stage4*PrintabilitySummary) and the optional plan-level BlueprintPrintabilityDiagnostic (staged_artifacts.py:501, run via staged_printability.run_blueprint_printability_diagnostic at :10729) live in this pipeline. They are distinct from the mesh-side and blueprint_triage printability types — do not cross-reference them. The blueprint diagnostic and geometry-attribution passes are opt-in, gated by emit_blueprint_printability (:10715) and emit_geometry_attribution (:10659); they are read-only diagnostics that never change geometry.

Stage 5 — Plan bridge

build_compatibility_bundle(...) (pipeline/staged_bridge.py:90) is the read-only adapter that projects the staged artifacts back into the legacy thickness-map shape the rest of the generator (mesh export, previews, dE diagnostics) expects.

It builds one (h, w) float32 thickness map per palette filament by painting each recipe’s thickness_by_filament onto its recipe_label_map mask (staged_bridge.py:103-112), then adds three white-channel maps: __white_cap__ (full cap height), __white_boundary_cap__ (cap-above-ceiling, floored at 0), and __white_detail_cap__ (:122-130). It also exports the __gamut_mask__ diagnostic and a dictionary of debug maps (zone labels, recipe labels, colour ceiling, cap tops, detail maps, etc., :135-178). Output CompatibilityBundle (staged_artifacts.py:571) plus the per-pixel image-domain extents.

Back in the runner, _finalize_staged_backend_state (pipeline/runner.py:533) copies bundle.thickness_maps into state.thickness_maps (:559-562), routes bundle diagnostics into state.diagnostics (never into thickness maps, :567-568), merges debug maps (:570), sets state.colour_committed = True, and — separately — builds the export-facing SolvedMaterialPlan via build_solved_material_plan_for_export (:542). That is the true Stage 5 handoff to mesh generation; see concept-thickness-maps and Mesh export.

Diagnostics, receipts, and performance

Throughout, the orchestrator records:

  • Timings per stage into StagedPerformanceProfile.timings_s (_record_timing, :261) — stage0_compile_directives_s, stage1_zone_plan_s, the Stage 2 sub-timings (stage2_beam_seed_s, stage2_coord_descent_s, stage2_pair_repair_s), stage3_filler_s, stage4_cap_s, stage5_bridge_s, and staged_backend_total_s (:10975-10979).
  • Counters for grid sizes, zone counts, frontier sizes, detail accept/reject tallies, and printability findings (_set_counter, :266).
  • Receipts (DirectiveReceiptBook) and a diagnostics stream (PlanningDiagnosticsStream) of human-readable PlanningDiagnosticEntry notes — Stage 1 zone count, Stage 2 seam/pressure notes, printability summaries.

These are what the Color Ceiling / Recipe Viewer UI and the run-record JSON read from; the per-recipe rollups shown in the app derive from the recipe_table and the color_recipe_breakdown artifact, not from re-solving.
