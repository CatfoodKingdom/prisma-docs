Stage 1 and 2 solver kernels

In one sentence: staged_solver_helpers.py is a bag of stateless NumPy kernels that the staged solver uses to carve an image into colour zones (Stage 1) and to turn the per-pixel colour stacks into a scored grid of cap-thickness colour predictions (Stage 2).

What this page is

pipeline/staged_solver_helpers.py holds the shared, side-effect-free math kernels for the two early stages of the live solve. They do not own any solver policy — no commitment logic, no zone graph traversal, no budgeting decisions. They take arrays in and hand arrays back. The orchestration that calls them lives in generator.pipeline.staged_runner; this module is the low-level toolbox.

These kernels run on every webapp solve. The webapp solve runs the staged backend (pipeline/runner.py:843 imports and calls run_staged_backend_path, defined at pipeline/staged_runner.py:10310), not the legacy “6-step” engine in solve.py. So everything below is on the hot path for a real generate.

Origin note (stale-docstring defuse)

The module docstring claims these functions “used to live in the retired dual-resolution solver wrapper” (pipeline/staged_solver_helpers.py:1-8). That is a historical note about where the code moved from, not about its current status. The functions are live — every public name in __all__ (pipeline/staged_solver_helpers.py:306-315) has at least one in-tree caller (see Liveness below). Do not read “retired … legacy … dead solver wrapper” in that header as a claim that this code is dead; the wrapper is gone, the kernels were lifted out and kept.

Stage 1 — zone-label generation

generate_stage1_zone_labels (pipeline/staged_solver_helpers.py:254) produces a 2-D integer label map the same height/width as the planning image, where each integer is a colour zone. It is “dense Stage 1 zone-label map without solver commitment logic” (:264) — it only segments; the runner decides what to do with the zones.

Cell size. If scale is not passed, it is derived as round(color_region_target_mm / solver_fine_pitch_mm), floored to ≥1 (:266-271). pixels_per_cell = scale * scale (:272). In the live path the runner passes an explicit scale override (coarse_scale_override, derived from the stage-1 coarsening factor) when staging is active (staged_runner.py:702-717), so the internal derivation is mostly a fallback.

Three cell modes (:274-298), selected by cfg.cell_mode:

cell_modeMechanismNotes
"grid"Plain scale × scale square tiling via np.repeatDeterministic axis-aligned cells; default-ish
"felzenszwalb"skimage.segmentation.felzenszwalb, scale = max(1, pixels_per_cell*0.8), sigma=0.8, min_size=pixels_per_cellContent-aware blobs
anything elseskimage.segmentation.slic, n_segments = (h*w)//(pixels_per_cell*4), compactness=10SLIC superpixels; the catch-all branch

After segmentation the labels are forced contiguous (:300), optionally boundary-smoothed if cfg.smooth_boundaries is set (:301-302, radius from cfg.boundary_smooth_radius), then relabelled contiguous again on the way out (:303).

_smooth_label_map (:216) iterates radius passes; each pass finds 4-neighbour boundary pixels and replaces each with the majority label in its 3×3 window (np.bincount(...).argmax(), :240-242). It short-circuits when a pass finds no boundary (:232-233) and finishes with a contiguous relabel (:244). _relabel_contiguous_labels (:247) is the trivial “unique + inverse-index reshape” that guarantees ids are 0..n-1 as int32.

The radius/boundary_smooth_radius plumbing here is the same smooth_boundaries feature noted as bug-fixed 2026-04-12 in project memory; this kernel is where the majority vote actually happens.

Stage 2 — from per-pixel stacks to a scored cap grid

Stage 2 (entry around staged_runner.py:6195) turns LUT-queried per-pixel thicknesses into a compact, scorable representation. The kernels do three jobs: encode, predict, score.

Encode — _vectorized_stack_ids

_vectorized_stack_ids (:21) collapses the per-pixel thickness dictionary into a small set of unique stacks. Mechanics:

  1. Round each filament’s thickness to an integer layer count: rint(raw / layer_height) per palette entry (:31-34).
  2. Pack the per-pixel layer-count vector into a single integer using a positional base of max_layers + 1 (:36-38) — a mixed-radix encoding where each filament occupies one “digit”. max_layers defaults to 50 but the live caller passes cfg.effective_max_layers() (staged_runner.py:6218).
  3. np.unique(..., return_inverse=True) gives pixel_stack_ids (per-pixel index into the unique table) and the unique codes (:40-41).
  4. Decode each unique code back into a {filament_id: thickness_mm} dict, dropping zero-layer entries (:43-53).

Returns (pixel_stack_ids, unique_codes, unique_stack_dicts). This is the key compression step: a megapixel image with a handful of distinct stacks becomes a few hundred unique-stack dicts the rest of Stage 2 reasons over.

Palette order matters for the photo-stack model. The caller chooses the palette ordering before encoding: for the photo-stack model it keeps cfg.palette order (staged_runner.py:6209-6212) because that model is an ordered physical stack; for the historical spline model it sorted()s the palette because spline composition is order-insensitive. The kernel itself just encodes whatever ordered palette it is handed.

Predict — _predict_transmission_batch

_predict_transmission_batch (:58) evaluates the spline transmission model for a whole array of thicknesses at once. It pulls the per-channel splines via lib.transmission._get_splines (:60-62) and:

  • thickness ≤ 0 → transmission 1.0 (:68, :72);
  • thickness within knot range → clipped [0,1] spline eval per R/G/B (:74-78);
  • thickness beyond the last knot → per-element lib.transmission._extrapolate (:80-82).

Returns an (N, 3) RGB transmission array. This is the spline-model batch evaluator; see lib.transmission for the underlying PchipInterpolator splines and the transmission contract T_total = T_wb · ∏ T_fi · T_wc.

Cap-OKLab precompute — the two grids

Stage 2 needs, for every unique stack, the OKLab colour it would show at each possible white-cap thickness. There are two implementations, picked by model kind at staged_runner.py:6241.

Spline model — _precompute_cap_oklabs

_precompute_cap_oklabs (:87) builds the cap grid for the historical spline model:

  1. Cap steps 0 .. d_wc_max at layer_height spacing (:94-98); d_wc_max = cfg.effective_boundary_d_wc_max().
  2. White-cap transmission for all cap steps via _predict_transmission_batch (:100-102).
  3. For each unique stack: compose white-base + colour layers with compose_stack (:108-112, from generator.model), multiply by every cap transmission, convert to OKLab with to_oklab (:114-115).
  4. Over-budget inf sentinel (:116-126): the cap headroom left by this stack’s colour thickness is computed with max_cap_height_for_colour_thickness from generator.pipeline.height_budget (remaining = t_max - d_wb - colour_thickness, clamped to d_wc_max). Any cap step beyond that headroom has its OKLab row set to np.inf (:124-125). Because the downstream scorer takes a Euclidean distance and then .min() over cap steps, an inf row can never be the chosen cap — so the optimizer is structurally forbidden from selecting an unprintable cap. This is the mechanism that keeps the solve inside the ~3 mm total-height budget.

Returns (cap_values, all_oklabs) where all_oklabs is (unique_stacks, n_steps, 3).

Photo-stack model — _precompute_cap_oklabs_vectorized

_precompute_cap_oklabs_vectorized (:131) does the same job for the photo-stack provider, but returns two views (:138-147):

ViewBudget handlingUsed for
scoring_oklabsover-budget cells masked with inf (:175-176)zone scoring — the optimizer can’t pick unprintable combos
dense_oklabsfinite at every cellStage-4 cap lookup always gets a colour answer; budget enforcement is the cap planner’s job

Cap steps come from the LUT cap grid (deduped from each LUT’s cap_thicknesses, :153-162) — never scavenged from the pruned LUT, never routed through the row-shaped predictor (docstring :144-146, behaviour :163-177). The actual grid evaluation is delegated to predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:957), which returns (dense_oklabs, within_budget); the budget mask is applied here at :175-176 with budget_mm = t_max - d_wb (:173).

The caller binds the dense view to dense_cap_oklabs and the scoring view to all_oklabs (staged_runner.py:6242-6248); the spline branch sets dense_cap_oklabs = all_oklabs since it has no separate dense view (:6250-6251).

Score — _score_candidates_batch

_score_candidates_batch (:190) scores a set of candidate stacks against a zone’s pixels. For each candidate it computes, per pixel, the OKLab distance to the candidate’s best cap step, then averages over the zone’s pixels — “mean optimal-cap dE” (:180-187). It has two code paths:

  • Vectorized (:205-208): if the pixels × candidates × steps × 3 tensor is under 50 M elements, it broadcasts the whole thing, squares-sums-sqrts to dE, takes min over cap steps then mean over pixels.
  • Per-candidate fallback (:210-213): above that size it loops candidates and calls _score_stack_for_cell (:180) one at a time to cap peak memory.

Both return a (candidates,) array of scores; lower is better. This is the kernel the zone-candidate machinery calls in two places: enumerating each zone’s own candidates (staged_runner.py:794) and scoring borrowed neighbour candidates during augmentation (staged_runner.py:889). The candidate ids being scored are unique-stack ids, and the cap grid passed in is the scoring view (all_oklabs), so the inf sentinel rows propagate into these scores as “never selected”.

Reuse by the luminance handler

_predict_transmission_batch is also imported and used outside Stage 2 by generator.pipeline.luminance_handler (pipeline/luminance_handler.py:19). In _sample_white_luminance_curve’s spline branch it computes white-cap transmission for an array of cap thicknesses (luminance_handler.py:407-410), then converts to OKLab. So this one kernel serves both the Stage 2 cap precompute and the white-cap luminance handling — a single source of truth for “spline transmission of many thicknesses at once.” (The photo-stack branch of that same method bypasses the kernel and asks the provider’s own sample_white_cap_oklab directly, luminance_handler.py:399-404.)
