The vectorized photo-stack LUT evaluator

In one sentence: photo_stack_lut.py re-implements the frozen photo-stack v2 colour model as pure NumPy arrays so the generator can evaluate hundreds of thousands of candidate stacks per second when building the Joint LUT and precomputing cap curves — without ever changing the model the slow row-shaped predictor exposes.

This page covers the fast path. The trustworthy-but-slow path is the row-shaped predictor on the appearance provider (predict_stack_model_linear_rgb_batch, appearance_model.py:381), which evaluates one stack per pandas row. That is fine for isolated predictions and calibration review, but LUT construction needs a different runtime shape: it sweeps a regular grid of millions of stacks. This module mirrors the same equations over array columns so that hot path never pays the per-row cost. Both routes must agree to floating-point tolerance — compare_vectorized_provider_predictions (photo_stack_lut.py:1103) exists precisely to assert that.

If you just want to drive the generator, you never call this module directly — it runs automatically whenever the active provider is a photo-stack bundle. The “how it works” sections below are for the developer who has forgotten the backend.

Why a second implementation exists

The model is nonlinear and stateful per stack: white-context optical density (OD), cap attenuation, multi-colour interaction, ordered tint retention, single-colour cap transfer, two-colour endpoint corridors, and a learned correction layer. The row predictor walks these stages one DataFrame row at a time. Re-expressing every stage as a batched array op lets one call process an entire filament subset’s grid at once.

The contract is “mirror, don’t reinvent”: every constant and helper is imported from the same lib.photo_stack_model.predictor and lib.photo_stack_model.correction_layer the row predictor uses (photo_stack_lut.py:21–photo_stack_lut.py:62). The builder version string photo_stack_lut_appearance_v2_2026_06_10 (photo_stack_lut.py:64) tags LUT caches so a model change invalidates them.

The OD-composition pipeline

predict_subset (photo_stack_lut.py:827) is the core. For one filament subset and a column of per-row layer counts plus cap indices, it composes the stack in optical-density space, where stacking is addition, then converts to linear RGB once at the end.

OD is the natural domain because transmission multiplies (T_total = ∏ T_i) and log turns products into sums. The evaluator builds total_od additively, then maps back with t_from_od (predictor.py:301), which is floor + (1 − floor)·exp(−od) — the floor models the lightbox/material light leak. layer_od (predictor.py:762) samples a filament’s measured OD curve at a thickness, with a frozen high-thickness taper.

The additive composition in predict_subset (photo_stack_lut.py:884) is:

total_od = latent_color
         + white_bulk          # white base OD + white cap OD
         + white_context       # white reacting to colour load
         + cap_attenuation     # cap surface darkening
         + interaction         # multi-colour cross terms

clipped to [0, 20], then rgb = t_from_od(total_od, floor) and lab = linear_rgb_to_oklab(rgb). After that base OKLab, OKLab-space refinements layer on (these are not OD-additive — they pull hue/chroma/lightness toward learned anchors):

Rows are grouped by an active-filament bitmask key (_active_key, photo_stack_lut.py:193) so every row in a group shares the same set of present colours and can run one stage path together.

The whole grid is sampled from precomputed OD tables built once in __init__: cap_od_table over cap steps (photo_stack_lut.py:178) and color_od_tables per filament over colour steps (photo_stack_lut.py:185). A row indexes these tables by its integer counts — no per-row curve sampling.

Model domain vs appearance projection

The evaluator works entirely in the model domain (flatfield-normalized model RGB). The conversion to the camera-appearance domain is a separate, explicit step applied to the finished array:

  • predict_combo_model_linear_rgb (photo_stack_lut.py:917) returns model-domain RGB — no projection.
  • iter_photo_stack_lut_arrays (photo_stack_lut.py:1038) and predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:957) call provider.project_model_linear_rgb_to_appearance (photo_stack_lut.py:1090, photo_stack_lut.py:1033) after model evaluation, then OKLab.

Trap, confirmed from code: that projection is currently an exact pass-through. project_model_linear_rgb_to_appearance (appearance_model.py:418) literally return np.asarray(rgb) — its docstring calls it a “compatibility pass-through for the retired solve-domain conversion.” So today the appearance and model domains coincide here; the call sites keep the seam so a real transform could be reintroduced without touching the evaluator. Do not document this as an active colour conversion — it is a no-op slot (the docstring at photo_stack_lut.py:972 that says appearance-named methods are “now an exact model-domain pass-through” is accurate). Camera appearance is handled by the camera transform / ingress elsewhere, not here.

The inf over-budget sentinel

predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:957) returns (dense, within_budget):

  • dense is (n_stacks, n_caps, 3) OKLab, initialized to np.inf (photo_stack_lut.py:1016) and filled only for representable cells — cells whose per-filament step count exceeds max_layers stay inf because they cannot exist on the evaluator grid (representable, photo_stack_lut.py:1013).
  • within_budget is a boolean mask: a cell is allowed when its total colour steps fit the height left after the cap (allowed_steps, photo_stack_lut.py:1004–photo_stack_lut.py:1012) and it is representable (photo_stack_lut.py:1014).

The split matters. The dense grid is finite at every representable cell so Stage-4 cap lookups always get a colour answer; budget enforcement is the cap planner’s job, and a missing colour answer would force the slow row predictor (docstring photo_stack_lut.py:976–photo_stack_lut.py:984). The caller _precompute_cap_oklabs_vectorized (staged_solver_helpers.py:131) materializes both views: it copies dense and stamps inf onto the over-budget cells to make the scoring view (staged_solver_helpers.py:175–staged_solver_helpers.py:176), so the zone optimizer’s nearest-cap dE (_score_stack_for_cell, staged_solver_helpers.py:180) can never pick an unprintable stack — the inf distance excludes it — while Stage-4 still reads the finite dense view. inf is the sentinel that says “exists in colour space but not in the height budget.”

This entry point is live: _precompute_cap_oklabs_vectorized is imported and called from staged_runner.py:27/staged_runner.py:6242, and the staged runner is what the webapp solve actually executes (run_staged_backend_path, staged_runner.py:10310, dispatched from runner.py:846 — not the legacy solve.py CLI engine).

The zero-cap row-provider fallback (correctness guard)

At the top of predict_subset (photo_stack_lut.py:837) is a deliberate escape hatch. Rows whose cap thickness is zero (cap_steps_d[cap_indices] <= 1e-9) are not evaluated by the fast path. They are turned into StackRequests and handed to provider.predict_stack_model_linear_rgb_batch — the canonical row predictor (photo_stack_lut.py:843–photo_stack_lut.py:859).

Why: a zero cap changes the physical evidence context. A base + colour + 0-cap stack is colour-over-white, not a sandwich — the model’s cap-transfer and white-context machinery were fit on sandwiched evidence and would mis-extrapolate at the boundary. Rather than special-case every nonlinear stage for the cap-absent geometry, the evaluator delegates that rare boundary to the oracle so the fast LUT path “cannot drift from the canonical stack predictor” (comment, photo_stack_lut.py:839–photo_stack_lut.py:842). It is a correctness guard, not a perf path — zero-cap rows are uncommon and the row cost is acceptable for them. Remaining (non-zero-cap) rows proceed through the vectorized stages.

A second, related guard lives inside _latent_parts (photo_stack_lut.py:247–photo_stack_lut.py:253): when there is no colour layer and base and cap are the same white filament, the two adjacent white layers are physically one bulk of white, so the evaluator samples the nonlinear white OD curve at the combined thickness (collapsed_same_white_od_table, photo_stack_lut.py:179) instead of summing two separate curve samples — mirroring how the provider collapses the stack.

The learned correction layer

After the geometric stages, _apply_corrections (photo_stack_lut.py:739) applies the same empirical residual the row predictor applies via apply_photo_stack_correction (appearance_model.py:404). The evaluator compiles the correction artifact’s training rows once (_compile_correction_artifact, photo_stack_lut.py:703), groups them by a context key (unordered_color_key | white_key | evidence_class), and for each target row does a Gaussian-weighted local regression over the matching group’s residuals in a scaled feature space (photo_stack_lut.py:805–photo_stack_lut.py:823), capped by norm and authority. The evidence_class (_evidence_class, photo_stack_lut.py:908) is white_only / single_color_sandwich / cross_color_multilayer_sandwich, matching the corrector’s context partitioning. This stays in OKLab and only nudges L within [0,1].
