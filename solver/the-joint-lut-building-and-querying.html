The Joint LUT building and querying

The Joint LUT building and querying

Properties1
tagsgenerator, lut

Jun 21, 202612 min read

In one sentence: the joint LUT enumerates every printable (cap + colour) stack under a height budget, stores each stack’s OKLab colour in a chroma-weighted KD-tree, and the solver answers “which stack reproduces this pixel?” with a nearest-neighbour query.

This page covers Prisma/generator/lut.py (the spline path, the query functions, the disk cache, the convex hull, and the legacy cap-curve helpers) and Prisma/generator/photo_stack_lut.py (the vectorized photo-stack build path). For the surrounding solve flow see The Joint LUT and Staged Solve and the Joint LUT concept note. Architecture nodes: generator.lut, generator.photo_stack_lut, generator.appearance_model.

What “joint” means

Older designs solved cap thickness (luminance) and colour thickness in two separate steps. The joint LUT folds them together: a single LUTEntry enumerates combinations of (d_wc, d_c1, …, d_ck) jointly and stores oklab(T_wb × T_wc(d_wc) × ∏ T_ci(d_ci)) for each (lut.py:129–136, docstring formula lut.py:9–10). White base (d_wb) is fixed and baked into every entry, so the query target divides it out conceptually but the entries already include it. The cap dimension is carried per-entry in cap_thicknesses, and the chosen cap comes back to the caller under the reserved '__white_cap__' key.

A LUTEntry is one filament subset (size 1..k_max), not one filament. The build loops over itertools.combinations(filament_ids, k) for each k (lut.py:490–491), so a 3-filament palette with k_max=3 produces 7 entries (3 singles + 3 pairs + 1 triple). Each entry owns its own KD-tree.

Entry enumeration under a height budget (stars-and-bars)

For each subset and each cap step, the remaining height budget caps how many colour layers fit: remaining_steps = max(0, min(max_layers, int((budget_mm − d_wc) / layer_height))) (lut.py:505–506). Within that, _enumerate_combos_budget(k, remaining_steps) produces all non-negative integer tuples of length k summing to ≤ remaining_steps (lut.py:221–247). This is a direct recursive stars-and-bars generation rather than itertools.product + filter — the docstring notes that for k=3, max_steps=25 it yields exactly C(28,3)=3276 tuples instead of product’s 17576 (lut.py:226–228). k=0 returns a single empty row; k=1 returns arange(max_steps+1) (lut.py:230–233).

photo_stack_lut.py keeps a local copy of this function (_enumerate_combos_budget, photo_stack_lut.py:78–97) “to avoid importing lut.py from this helper module” — same algorithm, but int16 dtype instead of int. The two implementations are independent and must stay in lockstep; the photo-stack copy is the one used when building provider LUTs.

The budget itself: if t_max is None it defaults to d_wc_max + max_layers * layer_height (lut.py:442–443). The live webapp passes t_max = config.t_max − config.d_wb (the budget after the white base) at runner.py:797, 809, 826.

Transmission → OKLab → pruning

Both build paths share the same post-processing tail:

  1. Compose transmission. Spline path multiplies precomputed per-step transmission tables: T_wb (fixed), T_wc_cache per cap step, and colour_T_cache[fid] per layer count, all from predict_transmission (lut.py:461–479, 517–538). The product is clipped to [1e-9, 1.0] (lut.py:555).
  2. OKLab. to_oklab converts the linear-RGB transmission array to OKLab (lut.py:556).
  3. Prune near-duplicates. _prune_entries bins OKLab space at bin_width=0.005 and keeps one entry per bin (lut.py:351–391). Per bin it keeps the entry with lowest total colour thickness (less material), tiebroken by lowest cap thickness (brighter), via a single np.lexsort((cap_arr, total_colour, keys)) (lut.py:382). Binning packs the 3 quantised OKLab coordinates into one int64 key (lut.py:374–378).
  4. Build KD-tree (see below) and append the LUTEntry.

OKLab indexing with chroma weighting

The KD-tree is built from OKLab, but when chroma_weight != 1.0 the L* channel is divided by the weight before tree construction (lut.py:564–569): scaled_oklab[:, 0] /= chroma_weight. Dividing L* shrinks lightness distances in the search metric, so nearest-neighbour matching prioritises colour (a, b) over lightness. A chroma_weight > 1 therefore tolerates more lightness error to nail hue/chroma. The stored oklab array stays unscaled — only the tree sees the scaled copy — so reported dE can be recomputed in true (unweighted) OKLab space.

Every query mirrors this: the target’s L* is divided by cw = luts[0].chroma_weight before tree.query, and the returned distance (which is in scaled space) is replaced with the true unweighted Euclidean OKLab distance against the stored oklab whenever cw != 1.0 (query_luts lut.py:915–943; query_luts_batch lut.py:973–981, 1029, 1038–1040). See OKLab and Chroma weight.

Querying

All query functions take the List[LUTEntry] and scan every entry’s tree, keeping the global best per pixel. There is no subset pre-filtering — the nearest stack across all subsets wins.

query_luts_batch — the live webapp query

This is the function the running webapp actually calls. It is imported and invoked in the staged backend at staged_runner.py:23 and staged_runner.py:762 (query_luts_batch(state.luts, targets)). It is the only LUT query reachable from run_staged_backend_path — the webapp solve runs the staged backend, not solve.py’s engine.

  • Input: (N, 3) OKLab targets. Output: a dict filament_id → (N,) float32 thickness array plus '__white_cap__', and a (N,) dE array (lut.py:946–1042). Filaments not used for a pixel get 0.0.
  • Parallelism: when parallel=True, n_luts > 1, and n > 1000, each entry’s tree.query runs on a ThreadPoolExecutor; SciPy’s cKDTree releases the GIL so this is real parallelism (lut.py:987–998). The reduction (picking the winning LUT per pixel) is sequential numpy (lut.py:1001–1016).
  • An optional on_lut_done(done, total) callback fires per entry for progress reporting (lut.py:1006–1007, 1015–1016).

query_luts — single-target

Scalar version of the above for one OKLab target; returns (thicknesses_dict, dE) (lut.py:906–943). Live in the legacy solve.py engine only (solve.py:106).

query_luts_fixed_cap — two-pass cap smoothing (legacy)

Re-solves colour layers with the cap pinned per pixel, used by the legacy two-pass smoothing. For each pixel it queries the min(20, len) nearest neighbours, then among those keeps the best whose cap_thickness matches the supplied fixed_cap within 0.5 × layer_height, falling back to the unconstrained best if none match (lut.py:1045–1143). The returned '__white_cap__' is set to the fixed cap, not the LUT entry’s (lut.py:1141). Liveness: called only from the legacy CLI engine — solve.py:547 (solve_image’s smoothing pass) and pipeline_cli.py:607 (imported at pipeline_cli.py:583, inside the solve_regions smoothing branch). Not reachable from the staged webapp path — see below.

query_cap_fixed_colour / query_cap_fixed_colour_batch — test-facing only

The duals of query_luts_fixed_cap: pin the colour stack and sweep the cap to minimise dE (lut.py:1146–1292). They do not use the LUTs (the luts arg is “accepted for API symmetry”, lut.py:1166, 1226); they recompose transmission directly via compose_stack/predict_transmission. Liveness: unwired in product code. A repo-wide grep finds no caller inside Prisma/generator/ — the only caller is tests/generator/test_query_cap_fixed_colour.py. Treat them as a tested-but-dormant utility.

Two build paths

The runner selects the path by the appearance provider’s model_kind (runner.py:798):

model_kind == "historical_spline"  →  build_luts(...)            (runner.py:799)
otherwise                          →  build_luts_with_provider() (runner.py:815)

See Appearance provider for what supplies model_kind.

Path A — build_luts (spline + pair corrections)

build_luts(colour_profiles, wb_profile, wc_profile, …) is the historical spline path (lut.py:394–599). It requires wb_profile and wc_profile (raises otherwise, lut.py:432–433), auto-derives d_wc_max via derive_d_wc_max if not given (lut.py:436–439), precomputes transmission tables, enumerates combos per subset/cap, and builds entries.

Pair corrections (k=2 only). When corrections is supplied and k_max ≥ 2, _build_pair_corr_cache restructures the fitter’s correction dict into per-(overlay, base) arrays interpolated to each layer count (lut.py:53–103, 481–486). Only single-base pairs are kept (len(bases) != 1 is skipped, lut.py:77–78); multi-base correction entries are dropped. During build, for each 2-filament subset the A-on-B and B-on-A correction curves are looked up; if both exist they are averaged, otherwise the available one is applied, indexed by the overlay filament’s layer count (lut.py:493–536). Corrections never touch k=1 or k=3 subsets. The pair-correction maths is a Theo domain concern; see Pair corrections.

Live caller: runner.py:799 (webapp, when the active provider is the historical spline) and pipeline_cli.py:545 (CLI).

Path B — build_luts_with_provider (live photo-stack model)

build_luts_with_provider(provider, …) is “the coexistence path for context-aware photo models” and returns ordinary LUTEntry objects so the query code stays shared (lut.py:630–901). It has two internal sub-paths:

  • model_kind == "photo_stack_bundle" (the current default model): it iterates iter_photo_stack_lut_arrays(provider, …) from photo_stack_lut.py, prunes, chroma-weights, and builds trees (lut.py:739–804). This is where the heavy vectorized appearance model runs.
  • Generic provider fallback: for any other non-spline provider it builds StackRequest objects per combo and calls provider.predict_stack_linear_rgb_batch(all_requests) in one batch (lut.py:806–901, StackRequest constructed at lut.py:825–836). Pair corrections are not applied on this path (no corrections argument exists in this function).

Live caller: runner.py:815 — the webapp’s normal path whenever the active model is not the historical spline. This is the path exercised by typical solves today.

The vectorized photo-stack evaluator (photo_stack_lut.py)

iter_photo_stack_lut_arrays (photo_stack_lut.py:1038–1100) yields one PhotoStackLUTArrays (raw, pre-prune) per subset. It builds cap steps, instantiates a _PhotoStackGridEvaluator, and for each subset/cap enumerates combos and calls evaluator.predict_subset(subset, combos, cap_indices) to get model-domain linear RGB, then projects to appearance via provider.project_model_linear_rgb_to_appearance before OKLab conversion (photo_stack_lut.py:1081–1091). _PhotoStackGridEvaluator (photo_stack_lut.py:152–915) is a NumPy mirror of the frozen photo-stack equations — white context, cap attenuation, multicolor interaction, ordered-tint retention, single-colour cap transfer / profile blend, two-colour endpoint corridor, and a kernel-weighted correction residual. Its physics is owned by lib.photo_stack_model.predictor and is out of scope here; the contract is just “grid-aligned counts → OKLab, identical to the row predictor” (verified by compare_vectorized_provider_predictions, photo_stack_lut.py:1103, test-facing).

Note: project_model_linear_rgb_to_appearance and the appearance-named provider methods are pass-throughs that return model-domain values after the projection-slot retirement (appearance_model.py:418–420; predict_stack_linear_rgb_batch aliases the model-domain batch, appearance_model.py:413–416). See Model-domain ingress.

predict_combo_model_linear_rgb (photo_stack_lut.py:917) and predict_unique_stack_cap_oklab_grid (photo_stack_lut.py:957) are sibling entry points to the same evaluator used at solve time (Stage-4 cap planning), not during LUT build. predict_unique_stack_cap_oklab_grid is imported and called by the staged cap planner (staged_solver_helpers.py:149, 163); it internally calls predict_combo_model_linear_rgb (photo_stack_lut.py:1020). predict_combo_model_linear_rgb is also reached from the appearance provider’s deduplicated row predictor _predict_unique_combo_model_linear_rgb (appearance_model.py:537). Neither is imported in staged_runner.py. They share the evaluator so hot paths never pay the row predictor’s per-row cost (photo_stack_lut.py:933–935).

Disk cache (npz, trees rebuilt)

LUTs are cached to data_paths.LUT_CACHE_DIR = <cache>/luts/ (lut.py:46–47; data_paths.py:54). KD-trees are never serialized — only the arrays are saved, and trees are rebuilt on load (_save_luts_to_cache lut.py:281–298; _load_luts_from_cache lut.py:301–348). Because the tree is rebuilt at load, chroma_weight is re-applied at load time (lut.py:325–330), so the same cached npz can serve different chroma weights — but the cache key still includes chroma_weight, so in practice each weight gets its own file.

The provider cache’s builder_version is PHOTO_STACK_LUT_BUILDER_VERSION ("photo_stack_lut_appearance_v2_2026_06_10", photo_stack_lut.py:64) for photo-stack bundles, else "provider_generic" (lut.py:675–679). On load, _load_luts_from_cache rejects the file if any expected_metadata key mismatches or if the metadata block is missing entirely (lut.py:309–319) — so a builder-version bump auto-invalidates stale provider caches. The provider path also fills a diagnostics dict (cache key/path/hit, lut/entry counts) for observability (lut.py:660–737, 785–793).

The spline path’s _save_luts_to_cache is called with no metadata (lut.py:591), and _load_luts_from_cache is called there without expected_metadata (lut.py:453–454), so its only guard against staleness is the hash in the filename.

Convex hull construction

build_hull_from_luts(luts) stacks every entry’s oklab, deduplicates by rounding to 4 decimals, and returns a scipy.spatial.ConvexHull of all achievable OKLab colours (lut.py:1295–1309). It is the achievable-gamut surface used for hull-mode gamut projection: out-of-gamut targets are pushed onto the nearest hull facet. Live callers: runner.py:122 (_lut_mod.build_hull_from_luts(state.luts) inside _apply_target_gamut_mapping, hull mode) and solve.py:484–485 (legacy engine). The hull feeds solve.gamut_map_hull_batch (solve.py:180), which the runner calls at runner.py:127/131. See Gamut mapping.

Legacy cap-curve helpers

A separate 1-D structure predates the joint LUT and is retained “for dual-resolution cap refinement”:

  • CapCurve (lut.py:120–125): maps OKLab L* → cap thickness d_wc, holding d_wc_steps, L_values, and a T_wc_table.
  • build_cap_curve (lut.py:162–190): builds it by stepping cap thickness and recording L*.
  • cap_curve_lookup_batch (lut.py:193–216): vectorised nearest-L* lookup with a broadcast-floats chunking guard.
  • derive_d_wc_max (lut.py:141–157): finds the cap thickness where mean transmission drops below a threshold (default 0.05) — beyond this the cap is effectively opaque. This one is not legacy: it is used by both build_cap_curve and build_luts to auto-derive d_wc_max (lut.py:174, 437).

Liveness of the cap-curve trio: build_cap_curve and cap_curve_lookup_batch are imported and used by the legacy engine only. build_cap_curve is imported and called by the CLI: pipeline_cli.py:45 imports it (from lut import build_luts, build_cap_curve) and pipeline_cli.py:653 calls it. cap_curve_lookup_batch is imported in solve.py:35–36 and called at solve.py:364 (build_cap_curve is not referenced in solve.py at all). Both solve.py (its solve_image/smooth_cap/solve_regions functions, solve.py:410/371/577) and pipeline_cli.py constitute the legacy CLI engine — pipeline_cli.py:46 imports solve_image, solve_regions, … from solve. The live webapp does not call them; it goes through run_staged_backend_path (runner.py:843–846) and queries LUTs with query_luts_batch. So CapCurve/build_cap_curve/cap_curve_lookup_batch are live in the CLI path, dormant in the webapp path.

Driving it (for users)

You never call these functions directly — the generator does. What you control maps to build parameters:

  • Palette → filament_ids / subsets (more filaments ⇒ more subsets ⇒ bigger LUT, longer first build).
  • k_max → how many colours may stack per pixel (1–3). Higher k_max multiplies subset count combinatorially.
  • Height budget (t_max, d_wb, layer height) → how many layers fit, hence how many combos per subset.
  • Chroma weight → favour colour accuracy over lightness in matching.

First solve of a new palette pays the build cost; subsequent solves hit the npz cache. Changing a filament’s measured profile, the pair corrections, or the photo-stack model version (builder_version) invalidates the relevant cache automatically.
