Preprocessing operators

Preprocessing operators

Properties1
tagsgenerator, preprocessing

Jun 21, 20269 min read

In one sentence: five self-registering image operators (A1, B1, B3, C1, C2) that condition the solve-grid raster before the solve — every one ships off by default — plus two shared helpers, feature_scale (a nozzle-derived spatial anchor) and hue_interp (circular hue interpolation).

Preprocessing operators

These operators live in the preprocessing slot, a chain that runs on the loaded image before the colour solve. They are discovered from the filesystem under preprocessing/operators/ (no hand-maintained name list — _discover_preprocessing_operators, pipeline/registry.py:33; the “no hand-maintained tuple” rationale is at pipeline/registry.py:101), self-register via the @register_preprocessing decorator (pipeline/registry.py:123), and each subclasses PreprocessingModule (pipeline/base.py:73).

The slot is executed by run_preprocessing_pipeline (preprocessing/runner.py:210), called once from the live solve path at pipeline/runner.py:761 — which is the same run_pipeline that hands off to the staged backend (run_staged_backend_path, pipeline/runner.py:846). So these operators are live in the webapp solve, not legacy CLI-only code. They run on the post-load_image() raster, before LUT construction and the solve.

Related: Feature scale anchor · Protect subject blending · preprocessing slot runner · PreprocessingModule contract · Module management

All five ship disabled

Every operator declares default_enabled = False on its class, and the shipped app/modules.json keeps all five false (app/modules.json:4-8). The default-state machinery reads this attribute (pipeline/modules.py:62). You turn them on per-run in the module manager; nothing here is part of the baseline pipeline.

A1 — bilateral denoise (Wing A)

Edge-preserving denoise of the solve-grid raster via a single OpenCV bilateralFilter.

apply (a1_bilateral_denoise.py:108) runs cv2.bilateralFilter once with d = 2*radius_px + 1 (:123), sigmaColor = sigma_range, sigmaSpace = sigma_spatial (:124-129). It is the simplest operator: no palette, no protect mask, no OKLab — purely spatial sRGB smoothing.

It computes a “flat-region” mask up front (Rec.709 luma, local 5×5 std ≤ 0.02 — a1_bilateral_denoise.py:12-13, :30-32, :119) but uses it only for the reported metrics (flat-patch variance before/after, :141-142); the filter itself is applied globally, not gated by the mask.

B1 — print-scale bilateral (Wing B)

Bilateral flatten whose spatial sigma is tied to the printer’s physical feature scale, not a raw pixel count.

The key difference from A1: B1’s spatial sigma is derived in millimetres from the nozzle, then converted to pixels using the solver’s fine pitch. In _resolve_bilateral_params (b1_printscale_bilateral.py:57): sigma_spatial_mm = feature_scale_multiplier * feature_scale_mm (:63), then sigma_spatial_px = sigma_spatial_mm / solver_fine_pitch_mm (:64), clamped to [0.5, 15.0] px (:19-20, :66-71), and the kernel diameter is 2*round(sigma_spatial_px)+1 (:72). feature_scale_mm comes from resolve_feature_scale_mm(context) (:196) — see feature_scale below; solver_fine_pitch_mm defaults to 0.20 if absent (:197-199).

The filter can run multiple passes (:91-97), then clips to [0, 1] (:98).

ParamDefaultRangeMeaning (:112-155)
feature_scale_multiplier1.00.5–2.0Multiplies the shared nozzle-derived feature scale (2×nozzle). 1.0 = blur exactly at print-feature scale; <1 preserves detail; >1 flattens more.
sigma_range0.050.005–0.25Intensity sigma on [0,1]. Set higher than A1’s because B1 is a flattener, not a denoiser.

Protect-mask path (supports_protect_mask = True, :110): when protect_subject_enabled and a protect_mask are present (:217-224), B1 runs a second, gentler variant whose multiplier is max(0.5, 0.5 * multiplier) (b1_printscale_bilateral.py:21-22, :249-252) and blends aggressive↔gentle by the resolved protect weight via blend_aggressive_and_gentle (:261-265). This protects the masked subject from over-flattening. See Protect subject blending. Reported metrics include the resolved feature_scale_mm, sigma_spatial_mm/px, kernel_d_px, and flat-region variance before/after (:304-320).

B3 — TV flatten (Wing B)

Total-variation (Chambolle) denoise that drives regions toward piecewise-constant patches, optionally in OKLab.

apply (b3_tv_flatten.py:324) runs denoise_tv_chambolle from scikit-image (:61, called through _tv_denoise). The wrapper reflectively adapts to the installed skimage API (max_num_iter/n_iter_max, channel_axis/multichannel) at :63-73, so it survives version drift.

Weight autoscaling is the Wing-B signature: with weight_autoscale=True, effective_weight = tv_weight * (feature_scale_mm / 0.40) (_effective_weight, :202-206; baseline _AUTOSCALE_BASELINE_MM = 0.40 at :24), then clamped to [0.005, 0.30] (:25-26, :207-209) with a warning if it clamps (:210-215). The 0.40 baseline is the default-nozzle feature scale, so at a 0.2 mm nozzle autoscale is a no-op and the weight you set is the weight applied.

ParamDefaultRangeMeaning (:129-182)
tv_weight0.040.005–0.40TV regularization weight; higher = stronger, more piecewise-constant.
weight_autoscaleTrueboolScale weight by feature_scale_mm/0.40 so TV strength tracks the print-feature scale.

_run_tv (:218) branches on channel_axis: srgb_rgb denoises RGB directly (:226-233); oklab_L_ab converts to OKLab and denoises all three channels (:236-242); oklab_L_only denoises just L and re-attaches the original a/b (:244-250), then converts back to sRGB and clips (:251-255).

Protect-mask path: like B1, when a protect mask is active B3 runs an aggressive and a gentle pass (gentle effective weight = 0.35 * effective_weight, b3_tv_flatten.py:27, :369-372) and blends them (:373-377). Its _realized_metrics (:274) count small connected components (≤6 px) per quantized luma bin (:87-116) in protected vs background regions to quantify how much speckle was removed (:314-322).

C1 — achievable tonemap (Wing C)

Palette-aware tonal compression: remaps source luminance (OKLab L) into the range the chosen filament palette can physically reproduce.

C1 is the first operator that requires palette context (required_context = frozenset({"palette_metadata"}), c1_achievable_tonemap.py:229); it raises ValueError if context.palette_metadata is None (:314-317). The palette supplies the achievable black/white L (:324-325).

How it works: source is converted to OKLab (:320); shadow/highlight anchors are taken as percentiles of source L (:327-330); a 3-anchor PCHIP curve maps [shadow, midpoint, highlight] source L onto [achievable_black, midtone_target, achievable_white] (_build_core_curve, :41-61), where the midtone target is placed via 0.5 ** midtone_contrast (:49). Pixels outside the anchor range are extended by linear tails using the curve’s end slopes (_linear_tail_remap, :64-105), then clamped into the achievable range. The remap is blended with the original L by strength (_tonemap_pass, :168-171), and only the L channel is rewritten — a/b are preserved (:173-174).

ParamDefaultRangeMeaning (:231-272)

The constructor additionally requires shadow_percentile < highlight_percentile, raising otherwise (:294-297). Degenerate guards: C1 returns the input unchanged in two cases — if the achievable range collapses (white <= black + 1e-4, with a degenerate_palette metric, :332-341) or if shadow/highlight L coincide (no degenerate_palette flag, :343-351); both route through _zero_result (:187). C1 declares a preview_key (:223) so it can drive a preview tile. Protect-mask path mirrors B1/B3 (gentle strength = 0.5 * strength, :24, :422-432). Debug maps: delta_L, clamp_mask (:384-387).

C2 — soft gamut compress (Wing C)

Hue-preserving soft-knee chroma compression: pulls over-saturated pixels in toward the palette’s per-hue maximum chroma without shifting their hue.

Also palette-required (required_context = frozenset({"palette_metadata"}), c2_soft_gamut_compress.py:382). It reads two arrays from palette metadata: hue_degrees (bin centres) and max_chroma_by_hue (the per-hue chroma envelope) (:446-453). For each source pixel it computes OKLab hue + chroma (_hue_and_chroma, :48-53) and queries the chroma bound at that exact hue via circular interpolation (_query_chroma_bound → interpolate_circular_degrees, :36-45) — see hue_interp.

The soft knee (_run_compression_pass, :88): compression starts at knee_start_ratio * chroma_bound (:94); above the knee, output chroma follows a tanh curve filling the remaining “room” up to the bound (:109-112). The code comment at :107-108 pins this exact tanh form (“Consensus R6 pins this tanh form exactly; do not substitute”). Hue is preserved by scaling a/b uniformly (chroma_scale, :128-144); L is untouched (:146-149).

Debug maps: chroma_scale, over_bound_mask (:251-253).

feature_scale — the Wing-B spatial anchor

A single helper that turns the active nozzle diameter into a millimetre “print-feature scale” so B1 and B3 share one definition of “blur at print scale.”

resolve_feature_scale_mm(context, explicit_mm=0.0) (feature_scale.py:45) returns:

  • explicit_mm verbatim if > 0.0 (a per-call override; :65-66);
  • otherwise nozzle_diameter * 2.0 — the constant _FEATURE_WIDTHS_PER_NOZZLE = 2.0 (:37, applied :72-73), encoding the heuristic that a reliably reproduced feature is ~2 bead widths wide;
  • otherwise (missing / non-numeric / non-positive nozzle) the fallback _DEFAULT_FEATURE_SCALE_MM = 0.40 (:42, returned :71, :74).

So at the default 0.2 mm nozzle, feature scale = 0.40 mm (2 × 0.20). Callers are exactly the two Wing-B operators (b1_printscale_bilateral.py:8, b3_tv_flatten.py:14) and the evaluation harness — confirmed via grep. The module header notes printer_min_line_width_mm is deliberately not the anchor (it’s the extrusion floor, ~0.8×nozzle, a different quantity; feature_scale.py:15-17). This 0.40 mm value is also the _AUTOSCALE_BASELINE_MM baseline B3 divides by, which is why autoscale is a no-op at the default nozzle. Detail page: Feature scale anchor.

hue_interp — circular hue lookup

Wrap-aware linear interpolation of a per-hue value array, used by C2 to query the chroma envelope at any OKLab hue angle.

interpolate_circular_degrees(query_degrees, sample_degrees, sample_values) (hue_interp.py:19) linearly interpolates sample_values (indexed by hue bin centres) at arbitrary query hues, wrapping continuously across the 360°→0° seam. Mechanics: queries are normalised mod 360 (:62); a single sample short-circuits to a constant (:64-65); otherwise the sorted bins are wrap-extended by one bin on each side (last −360°, first +360°, :79-80) so a plain np.interp handles the seam without per-query branching (:82). Output is float32, same shape as the query (:82-83). Its only live caller is C2 (c2_soft_gamut_compress.py:13, used at :41) — confirmed via grep; the docstring notes it sits next to feature_scale.py as shared Wing-C infrastructure (:9-10).
