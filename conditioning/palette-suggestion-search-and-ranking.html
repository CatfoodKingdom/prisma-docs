Palette suggestion search and ranking

In one sentence: given an image’s colour signature and a pool of calibrated filaments, this picks the best small subset of colour filaments by greedily minimising weighted colour error against each filament’s printable gamut, then returns a requested number of distinct candidate palettes ranked by either mean error or a hole-penalising robust score.

This page covers the search (how palettes are explored) and ranking (how palettes are scored and ordered) halves of generator.palette.suggest. For how the image is turned into the colour signature that drives it, see Colour signature extraction. For the filament-gamut clouds the search scores against, see Palette gamut backends.

All code references are to generator/palette/suggest.py unless noted.

How to drive it (user-facing)

The generator web app’s Auto-suggest flow (POST /api/palette/suggest, generator/server.py:3746) takes these knobs from PaletteSuggestPayload (generator/server.py:3511):

FieldDefaultEffect
n_filaments7Target palette size (colour filaments, white not counted).
top_k5How many distinct candidate palettes to return. This is a contract — see below.
filament_idsnullRestrict the search pool; null = all profiled non-white filaments.
max_swapsnullIf set, run the swap-tier sweep instead of a single-size search.
palette_mode"standard""standard" or "luminance_detail" (chroma-emphasised). Validated at generator/server.py:3526.
improvement_thresholdnullCoverage gain (%) required to justify another swap tier.
force_all_tiersnullEvaluate every swap tier even if improvement stalls.

The web app always runs the thorough search. The endpoint hard-codes search_mode="thorough" (generator/server.py:3875); the old fast/quality switches were removed as user-facing complexity (generator/server.py:3755). The removed search_mode/quality_weights fields are now rejected loudly — the payload forbids extra fields (generator/server.py:3515) and search_mode="quality" raises inside suggest_palettes() (suggest.py:1411).

The job runs on a background thread; poll status at GET /api/palette/suggest/status (generator/server.py:3942) and cancel via POST /api/palette/suggest/cancel (generator/server.py:3956).

Two search modes

suggest_palettes() (suggest.py:1337) dispatches on search_mode after precomputing gamuts. Both modes share the same precomputed per-centroid distance tables (suggest.py:1448) so scoring a trial palette is a cheap np.minimum reduction, never a fresh KD-tree query.

Fast mode (CLI default, not used by the web app)

search_mode="fast" (the function default) runs a single deterministic pass (suggest.py:1485 onward):

  1. Greedy build — repeatedly add the one filament that most lowers the rank score, until n_filaments are selected (suggest.py:1489).
  2. Local search — repeatedly try swapping each selected filament for each unselected one; accept a swap only if it improves the score by more than 0.001 (suggest.py:1552). Capped at 20 sweeps (suggest.py:1521).
  3. Alternatives — fill the remaining top_k slots with the best single-swap neighbours of the primary palette (suggest.py:1581), then double-swap neighbours if still short (suggest.py:1625), then sort (suggest.py:1670).

Thorough mode (web app default)

_thorough_search() (suggest.py:968) chooses between two strategies by combination count:

  • Exhaustive when C(n_available, n_filaments) <= 50_000 (suggest.py:1002) → _exhaustive_search() (suggest.py:1022) enumerates every combination and keeps the best top_k, periodically trimming the running list to top_k once it grows past top_k * 5 (suggest.py:1087).
  • Multi-start greedy otherwise (suggest.py:1012) → _multi_start_search() (suggest.py:1095). It seeds from the 8 best individual filaments (n_starts = min(8, len(ranked)), suggest.py:1130), runs the same greedy-build-then-local-swap procedure from each seed (suggest.py:1159 build, suggest.py:1196 swap loop), and dedupes converged palettes by frozenset (suggest.py:1254).

Trap: there are unrelated “greedy”/“beam-search” implementations elsewhere in the generator (post-solve grouping/scheduling). The greedy here is palette-selection greedy over filament subsets — it has nothing to do with layer grouping.

Ranking: mean vs robust

Every trial palette is scored from precomputed distances by _score_palette_metrics() (suggest.py:878), which returns (mean_de, max_de, pct_above_threshold, p90_de). The single scalar used to order palettes comes from _palette_rank_score() (suggest.py:913):

ModeObjectiveCode
"mean"mean_de onlysuggest.py:923
"robust"mean_de + 0.35·p90_de + 0.15·max_de + 0.03·(pct_above_threshold/100)suggest.py:924–928

Robust mode deliberately penalises visible holes (a high 90th-percentile or worst-case centroid distance), not just the average — a palette with a great mean but one badly-missed colour region ranks worse than its mean alone suggests.

Default mode is data-driven (suggest.py:1405): "robust" when a gamut_backend is supplied (the model-backed web-app path), "mean" otherwise (legacy spline-gamut CLI path). Any value other than "mean"/"robust" raises (suggest.py:1408).

The component metrics:

  • mean_de — weight-averaged nearest-gamut OKLab distance across signature centroids.
  • max_de — worst single centroid distance.
  • pct_above_threshold — % of image weight whose nearest-gamut distance exceeds de_threshold (default SUGGESTION_COVERAGE_DE_THRESHOLD = 0.02, suggest.py:61, ~1 JND). Coverage surfaced to the UI is 100 - pct_above_threshold, computed in the response formatter (generator/server.py:3604); the swap-tier sweep computes the same quantity internally (suggest.py:1875).
  • p90_de — weighted 90th percentile via _weighted_percentile() (suggest.py:777).

The final candidate sort key is (rank_score, mean_de, max_de) (_candidate_sort_key, suggest.py:963) — rank score first, with mean and max as tie-breakers.

The requested-count distinctness contract

N requested = N distinct palettes whenever the pool allows. This is an explicit user contract, not a best-effort. The danger is that multi-start greedy converges to the same optimum from many seeds — and near-equal colour error is not user-equivalence (colour-distance metrics are not the final word; the right palette is the one the user picks). See Requested count is a contract and feedback-intuition-through-interaction.

When multi-start greedy returns fewer than top_k distinct palettes, _multi_start_search() fills the gap (suggest.py:1296–1331): it expands a frontier of the best single-swap neighbours of the palettes already found, skipping any subset already seen (suggest.py:1314), scoring each, and taking the best until top_k distinct palettes exist. The fast-mode alternatives generator does the analogous single-swap → double-swap fill (suggest.py:1581, suggest.py:1625).

Note: distinctness is by set of filament IDs (frozenset), not by recipe. Two palettes with the same filaments but different thickness assignments are the same candidate here — thickness is decided downstream by the solver, not by suggestion.

Swap-tier sweep

suggest_palettes_swap_aware() (suggest.py:1803) models the reality that an AMS unit only holds a few filaments at once, so reaching more colours means mid-print filament swaps. It sweeps tiers 0..max_swaps:

  • Tier t allows n_groups = t + 1 AMS loads (suggest.py:1854), so max_filaments = colour_slots_per_load * n_groups (suggest.py:1855), where colour_slots_per_load = slots_per_ams*n_ams_units - reserved_white - reserved_filler (suggest.py:1843).
  • For each tier it calls suggest_palettes() with that n_filaments and packages a SwapTierResult (suggest.py:1792) carrying the tier’s candidates, best mean dE, and coverage.
  • Early stop: after tier 0, if coverage improvement over the previous tier is below improvement_threshold (default 5.0%) it stops, unless force_all_tiers (suggest.py:1893).

Endpoint wiring

The /api/palette/suggest job (generator/server.py:3776) builds a common_kwargs dict once (generator/server.py:3874) — search_mode="thorough", white profiles, de_threshold, the excluded-filament set, and gamut_luminance_weight — then branches on max_swaps (generator/server.py:3891):

  • max_swaps set → suggest_palettes_swap_aware(...) (generator/server.py:3892), result formatted by _format_tier_response (generator/server.py:3903, defined at generator/server.py:3620).
  • max_swaps unset → suggest_palettes(...) (generator/server.py:3910), formatted by _format_candidate_response (generator/server.py:3916).

Two availability guards run before any palette is suggested: a configured white base/cap that is exclude_from_model raises 400 up front (generator/server.py:3768), and the colour pool is filtered through excluded_filament_ids(...) (generator/server.py:3886) so an excluded filament can never enter a suggestion. suggest_palettes() enforces the same drop internally (suggest.py:1400) and additionally filters to filaments the gamut backend supports() (suggest.py:1396).

Dead printability heuristics (flagged)

suggest.py defines three “printability metrics” under a # ── Printability metrics ── banner (suggest.py:1730):

FunctionLocationLiveness
estimate_fragmentationsuggest.py:1732Dead in production
estimate_grouping_costsuggest.py:1754Dead in production
estimate_swap_costsuggest.py:1776Dead in production

A whole-repo grep for these three names finds callers only in tests/generator/test_palette_suggest.py (lines 9–98) and their own definitions — no production code path imports or calls them. They are not wired into suggest_palettes(), suggest_palettes_swap_aware(), the rank score, or the server endpoint. None of the ranking objectives (suggest.py:913) reference fragmentation, grouping cost, or swap cost; ranking is purely colour-error driven. These are vestigial heuristics kept alive only by their unit tests.

Caveat: “dead” here means no production caller as of this audit. The functions still pass their tests and could be revived. Do not delete blindly — confirm the tests’ intent first.
