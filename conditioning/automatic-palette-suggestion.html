Automatic palette suggestion

In one sentence: given your source image and a library of calibrated filaments, palette suggestion answers “which N colour filaments should I load to print this picture?” — it summarises the image as a handful of weighted OKLab colours, builds the colour cloud each filament (and each pair of filaments) can physically reach when backlit, and picks the subset whose reachable cloud sits closest to the image’s colours.

This page covers the concept and the gamut machinery — how the image is reduced to a colour signature, how filament gamut clouds are computed, and how a palette is scored by distance-to-nearest-gamut. The search, ranking, and swap-tier sweep that turn those scores into a ranked list live on Palette suggestion search and ranking. Backend node: generator.palette.suggest.

Trust the code, not the header. The module docstring at palette/suggest.py:8 still describes a 6-step “greedy → pairwise → local search → top-K” pipeline, and suggest_palettes still defaults search_mode="fast" (palette/suggest.py:1342). The web app no longer uses that path: the endpoint forces search_mode="thorough" (server.py:3875) and the “quality” mode raises if requested (palette/suggest.py:1412). Everything below is read from the live code.

How to drive it

Suggestion is a web-app feature on the conditioning side of the generator. The endpoint is POST /api/palette/suggest (server.py:3746); it kicks off a background thread and returns {"status": "started"} immediately (server.py:3938), and you poll GET /api/palette/suggest/status (server.py:3942) for progress and the final result. A POST /api/palette/suggest/cancel (server.py:3956) requests cancellation.

The request body is PaletteSuggestPayload (server.py:3511), which forbids unknown fields — stale clients that still send the removed search_mode/quality_weights get a loud 422 (server.py:3515):

FieldDefaultMeaning
image_pathrequiredimage under the generator’s images dir (server.py:3517)
n_filaments7target palette size, colour filaments only (server.py:3518)
top_k5how many candidate palettes to return (server.py:3519)
filament_idsNonerestrict the pool; None = all profiled filaments (server.py:3520)
max_swapsNoneif set, run the AMS swap-tier sweep instead of a single suggest (server.py:3521)
palette_mode"standard""standard" or "luminance_detail" (server.py:3522)
improvement_thresholdNoneswap-tier early-stop gain % (server.py:3523)
force_all_tiersNoneswap-tier: evaluate every tier regardless of gain (server.py:3524)

palette_mode is normalised before validation (server.py:3526): "source"/"source_color"/"source_colour" all fold to "standard"; "luminance"/"detail"/"luminance-detail" fold to "luminance_detail"; anything else is rejected.

Two guardrails run before any work starts. The configured white base/cap are fixed inputs the suggester cannot drop, so if either is flagged exclude_from_model the endpoint refuses up front with a 400 (server.py:3766–3774). And colour candidates flagged exclude_from_model are stripped from the pool via excluded_filament_ids(...) (server.py:3886) so an excluded filament never appears in a suggestion.

The three-part idea

  1. Colour signature — reduce the image to K weighted OKLab centroids (k-means). Each centroid is a representative colour; its weight is how much of the image is that colour.
  2. Filament gamut clouds — for every filament, enumerate every printable (colour-thickness × cap-thickness) stack and convert the predicted backlit RGB into OKLab. That point cloud is everything that filament can reproduce. Pairs of filaments get their own sampled cloud to capture mixed colours (a green from cyan + yellow).
  3. Score = distance to nearest gamut — for a candidate palette, every signature centroid looks up its nearest point across the union of the palette’s single and pair clouds. The weighted mean of those nearest-distances (plus, in robust mode, the tail) is the palette’s error.

Steps 1 and 2 are this page. Step 3’s search and ranking are on Palette suggestion search and ranking.

Step 1 — the image colour signature

The signature is a ColourSignature (palette/suggest.py:95): centroids (K×3 OKLab), weights (K, summing to 1), n_pixels, and a domain tag (default MODEL_OKLAB_DOMAIN, i.e. "model_oklab").

The web app does not cluster raw image pixels. It first runs the image through the same target-cloud path the solve runner uses, so the colours being matched are the colours a solve would actually try to hit. solve_target_oklab_for_signature (palette/suggest.py:323) calls compute_solve_target_cloud (pipeline/target_cloud.py:64) and returns its solve_oklab cloud, optionally applying the gamut-white rescale (palette/suggest.py:341). That cloud is then clustered by extract_colour_signature_from_oklab (palette/suggest.py:286), which runs k-means and turns per-cluster pixel counts into normalised weights (palette/suggest.py:307).

Why the solve-equivalent cloud, not raw pixels? The signature’s domain must match the gamut clouds’ domain, or scoring is meaningless. The endpoint asserts this — _assert_signature_gamut_domain_match (palette/suggest.py:467) raises if sig.domain != gamut_backend.domain (called from palette/suggest.py:1404). Routing the image through the solve target cloud guarantees both sides live in model OKLab.

The k-means itself (_kmeans_oklab, palette/suggest.py:589) is a hand-rolled implementation: k-means++ seeding via a running-minimum distance (palette/suggest.py:599), then up to 30 Lloyd iterations using a scipy.spatial.KDTree for the assignment step and np.bincount for vectorised centroid updates (palette/suggest.py:617–632). Fixed seed 42 (palette/suggest.py:593), so a given image yields a stable signature. The web app asks for 100 clusters in standard mode (server.py:3842).

Saturated-corner caveat (from the code). Both solve_target_oklab_for_signature (palette/suggest.py:330) and extract_colour_signature (palette/suggest.py:383) carry a docstring note: deeply saturated source pixels map to inverse-LUT corners that are extrapolated beyond measured swatch evidence and can shift between Camera Transform generations. Suggestion deliberately mirrors solve ingress for those pixels rather than promising stable precision — it leaves downstream gamut handling to the normal solve machinery. See Gamut mapping and Model-domain ingress.

Luminance-detail mode

When palette_mode == "luminance_detail", the endpoint swaps in extract_luminance_residual_signature (palette/suggest.py:482) with 120 clusters (server.py:3827). The premise (its docstring, palette/suggest.py:491): a luminance-detail solve lets the white cap carry most of the source’s lightness structure, so palette suggestion should chase chroma reach instead of fitting full source luminance as if the colour stacks carried all the detail.

It does two things differently:

  • L is down-weighted for clustering. _scale_oklab_l (palette/suggest.py:454) multiplies the OKLab L axis by a small luminance_weight (0.15, server.py:3822) before k-means, so clusters split on chroma, not lightness (palette/suggest.py:529).
  • Centroids are chroma-weighted. Each cluster’s centroid is a chroma-importance-weighted average of its members (palette/suggest.py:556), and a cluster’s weight is the sum of its members’ chroma importance (palette/suggest.py:561), where chroma importance is the member’s chroma normalised against the 90th-percentile chroma and clipped to [0,1] (palette/suggest.py:519–521). Low-chroma greys contribute little weight; vivid colours dominate.

There is a companion metric knob, gamut_luminance_weight, derived from the session’s chroma_weight as 1.0 / chroma_weight in standard mode and detail_l_weight / chroma_weight in luminance-detail mode (server.py:3820, 3823). This scales the L axis again at scoring time (see “How a palette is scored” below). It is distinct from the clustering luminance_weight above.

extract_colour_signature (palette/suggest.py:359) and extract_appearance_colour_signature (palette/suggest.py:434, a deprecated alias with no remaining callers) are convenience wrappers that load + downsample + cluster in one call. extract_colour_signature is exercised by the dev CLI (main, palette/suggest.py:1926) and tests, not the web endpoint, which assembles the signature step-by-step. Confirmed by grepping server.py: the endpoint imports extract_colour_signature_from_oklab / extract_luminance_residual_signature (server.py:3788–3789), never the wrapper.

Step 2 — filament gamut clouds

A filament’s gamut is the set of OKLab colours it can produce when backlit, across every printable stack. Two providers exist for these clouds, chosen by which colour model is active.

Which provider you get

_build_palette_suggestion_model (server.py:3656) resolves the backend from the session’s appearance_model_provider:

Active colour modelGamut sourceranking_mode
historical_spline (default)the spline-profile functions in this module (server.py:3667)"mean" (server.py:3673)
photo-stack providerPhotoStackPaletteGamutBackend (server.py:3696)"robust" (server.py:3722)

When the spline path is used gamut_backend is None, and suggest_palettes falls back to the in-module gamut functions. When the photo-stack model is selected the backend object is passed through and used instead — same scoring contract, different colour predictions. (Both report domain "model_oklab".) The photo-stack branch requires a calibration-fit bundle and 400s if none exists (server.py:3686).

Single-filament gamut

For the spline path, _compute_single_filament_gamut (palette/suggest.py:639) enumerates a 2-D grid: every colour-layer count 0..max_layers × every sampled cap thickness from d_wc_min up to d_wc_max (sampling every 4th cap step for speed — cap_step=4, palette/suggest.py:648). It batch-evaluates the white-base, white-cap and colour transmissions, multiplies them per the transmission model

T_total = T_wb · T_wc · T_colour (palette/suggest.py:684),

masks out any stack whose cap + colour height exceeds the budget t_max (palette/suggest.py:689), clips, and converts to OKLab (palette/suggest.py:697). The result is a few-hundred-point cloud per filament.

For the photo-stack path, PhotoStackPaletteGamutBackend.single_gamut (palette/suggest.py:227) does the same enumeration but predicts RGB through a _PhotoStackGridEvaluator (palette/suggest.py:158, 247) instead of multiplying spline transmissions, then converts to OKLab via _gamut_oklab_from_model_rgb (palette/suggest.py:214). Single clouds are cached per filament (palette/suggest.py:229).

Pair gamut — capturing mixed colours

Two filaments stacked produce colours neither can reach alone (the canonical example in the code: green from cyan + yellow, palette/suggest.py:15). _compute_pair_gamut (palette/suggest.py:700) samples n_samples=10 evenly-spaced thicknesses per filament (palette/suggest.py:732) across a coarser cap grid (cap_step=8, palette/suggest.py:711), builds the full T_wb · T_wc · T_a · T_b product over the 3-D meshgrid (palette/suggest.py:741), budget-masks, and converts to OKLab. The photo-stack equivalent is PhotoStackPaletteGamutBackend.pair_gamut (palette/suggest.py:253), cached per unordered pair.

Pairs are on by default (include_pairs=True, palette/suggest.py:1353). Pair clouds are precomputed for all C(N,2) filament pairs in _precompute_centroid_distances (palette/suggest.py:833–855), which is the dominant cost and the source of the “Computing pair gamuts i/N” progress messages (palette/suggest.py:839).

Whites are not colour candidates

The photo-stack backend’s supports(fid) (palette/suggest.py:187) returns False for any white filament (is_white(text), palette/suggest.py:193) and for filaments absent from the model’s curves. The white base and white cap are fixed parameters of every gamut (the T_wb/T_wc factors), never selectable members of the palette.

How a palette is scored (the bridge to ranking)

The gamut clouds feed scoring through one precomputation. _precompute_centroid_distances (palette/suggest.py:795) builds, for each filament and each pair, a per-centroid nearest-neighbour distance array: it scales both the gamut points and the signature centroids’ L axis by gamut_luminance_weight (palette/suggest.py:820, 827), builds a KDTree over the scaled gamut, and queries each centroid (palette/suggest.py:828). The result is dist_single[fid] and dist_pair[(a,b)], each a (K,) vector.

Given a candidate palette, _palette_distance_vector (palette/suggest.py:859) takes the element-wise minimum across the palette’s single distances and all its pair distances (palette/suggest.py:868–874) — for each signature centroid, the distance to the nearest reachable colour in the whole palette. From that vector _score_palette_metrics (palette/suggest.py:878) produces four numbers: weighted mean dE, max dE, % of image weight above the JND threshold, and weighted p90 dE (palette/suggest.py:892–895). The in-gamut threshold is SUGGESTION_COVERAGE_DE_THRESHOLD = 0.02 OKLab (~1 JND) (palette/suggest.py:61).

These four metrics collapse into one rank score by _palette_rank_score (palette/suggest.py:913):

  • mean mode (spline path): score = mean_de (palette/suggest.py:923).
  • robust mode (photo-stack path): score = mean_de + 0.35·p90_de + 0.15·max_de + 0.03·(pct_above/100) (palette/suggest.py:924–929) — penalises visible holes in coverage, not just the average.

The actual greedy/exhaustive/multi-start search over palettes, the top-k assembly, the swap-tier sweep, and the response shape are all on Palette suggestion search and ranking.

What comes back

The endpoint formats either a candidate list (single suggest, _format_candidate_response at server.py:3590) or a tier list (swap-aware, _format_tier_response at server.py:3620), each candidate carrying filament_ids, mean_de, max_de, and coverage (server.py:3600, 3632). Alongside the candidates it returns signature_stats (clustering + ingress provenance, server.py:3846) and model_metadata (gamut backend, domain, provider fingerprint, ranking mode, server.py:3855). Both palette_mode and metric_luminance_weight are echoed so the UI can label the scoring space honestly.
