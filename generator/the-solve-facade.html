The Solve Facade

In one sentence: the facade (generator.facade, facade.py) is the thin front door to the solver — it takes a typed SolveConfig, picks a quality preset, resolves the pluggable grouping/preprocessing slots, translates everything into a PipelineConfig, and hands off to the one orchestrator (run_pipeline) that runs the staged backend.

This page is about the handoff layer, not the solve itself. For the solve walked end-to-end, see How a Solve Works; for the inversion math, The Joint LUT and Staged Solve; for the stage-by-stage diagram, Pipeline Map. Here we stay at contract altitude: what the entry points are, what they translate, and which one is dormant.

Why a facade exists

The module docstring (facade.py:2) names a stale filename (lith_facade.py) — ignore it. The real job, stated in the same header block (facade.py:4–10), holds up against the code: callers (chiefly the web server) should never reach into pipeline internals. They build one SolveConfig, call one of three functions, and get back a SolveResult. Everything between — module-state resolution, the SolveConfig → PipelineConfig translation, the conversion of the runner’s PipelineState back into a SolveResult — lives here so the rest of the app doesn’t have to know it exists.

The three live entry points

All three production entry points have the same shape: (img, config, progress=None, modules_path=None, module_state=None), returning a SolveResult (solve_compare returns a list). They differ only in the quality preset they pass and, for compare, the per-palette loop.

Entry pointDefinedUsed forPresetServer call site

Liveness is confirmed from callers, not docstrings. solve_preview, solve_full, and solve_compare are all imported in server.py:79–81 and invoked at the call sites above. solve_full has a second live caller in the preprocessing evaluation harness (evaluation/preprocessing_harness.py:166). These are the production solve surface.

Each one does the same four-step dance:

  1. Resolve pluggable slots — _resolve_pipeline_slots (facade.py:584) loads module state and builds the grouping module + the ordered preprocessor chain.
  2. Translate config — _to_pipeline_config (facade.py:612) maps SolveConfig → PipelineConfig.
  3. Run — run_pipeline (runner.py:587) executes the staged backend.
  4. Convert back — _state_to_solve_result (facade.py:864) turns the returned PipelineState into a SolveResult.

solve_compare (facade.py:992) wraps steps 1–4 in a loop over palettes: it loads module state once (facade.py:1004), then for each palette clones the config with the new palette via _replace_solve_config (facade.py:769), runs the four steps with palette_index/palette_count threaded into the runner for progress reporting (facade.py:1025), and catches per-palette exceptions — a failing palette becomes a {"error": ..., "palette": ...} dict in the result list rather than aborting the whole batch (facade.py:1031). Empty palettes short-circuit to an error dict before solving (facade.py:1007).

Quality presets

A QualityPreset is a tiny named record — name, max_layers, grouping_enabled (state.py:31). Three are defined as module constants:

Presetnamemax_layersgrouping_enabledDefined
PREVIEW_PRESET"preview"15Falsestate.py:39
FULL_PRESET"full"None (auto)Truestate.py:45
COMPARE_PRESET"compare"15Truestate.py:51

The preset is the only thing distinguishing the three entry points. It is passed through _to_pipeline_config onto PipelineConfig.preset (facade.py:765) and read back inside the runner. Two effects:

  • Layer ceiling. max_layers=15 caps preview/compare solves to a cheap low-resolution height stack; None means full solve lets the config derive it from t_max (see SolveConfig.effective_max_layers, facade.py:291).
  • Grouping gate. The runner only counts and runs the grouping stage when preset.grouping_enabled is true and a grouping module is actually present (runner.py:597). So even with grouping_enabled=True, a preset gets grouping only if _resolve_pipeline_slots handed one over.

Note the preset name also drives diagnostics: the palette-fit best-case diagnostics in _compute_palette_fit_diagnostics only compute when preset.name == "full" (facade.py:787), so the “solver loss” overlay is a full-solve-only artifact.

The dormant fourth entry point

solve_preview_progressive (facade.py:924) is the one to know about. Its own docstring (facade.py:932–941) says the progressive-solve HTTP feature and its mid-solve snapshot emitter were removed in the “Stage 3 cleanup,” and that the function survives only to thread an optional SnapshotPublisher (generator.pipeline.snapshot) into the preprocessing preview hook. This docstring is accurate — and verified independently from callers, not taken on faith:

  • No production code imports or calls it. A repo-wide grep finds it imported/called only in two tests: tests/generator/preprocessing/test_facade_threading.py:286 and tests/generator/preprocessing/test_f1_smoke.py:169.
  • The server’s only remaining mention of “progressive” is a static-file route comment (server.py:5914) that serves cached diagnostic/preview PNGs — there is no progressive solve endpoint.
  • The one other hit is a stale traceback in Prisma/output/generator.log (a log artifact, not live code).
  • A removal plan exists for it: Prisma/generator/docs/legacy_audit/12_WEBAPP_DEAD_BACKEND_CANDIDATES_REMOVAL_PLAN.md:59 lists removing solve_preview_progressive from facade.py.

So: DORMANT in production, retained only as a test vehicle. It runs FULL_PRESET (facade.py:943), and unlike the three live entries it forwards a snapshot_publisher into run_pipeline (facade.py:962; the runner accepts and attaches it at runner.py:593/runner.py:841). The _progressive suffix is, per its docstring, a historical artifact and a rename candidate. Do not wire new code to it without reviving the publisher path.

Resolving the pluggable slots

_resolve_pipeline_slots (facade.py:584) returns a (grouping, module_state, preprocessors) triple. It first loads module state via _load_module_state (facade.py:534) — which prefers an in-memory module_state dict, else reads modules_path through load_module_state, else returns None. The server passes modules_path=_MODULES_PATH so the live solve reads the on-disk module configuration.

Grouping — _resolve_grouping_from_state

_resolve_grouping_from_state (facade.py:513) picks the grouping module from saved state:

  • If module state has group_budget truthy, it builds GroupBudgetGrouping (the beam-search grouper, generator.grouping.beam_search), threading the nine grouping_* weights from SolveConfig (iterations, beam width, z-waste / overflow / swap-count / slot-stability weights, dE scoring toggles, in-group substitution) — facade.py:519–530.
  • Otherwise it returns GreedyGrouping (the default greedy grouper, generator.grouping.greedy_optimize) — facade.py:531.

This grouping object is only built when the preset’s grouping_enabled is true (facade.py:604); preview solves get None.

Disambiguation: the live grouping code here (generator.grouping.beam_search / generator.grouping.greedy_optimize) is not the experimental beam-search/greedy schedulers under generator.scheduling.policies. There are two unrelated beam-search and two unrelated greedy implementations in the tree — the facade wires the grouping ones.

Preprocessing — _resolve_preprocessing_from_state

_resolve_preprocessing_from_state (facade.py:547) builds the ordered list of enabled preprocessing operator instances. Unlike grouping, it is always resolved (legacy callers with no module state simply get an empty list, facade.py:561). It walks the operator registry (generator.pipeline.registry), keeps each operator whose module-state flag is on (falling back to the operator’s default_enabled, facade.py:569), passes the operator’s params block from config.preprocessing_params as constructor kwargs, then sorts by each operator’s order with ties broken by import path (facade.py:575). The chain is then threaded into the runner’s preprocessing slot. See How a Solve Works for how the chain runs inside the pipeline (and the fact that all built-in operators ship disabled by default).

The config translation — _to_pipeline_config

_to_pipeline_config (facade.py:612) is the big, boring, load-bearing function: it copies the dozens of fields from a SolveConfig (generator.facade) into a PipelineConfig (generator.pipeline.state) and attaches the resolved grouping, preprocessors, preprocessing_params, and preset. A few translation facts worth knowing:

  • Resolution is canonical-pitch only. The translation passes image_sample_pitch_mm and solver_fine_pitch_mm plus the stage-1 coarsening/lattice-offset fields (facade.py:696–700); there are no legacy resolution fields. The SolveConfig.__post_init__ applies a resolution backstop first (facade.py:283, via config.resolution_schema). See Settings, resolution, and the config contract and generator.config.resolution_schema.
  • Colour-model ingress passes through verbatim. model_domain_ingress and model_domain_ingress_lut_path ride along (facade.py:645) to the Model-domain ingress step; appearance_model_provider selects the Appearance provider (facade.py:691).
  • de_threshold defaults differ across layers. SolveConfig.de_threshold defaults to 0.01 (facade.py:212) while PipelineConfig.de_threshold defaults to 0.05 (state.py:72) — but the translation always copies the SolveConfig value through (facade.py:639), so the config you build wins; the PipelineConfig default only matters for direct construction.
  • Everything else is a near-mechanical 1:1 copy — whites, layer height, t_max/k_max, gamut mode, chroma weight, the full luminance-handler block, the staged-backend stage-2/stage-4 knobs, cap mode, protect-subject mask settings, and the printability fields. The list is long because SolveConfig is the kitchen-sink settings object; the translation is where it narrows to what the runner reads.

What comes back — SolveResult

run_pipeline returns a PipelineState; _state_to_solve_result (facade.py:864) converts it into the SolveResult dataclass (facade.py:359) that callers actually consume. The result carries the thickness maps (normalised to a typed ThicknessMaps in __post_init__, facade.py:394), the colour/white profiles, aggregate SolveStats, the original SolveConfig, the appearance provider, diagnostics (dE map, gamut mask — preferred from diagnostics, falling back to thickness maps, facade.py:405–415), grouping result, the canonical SolvedMaterialPlan, and the blueprint-triage printability report.

Disambiguation: SolveResult.blueprint_triage is the blueprint-triage PrintabilityReport (generator.pipeline.blueprint_triage.report), imported at facade.py:36. That is a different class from the mesh-side printability report (generator.mesh.printability). Don’t conflate them.

Two reconstruction methods live on SolveResult and matter for the UI’s colour views:

  • predict_image (facade.py:437) composes the full backlit sRGB image (base × colours × white cap) — routing through the appearance provider when it isn’t the historical spline, else predict_image_fast (generator.solve).
  • predict_image_color_only (facade.py:494) composes base + colours with the white cap dropped (every cap term zeroed via _cap_zeroed_thickness_maps, facade.py:474) so the cap’s luminance shaping doesn’t drown out the colour story. A zero cap thickness is the multiplicative identity in the transmission model, so this cleanly removes the term without touching the composition math. This is what feeds the recipe viewer’s colour-only render.

What this layer does not do

  • It does not run the legacy solve.py “6-step” engine. run_pipeline always dispatches to run_staged_backend_path (generator.pipeline.staged_runner) at runner.py:846, for every preset. The 6-step engine in generator.solve is the separate CLI engine; the webapp path is the staged backend. (predict_image_fast from solve.py is still used for fast forward prediction — that is just the composition helper, not the solve engine.)
  • It does not decide resolution, gamut mode, or which operators are enabled — those come in on the SolveConfig / module state. The facade only resolves and translates.
  • It does not persist anything. Saving runs, naming, archives, and caches are the server’s job (generator.server, generator.run_store).

Progress reporting — ProgressTracker

The facade defines a ProgressTracker (facade.py:45) — a structured progress reporter that wraps a callback and emits a dict at each stage advance and intra-stage percent update, with ETA estimation. Note the duplication: the runner has its own internal _ProgressTracker (runner.py:606), and that is the one driving the live solve’s stage callbacks; the facade entry points pass the caller’s raw progress callback straight into run_pipeline, not this class. The facade’s ProgressTracker is therefore a public helper at the facade altitude; treat its in-production use as unconfirmed here (I did not trace a live caller of the facade-level class) — the per-stage progress you see in the UI is emitted by the runner’s tracker. The emitted dict shape (stage key/label/index/count, pct, elapsed, ETA, palette index/count — facade.py:144) documents the progress contract either way, and palette_index/palette_count are the fields solve_compare populates per palette.
