Pipeline Map

In one sentence: one webapp solve runs a fixed six-step spine (run_pipeline) with two pluggable slots — preprocessing before targets, grouping after the solve — and the heavy lifting in step 4 is the staged Stage 0–5 backend (run_staged_backend_path), not the legacy CLI engine.

This is the wiring diagram for one full solve. For the narrative walk-through read How a Solve Works; for the optics read The Transmission Model and The Joint LUT and Staged Solve. The Mermaid below renders natively in Obsidian and in a Quartz-published site, so it travels with the docs.

Two layers: the spine, and the staged backend inside step 4

There are two nested orchestrators, and it matters which one you are looking at:

  1. The spine — run_pipeline in pipeline/runner.py:587. Six steps: load → build LUTs → gamut → solve → group → stats. This is fixed; the steps always run in this order.
  2. The staged backend — run_staged_backend_path in pipeline/staged_runner.py:10310. This is the spine’s step 4 (“solve”). Internally it runs its own Stage 0–5 sequence. The webapp always takes this path (runner.py:843-846); the “6-step” engine in solve.py is the legacy CLI engine and is not what the web app runs.

Fixed spine vs. pluggable slots

The orange nodes are the two slots — the only parts of the spine you can swap or disable from module settings. Everything else is hard-wired.

SlotWhere it plugs inWhat it can beEmpty / off behaviour
F1PreprocessingInside step 1, after profile load and before the target cloud (runner.py:695)An ordered chain of operators from the operators/ auto-discovery package (pipeline/registry.py:29)Empty chain is a legal no-op; the original raster passes through and state.source_image stays None (runner.py:695)
—GroupingStep 5, only when the preset enables it (runner.py:852-855)greedy_optimize (GreedyGrouping) or group_budget (GroupBudgetGrouping) — the two registered grouping modules (pipeline/registry.py:22)When config.grouping is None or the preset disables grouping, step 5 is skipped entirely (runner.py:597-600)

Slot resolution happens once, in the facade: _resolve_pipeline_slots reads saved module state and returns the grouping module + the preprocessing chain (facade.py:602-609). The preset controls whether grouping is eligible — FULL_PRESET.grouping_enabled = True (pipeline/state.py:45-49), PREVIEW_PRESET is False.

Disambiguation (do not confuse these): the grouping slot lives in grouping/ and chooses AMS swap groups. The Stage 2 beam-search inside the solve (_seed_zone_recipe_labels_with_beam, staged_runner.py:1440) is a different beam search that seeds zone recipes — unrelated to group_budget’s beam in grouping/beam_search.py.

Inside step 4 — the staged Stage 0–5 backend

run_staged_backend_path (staged_runner.py:10310) is a strict pipeline of artifact builders. Each stage consumes the prior artifacts and emits a new one; the whole lineage is returned as a StagedBackendResult (pipeline/staged_artifacts.py:584). The stage titles below are short paraphrases; the literal _emit(...) strings the progress bar shows are “Planning solve directives…”, “Planning color regions…”, “Solving visible color stacks…”, “Planning filler support…”, “Solving white cap structure…”, and “Building solved material maps…”.

Two diagnostic passes are gated by config and run between Stage 4 and Stage 5 — they emit counters, not geometry: geometry attribution when emit_geometry_attribution (:10659) and the blueprint printability diagnostic when emit_blueprint_printability (:10715). Both are confirmed wired (called inside the same function) but optional.

What lands on PipelineState

After the staged result returns, _finalize_staged_backend_state (runner.py:533) copies one bundle onto the legacy-facing state exactly once:

  • state.staged_result = the full StagedBackendResult
  • state.solved_plan ← build_solved_material_plan_for_export(...) (the export-facing plan; runner.py:539-547)
  • state.thickness_maps ← bundle thickness maps (float32 copies)
  • state.diagnostics[...] ← bundle diagnostics (the __de__ map is recomputed here, never read from thickness_maps — runner.py:577, see _recompute_de_diagnostics :165)
  • state.cap_quality ← _summarize_staged_cap_quality(...)

Appearance provider — the colour oracle on the side

The Appearance provider is not a stage; it is built once in step 1 (runner.py:668-677) and queried by step 2 (LUT build) and step 4 (the staged solve). model_kind == "historical_spline" is the default spline model; anything else (e.g. photo-stack) is a non-spline provider and triggers the provider-LUT path and the wider Stage-4 cap range (_provider_lut_d_wc_max, runner.py:44). See The Transmission Model.
