What Actually Runs

In one sentence: this is the single liveness map for the generator backend — which solve path actually executes, which modules are legacy or dormant, and which symbols survive only as test scaffolding — with every verdict confirmed by grepping the call graph, not by reading docstrings (most of which are stale).

The generator backend is large and has accreted dead ends: removed features that left remnant functions, experimental subsystems wired only into tests, and two whole modules that look live but no production caller touches. Module headers and docstrings are an unreliable guide — many still cite filenames and ports that no longer exist (see Stale headers — do not trust them). This page is the authority. Other liveness/printability pages link here rather than re-deriving each verdict.

How to read the status column:

  • LIVE — on the production solve or export path; runs on a normal web-app solve.
  • LEGACY — real, working code, but only reachable through the old CLI engine, not the web app.
  • DORMANT — imported and constructable, but no production path invokes it; wired only to tests/scripts.
  • REMNANT — a leftover of a removed feature; survives because something cheap still references it.
  • SUSPECTED INERT — strong evidence of no live caller, but the reference graph is subtle and a prior audit was burned by missing callers; treat as a hint, re-verify before deleting.

The live solve path, end to end

When you press Solve, server.py calls one of three facade functions — never solve_image:

Facade entryServer call sitePreset
solve_preview (facade.py:897)server.py:3998PREVIEW_PRESET
solve_full (facade.py:967)server.py:4740FULL_PRESET
solve_compare (facade.py:992)server.py:4094COMPARE_PRESET

All three translate their SolveConfig to a PipelineConfig and funnel into run_pipeline (runner.py:587). Inside run_pipeline, after the load / LUT / gamut stages, the solve stage does exactly one thing: it imports and calls run_staged_backend_path (runner.py:843-846). There is no branch here — the staged backend is not one solver among several, it is the solver. _finalize_staged_backend_state (runner.py:533) then copies that one result bundle onto the legacy-facing PipelineState fields the rest of the app reads. See How a Solve Works for the stage-by-stage walk and The Joint LUT and Staged Solve for what the staged backend does internally.

The “6-step” engine in solve.py is not this. solve.py’s module docstring (solve.py:2-18) describes a “joint LUT + two-pass cap smoothing” pipeline in six numbered steps. That is the legacy CLI engine (solve_image, solve.py:410), reached only through pipeline_cli.py. The web app never runs it. A few utilities from solve.py are still imported by the live runner (e.g. gamut_map_hull_batch, gamut_map_batch at runner.py:127, 138, 140, and predict_image_fast re-exported through generator.facade), but the solve_image orchestration body is legacy.

Dormant and inert subsystems

blueprint_triage (printability triage) — dormant, and not the mesh report

pipeline/blueprint_triage/ is a full printability-triage subsystem (analyze_triage, plan_fixes, apply_fixes, its own PrintabilityReport/PrintabilityError). On the live path it never runs: _finalize_staged_backend_state sets state.blueprint_triage = None (runner.py:555) and nothing on the staged path writes a real report; application.py:13-14 likewise only ever clears it. The facade carries the field through for compatibility (facade.py:392, 890) and the server reads it (server.py:4643, 4793) but always finds None. Its analysis/apply functions are exercised solely by tests/generator/blueprint_triage*.

Two unrelated PrintabilityReport classes. pipeline/blueprint_triage/report.py defines one (a triage report, with PrintabilityError, at report.py:180); mesh/printability.py:680 defines a completely different one (an export-facing mesh summary). They share a name and nothing else — printability.py:1069-1070 warns against conflating them. When a page says “PrintabilityReport,” it must say which.

scheduling — experimental offline layer scheduling

Prisma/generator/scheduling/ evaluates post-solve layer-swap schedules under fixed-budget policies (scheduling/__init__.py). No production module imports it — the only mention in source is a forward-looking comment in state.py:256. It is offline/experimental research code driven by tests.

Two beam-searches, two greedies. The live grouping module is grouping/beam_search.py (GroupBudgetGrouping, beam_search.py:436) / grouping/greedy_optimize.py (GreedyGrouping, greedy_optimize.py:35), selected in facade.py:515-531 (greedy is the default; the budget/beam variant only when module state opts in). The scheduling package has its own setup_beam_search_policy / layer_sparse_greedy_policy (scheduling/__init__.py:48-50) — same names, different subsystem, not on the solve path.

geometry — dormant region containers

Prisma/generator/geometry/ extracts vector ColourRegion polygons from a SolvedMaterialPlan (geometry/extract.py:210) and simplifies them (geometry/simplify.py). The package is internally consistent (__init__.py re-exports extract_regions/simplify_regions) but no module outside the package imports it — it is dormant. (The unrelated mesh/geometry_policy.py and assorted shapely.geometry imports are a different thing.)

mesh printability + canonical mesh — suspected inert

mesh/printability.py is a measurement-only toolkit (footprint alignment, inter-mesh seal, thin-island risk). The low-level measurement functions may be consumed by other mesh code, but the export-facing roll-up — build_printability_report (printability.py:1071) and the pass/warn/fallback/block + next_action=do_not_export classification ladder (in _classify_printability_summary, printability.py:1016-1038) — is flagged suspected inert in a code comment at printability.py:1061-1070. The code comment lists both the dedicated test and scripts/characterize_mesh_printability.py as callers, but grepping confirms the script imports only summarize_printability / render_summary_markdown (printability.py:727, 1139), not build_printability_report itself — so the export roll-up’s sole confirmed caller is tests/generator/test_mesh_printability.py. That comment is deliberately cautious because an earlier audit declared this “dead” after missing real references. Treat “inert” here as a hint, not a fact, and re-verify across tests, scripts, the config chain, and the separate blueprint_triage module before removing anything.

mesh/canonical_mesh.py (canonical_triangle_array, canonical_mesh.py:43) computes an order-insensitive geometry hash for output-equivalence checks. It is reached only through its canonical_mesh_hash wrapper (canonical_mesh.py:76), whose only non-test reference in the tree is scripts/benchmark_mesh_export_heavy_options.py; no Prisma/generator source path calls it on a live export — suspected inert by the same standard.

Reference-bundle replay — rejected for live solves

The photo-stack Appearance provider (PhotoStackBundleAppearanceProvider, appearance_model.py:210) requires an explicit live calibration candidate or its runtime_bundle.json. Passing a bare reference bundle path is allowed only as replay; the constructor raises otherwise (appearance_model.py:232-236: “select a live calibration candidate or pass a reference path for replay only”). So a default/reference bundle is never the live appearance model — the default provider is "historical_spline" (SolveConfig.appearance_model_provider, facade.py:241; wired into the runner at runner.py:670-671).

Removed-feature remnants

The progressive solve feature (mid-solve snapshots streamed to the browser) was deleted in the Stage 3 cleanup. What survives:

  • solve_preview_progressive (facade.py:924) — not imported by server.py (absent from the server.py:79-81 import block). Its docstring (facade.py:935-942) explains it is retained only as the facade-level vehicle that threads a SnapshotPublisher into the preprocessing preview hook, dormant in production, exercised by tests/generator/preprocessing/test_facade_threading.py and test_f1_smoke.py. Computationally it is identical to solve_full (both use FULL_PRESET); the _progressive suffix is a historical artifact and a queued rename candidate.
  • SnapshotPublisher.maybe_publish — the actual snapshot emitter — was removed; snapshot.py:6 records this and no maybe_publish call site remains in runner.py. The surviving publish_image_preview / snapshot_publisher threading (runner.py:593, 766, 841) is the preprocessing image-preview path, deliberately preserved as a cheap dormant hook, not the removed progressive-solve renderer.

Stale headers — do not trust them

Liveness can never be read off a module header in this codebase; cite line anchors instead. Confirmed stale headers:

FileHeader saysReality
solve.py:2lith_solver.pyfile is Prisma/generator/solve.py
facade.py:2lith_facade.pyfile is Prisma/generator/facade.py
model.py:2lith_model.pyfile is Prisma/generator/model.py
server.py:1-9”unified_generator/pipeline”, “port 8001”real dir Prisma/generator, port 8010
grouping/__init__.py:1, pipeline/base.py:1, pipeline/registry.py:1, pipeline/state.py:1# lithophane_generator/... pathsall under Prisma/generator/

Likewise, solve.py’s six-step pipeline docstring and the appearance-model “appearance-named” method docstrings describe shapes that no longer hold: the appearance methods are pass-through (they return model-domain values, not display-converted ones) after the projection-slot retirement (appearance_model.py:218-221). When in doubt, grep the caller.
