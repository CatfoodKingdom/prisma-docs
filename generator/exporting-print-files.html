Exporting Print Files

In one sentence: export turns a completed solve’s per-pixel layer thicknesses into printable 3D geometry — a white base, one object per colour filament, and a white cap — written as STL or 3MF for your slicer, with a separate AMS swap plan telling you when to change filament.

What export produces

A finished export folder contains, per object, a watertight mesh (one STL each, or all of them bundled into a single .3mf), plus an export_manifest.json describing every object, its material, the coordinate frame, and a quality/build report. The objects are always: a white base plate, one z-slab object per colour filament, and the white cap (possibly split into several bodies). Each object is tagged with the material it prints in (build_export_manifest, post_solve_export.py:1820; per-object record at post_solve_export.py:1875).

The contract lives in generator.mesh.post_solve_export (Prisma/generator/mesh/post_solve_export.py), deliberately kept clear of any FastAPI/UI concern. The webapp calls into it through one entry point, export_solve_bundle (post_solve_export.py:2120).

How you drive it (the webapp)

Export runs in the background so the UI can poll progress. The flow is:

HTTP routeWhat it doesCode
POST /api/export/files/startkicks off a background export job, returns a job_idserver.py:5666
GET /api/export/files/statuspolls stage/progress and, when done, the resultserver.py:5745

POST /api/export/filessynchronous variant retained for direct API/test callersserver.py:5651

The request body (ExportFilesPayload, server.py:742) has four export knobs, plus an optional card_id target selector (covered below):

  • geometry_source — "field_derived" (default) or "exact_raster" (server.py:743).
  • field_scale — must be one of 2, 4, 8, 16; default 4 (server.py:744, server.py:754). Only affects the field-derived white cap.
  • output_format — "3mf" (default) or "stls" (server.py:745, server.py:761).
  • validate_written_meshes — re-load each written mesh and re-check topology after writing (off by default; server.py:746).

Staleness guard: re-solve before exporting

If a solve-owned setting changed since the last solve, export refuses with HTTP 409 and the message “Solve is stale … Re-solve before exporting.” The check compares the current solve-owned fingerprint against the one captured at solve time (server.py:5443–5450). The swap-instructions endpoint enforces the same guard (server.py:5781–5788). This only fires for the live current target — exporting a saved card by card_id skips it.

The two geometry sources

Export can build the geometry two ways (GeometrySource, post_solve_export.py:55). Field-derived is the default; exact-raster is the faithful-to-the-solve alternative.

SourceColour stacks + baseWhite capEntry point
field_derived (default)exact rectilinear solve-grid objectsreconstructed as a smoother field, optionally on a finer grid (field_scale)build_field_derived_mesh_bundle_mixed_resolution, post_solve_export.py:1634
exact_rasterexact rectilinear solve-grid objectsone rectilinear cell per solve pixel — matches the solve exactlybuild_exact_raster_mesh_bundle, post_solve_export.py:1407

A key fact that holds for both sources: the colour stacks and white base are always exact solve-grid geometry. They are built the same way regardless of geometry_source (_base_and_color_objects, post_solve_export.py:1291, called from both builders at post_solve_export.py:1423 and post_solve_export.py:1706). The geometry source only changes how the white cap is built.

Because the colour layers are exact, the colour part of the print is blocky at the solve resolution — by design. This is the same fidelity rule the preview honours: the geometry never fakes detail the solve didn’t produce. See Thickness map and the white base / cap budget in How a Solve Works.

Why field-derived is the default

In the field-derived path, the combined colour-top “witness” surface is nearest-neighbour upsampled to the field grid (_nearest_upsample_map, post_solve_export.py:2067; lifted at post_solve_export.py:1721), and the reconstructed white cap is meshed on that finer grid via the hybrid white-cap builder. The result is a cap that can carry sub-pixel luminance detail and a smoother top surface than a per-pixel staircase, without disturbing the exact colour layers underneath. field_scale (2/4/8/16) sets how much finer the cap grid is than the solve grid.

The exact-raster path skips reconstruction entirely: it meshes the cap as one rectilinear interval on top of the colour floor (post_solve_export.py:1434), then falls through topology-safety strategies (below) only if that single body would weld badly.

The post-solve export contract

export_solve_bundle (post_solve_export.py:2120) is the single integration point. It is fed a materialized solve bundle — not the live session — and walks nine named stages (DEFAULT_EXPORT_STAGES, post_solve_export.py:187), each surfaced as an ExportProgressEvent (post_solve_export.py:88) the UI polls. The stages: load bundle → detect solve mode → prepare material maps → build geometry source → build colour/base meshes → build white-cap meshes → serialize outputs → validate meshes → write manifest.

What the solve owns vs. what export adds

Export reads, never re-derives, the solve’s geometry. Before the bundle is built, the server materializes the solve’s Thickness maps through _prepare_export_materialization (server.py:835) → prepare_export_material_maps. That step also pins mandatory product safety settings on the config (_force_mandatory_product_settings, server.py:847): the minimum white-cap thickness is snapped up to a whole number of layers, printability enforcement and cap-continuity cleanup are forced on, etc. These guarantee every viewer-facing surface keeps at least one white skin layer — a hard print constraint.

From the materialized bundle, export_solve_bundle reads three settings out of the solve’s own metadata (it raises rather than guessing if they’re missing — _first_config_float, post_solve_export.py:1952):

SettingLookup keysMeaning
pitch_mmpitch_mm, evaluation_pitch_mm, solver_fine_pitch_mm, solve_grid_pitch_mmsolve-grid XY pitch
layer_height_mmlayer_height_mm, layer_heightprint layer height (typically 0.08 mm)
d_wb_mmd_wb_mm, d_wb, white_base_thickness_mmwhite base thickness (typically 0.20 mm)

These flow into a RectilinearExportConfig (post_solve_export.py:200) and a GeometryExportPolicy (generator.mesh.geometry_policy) that all builders share. The defaults that originally shaped these come from PipelineConfig (pipeline/state.py:58): layer height 0.08 mm, white base 0.20 mm (d_wb), total height budget ~3 mm (t_max), cap variable for luminance.

Solve mode is auto-detected, not a toggle

Standard vs. luminance behaviour is detected from run/bundle metadata (detect_solve_mode_from_metadata, post_solve_export.py:253) — preferring the luminance_mode flag, with an array-presence fallback for old bundles. The webapp deliberately does not expose solve mode as an export option.

Optional border frame

If the solve was configured with a border, export wraps the content in a white frame and shifts all content objects inward by the border width (_with_export_border, post_solve_export.py:1178). The border prints in the white-cap material and is reported as a separate __border__ object. Border dimensions are read from solve metadata unless overridden (post_solve_export.py:2191–2226).

How the white cap is built (mesh internals → see linked page)

The cap is the most involved object and the only one whose construction differs by geometry source. The short version:

  • Field-derived: the reconstructed cap field is meshed by the hybrid builder (generator.mesh.hybrid_white_cap) on the finer grid; reconstruction itself lives in generator.mesh.field_white_reconstruction.
  • Exact-raster: the cap is a single rectilinear interval if it welds cleanly; otherwise export tries, in order, a topology-risk quarantine split, then an adaptive Z-partition, then per-level slabs — each a same-material body that keeps the geometry exact while avoiding non-manifold pinches after STL vertex welding (post_solve_export.py:1454–1509; topology_risk_column_mask from generator.mesh.rectilinear_interval).

Colour stacks get the same quarantine/slab fallbacks if a single colour body would weld badly (_build_color_quarantine_parts / _build_color_z_slab_parts, post_solve_export.py:1102, post_solve_export.py:985).

The full per-cell meshing, the rectilinear interval mesher, and the cap reconstruction math are out of scope here — they live in From solve to mesh the export pipeline.

Quality gates and the manifest

Every built mesh is topology-checked (_quality_for, post_solve_export.py:324; check_mesh_quality from generator.mesh.quality). A part “passes” only if it is watertight with zero open edges and zero pinch edges (_quality_passes, post_solve_export.py:328), and colour/cap parts additionally re-check quality after a strict STL-style re-weld (_strict_processed_quality, post_solve_export.py:336). Parts that still fail are quarantined into their own bodies rather than silently shipped.

The manifest’s top-level status is "ready" only if no object has open edges, pinch edges, or a watertight failure; otherwise "mesh_quality_failed" (post_solve_export.py:1833–1844). With validate_written_meshes=true, export additionally re-loads each written file from disk and re-checks it (_reload_quality_for_path, post_solve_export.py:2096).

STL vs 3MF

  • STL (output_format="stls"): each object becomes one .stl under …/stls/ (write_export_mesh_bundle_as_stls, called at post_solve_export.py:2344). The manifest names every file and its material so you can assign filaments in the slicer by hand.
  • 3MF (output_format="3mf", the default): all objects are packaged into a single {export_id}.3mf with filament assignments and material display names baked in (server.py:5546–5555), so OrcaSlicer opens it with materials already mapped. The single-file name keeps multiple lithophanes from colliding in one slicer project.

Both formats are handled symmetrically by generator.mesh.export_serializers.

AMS swap instructions (M600)

A multi-colour lithophane usually needs more colour filaments than your AMS has slots. The solver groups colours into swap groups that each fit, stacked by Z height, so you load one group, print up to its top, pause, swap to the next group, and continue. White base and white cap stay in fixed slots the whole print.

GET /api/export/swap-instructions (server.py:5774) returns this plan. It is computed live, not stored: AMS capacity is read from the current printer profile (ams_slots, white_slots — server.py:5800–5802), and the groups are re-reconciled against that capacity (reconcile_export_groups, server.py:5807) so changing your AMS after solving regroups correctly without a re-solve.

The response carries two artifacts, both built in generator.swap:

  1. Human-readable instructions (generate_swap_instructions, swap.py:272) — a text block with print dimensions, total height, per-group AMS slot assignments, the exact remove/load actions at each pause, and the white-cap section. Fixed slots are annotated [FIXED white base — do not change] (swap.py:382–396).
  2. Pause G-code (generate_orcaslicer_pause_gcode, swap.py:618) — one M600 ; pause for filament change per swap, each annotated with the approximate layer and Z height (swap.py:632–637).

How M600 maps to your print

For each boundary between consecutive groups, the swap height is the previous group’s z_end, and the layer is round(z_end / layer_height) (swap.py:402–403, swap.py:633). You add an OrcaSlicer pause (which emits M600) at that layer; when the printer pauses, you make the listed slot changes and resume. N groups means N-1 mid-print swaps. If everything fits in one AMS load, there are zero swaps and the G-code is just a ; No filament swaps needed comment (swap.py:628).

Note on the default AMS count: generate_swap_instructions defaults ams_slots=8 (2×AMS) when called directly (swap.py:283), but the live webapp passes the printer profile’s ams_slots, falling back to 4 if unset (server.py:5801). The number you see comes from your selected printer, not the function default.
