The pipeline orchestrator and shared state

In one sentence: pipeline/ is the small framework layer — a single orchestration function (run_pipeline) that loads profiles, runs an optional preprocessing chain, builds LUTs, hands the heavy solve to the staged backend, and finalises one shared PipelineState carrier, with two pluggable slots (preprocessing operators and grouping) that self-register from disk and persist their on/off state to JSON.

This is the developer companion to the generator.pipeline.runner package. It covers the data carriers, the fixed-spine-plus-two-slots design, the module plugin base classes, parameter self-description, registry auto-discovery, and module on/off persistence. It also flags two seams (revalidate() and snapshot.py) that are wired but dormant in production.

Related: generation_pipeline (narrative walkthrough) · generator.facade (the entry layer above this) · generator.pipeline.staged_runner (the solve engine below it) · The staged backend solve · Module management and settings.

How to drive it (users)

You never call this package directly — you change its behaviour through the Modules panel and Settings in the generator web app (port 8010). Three knobs land here:

  • Preprocessing operators — a chain of optional image-cleanup / gamut steps that run on the source raster before colour solving. Several can be on at once.
  • Grouping strategy — picks how filaments are packed into AMS swap groups when the palette has more colours than colour slots. Exactly one is active.
  • Quality preset — preview vs full vs compare; controls how many layers and whether grouping runs at all.

Toggling a module in the UI writes to a JSON file (modules.json) so the choice survives a restart. The contract is enforced server-side: see Module on/off persistence below.

The shared carriers (pipeline/state.py)

Everything the pipeline produces is accumulated on one mutable object that is threaded through every stage. There are four dataclasses, all defined in pipeline/state.py.

PipelineConfig — the frozen request

pipeline/state.py:58 is the full parameter set for one solve. It is built by the facade’s _to_pipeline_config (facade.py:612), not by hand. Beyond the ~120 plain fields it carries three slot-related members and a set of effective_* resolver methods:

  • grouping: Any | None (pipeline/state.py:161) — the resolved grouping instance (or None).
  • preprocessors: List[Any] (pipeline/state.py:170) — the ordered list of enabled operator instances. Sorting happens in the facade resolver, not here.
  • preprocessing_params: Dict[str, Dict] (pipeline/state.py:171) — the FULL per-operator params dict (every registered operator’s block at its default), rides along for fingerprinting.
  • preset: QualityPreset (pipeline/state.py:173) — defaults to FULL_PRESET.

The effective_* methods compute derived values so callers never duplicate the arithmetic: effective_max_layers() (pipeline/state.py:183) lets the preset cap layers, effective_white_cap() falls back to the base white, effective_d_wc_max() / effective_boundary_d_wc_max() derive cap authority, colour_slots() = ams_slots - effective_white_slots(). __post_init__ (pipeline/state.py:175) applies a resolution backstop from config.resolution_schema.

ProfileSet (pipeline/state.py:23) is a trivial three-field bundle of loaded filament profiles: colour_profiles, wb_profile, wc_profile. QualityPreset (pipeline/state.py:31) carries name, max_layers, and grouping_enabled. Three named instances exist:

The orchestrator: fixed spine plus two slots (pipeline/runner.py)

run_pipeline (pipeline/runner.py:587) is the whole orchestration. The structure is a fixed spine of always-run stages with two pluggable slots woven in. Reading the function top to bottom:

#StageKindAnchor
1Load — validate palette, load profiles, create appearance providerspinepipeline/runner.py:645-687
—F1 Preprocessing — run the enabled operator chain, overwrite state.imageslotpipeline/runner.py:689-774
2Compute observation + solve OKLab target cloudsspinepipeline/runner.py:776-782
—Configure luminance handler runtime (default-off)spinepipeline/runner.py:788-791
3Build LUTs — historical-spline path or provider pathspinepipeline/runner.py:793-830
4Gamut — _apply_target_gamut_mapping (incl. optional white rescale)spinepipeline/runner.py:831-833
5Solve — run_staged_backend_path then _finalize_staged_backend_statespinepipeline/runner.py:843-851
—Grouping — config.grouping.group(state, ...)slotpipeline/runner.py:852-863
6Stats — _compute_statsspinepipeline/runner.py:864-867

Two facts that the stale module header hides (cite the line anchors, not the header):

  • The webapp solve is the STAGED backend. Step 5 calls run_staged_backend_path from pipeline.staged_runner (pipeline/runner.py:843-846). It does not run solve.py’s legacy “6-step” CLI engine. _finalize_staged_backend_state (pipeline/runner.py:533) copies exactly one staged result bundle onto the legacy-facing state fields, and recomputes dE via _recompute_de_diagnostics straight into state.diagnostics (pipeline/runner.py:577).
  • Only the two slots are optional. The preprocessing slot is a legal no-op when config.preprocessors is empty (pipeline/runner.py:695 — the whole block is guarded). The grouping slot runs only when preset.grouping_enabled and config.grouping is not None (pipeline/runner.py:597-600), and the stage count bumps from 5 to 6 accordingly (pipeline/runner.py:602-604).

Observation vs solve grid

The runner is the single owner of target-cloud computation (pipeline/runner.py:776-782). observed_target_oklab lives on the observation grid (image_sample_pitch_mm); solve_target_oklab is projected onto the solve grid (solver_fine_pitch_mm) and is what the solve path and dE recomputation both consume. The white-point rescale and gamut map reassign solve_target_oklab in place (pipeline/runner.py:91, :146), so it is not necessarily the original projection array.

Progress reporting

_ProgressTracker (pipeline/runner.py:259) wraps the optional progress callback into the WebSocket stage protocol — advance(key, label) per stage, update_pct(done, total) for in-stage progress. It emits a dict with stage, stage_index, stage_count, elapsed_s, and palette index/count. No callback ⇒ tracker is None and nothing is emitted.

The module plugin contract (pipeline/base.py)

Two abstract base classes define what a pluggable module is. Both are ABCs with one abstract method and a describe() that serialises the module for the UI.

The live operators all live under preprocessing/operators/ and self-register — e.g. a1_bilateral_denoise, b1_printscale_bilateral, b3_tv_flatten, c1_achievable_tonemap, c2_soft_gamut_compress (each @register_preprocessing at e.g. preprocessing/operators/a1_bilateral_denoise.py:35). See generator.preprocessing.

GroupingModule

pipeline/base.py:122. An AMS grouping strategy. Same name / description / params / default_enabled attributes, with abstract method group(state, progress) -> None (pipeline/base.py:130) that mutates state in place. Two live implementations:

Classnamedefault_enabledAnchor
GreedyGroupinggreedy_optimizeTruegrouping/greedy_optimize.py:35
GroupBudgetGroupinggroup_budgetFalsegrouping/beam_search.py:436

GreedyGrouping partitions filaments into swap groups by brightness order (no-op when the palette fits one load). GroupBudgetGrouping is a beam search minimising wasted Z-band volume and exposes tuning params (grouping_priority, grouping_de_scoring, …) via ParamDef. Disambiguation: this group_budget beam search is the live grouping module — distinct from the experimental scheduling beam-search referenced elsewhere in the codebase. The facade’s _resolve_grouping_from_state (facade.py:513) instantiates GroupBudgetGrouping only if module state has group_budget on, else falls back to GreedyGrouping.

Asymmetry worth knowing: pipeline/__init__.py re-exports GroupingModule, register_grouping, get_grouping, list_groupings — but not PreprocessingModule or any of the preprocessing registry helpers (pipeline/__init__.py:2-26). Preprocessing operators import the registry decorator directly from pipeline.registry; grouping is the slot the package surfaces publicly.

ParamDef — parameter self-description

pipeline/base.py:24. A dataclass that lets a module describe one tunable to both the solver and the frontend renderer in one place. Core fields: name, label, type ("int" | "float" | "bool" | "choice" | "html" | "computed_text"), default, plus choices/choice_labels/min/max/description. UI-only fields: unit, tooltip, group, show_when (conditional visibility keyed on another param’s value), and order (pipeline/base.py:40-45). to_dict() (pipeline/base.py:47) emits the JSON the API/UI consumes, omitting None-valued optional keys. This is why the Modules panel can render parameter forms without any hand-written per-module frontend code.

Registry and auto-discovery (pipeline/registry.py)

The registry is two module-level dicts — _GROUPINGS and _PREPROCESSORS (pipeline/registry.py:15-16) — populated by class decorators at import time:

  • @register_grouping (pipeline/registry.py:117) stores cls under cls.name.
  • @register_preprocessing (pipeline/registry.py:123) stores cls and adds its name to PREPROCESSING_MODULE_IDS.

Two different discovery strategies:

Grouping is hand-listed. _KNOWN_GROUPING_MODULES (pipeline/registry.py:18) names the two modules to import and _KNOWN_GROUPING_NAMES = {"greedy_optimize", "group_budget"} (pipeline/registry.py:22) is the expected set. _ensure_store_populated (pipeline/registry.py:66) re-imports them when the store is empty or partial, with care to avoid creating duplicate class objects.

Preprocessing is filesystem-driven. _discover_preprocessing_operators (pipeline/registry.py:33) walks preprocessing.operators with pkgutil.iter_modules, imports every public (non-_, non-package) submodule in lex-sorted order (pipeline/registry.py:52-62), and that import position becomes each operator’s order tiebreaker. An empty operators/ package is legal — the slot becomes a no-op (pipeline/registry.py:40). Discovery runs once per process: _ensure_preprocessing_populated (pipeline/registry.py:98) re-discovers only when _PREPROCESSORS is empty.

Public accessors all call _ensure_registry_populated first: get_grouping / get_preprocessing (pipeline/registry.py:132 / :137), list_groupings / list_preprocessings (:142 / :147), and list_all_modules (pipeline/registry.py:159) which instantiates each class via cls.__new__ and returns its describe() dict. _clear_registry (pipeline/registry.py:152) is testing-only.

Module on/off persistence (pipeline/modules.py)

pipeline/modules.py reads and writes the JSON file of {module_name: enabled} flags. This is fully live — the generator server wires every endpoint to it.

FunctionBehaviourAnchor
load_module_state(path)read JSON, fill missing keys with defaults, normalisepipeline/modules.py:66
save_module_state(path, state)normalise then writepipeline/modules.py:75
toggle_module(path, id, enabled)flip one flag, validate the id, normalise, persist, return full statepipeline/modules.py:83

Two normalisation rules enforce the slot contract:

  • Grouping is exclusive. _normalise_grouping_slot (pipeline/modules.py:15) collapses the grouping flags to exactly one active module: if none are on, it picks the default_enabled one (greedy_optimize); if several are on, a non-default selection wins.
  • Preprocessing is non-exclusive. _get_all_defaults (pipeline/modules.py:51) collects every module’s default_enabled; preprocessing operators each contribute independently and several may be on at once. The zero-enabled case is a legal no-op.

The server side (all reading _MODULES_PATH): the modules-list endpoint (server.py:2904), the toggle endpoint calling toggle_module (server.py:2915-2921), a bulk save calling save_module_state (server.py:2932), and several solve paths that snapshot load_module_state into the run record (e.g. server.py:2066, :2144, :2175). The facade’s _load_module_state (facade.py:534) is the resolver-side reader that feeds _resolve_pipeline_slots (facade.py:584), turning the flag dict into resolved grouping + preprocessors for PipelineConfig.

Dormant and test-only seams

Two seams in this package are wired but not exercised by the production webapp solve. Both confirmed by grepping callers.

revalidate() — wired, narrow production use, mostly test-facing

revalidate(state) (pipeline/runner.py:250) recomputes __de__ from the current thickness maps against the solve-grid target, writing straight into state.diagnostics['__de__'] (Task 5.4 — no longer touches thickness_maps). It is a thin wrapper over _recompute_de_diagnostics (pipeline/runner.py:165).

Liveness: inside run_pipeline, the solve path calls _recompute_de_diagnostics directly during staged finalisation (pipeline/runner.py:577), not revalidate. revalidate itself is invoked in production only after a grouping run that actually substituted pixels — config.grouping.group() is followed by a conditional _recompute_de_diagnostics guarded on n_substituted_pixels > 0 (pipeline/runner.py:856-863; that branch calls _recompute_de_diagnostics, not the wrapper). The public revalidate symbol is re-exported (pipeline/__init__.py:7) and its direct callers are the test suite: tests/generator/test_pipeline_runner.py:64/:77/:91 and tests/generator/test_phase3_observation_solve_grid.py:189/:221. Historically it was the post-refinement dE hook for the now-removed refinements slot. Status: live function on a narrow grouping branch; otherwise a test/compatibility seam.

snapshot.py / SnapshotPublisher — one live hook, one dormant field

SnapshotPublisher (pipeline/snapshot.py:27) writes preprocessed source-image preview PNGs and their URLs into a shared progress dict via publish_image_preview (pipeline/snapshot.py:47). Liveness, two halves:

  • The preview hook is live but only reachable via a dormant facade entry point. publish_image_preview is called by the preprocessing runner per enabled operator (preprocessing/runner.py:281), which receives the publisher as a direct parameter (preprocessing/runner.py:216, threaded from pipeline/runner.py:766). A publisher reaches run_pipeline only through facade.solve_preview_progressive(..., publisher=...) (facade.py:930, :962). That facade function has no production caller — grep finds only its own definition (facade.py:924); the production webapp uses solve_full (server.py:4740), which never passes a publisher. Its own docstring marks it “currently dormant in production, exercised by the preprocessing preview tests” (facade.py:938-939).
  • The state.snapshot_publisher field is write-only and dead. The runner assigns it (pipeline/runner.py:841) but nothing reads it back — grepping .snapshot_publisher across Prisma/ finds only that single write. The live preview path threads its publisher as a function parameter, not via this field. The progressive-solve snapshot emitter (maybe_publish) was removed in the Stage 3 cleanup; the field’s docstring at pipeline/state.py:277-281 is code-true about this. A standing removal candidate is documented in Prisma/generator/docs/legacy_audit/12_WEBAPP_DEAD_BACKEND_CANDIDATES_REMOVAL_PLAN.md. Status: publish_image_preview hook = live but production-dormant (test-only entry); state.snapshot_publisher field = dead (write-only).
