How a Solve Works

In one sentence: a solve takes your source image and a palette of calibrated filaments and produces, for every pixel, how thick each filament should be so the backlit print matches the image — measured in OKLab, the colour space that tracks human perception.

This page follows one solve from the button press to the finished result. See Pipeline Map for the same thing as a diagram, and The Joint LUT and Staged Solve for the deep dive on the inversion itself.

Where a solve begins

When you press Solve in the web app, the server endpoint start_solve (server.py:4654) runs the solve on a background thread. It first translates your session settings into a typed SolveConfig via _build_solve_config (server.py:984) — palette, white base/cap, layer height, resolution, the chosen colour model, gamut mode, and the dozens of staged-backend knobs — then calls solve_full (server.py:4740 is the call site; solve_full itself is facade.py:967).

solve_full is one of three entry points in the generator.facade:

Entry pointUsed forQuality presetServer call site
solve_preview (facade.py:897)fast low-res gamut checkPREVIEW_PRESET (15 layers, no grouping)server.py:3998 (/api/gamut-preview)
solve_full (facade.py:967)the real production solveFULL_PRESET (full layers + grouping)server.py:4740 (/api/solve/start)
solve_compare (facade.py:992)batch preview across several palettesCOMPARE_PRESETserver.py:4094 (/api/palette/compare)

All three resolve their pluggable slots (grouping + preprocessing) via _resolve_pipeline_slots (facade.py:584), translate SolveConfig into a PipelineConfig via _to_pipeline_config (facade.py:612), then funnel into the same orchestrator: run_pipeline (runner.py:587). The preset just toggles how many stages run and how deep they go — only solve_full/solve_compare enable the grouping stage (runner.py:597), and the preset’s grouping_enabled flag gates it.

There is a fourth facade entry, solve_preview_progressive (facade.py:924); its docstring says the progressive-solve HTTP feature was removed, and it survives only as the test vehicle that threads a SnapshotPublisher into the preprocessing preview hook. It is not on the production solve path.

The pipeline spine

run_pipeline runs a fixed sequence of stages (runner.py:587). The stage count is computed up front: five for a preview, six when grouping is enabled (runner.py:602). Before any stage runs, the runner stamps a __solve_identity__ diagnostic recording every setting the solve will use (runner.py:616) — palette, whites, layer height, gamut mode, ingress toggle, the resolved preprocessor list, and more. That record is what makes a finished run reproducible and is carried all the way out to the UI.

1. Load

This stage does three jobs, in order.

Profiles + appearance provider. It validates the palette (validate_palette, runner.py:654) and loads the spline profiles for every colour filament plus the white base and white cap (runner.py:656–667). The cap profile is the base profile when base and cap are the same filament. It then builds the Appearance provider via create_appearance_provider (runner.py:670) — the swappable colour model the rest of the solve queries. Which provider you get is set by appearance_model_provider (default "historical_spline"); the photo-stack provider is the alternative. A __appearance_provider__ diagnostic records its kind and fingerprint (runner.py:678).

The F1 preprocessing slot. If — and only if — the resolved preprocessor chain is non-empty, preprocessing runs here (runner.py:695–774), after profile load (so palette-aware operators can resolve filament context) and before the target cloud is computed (so targets are derived from the post-preprocess raster). The chain is built by _resolve_preprocessing_from_state (facade.py:547): it walks the registry of operators, keeps the ones turned on in module state, and sorts them by each operator’s order (ties broken by import path). When the chain runs, run_preprocessing_pipeline (preprocessing/runner.py:210) replaces state.image with the processed raster and stashes the original in state.source_image (runner.py:768). When the chain is empty it is a legal no-op — the original raster passes straight through and state.source_image stays None (runner.py:695).

What ships enabled: there are five built-in F1 operators — a1_bilateral_denoise, b1_printscale_bilateral, b3_tv_flatten, c1_achievable_tonemap, c2_soft_gamut_compress — and every one ships with default_enabled = False (e.g. preprocessing/operators/a1_bilateral_denoise.py:73). So the slot is fully wired and live, but on a default solve the chain is empty and preprocessing does nothing until you enable an operator in the module panel. This is the slot, not a guarantee that anything runs in it.

The optional subject-protect mask also lives in this block (runner.py:714–752): when protect_subject_enabled is set and at least one enabled operator declares supports_protect_mask, a foreground mask is resolved (default provider rembg) and threaded into the chain so operators can spare the subject.

The target cloud. Finally the runner computes the target cloud — the per-pixel colours the solve aims for, in OKLab — via compute_solve_target_cloud (runner.py:779, defined pipeline/target_cloud.py:64). This is also where Model-domain ingress is applied: image_to_target converts source pixels through the Camera Transform inverse LUT (when model_domain_ingress is on, the default) so targets live in the same colour space the model was calibrated in (target_cloud.py:72).

Observation grid vs. solve grid

The target cloud is produced on two grids, and the distinction matters for everything downstream:

GridWhat it isPitch fieldStored on state
Observationone cell per image sample — the raster as loadedimage_sample_pitch_mmobserved_target_oklab (runner.py:781)
Solveone cell per solver cell — the lattice the staged backend actually plans onsolver_fine_pitch_mmsolve_target_oklab (runner.py:782)

The solve grid is derived from the observation grid by project_observation_to_solve_grid (derived_views.py:125). When the two pitches are equal — the common case, both default to 0.20 mm — the projection is a zero-cost identity pass and the same array is reused (derived_views.py:154). When they differ, the observation raster is bilinearly resampled to the solve-grid shape (derived_views.py:163). All later dE comparisons, gamut mapping, and LUT queries happen on the solve grid; the observation grid is the faithful record of what the image actually sampled. Keeping them separate is what lets the solver plan at a different resolution than the image was read at without losing the source of truth.

2. Build LUTs

Builds the Joint LUT — a precomputed table mapping candidate layer recipes (a colour combination plus a white-cap height) to the OKLab colour they produce (runner.py:793–830). There are two builders, chosen by which appearance provider is active:

  • spline model ("historical_spline") → build_luts (lut.py, imported as _build_luts_raw, runner.py:799)
  • photo-stack model → build_luts_with_provider (runner.py:815)

The cap range the LUT must cover comes from _provider_lut_d_wc_max (runner.py:44): it spans the Stage 2 boundary-cap budget plus the extra steps Stage 4 may add as a detail surface, so the solver never asks for a cap height the LUT can’t score. LUTs are cached so repeat solves skip the rebuild.

3. Gamut

Some target colours sit outside what the filaments can physically reproduce. _apply_target_gamut_mapping (runner.py:67) projects those back onto the achievable set — by convex hull, by chroma compression, or not at all, per the gamut_mode setting (default "hull"; "none"/"off" skips it). An optional white-point rescale runs first, regardless of mode (runner.py:83). The remapped targets overwrite solve_target_oklab, and a __target_gamut_mapping__ diagnostic records how many targets moved and how far. See Gamut mapping.

4. Solve

The heart of it. The production path calls run_staged_backend_path (runner.py:846, defined in generator.pipeline.staged_runner at staged_runner.py:10310) — the staged backend, an internal Stage 0–5 process. Its own progress labels trace the arc (staged_runner.py:10334+):

StageLabel emittedWhat it does
0Planning solve directivescompile per-region directives; fix the solve-grid shape
1Planning color regionslateral zone plan — segment the image into colour regions
2Solving visible color stackschoose, per region, a printable colour-layer recipe + boundary cap
3Planning filler supportfill structural/support geometry under the colour ceiling
4Solving white cap structureauthor the white cap, incl. the optional detail-relief surface
5(geometry attribution, optional diagnostics)emit attribution maps when requested

Throughout, candidate recipes are scored against the joint LUT in OKLab. The staged result is then copied onto the pipeline state by _finalize_staged_backend_state (runner.py:533): the Thickness map for each filament, the white-cap maps (total, boundary, detail), the canonical solved_plan for export, and a freshly recomputed per-pixel ΔE (_recompute_de_diagnostics, runner.py:577) written into state.diagnostics — never into the thickness maps.

Legacy vs. live — read this if you are tracing code. The web app you use runs the staged backend above. There is an older, separate per-pixel engine in solve.py (solve_image) — the legacy CLI engine — and run_pipeline does not call it. Grepping confirms the only production entry into the solver is run_staged_backend_path (runner.py:846); solve.py’s solve_image is reached only by the CLI engine, not by solve_full/solve_preview/solve_compare. solve.py is not dead, though: the runner imports its gamut helpers (gamut_map_hull_batch, gamut_map_batch) in stage 3 (runner.py:127, runner.py:138, runner.py:140) and the facade imports predict_image_fast for forward prediction (facade.py:31). So solve.py contributes shared utilities, but it does not solve your images. For the fuller “which of these modules is actually on the live path” map, see What Actually Runs.

5. Group (only when grouping is enabled)

config.grouping.group(...) (runner.py:855) consolidates the palette into AMS swap groups — choosing which filaments share a slot — without rewriting the geometry. The grouping module is resolved from module state in _resolve_grouping_from_state (facade.py:513): the default is GreedyGrouping, with a beam-search GroupBudgetGrouping available when the group_budget flag is set. If grouping ever substitutes pixels, the runner recomputes ΔE to keep diagnostics honest (runner.py:863).

6. Stats

_compute_stats (runner.py:305) summarises the solve into a SolveStats: mean/max ΔE, coverage (the fraction of pixels within the ΔE threshold, runner.py:353), the maximum print height (base + colour stack + cap, runner.py:347), the source RMS ΔE, and per-filament pixel/thickness stats. This is the quality readout the UI shows.

What you get out

run_pipeline returns a PipelineState, which the facade converts back into a SolveResult via _state_to_solve_result (facade.py:864). Between them they carry everything the rest of the app needs:

  • thickness_maps — a Thickness map per filament, plus the white-cap maps and diagnostic maps. SolveResult exposes de_map, gamut_mask, cap_map, boundary_cap, and detail_cap as convenience properties (facade.py:405–429).
  • solved_plan — the canonical SolvedMaterialPlan consumed by export (built in finalization, runner.py:542).
  • stats — the quality summary above.
  • diagnostics — ΔE, gamut masks, and the __solve_identity__ record of every setting the solve ran with (runner.py:616).
  • For full solves only, best-case palette-fit diagnostics (_compute_palette_fit_diagnostics, facade.py:784): a per-pixel “best the palette could do” image and the gap between that and what the solver actually achieved — a way to separate palette-limited error from solver-limited error.

SolveResult can also reconstruct the predicted backlit image two ways: predict_image (full composition) and predict_image_color_only (facade.py:494), which zeroes the white-cap term so the colour story isn’t drowned out by the cap’s luminance shaping — this is what the recipe viewer’s colour-only render uses.

From here, Exporting Print Files turns the thickness maps and solved plan into printable geometry.
