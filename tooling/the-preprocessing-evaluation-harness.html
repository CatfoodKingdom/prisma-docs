The preprocessing evaluation harness

The preprocessing evaluation harness

Properties1
tagsgenerator, evaluation

Jun 21, 20268 min read

In one sentence: an offline A/B bakeoff that solves two images through the production pipeline under one shared config and reports a fixed metric bundle (mean/p95 dE, out-of-gamut pixels, small-component count, cap total-variation), optionally dropping predicted-PNG + heatmap + report.json artifacts to disk.

This page documents the evaluation/ package under Prisma/generator/: how to drive it from the CLI or a Python caller, what each metric means, and the generator.evaluation internals. It exists to answer “did this preprocessing operator (or solver tweak) actually help?” with comparable numbers instead of eyeballing two renders.

What it is for

The harness compares two versions of an image — a baseline and a candidate — by running each through the full generator solve and diffing the results. It is corpus-agnostic: both images are passed in as explicit arrays, so the difference between baseline and candidate can be anything the caller wants (a preprocessing operator applied to one, a different denoise setting, etc.). It does not generate the candidate; you do that, then hand both to evaluate_pair.

Both arms run through the same SolveConfig, so any metric delta is attributable to the image difference, not config drift.

The contract: evaluate_pair

The single public entry point is evaluate_pair(request, *, modules_path=None, module_state=None) at Prisma/generator/evaluation/preprocessing_harness.py:105. It takes an EvaluationInput and returns an EvaluationResult.

Flow

  1. Two solves. _run_arm (preprocessing_harness.py:157) calls solve_full (from generator.facade) once per image. solve_full runs run_pipeline under FULL_PRESET (facade.py:975), i.e. the staged production backend — not the legacy 6-step CLI engine in solve.py. If either solve raises, it is wrapped as EvaluationRunError(arm, exc) (preprocessing_harness.py:174) rather than crashing silently.
  2. Metric aggregation. _compute_metrics (preprocessing_harness.py:177) reads the two SolveResult objects and builds the EvaluationMetrics bundle.
  3. Optional artifacts. Only when request.out_dir is not None (preprocessing_harness.py:135) does it lazily import render_evaluation_artifacts and write files. The lazy import is deliberate — in-memory metric callers never pull in PIL (preprocessing_harness.py:136).

Metrics are always returned in memory; artifacts are opt-in.

Metric primitives — preprocessing_metrics.py

Two metrics are non-trivial and live in Prisma/generator/evaluation/preprocessing_metrics.py:

count_small_components (preprocessing_metrics.py:32) — counts speckle. For each per-filament thickness map (keys starting with __ are diagnostics and skipped, preprocessing_metrics.py:56):

  • Mark a pixel “occupied” if its thickness exceeds 5% of that map’s max (_SMALL_COMPONENT_REL_THRESHOLD = 0.05, preprocessing_metrics.py:29; applied at :64).
  • Run 8-connectivity connected-component labelling — the 3×3 structuring element of ones (preprocessing_metrics.py:52) via scipy.ndimage.label (:67).
  • Convert each component’s pixel count to physical area as pixel_count × pixel_pitch_mm² (preprocessing_metrics.py:51, :72).
  • Accumulate the count of components whose area is below min_area_mm2 (preprocessing_metrics.py:73).

The min_area_mm2 threshold is derived in the harness, not hard-coded: feature_scale_mm², where feature_scale_mm comes from resolve_feature_scale_mm (preprocessing_harness.py:192). That helper returns 2.0 × nozzle_diameter (the constant _FEATURE_WIDTHS_PER_NOZZLE = 2.0, feature_scale.py:37; applied at feature_scale.py:73), i.e. 0.40 mm at the default 0.20 mm nozzle, so min_area = 0.40² = 0.16 mm² (preprocessing_harness.py:193). This is the value the retired cleanup_min_area_mm2 carried (preprocessing_harness.py:191).

cap_total_variation (preprocessing_metrics.py:77) — measures how “busy” the white-cap surface is. Returns the anisotropic L1 total variation Σ(|Δx| + |Δy|) over the 2-D cap map: abs(diff(axis=1)).sum() + abs(diff(axis=0)).sum() (preprocessing_metrics.py:89). It is a grid-space sum, not a per-mm integral (preprocessing_metrics.py:82) — a non-2-D or empty map returns 0.0 (:85). Lower means a smoother cap.

Artifacts — preprocessing_render.py

When out_dir is set, render_evaluation_artifacts (Prisma/generator/evaluation/preprocessing_render.py:49) writes exactly four files:

FileConstant / anchorContent
baseline_predicted.pngpreprocessing_render.py:44, written :64Baseline predict_image() as RGB PNG.

The heatmap (_save_delta_de_heatmap, preprocessing_render.py:89) is signed: it normalises delta = candidate − baseline by its peak absolute value, then puts positive delta (candidate worse) in the red channel and negative delta (candidate better) in the green channel (preprocessing_render.py:94, :110-111). Mismatched shapes are defensively cropped to the smaller grid (:97-103), though they are expected to match.

report.json’s schema is locked to the EvaluationMetrics dataclass via asdict (preprocessing_render.py:121); the drift-regression test in tests/generator/test_preprocessing_evaluation_metrics.py guards it.

How to drive it

From the CLI

Prisma/generator/preprocessing_eval_cli.py is a thin wrapper that loads two images, builds a shared SolveConfig, calls evaluate_pair, and prints the report to stdout (preprocessing_eval_cli.py:97). Artifacts are opt-in via --out-dir (preprocessing_eval_cli.py:72).

python preprocessing_eval_cli.py \
    --case-id my_case \
    --baseline baseline.png \
    --candidate candidate.png \
    --profiles Prisma/data/filaments/profiles \
    --palette bambu-basic-cyan bambu-basic-yellow \
    --white-base panchroma-matte-cotton-white \
    --out-dir /tmp/eval_out

Required flags: --case-id, --baseline, --candidate, --profiles, --palette (one or more filament IDs), --white-base (preprocessing_eval_cli.py:61-71). Images are EXIF-transposed and forced to RGB uint8 on load (preprocessing_eval_cli.py:85). --solver-preset accepts full only (preprocessing_eval_cli.py:49, :75).

From Python

The package re-exports the full surface (Prisma/generator/evaluation/__init__.py:15): evaluate_pair, the three dataclasses, EvaluationRunError, and the two metric primitives.

The bakeoff runner script

scripts/evaluate_preprocessing_first_bakeoff.py is the F4 MVT batch runner that sweeps the landed first-wave preprocessing operators across a small real-photo corpus. Its run_bakeoff (evaluate_preprocessing_first_bakeoff.py:281) loops a 5-photo corpus (_CORPUS, :84) × the operator set A1/B1/B3/C1/C2 (_OPERATORS, :95). For each cell it:

  1. Applies the operator offline to the source raster via _offline_apply (evaluate_preprocessing_first_bakeoff.py:189) to produce the candidate — both arms then solve with an empty preprocessing slot (:144). This sidesteps the single-module_state constraint of the harness while still exercising each operator’s real kernel (:5-8).
  2. Calls evaluate_pair with a per-case out_dir (evaluate_preprocessing_first_bakeoff.py:315).
  3. Assigns a coarse _verdict label — promising / neutral / harmful / needs_tuning (evaluate_preprocessing_first_bakeoff.py:219) — by diffing the metrics itself (the bundle only ships the dE delta precomputed).

It writes runs/<image>__<op>/... per-case artifacts plus summary.json and summary.csv (_write_summary, evaluate_preprocessing_first_bakeoff.py:379). Key flags: --out-dir (required), --max-edge-px (default 256, :441), --palette, --white-base, --cleanup-enabled/--no-cleanup-enabled (:458-470), and --solver-backend (default dual_resolution; use joint_lut to expose raw per-pixel speckle for the small-component metric, :471-487).

Two sibling runner scripts reuse the harness internals (_compute_metrics + render_evaluation_artifacts, not the evaluate_pair entry point) for narrower studies: scripts/evaluate_b1_b3_preservation.py and scripts/evaluate_b1_parameter_sweep.py.

Caveats

  • Production solve path. Both arms go through solve_full → run_pipeline / FULL_PRESET (facade.py:975) — the staged backend, the same engine the webapp uses. The metrics reflect production solver behaviour, including grouping/cleanup, not the legacy solve.py CLI engine.
  • Shapes must match. Metrics assume baseline and candidate solved to the same grid (same config, same image dimensions). The heatmap renderer crops defensively (preprocessing_render.py:97) but the dE mean/p95 do not align grids — feed same-sized images.
  • Cap-TV is grid-space. cap_total_variation is a raw grid sum (preprocessing_metrics.py:82); it is only comparable between two solves at the same resolution. Do not compare TV across differing solver_fine_pitch_mm.
